# Decisions

Standing decisions and their reasons. Many come from an audit of one long session of the predecessor plugin (HolyClaude): 299 specialist spawns, 326 Assignments and about 397 commits. Finding ids in parentheses are the audit's. Audit figures marked "estimate" were not measured exactly.

## Changed by the audit

**Warm specialist reuse, not always-fresh workers.** The predecessor gave every repair and follow-up a new worker and never used its `select` step: 299 spawns against about 10 genuine resumes, 87 agents on Repair/Fix descriptions, and a re-orientation cost of roughly 8 to 40 thousand tokens each (estimate). Now `assignment dispatch` makes the decision from role, model and effort, the cache window, independence and relevance of context, and prints the exact continuation ([cache-and-workflows.md](cache-and-workflows.md)). Reviewers stay fresh: never the writer or an earlier reviewer of the change. (`cache-reuse-1`, `mechanisms-2`)

**State rides the work commits (replaced by the state branch, below).** In the predecessor 328 of 397 commits were state transitions and 335 pushes carried them, about a thousand Bash writes. The audit's answer was that `vcs commit` added the changed Intent state of the worktree it ran in to the work commit, so state never had a commit of its own. Per-clone data lives in the ignored `.holyagent/local/`. (`stacks-vcs-1`)

**No write guard.** The predecessor's `PreToolUse` guard on Bash, PowerShell, Monitor, Write and Edit started a process for each of 11,949 Bash calls (1,456 seconds of hook latency in all) and denied 114 calls. An estimated 78 percent of those denials were false positives, classified from the denial reasons: `.git` named inside `tar` excludes, `git apply` to a scratch copy, computed program names. 18 follow-ups were denied or failed again. It also failed open when Bun was missing or crashed, and any interpreter bypassed it. The rules (the specialists leave VCS and state to the root; undo your own edit by editing it back) are now instructions, with no guard of any kind ([hooks.md](hooks.md)). The maintainer chose this trade: no false denials in exchange for enforcement that rests on the text. (`mechanisms-3`)

**Instructions, not a Bash guard.** A `PreToolUse` hook on Bash once denied `git commit` (pointing to `holyagent vcs commit`) and force pushes, behind a scanner that read every shell command mentioning git. The user chose instructions over a guard: the hook and its scanner are removed entirely, and the version-control rules live in the instruction text of the root and the specialists, with hooks that only add that text as context at the right moment (a `SubagentStart` hook for every specialist and a `PreToolUse` reminder for a Bash command that mentions git commit or push). Neither can deny or block. The rules are: commit only with `holyagent vcs commit`, plain Git and `gh` for the rest, no force-push or push to a protected branch without the user's approval, no workaround of a denial, and no version-control writes by specialists.

**Built-in reviews start every review, on a committed range.** The predecessor made Claude Code's built-in review the mandatory first pass, so code was reviewed twice per change and reviewers were 41 percent of all spawns, and its yield over the manual pass was never measured. Reviewer.code and Reviewer.security now always start with `/code-review` and `/security-review` respectively and then review on their own, inside the one specialist. The built-ins read committed changes, so the order is a local commit, review of that commit, repairs as new local commits and a re-review, with the push after acceptance; only blocking findings start a repair. (`mechanisms-1`)

**Three calls per Assignment.** The predecessor needed four or more commands per Assignment and built JSON through python one-liners; its `select`, `verify` and `accept` steps ran zero times in 326 Assignments, so the independence and evidence checks never ran. Now `assignment dispatch` creates, reserves and selects in one step, `assignment record` binds, and `assignment close` finishes and optionally accepts. Acceptance reads the report's `evidence:` block and the CLI refuses when a blocking criterion or a required label has no support, so there is no restated map for the root to write. (`tool-use-8`, `mechanisms-5`, `mechanisms-6`)

**No `autoCompactWindow`.** HolyAgent does not set it (the maintainer's decision), so Claude Code's own default applies. The predecessor's root grew to about 784 thousand tokens and was auto-compacted four times, discarding about 2.9 million cache tokens. A host that sets its own window, such as T3 Code, keeps it. (`cache-reuse-3`)

**Inline workflows, no prebuilt ones.** The predecessor used workflows zero times and launched parallel work call by call. Workflows now run all new work, a single Assignment as a one-entry workflow, and the root writes each script on the spot: a prebuilt script fixes a shape in advance, while the point of a workflow is a script composed for the work at hand. To keep that free of prompts, the `Workflow` hook allows an inline script in which every `agent()` call names a holyagent specialist by a string-literal `agentType` ([hooks.md](hooks.md)); anything else asks the user (the maintainer's decision). The hook decides with a real JavaScript parser (acorn, pinned): a hand-written lexer leaked one bypass after another (string and computed keys, whitespace lookalikes, shadowed globals), so the check walks the syntax tree against a closed set of node types and resolves names through real scopes. Choosing the holyagent agent is the opt-in; direct subagents remain only as a fallback for a session where the `Workflow` tool is disabled or unavailable ([cache-and-workflows.md](cache-and-workflows.md)). (`cache-reuse-7`)

**Commits are built by the CLI.** Trailers and "Generated with" lines were on nearly every commit and PR body. `vcs commit` cleans the text and refuses text that talks about the user or the agent, and the `commit-msg` hook does the same for commits made by hand ([commit-authorship.md](commit-authorship.md)). (`stacks-vcs-4`)

**`holyagent vcs` is three commands.** It was once the whole path of a change (detect, commit through GitHub's API, push, branch, pr, ci). Only the steps that carry a rule of the plugin stay: `vcs commit` (exact paths, Intent state, message check, no agent identity) `vcs pr` (PR text check) and `vcs identity` (sets the commit author in a claude.ai cloud session, which keeps the platform's Claude as committer so that branch commits stay Verified; see [commit-authorship.md](commit-authorship.md)). The API commit path is removed, since it depended on an endpoint that hosted sessions block and made signing vary; branches, pushes, merges and CI are plain Git and `gh` under instruction text (no force-push), and a `commit-msg` hook keeps attribution out of every commit (the maintainer's decision).

**CI is watched with one command.** `gh pr checks <n> --watch` through Monitor prints the checks as they change and exits when they settle, instead of ad hoc polling loops. (`stacks-vcs-6`)

**Specialists with Bash also get Monitor.** The predecessor's specialists were told to use Monitor and did not have it: 19 failed calls and polling loops. (`tool-use-3`)

**Cache and TTL reasoning left the prompts.** The predecessor's root prompt told the model to reason about cache lifetimes and model switches. Now the CLI embeds the window and the prompts carry none. (`mechanisms-9`)

**No observation hooks, one launch recorder.** `SubagentStart`, `SubagentStop`, `PostToolUse` on Agent and effort recording on `PreToolUse` cost about 1,281 process starts and 326 seconds to feed `assignment verify`, which ran zero times in 326 Assignments. `assignment record` now stores the agent id with the route's model and effort. What is gone is the check of the model that actually ran against the one requested. One `PostToolUse` hook on Agent came back, narrowed: `agent-launch` runs only for a prompt that `assignment dispatch` printed and records the agent id, so the root no longer spends a command on it. It checks the launched `subagent_type` against the route, authorizes nothing and on failure adds a note ([hooks.md](hooks.md)). A `SubagentStart` hook returned later for a different purpose: it only adds the version-control rules as context to a specialist at its start, and records and checks nothing. (`mechanisms-4`)

**No dispatch guard.** The root's tool list restricted which agents it could start, with `Agent(holyagent:explorer-map, …)` naming the eighteen specialists, so the hook was redundant. The root has since moved from a `tools:` allowlist to a `disallowedTools:` denylist so that it inherits every MCP server, which drops that spawn list; its instruction text still names the specialists, and the dispatch hooks add no guard. (`mechanisms-11`)

**Skills folded into the root prompt.** `grill-me`, `stacks-and-ci`, `continue-work` and `assignments` are gone as skills. Their rules (asking, stacks, CI, resuming, assignments) sit in the root prompt, which is always loaded, and the command details in `holyagent help [command]`. What an agent kind always needs is fixed text in that agent rather than a skill it may load: the mergeability rubric in the seven roles that write or review code, the interface inspection rules and the embedded `frontend-design` guidance in the two visual roles. Two skills remain because they apply to one situation only: `dev-server`, which has the root start one dev server that the visual specialists share, and `user-busy`.

**A small, bounded session-start hook.** The predecessor loaded every record on every start. With 326 Assignments its resume hook took 11.6 and 11.9 seconds against a 10-second budget and twice injected a 77-character message instead of state (that the load time grew with state size is an inference), and it re-injected 8.4 to 9.9 thousand characters of rules at each of four compactions. The hook now reads only open Intents, caps its context and adds the rules only when the root is not the main agent; after a resume or compaction it also adds the Running rows of `reconcile` ([hooks.md](hooks.md)). (`mechanisms-7`)

**Prompts are one file per section.** The root, the specialist conduct and each role are folders of section files whose order is fixed in `agents.ts`, so a change touches one section and a test catches a file left out. The root carries `instruction-guidelines.md`, which turns Anthropic's Claude 5.5 prompting guidance into rules for the text it writes (effort through the route, keep working versus stop and report, a real check before done).

**Language follows the artifact.** PRs, commits, docs and instruction text are in English unless the target repository's convention says otherwise; the task list and the root's messages to you are in the language of your latest message.

**Progress lives in the task list.** The root creates the list first, updates it at every dispatch, close and verdict, and writes to you only for a decision, a blocker and the final report, with one exception: a brief acknowledgment of each user message.

## Changed since the audit

**State lives on its own branch.** State that rode the work commits sat on every work branch, so stacked and merged branches conflicted on state records and worktrees needed manual repair to agree. The requirement is that it must always be easy to stack onto other branches and merge seamlessly. Now every command reads and writes `.holyagent/` in one worktree shared by the whole clone, checked out on `holyagent/state` (another branch via git config `holyagent.stateBranch`), and commits each transition there; each record is its own file. The one exception is the Intent in use, which is kept per work tree under `local/`, so sessions in different worktrees of one clone never switch each other's Intent; a work tree with no choice of its own resolves the Intent when exactly one is open. `vcs commit` refuses `.holyagent/` paths, so a work branch never carries state, and the state branch merges with any branch without conflict. State found in a work tree is migrated once. Intents record the branches committed on and the pull requests opened for them. The root pushes `holyagent/state` with plain Git beside the work branches; the runtime never pushes.

**State lives where the project's conventions and ownership allow.** The state branch fixed conflicts for stacked PRs, but it asks every project to carry a second branch that the root must push, whatever the project's conventions say. A project whose PRs do not stack gains nothing from it, and mergeability puts the project's own conventions first. The state mode (git config `holyagent.stateMode`, per clone and never a repository file, for the same reason `holyagent.stateBranch` is) now picks the place. Unset or `branch` is today's behavior, for stacked PRs. `work` keeps the state in the work tree and `vcs commit` stages the changed state files with the work, as before the state branch, for a repository that already tracks `.holyagent/` (its `config.json` is project settings, not state, and does not count); the commit that records a branch on the Intent changes the state again, so that change rides the next commit. `local` keeps it in the work tree too, excluded through `.git/info/exclude` rather than the project's `.gitignore`, which the project's PRs should not edit. The root chooses the mode before the first Intent and records it with `holyagent state mode`, by the first signal that applies: the owner's words; a tracked `.holyagent/` other than `config.json` (`work`); conventions that ask for independent PRs from the base, or a repository the owner does not control (`local`); otherwise `branch`; it pushes `holyagent/state` only in `branch` mode. Records are never moved between modes: the command refuses to leave `branch` once the state branch exists, to enter it while the work tree holds records, and to set `local` while git tracks state in `.holyagent/` (`config.json` aside). Moving records was left out because the once-only migration and the shared state worktree make a move unsafe to automate; a deliberate change is a manual copy. `local` state is per work tree, so linked worktrees do not share it.

**Search runs on bundled ripgrep and fd.** Agents searched with whatever grep, find or built-in search each session had, so the same query could answer differently from one machine to the next. The plugin now bundles ripgrep and fd for darwin-arm64, linux-x64 and windows-x64, pinned by version and SHA-256, and exposes them as `holyagent rg` and `holyagent fd`; every agent with Bash uses them, and agents without Bash keep the built-in Grep and Glob. The fff search tool was considered and dropped. The programs add about 24 MB to the committed plugin and sit under `scripts/` because claude.ai refuses a top-level `bin/`.

## Kept

- **Static-first prompts and a session-start status.** The layout and the re-injection after compaction cost nothing measurable; HolyAgent adds nothing dynamic to the system prompt, tools, skills or roster mid-session. (`cache-reuse-9`)
- **Models do not reason about cache, TTL or cost.** The predecessor's root text did not either, apart from the prompt lines removed above. (`root-conduct-11`)
- **Narrow, matcher-scoped hooks.** The cheap ones were worth keeping; the broad one was not. (`mechanisms-11`)
- **Warm continuation where it worked.** One agent carried five or six merge-conflict resolutions at about a 0.98 cache ratio. (`cache-reuse-10`)
- **The root plans and judges; specialists do the work.** The root owns the user relationship, acceptance and version control, runs no gates itself and does not poll: completion notices are its only wake-ups. It speaks to the user only for a decision, a blocker only the user can clear and the final report, with one exception: a brief acknowledgment of each user message; everything else lives in its task list.
- **Eighteen specialists with pinned model and effort**, writers confined to disjoint ownership paths, and independent review of every change to code or artifacts, with a security review for trust boundaries.
- **Mergeability as the bar**, in six dimensions with blocking and non-blocking criteria, the repository's own conventions first.
- **One PR per reviewable change**, every PR of one delivery stacked in work order by default (the target repository's conventions first, other work branched from the base), with a CI PR first when the work adds CI, disjoint paths for parallel writers, a PR opened or updated in the same step as every push, merge-forward with merge commits, no force-push without your approval.
- **Compact interfaces.** JSON in, TOON out, long logs in files, fixed report shape.
- **Effect and Bun.** Failures are tagged errors and the toolchain is Bun's own ([development.md](development.md)).
- **State in the repository.** Versioned state in `.holyagent/` is inherited from the predecessor; the audit changed how it is committed and the state branch changed it again (both above); the state mode now lets the project's stack convention decide (above). Moving it outside the project tree was proposed (`mechanisms-8`). It stays versioned in `.holyagent/`; the costs behind the proposal are met differently: `status`, `plan`, `reconcile` and the session-start hook read only open Intents, and state has a branch of its own rather than riding the work.
