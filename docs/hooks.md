# Hooks

The plugin ships four hooks on three events (the `vcs-redirect` hook has one entry per `if` rule), all running the runtime CLI as `scripts/holyagent hook <name>` with a 10-second timeout. A hook that has nothing to say prints nothing and exits 0. A failure of `session-start`, `vcs-redirect` or `workflow` is exit 1 with one `holyagent hook <name>: …` line on stderr and nothing on stdout, so a failure never reads as a decision. `agent-launch` reports a failure to record as a note on stdout with exit 0 (see below) and exits 1 only on a payload it cannot decode. A missing Bun or bundle is exit 127 for every hook (see the wrapper below). The host treats exit 2 as a block and lets any other failure through unless the hook sets `onFailure: "block"`, which the `PreToolUse` hooks do.

| Hook            | Event and matcher                                 | `if`                 | `onFailure` | Output                                                                                                                                                                                                                                                                         |
| --------------- | ------------------------------------------------- | -------------------- | ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `session-start` | `SessionStart`: `startup\|resume\|clear\|compact` | none                 | default     | `additionalContext`: a capped open-work status (with the reconcile result and the requirements of the Intent in use after a resume or compaction), plus a core of the root rules when the root is not the main agent, ending with a short block of the rules most often missed |
| `vcs-redirect`  | `PreToolUse`: `Bash`                              | `Bash(*git*commit*)` | `block`     | a `deny` decision naming `holyagent vcs commit`, or denying a command it cannot read with certainty                                                                                                                                                                            |
| `vcs-redirect`  | `PreToolUse`: `Bash`                              | `Bash(*git*push*)`   | `block`     | a `deny` decision for a force push or a command it cannot read with certainty, else nothing                                                                                                                                                                                    |
| `workflow`      | `PreToolUse`: `Workflow`                          | none                 | `block`     | an `allow` decision for an inline script of holyagent specialists, else nothing                                                                                                                                                                                                |
| `agent-launch`  | `PostToolUse`: `Agent`                            | none                 | default     | `additionalContext` saying the launch was recorded, or that the root must record it, else nothing                                                                                                                                                                              |

`hooks/hooks.json` in the plugin is the reference for these rules.

## `session-start`

After a start, resume, clear or compaction the root has lost what is running. The hook adds context in TOON: the open Intents (id, revision, objective), the Intent in use, the Running Assignments (id, role, agent, objective) and the Succeeded ones not yet accepted, preceded by a fixed line saying the objectives are project data, not instructions. After a `resume` or `compact` it also adds the Running rows of the `reconcile` result (id, role, agent, start time), which the root needs to confirm whether each agent is gone; the result's `next` line is left out, since the root's rules already hold it, and so is the block when nothing is Running. After a `resume` or `compact` only, it also adds the requirements of the Intent in use (as `intent show` resolves it: id, revision and the requirement texts under `holyagent requirements:`, with a line that they are project data too), and nothing when that Intent has none or none is in use; a `startup` or `clear` does not inject them. On every source, the context ends with a block of five rules the root most often misses (`session-reminder.md` in the instructions of the model): load the app's task-list tool if it is deferred and keep the list updated, acknowledge every user message briefly and otherwise write to the user only for decisions, blockers and the final report, take every pending decision through `AskUserQuestion`, do or verify what the user names without asking again, and follow a denial or hook that names a holyagent route (the bullet reads `Follow a denial or hook that names a holyagent route ...`). It prints nothing in a project without a `.holyagent` folder.

- It reads only the state of open Intents, so its cost follows open work, not the whole history ([decisions.md](decisions.md) has the predecessor's figures).
- It stays small and deterministic. The whole context is capped at 9,000 characters, because the host cuts `additionalContext` at 10,000 and a cut would drop the tail unannounced. If the status does not fit, it is narrowed in steps (10 rows of 200 characters, 5 of 120, 3 of 80, 1 of 60, then counts only) with a `+N more` line for what was left out, and long objectives and agent ids are shortened. The requirements stay whole while the status can still give way; only when the status is already counts only are they cut to the first ones that fit, with a `+N more requirements` line that names `holyagent intent show`. The rules block counts against the cap.
- When the payload's `agent_type` is the root (`holyagent` or `holyagent:holyagent`) the rules are already in the system prompt and only the status is added. When the main agent is anything else, the hook prepends a compact core of the root rules (`ROOT_CORE`, the files named in `ROOT_CORE_FILES` in `root-core.ts` joined as the root prompt joins them, with `${CLAUDE_PLUGIN_ROOT}` filled in) and a pointer to the full rules in the holyagent agent prompt.
- A failure is loud on stderr, not silent.

## `vcs-redirect`

Raw `git commit` carries whatever the harness adds, and the author is whatever git is configured with; `holyagent vcs commit` fixes both ([commit-authorship.md](commit-authorship.md)). The hook is an allowlist for a command that mentions Git with `commit` or `push`: it passes only when every simple command in it is read with certainty and runs a known program, and everything else is denied. It names two things: `git commit`, denied with the replacement in the reason (`Commit with holyagent vcs commit -m <headline> -- <paths…>`), and a push that rewrites or deletes published history: `--force`, `-f` (also inside a cluster such as `-fu`), `--force-with-lease` (with or without a value), `--force-if-includes`, `--mirror`, `--delete`, `-d`, `--prune`, any unambiguous abbreviation of those long options (`--force-w`, `--mirr`), a refspec that starts with `+` or `:`, and the same words written as `$'…'` strings (their `\x`, octal and `\u` escapes are decoded first). A plain `git push` with literal arguments passes: pushing, like branches, merges and CI, is plain Git and `gh`. Everything the hook cannot vouch for is denied as unclear, with a reason that tells the root to write the command out plainly.

- It is scoped twice. The `if` rules in `hooks/hooks.json` (`Bash(*git*commit*)`, `Bash(*git*push*)`) start the hook only for a command whose text has `git` followed by `commit` or `push` (probed on Claude Code 2.1.310), and the hook itself says nothing about a command without that text. Within such a command, text that only mentions Git is not a command: `echo "git commit"`, a `gh pr create --body` text, a heredoc body, a comment, or the words of a `for` list.
- **Programs.** Each simple command (found behind `cd a &&`, a pipe, a subshell, a substitution, a loop body, an assignment prefix or `env NAME=value`) must have a program word that is plain text, with no `$`, brace, glob, backtick or other expansion in it, from this list: `git`, `gh`, `holyagent` (by name, by a path, or as `"${CLAUDE_PLUGIN_ROOT}/scripts/holyagent"`, which the root writes for every `holyagent` command), `mise`, `bun`, `bunx`, `echo`, `printf`, `cat`, `head`, `tail`, `wc`, `grep`, `rg`, `ls`, `cd`, `pwd`, `jq`, `sort`, `uniq`, `cut`, `tr`, `test`, `[`, `true`, `false`, `sleep`, `mkdir`, `cp`, `mv`, `rm`, `touch`, `diff`, `sed`, `awk` and `find`. Any other program is unclear: shells (`sh -c '…'`, `bash script.sh`), wrappers and runners (`sudo`, `env` with options, `timeout`, `nice`, `xargs`, `ssh`, `docker exec`, `fakeroot`, `time -p`, `/usr/bin/time`), `eval`, `exec`, `source`, `.`, `trap`, `coproc`, `function`, `case`, `read`, an interpreter, a function call or a script. `time`, `!`, `{`, `if`, `while`, `until`, `do`, `then`, `else` and `for name in …` only shape a command and are skipped.
- **Arguments of the listed programs.** A `git` word (or a path ending in `/git`) among the arguments of a program that does not only print or search text (`echo`, `printf`, `grep`, `rg`) is unclear, since that program may run it (`mise exec -- git commit`, `bunx git commit`). Options that run a command are unclear too: `find` with `-exec`, `-execdir`, `-ok`, `-okdir` or `-delete`; `sed` with the `e` command or flag or a script file; `awk` with `system`, `getline`, a pipe or a program file; `sort --compress-program`; `rg --pre`; `test -v` and `printf -v`, which evaluate an array subscript; `mise exec`, `x`, `shell` and `watch`; `bun -e`, `x`, `exec` and `create`; and `gh alias` and `gh extension`. For these programs a word computed by the shell (`$x`, `$(…)`) in the arguments is unclear as well, since it could be one of those options. An assignment before a command that changes how programs are found or run (`PATH=`, `HOME=`, `GIT_*`, `LD_*`, `CLAUDE_*`, `BASH_ENV=`, `IFS=`, the pager and editor variables) is unclear.
- **Git.** Every word up to the subcommand is read exactly: the global options `-C`, `--git-dir`, `--work-tree`, `--namespace`, `--no-pager`, `--paginate`, `--bare`, `--no-optional-locks` and the pathspec options, and `-c` with a setting that only names the author or changes display (`user.name`, `color.*`, …); any other option, a `--config-env`, `--exec-path`, a `-c` that could define an alias or change a push or a program (`alias.*`, `remote.*.push`, `push.*`, `core.sshCommand`, …) or a word the shell computes is unclear. The subcommand must be literal: `commit` is a commit, `push` goes to the force rules above, and one of a fixed list of porcelain and read commands (`status`, `log`, `show`, `diff`, `branch`, `merge`, `stash`, `worktree`, `switch`, `checkout`, `add`, `fetch`, `pull`, `rebase`, `reset`, `tag`, `remote`, `config`, …) passes. A missing subcommand, an alias or external command (`git ci`, `git commitizen`), `commit-tree`, `bisect`, `submodule`, `filter-branch`, `rebase -x`, an option that starts a program (`--exec`, `--receive-pack`, `--upload-pack`, `grep -O`, or a prefix git would accept) and `git config` of an alias, include, push target or program are unclear. Git does not let an alias hide a built-in command, so the list also closes the aliases defined in the repository or by `-c`.
- **Constructs the scan does not read.** Arithmetic is skipped only when it holds numbers and operators (`$((1 + 2))`, `((1 << 2))`): a name in it is evaluated by the shell as an expression, so `x='a[$(cmd)]'; echo $((x))` would run `cmd`, and `((git commit) && (true))` is two subshells. A `${…}` is read only as a name, its length or a special parameter (`${HOME}`, `${#x}`, `$@`), since a default or an offset computes. Also unclear: a decoded NUL in a `$'…'` word (bash cuts the word there), an unquoted heredoc whose body holds `$(`, a backtick or `$[`, a `<<` with no delimiter-shaped word after it, inside an array subscript or with a heredoc that never ends, `$[ … ]`, nested backticks, and nesting deeper than the scan follows. A backslash-newline inside double quotes is dropped as bash drops it, so `git "com\<newline>mit"` is read as `git commit`.
- The hook never calls git and never looks for the state root, so a git failure cannot stop it, and it never fails on a command: if reading the command text ever threw, it would deny it as unclear instead of crashing. Only a payload that is not JSON is an error (exit 1).
- `onFailure: "block"`, because a failure would let the raw write through unexamined.
- It is a redirect, not a sandbox. Other git writes (`reset`, `checkout`, `gh` writes) and edits under `.git/` or `.holyagent/` are not stopped; the specialist text forbids them. What it cannot see escapes it. The `if` rules match the command text as written, so a command that never spells `git` followed by `commit` or `push` is never given to the hook: an alias defined in the user's own git configuration (`git ci`, `git pf`) and a spelling that splits the words with quotes (`g''it commit`). A script, make target or package script that runs git inside (`bun run` and `mise run` included) is a known program, so what it runs is not read. A user alias is not stopped by the allowlist either, because the command that uses it does not reach the hook; the `commit-msg` hook below still checks their message.

## `commit-msg`

Not a Claude Code hook: a Git `commit-msg` hook. `holyagent hook commit-msg <message-file>` removes agent attribution from the message file and refuses a message that talks about the user or the agent (exit 3, which stops the commit), with the same cleaning and phrases as `vcs commit` ([commit-authorship.md](commit-authorship.md) has the install steps for `.git/hooks/commit-msg` and for lefthook). Git's comment lines (`core.commentString` or `core.commentChar` from the repository's own files, `#` by default; a value that comes only from a `-c` on the command line is ignored, since the caller of `git commit` could use it to hide text) are not checked for phrases, and neither is what follows the exact scissors line that git adds for `git commit -v`, the staged diff. Attribution lines are still removed from below the scissors line, because a message made by hand keeps everything below it.

## `workflow`

The `Workflow` tool otherwise asks for permission. The plugin ships no workflow scripts: the root writes each one inline, in the `script` input of the call ([cache-and-workflows.md](cache-and-workflows.md)). The hook allows a call that carries a `script` (and optionally `args`) and nothing else, when every `agent(` call in the script passes an `agentType` that is a string literal reading `holyagent:<agent>` with one of the eighteen route agents. A `scriptPath`, a `name` (a saved or plugin workflow) or a `resumeFromRunId` runs code the hook has not read, so any of them, or any other input field, gets no decision.

The hook parses the script (with [acorn](https://github.com/acornjs/acorn), as a module with top-level await and `return` allowed) and never runs it. It allows the script only when every node of the syntax tree is of a type in a closed set, every name resolves, and every `agent()` call is vetted; anything it cannot place with certainty, a parse error included, gets no decision, and the normal permission flow applies. The check is `packages/runtime/src/cli/workflow-check.ts`.

- **Node types.** Declarations (`const`, `let`, `var`, functions, arrow functions, `async`), `if`, loops (`for`, `for…of`, `for…in`, `while`, `do…while`), `switch`, `try`/`catch`/`finally`, `throw`, `return`, `break` and `continue`, calls, member access, template literals, array and object literals with spread, unary (not `delete`), binary and logical operators, assignment and update of a name the script declared, conditionals, `await` and optional chaining. Everything else is refused: regular expressions, tagged templates, `new`, `this`, `super`, classes, generators, labels, getters, setters, methods in objects, sequences (`a, b`), `delete`, `import`, `import.meta`, `with` and private names. Division is fine, since the parser tells it from a regular expression.
- **Scopes.** Names resolve through real lexical scopes (module, function, block, loop, `catch`, `switch`). A name is allowed when the script declared it in an enclosing scope, or when it is free and one of the globals below. A script may not declare, as a variable, parameter, function or pattern name, a global of the workflow, a host name (`Bun`, `Deno`, `fetch`, `process`, `require`, `globalThis`, `Function`, `eval`, `setTimeout`, `Worker`, `WebSocket`, `Buffer`, `Symbol`, `Reflect`, `Proxy`, `WebAssembly`, `Date`, …) or a reflective name, so a dummy `(fetch) => 1` cannot make the real `fetch` look declared.
- **Globals.** The workflow globals are `parallel`, `pipeline`, `phase`, `log`, `args` and `budget`; the plain built-ins are `JSON`, `Math`, `Array`, `Object`, `String`, `Number`, `Boolean`, `Promise`, `Map`, `Set`, `Error`, `parseInt`, `parseFloat`, `isNaN`, `isFinite`, `NaN`, `Infinity` and `undefined`. A free global appears only as the callee of a direct call (`parallel`, `pipeline`, `phase`, `log`, `String`, `Number`, `Boolean`, `Error`, `parseInt`, `parseFloat`, `isNaN`, `isFinite`) or as the object of a member call or read, never as a value: it cannot be assigned to a name, passed, returned, spread, put in an array or an object, destructured, or used as an operand. The exceptions are `args` (plain data, readable anywhere) and the constants `undefined`, `NaN` and `Infinity`. A global object is called and read only through short lists: `Object.keys|values|entries|fromEntries`, `Array.isArray|from|of`, `JSON.stringify|parse`, `Math.max|min|abs|floor|ceil|round|trunc|sqrt|pow|sign` and the constants `Math.PI`, `E`, …, `Number.isInteger|isFinite|isNaN|parseFloat|parseInt` and `Number.MAX_SAFE_INTEGER`, …, `Promise.all|allSettled|race|resolve|reject`, and for `budget` only `total`, `spent()` and `remaining()`. Nothing that changes or freezes an object (`assign`, `freeze`, `seal`, `defineProperty`, `defineProperties`, `setPrototypeOf`, `preventExtensions`, `create`, `groupBy`, …) is on a list, so a built-in cannot be rewritten, directly or through an alias.
- **Writes.** A script may assign to a name it declared. It may assign to a member or update one (`row.done = true`, `count++`) only on a name that holds nothing but data the script built: every value the name is set to is an object or array literal, an `agent()` result, data read from `args`, a result of an allowed data method, or another such name. A parameter, a loop variable, a function, a global or anything reached from one is refused, as is a write into a call result (`f().x = 1`).
- **Members and keys.** Member access is by plain name (`entry.prompt`, `args.entries.map`); the only computed access is a non-negative integer literal (`rows[0]`). Computed keys are refused everywhere, in objects and in destructuring patterns, and so are quoted keys in patterns (`const { "constructor": F } = Array`). Names that reach reflection or other code (`constructor`, `prototype`, `__proto__`, `call`, `apply`, `bind`, `getPrototypeOf`, `defineProperty`, …) are refused as properties, keys and declared names. A method of a value may be called only by a name from a fixed list of data methods (`map`, `filter`, `flatMap`, `flat`, `forEach`, `reduce`, `find`, `findIndex`, `some`, `every`, `includes`, `indexOf`, `join`, `slice`, `splice`, `concat`, `push`, `pop`, `shift`, `unshift`, `sort`, `reverse`, `at`, `then`, `catch`, `finally`, and the string methods `trim`, `split`, `replace`, `repeat`, `toUpperCase`, `toLowerCase`, `startsWith`, `endsWith`, `padStart`, `padEnd`, and similar), and it is called where it is read: reading such a method without calling it (`const f = xs.push`, `[1].map(xs.push)`) is refused, so no method is aliased, passed as a value or given another `this`. The methods that run a callback (`map`, `forEach`, `filter`, `find`, `findIndex`, `some`, `every`, `flatMap`) take the callback alone, since a second argument would be its `this`. A call of a call result, an optional call and a call of anything but a name, a listed method or a function expression are refused.
- **`agent()`.** The callee is the free global `agent`, never shadowed (it cannot be declared) and never aliased, passed or reassigned, since any other mention of `agent` is a reference to an undeclared name. The call has exactly two arguments, the second an object literal with plain keys from `agentType`, `model`, `effort`, `label` and `phase`, and exactly one `agentType`, a string literal that reads `holyagent:<agent>` for one of the eighteen route agents. At least one `agent()` call must exist.
- **`meta`.** The only export is `export const meta = { … }`, an object literal of literals (strings, numbers, booleans, `null`, arrays and objects of them).
- **Limits.** A script over a million characters, or nested deeper than the walk follows, is refused; the parser or the walk running out of stack is a refusal too, and the hook never throws.

Like the redirect, the hook never calls git. Choosing the holyagent agent is the opt-in to workflows. `onFailure: "block"`, because a failure would let an unvetted workflow through.

## `agent-launch`

A specialist launched directly (the fallback for a session without the `Workflow` tool) used to need a second command from the root to bind its agent id to the Assignment. When the `Agent` tool's prompt came from `assignment dispatch`, the hook now runs the same record step (`assignment record <id> --agent <agentId>`) and adds a line saying so. A launch whose prompt came from elsewhere gets no output.

- It compares the launched `subagent_type` with the agent the Assignment's route names, bare or `holyagent:`-prefixed. A mismatch records nothing and tells the root to dispatch the Assignment again with the printed agent.
- It authorizes nothing and has no `onFailure`. Any failure (no agent id in the response, no state folder, an Assignment that is not Running) only adds a note that the launch could not be recorded, with the command for the root to run, or the reason it cannot succeed.
- It finds the state root itself, inside its own failure handling, so a git failure is reported as that note instead of stopping the hook.
- A workflow's agents are not launched through the `Agent` tool, so the root still records them by hand ([cache-and-workflows.md](cache-and-workflows.md)); a continued agent is reached by `SendMessage`, which this hook does not see, so that too is recorded by hand.

## Removed from the predecessor

The Bash and write guard, the other observation hooks (`SubagentStart`, `SubagentStop` and effort recording) and the dispatch guard are gone, by the maintainer's decision. `PostToolUse` on Agent returned in a narrower form, above: it records a launch and checks no model. The reasons and the audit figures are in [decisions.md](decisions.md).

## The wrapper

The hooks run `scripts/holyagent`, a POSIX `sh` wrapper around the bundled CLI (`scripts/holyagent.js`, one file made by Bun's bundler).

- It must be started by its path (`${CLAUDE_PLUGIN_ROOT}/scripts/holyagent`); started by a bare name from `PATH`, it prints `error: WrapperPath` and exits 127, since the directory it would resolve is the project's.
- It finds `bun` on `PATH`, else in `$BUN_INSTALL/bin` or `~/.bun/bin`. Without one it prints `error: BunMissing: …` with the fix on stderr and exits 127 for every caller, hooks included, so a missing runtime is never mistaken for a quiet success. The same exit and message cover a missing `holyagent.js` bundle.
- It starts Bun with `--no-env-file --config=scripts/empty-bunfig.toml`. The working directory is the project, and Bun would otherwise load the project's `.env` and `bunfig.toml`: an `.env` could redirect the state folder, and a bunfig `preload` would run code on every call. The CLI reads neither.
- On the common path it forks nothing (parameter expansion and builtins only), because each fork is a process under Git Bash on Windows.
