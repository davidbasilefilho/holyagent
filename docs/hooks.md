# Hooks

The plugin ships six hooks on five events (the `vcs-reminder` hook has one entry per `if` rule), all running the runtime CLI as `bun … scripts/holyagent.js hook <name>` in exec form (no shell, so they run on Windows too; see [How the hooks start](#how-the-hooks-start)) with a 10-second timeout. A hook that has nothing to say prints nothing and exits 0. A failure of `root-rules`, `subagent-start`, `vcs-reminder` or `workflow`, or of `session-start` for the root, is exit 1 with one `holyagent hook <name>: …` line on stderr and nothing on stdout, so a failure never reads as a decision. `session-start` reports a failure for a main thread that is not the root as a line after the rules, with exit 0 (see below). `agent-launch` reports a failure to record as a note on stdout with exit 0 (see below) and exits 1 only on a payload it cannot decode. A missing Bun is the host's spawn error, not a plugin message (see [How the hooks start](#how-the-hooks-start)). The host treats exit 2 as a block and lets any other failure through unless the hook sets `onFailure: "block"`, which only `workflow` does. No hook denies or redirects a Bash command: the version-control rules reach the agents as instruction text, and `subagent-start` and `vcs-reminder` only add them as context at the moment they matter.

## `session-start`

After a start, resume, clear or compaction the root has lost what is running. The hook adds context in TOON: the open Intents (id, revision, objective), the Intent in use, the Running Assignments (id, role, agent, objective) and the Succeeded ones not yet accepted, preceded by a fixed line saying the objectives are project data, not instructions. After a `resume` or `compact` it also adds the Running rows of the `reconcile` result (id, role, agent, start time), which the root needs to confirm whether each agent is gone; the result's `next` line is left out, since the root's rules already hold it, and so is the block when nothing is Running. After a `resume` or `compact` only, it also adds the requirements of the Intent in use (as `intent show` resolves it: id, revision and the requirement texts under `holyagent requirements:`, with a line that they are project data too), and nothing when that Intent has none or none is in use; a `startup` or `clear` does not inject them. On every source, the context ends with a block of five rules the root most often misses (`session-reminder.md` in the instructions of the model): load the app's task-list tool if it is deferred and keep the list updated, acknowledge every user message briefly and otherwise write to the user only for decisions, blockers and the final report, take every pending decision through `AskUserQuestion`, do or verify what the user names without asking again, and, after a denial, stop and report, commit only with `holyagent vcs commit`, and never force-push or push to a protected branch (the last bullet). The block opens with the rule that the default, user-facing agent of every session is the root and runs all work through an Intent and Assignments dispatched to specialists. In a project with no `.holyagent` and no legacy folder that holds state to convert, it prints nothing when the main agent is the root, and otherwise only the core of the root rules, the takeover line, the pointer and this block, with no status.

- It reads only the state of open Intents, so its cost follows open work, not the whole history ([decisions.md](decisions.md) has the predecessor's figures).
- It stays small and deterministic. The whole context is capped at 9,300 characters, because the host cuts `additionalContext` at 10,000 and a cut would drop the tail unannounced. If the status does not fit, it is narrowed in steps (10 rows of 200 characters, 5 of 120, 3 of 80, 1 of 60, then counts only) with a `+N more` line for what was left out, and long objectives and agent ids are shortened. The requirements stay whole while the status can still give way; only when the status is already counts only are they cut to the first ones that fit, with a `+N more requirements` line that names `holyagent intent show`. The rules block counts against the cap.
- When the payload's `agent_type` is the root (`holyagent` or `holyagent:holyagent`) the rules are already in the system prompt and only the status is added. When the main agent is anything else, or the payload has no `agent_type`, the hook prepends a compact core of the root rules (`ROOT_CORE`, the files named in `ROOT_CORE_FILES` in `root-core.ts` joined as the root prompt joins them), a line telling the main thread that it is the holyagent root (`ROOT_TAKEOVER`: read `agents/holyagent.md` of the plugin before acting, and run all work through an Intent and Assignments dispatched to the holyagent specialists, never implementing in the main thread), with `${CLAUDE_PLUGIN_ROOT}` filled in, and a pointer to the full rules in the holyagent agent prompt. The Claude Code hooks reference lists `agent_type` as an optional SessionStart field, "present when you start Claude Code with `claude --agent <name>`" (https://code.claude.com/docs/en/hooks, SessionStart input), so a plain session sends none and is read as not the root. The reference does not say what the field holds when the `agent` setting of the plugin's `settings.json` selects the agent; the check accepts both the bare and the namespaced name, and a session where the field is missing gets the rules once more, which costs little.
- When no `.holyagent/` state folder exists (where the state mode puts it) and `.holyclaude/` or `.holycodex/` in the work tree holds convertible state (a project that was never migrated), the hook has no status to show. A folder counts only with state to convert: `.holyclaude/` needs files under `intents/<folder>/`, and `.holycodex/` needs a path under a folder whose name does not start with a dot. The hook adds the same core and takeover line for a main thread that is not the root, a notice naming the legacy folder or folders with state and `holyagent migrate` (`--dry-run` first), and the rules block. An empty legacy folder gets no notice, and without `.holyagent` and any such folder it adds the core, the takeover line, the pointer and the rules block for a main thread that is not the root (a claude.ai cloud session starts in a fresh directory with none of the folders and no `agent_type`), and stays silent for the root. The `${CLAUDE_PLUGIN_ROOT}` filled into the core is what makes the CLI resolvable there: the main thread's Bash has no `CLAUDE_PLUGIN_ROOT` and `holyagent` is not on its `PATH`, so `holyagent <command>` in the rules is `bun --no-env-file --config="<plugin>/scripts/empty-bunfig.toml" "<plugin>/scripts/holyagent.js" <command>` with the absolute plugin path, which runs the same in bash, PowerShell and cmd. That hand-run form carries the `--no-env-file` and `--config` flags, as the hooks do, so a `.env` file or `bunfig.toml` in the repository you work in never changes how the CLI starts; the root core's cap is 4,100 characters to make room for them.
- When `CLAUDE_CODE_REMOTE` is `true` (a claude.ai cloud session) the context also holds `CLOUD_IDENTITY` (`session-cloud-identity.md`): the `get_me` and `holyagent vcs identity` steps that make the user the commit author while the committer stays Claude ([commit-authorship.md](commit-authorship.md)). It follows the core, before the state, and counts against the cap. Elsewhere the text is left out and the root rules say only that commits use the configured git identity.
- The setup check adds one line of `additionalContext` (`setupNotice` in `packages/runtime/src/setup/check.ts`) when `ctx7` is not found, a key `holyagent setup` merges into the user settings is missing, or an earlier Billion Context setup left entries in the Claude Code files (the scan `holyagent doctor` runs, `findLeftovers` in `packages/runtime/src/setup/leftovers.ts`, narrowed by `hasRemovableLeftovers` to what `holyagent setup` can remove: a project or local plugin install whose folder is missing, not yours or not recorded is left out, because setup only prints the command to run there, so the line would never clear): `holyagent: setup is incomplete (missing …; leftovers from an earlier Billion Context setup). Offer the user to run /holyagent:setup, which installs, configures and cleans up; do not run it unasked.` The line follows the core and the cloud text and counts against the cap. When everything is in place and nothing is left over the hook adds nothing, and in a cloud session (`CLAUDE_CODE_REMOTE=true`) it says nothing at all, since `holyagent setup` skips `ctx7` there and the settings are not the user's machine. The check is bounded for the 10-second timeout: it spawns no process and makes no network call, only `Bun.which` lookups on `PATH` (and Bun's global bin directory, where `bun add -g` puts `ctx7`) and reads of `settings.json`, `.claude.json`, the plugin records and `commands/acp-cache.md` in `CLAUDE_CONFIG_DIR` (default `~/.claude`), a stat of each recorded project or local install folder, and it never installs anything or writes a file. A file that is not a JSON object is left to `holyagent setup`, which reports it, and does not trigger the line.
- A failure is loud on stderr, not silent, for the root (exit 1, one `holyagent hook session-start: …` line). A main thread that is not the root would be left with nothing, since the host reads no output from a failed hook, so it gets the core and the rules block as for a project with no state, followed by one line naming the failure tag and `holyagent status`, with exit 0.
- When the context carries the core rules and the payload has a usable `session_id`, the hook also records that the session has them, so that `root-rules` stays quiet (see below). The record is best effort, with the same folder checks as below: a marker that cannot be written costs one more delivery, never the hook.

## `root-rules`

The `session-start` output reaches the main thread only if the host has joined the plugin's hooks by then. In a claude.ai cloud session the synced plugin's hooks can join after the first prompt (a session measured `hooks_init_ms` 47,165 and `new_plugin_hooks_join_ms` 81,167), and the `agent` key of the plugin's `settings.json` did not make the main thread the root, so the main thread ran as the default agent for its first 13 actions with no rules. This hook closes that gap: it runs on `UserPromptSubmit` and on `PreToolUse` for every tool (no matcher, a second entry after the existing ones, which are unchanged), and on the first of these events of a session that has not been given the rules it adds them as `additionalContext` of that event.

- The text is what `session-start` adds for a project with no state: `ROOT_CORE`, the takeover line with `${CLAUDE_PLUGIN_ROOT}` filled in (so the CLI form is absolute), the pointer to the full rules, the cloud identity steps when `CLAUDE_CODE_REMOTE=true`, and the rules block. It stays within the `session-start` budget.
- It says nothing for the root (`agent_type` `holyagent` or `holyagent:holyagent`), for a subagent (the payload has an `agent_id`, or an `agent_type` that is a specialist of the plugin), for an event other than the two above, and for a payload with no `session_id` that is safe to use as a file name.
- Once per session: the hook claims the delivery by creating `holyagent-sessions-<uid>/<session_id>` in the temporary folder of the machine (`os.tmpdir()`, outside every repository and state worktree) with an exclusive create, so parallel tool calls cannot both win. The folder is per user (the user name stands in for the uid where the system has none), made with mode 0700, and used only when `lstat` shows a real directory owned by this user and closed to others; markers are always opened with an exclusive create, so no write follows a link. `session-start` creates the same marker when it delivers the core, so a session whose output arrived has nothing more to receive, and a `compact` delivers again as before and keeps the marker. A resumed session after the temporary folder was cleared gets the rules from its own `session-start`.
- It is `stateless`: it never calls git or looks for the state. A marker folder that is unusable (not private, not owned by this user, a link, read-only or full) makes the hook exit 0 with no output: the late delivery is skipped quietly, never repeated and never an error on every tool call.
- It spawns Bun for every tool call of a main thread, which costs a process start; it prints nothing after the first delivery. It adds context only, so it carries no decision and no `onFailure`.

## `subagent-start`

Specialists share one tree with each other and with the root, so a stray commit, checkout or state edit from one corrupts the others' work. The agent prompt already forbids these writes, and this hook repeats the rule where a specialist starts: it adds the text of `specialist/state-changes.md` (the same file the agent prompts include, so the rule has one owner) as `additionalContext` of the `SubagentStart` event. The text forbids `git commit`, `branch`, `push`, `checkout`, `stash`, `merge` and `reset`, `gh` writes, `holyagent vcs`, `assignment` and `intent` commands and any edit under `.git/` or `.holyagent/`, and asks for the changed paths in the report, which the root records.

- It has no matcher, so the host starts it for every subagent, and the hook itself says nothing for the root (`holyagent`, `holyagent:holyagent`) or any agent type that is not namespaced by the plugin (`holyagent:<specialist>`).
- It adds context only, so it carries no decision and no `onFailure`; it never calls git or looks for the state.

## `vcs-reminder`

Raw `git commit` carries whatever the harness adds, and the author is whatever git is configured with; `holyagent vcs commit` fixes both ([commit-authorship.md](commit-authorship.md)). For a Bash command whose text has `git` followed by `commit` or `push`, the hook adds one line of context: the root commits with `holyagent vcs commit`, never force-pushes and pushes to a protected branch only with the user's approval, and a specialist makes no version-control writes. The command is never denied, rewritten or held for a prompt.

- It is scoped twice. The `if` rules in `hooks/hooks.json` (`Bash(*git*commit*)`, `Bash(*git*push*)`) start the hook only for a command whose text has `git` followed by `commit` or `push` (probed on Claude Code 2.1.310), and the hook itself says nothing about a command without that text. A command with both words matches both rules and gets the line twice, which costs nothing.
- It carries no permission decision and no `onFailure`, so a failure never stops a Bash call. Only a payload that is not JSON is an error (exit 1), and the host lets the call through.
- It never calls git and never looks for the state.
- It is a reminder, not a guard. A command that never spells `git` followed by `commit` or `push` (a git alias such as `git ci`, a spelling that splits the words with quotes, a script, make target or package script that runs git inside) gets none, and nothing stops any git or `gh` write or any edit under `.git/` or `.holyagent/`. The rules rest on the instruction text of the root and the specialists, which the user chose over a guard ([decisions.md](decisions.md)); the `commit-msg` hook below still checks the message of a commit made by hand.

## `commit-msg`

Not a Claude Code hook: a Git `commit-msg` hook. `holyagent hook commit-msg <message-file>` removes agent attribution from the message file and refuses a message that talks about the user or the agent (exit 3, which stops the commit), with the same cleaning and phrases as `vcs commit` ([commit-authorship.md](commit-authorship.md) has the install steps for `.git/hooks/commit-msg` and for lefthook). Git's comment lines (`core.commentString` or `core.commentChar` from the repository's own files, `#` by default; a value that comes only from a `-c` on the command line is ignored, since the caller of `git commit` could use it to hide text) are not checked for phrases, and neither is what follows the exact scissors line that git adds for `git commit -v`, the staged diff. Attribution lines are still removed from below the scissors line, because a message made by hand keeps everything below it.

## `workflow`

The `Workflow` tool otherwise asks for permission. The plugin ships no workflow scripts: the root writes each one inline, in the `script` input of the call ([cache-and-workflows.md](cache-and-workflows.md)). The hook allows a call that carries a `script` (and optionally `args`) and nothing else, when every `agent(` call in the script passes an `agentType` that is a string literal reading `holyagent:<agent>` with one of the eighteen route agents. A `scriptPath`, a `name` (a saved or plugin workflow) or a `resumeFromRunId` runs code the hook has not read, so any of them, or any other input field, gets no decision.

The hook parses the script (with [acorn](https://github.com/acornjs/acorn), as a module with top-level await and `return` allowed) and never runs it. It allows the script only when every node of the syntax tree is of a type in a closed set, every name resolves, and every `agent()` call is vetted; anything it cannot place with certainty, a parse error included, gets no decision, and the normal permission flow applies. The check is `packages/runtime/src/cli/workflow-check.ts`.

- **Node types.** Declarations (`const`, `let`, `var`, functions, arrow functions, `async`), `if`, loops (`for`, `for…of`, `for…in`, `while`, `do…while`), `switch`, `try`/`catch`/`finally`, `throw`, `return`, `break` and `continue`, calls, member access, template literals, array and object literals with spread, unary (not `delete`), binary and logical operators, assignment and update of a name the script declared, conditionals, `await` and optional chaining. Everything else is refused: regular expressions, tagged templates, `new`, `this`, `super`, classes, generators, labels, getters, setters, methods in objects, sequences (`a, b`), `delete`, `import`, `import.meta`, `with` and private names. Division is fine, since the parser tells it from a regular expression.
- **Scopes.** Names resolve through real lexical scopes (module, function, block, loop, `catch`, `switch`). A name is allowed when the script declared it in an enclosing scope, or when it is free and one of the globals below. A script may not declare, as a variable, parameter, function or pattern name, a global of the workflow, a host name (`Bun`, `Deno`, `fetch`, `process`, `require`, `globalThis`, `Function`, `eval`, `setTimeout`, `Worker`, `WebSocket`, `Buffer`, `Symbol`, `Reflect`, `Proxy`, `WebAssembly`, `Date`, …) or a reflective name, so a dummy `(fetch) => 1` cannot make the real `fetch` look declared.
- **Globals.** The workflow globals are `parallel`, `pipeline`, `phase`, `log`, `args` and `budget`; the plain built-ins are `JSON`, `Math`, `Array`, `Object`, `String`, `Number`, `Boolean`, `Promise`, `Map`, `Set`, `Error`, `parseInt`, `parseFloat`, `isNaN`, `isFinite`, `NaN`, `Infinity` and `undefined`. A free global appears only as the callee of a direct call (`parallel`, `pipeline`, `phase`, `log`, `String`, `Number`, `Boolean`, `Error`, `parseInt`, `parseFloat`, `isNaN`, `isFinite`) or as the object of a member call or read, never as a value: it cannot be assigned to a name, passed, returned, spread, put in an array or an object, destructured, or used as an operand. The exceptions are `args` (plain data, readable anywhere) and the constants `undefined`, `NaN` and `Infinity`. A global object is called and read only through short lists: `Object.keys|values|entries|fromEntries`, `Array.isArray|from|of`, `JSON.stringify|parse`, `Math.max|min|abs|floor|ceil|round|trunc|sqrt|pow|sign` and the constants `Math.PI`, `E`, …, `Number.isInteger|isFinite|isNaN|parseFloat|parseInt` and `Number.MAX_SAFE_INTEGER`, …, `Promise.all|allSettled|race|resolve|reject`, and for `budget` only `total`, `spent()` and `remaining()`. Nothing that changes or freezes an object (`assign`, `freeze`, `seal`, `defineProperty`, `defineProperties`, `setPrototypeOf`, `preventExtensions`, `create`, `groupBy`, …) is on a list, so a built-in cannot be rewritten, directly or through an alias.
- **Writes.** A script may assign to a name it declared. It may assign to a member or update one (`row.done = true`, `count++`) only on a name that holds nothing but data the script built: every value the name is set to is an object or array literal, an `agent()` result, data read from `args`, a result of an allowed data method, or another such name. A parameter, a loop variable, a function, a global or anything reached from one is refused, as is a write into a call result (`f().x = 1`).
- **Members and keys.** Member access is by plain name (`entry.prompt`, `args.entries.map`); the only computed access is a non-negative integer literal (`rows[0]`). Computed keys are refused everywhere, in objects and in destructuring patterns, and so are quoted keys in patterns (`const { "constructor": F } = Array`). Names that reach reflection or other code (`constructor`, `prototype`, `__proto__`, `call`, `apply`, `bind`, `getPrototypeOf`, `defineProperty`, …) are refused as properties, keys and declared names. A method of a value may be called only by a name from a fixed list of data methods (`map`, `filter`, `flatMap`, `flat`, `forEach`, `reduce`, `find`, `findIndex`, `some`, `every`, `includes`, `indexOf`, `join`, `slice`, `splice`, `concat`, `push`, `pop`, `shift`, `unshift`, `sort`, `reverse`, `at`, `then`, `catch`, `finally`, and the string methods `trim`, `split`, `replace`, `repeat`, `toUpperCase`, `toLowerCase`, `startsWith`, `endsWith`, `padStart`, `padEnd`, and similar), and it is called where it is read: reading such a method without calling it (`const f = xs.push`, `[1].map(xs.push)`) is refused, so no method is aliased, passed as a value or given another `this`. The methods that run a callback (`map`, `forEach`, `filter`, `find`, `findIndex`, `some`, `every`, `flatMap`) take the callback alone, since a second argument would be its `this`. A call of a call result, an optional call and a call of anything but a name, a listed method or a function expression are refused.
- **`agent()`.** The callee is the free global `agent`, never shadowed (it cannot be declared) and never aliased, passed or reassigned, since any other mention of `agent` is a reference to an undeclared name. The call has exactly two arguments, the second an object literal with plain keys from `agentType`, `model`, `effort`, `label` and `phase`, and exactly one `agentType`, a string literal that reads `holyagent:<agent>` for one of the eighteen route agents. At least one `agent()` call must exist.
- **`meta`.** The only export is `export const meta = { … }`, an object literal of literals (strings, numbers, booleans, `null`, arrays and objects of them).
- **Limits.** A script over a million characters, or nested deeper than the walk follows, is refused; the parser or the walk running out of stack is a refusal too, and the hook never throws.

Like the reminder, the hook never calls git. Choosing the holyagent agent is the opt-in to workflows. `onFailure: "block"`, because a failure would let an unvetted workflow through.

## `agent-launch`

A specialist launched directly (the fallback for a session without the `Workflow` tool) used to need a second command from the root to bind its agent id to the Assignment. When the `Agent` tool's prompt came from `assignment dispatch`, the hook now runs the same record step (`assignment record <id> --agent <agentId>`) and adds a line saying so. A launch whose prompt came from elsewhere gets no output.

- It compares the launched `subagent_type` with the agent the Assignment's route names, bare or `holyagent:`-prefixed. A mismatch records nothing and tells the root to dispatch the Assignment again with the printed agent.
- It authorizes nothing and has no `onFailure`. Any failure (no agent id in the response, no state folder, an Assignment that is not Running) only adds a note that the launch could not be recorded, with the command for the root to run, or the reason it cannot succeed.
- It finds the state folder itself, inside its own failure handling, so a git failure is reported as that note instead of stopping the hook.
- A workflow's agents are not launched through the `Agent` tool, so the root still records them by hand ([cache-and-workflows.md](cache-and-workflows.md)); a continued agent is reached by `SendMessage`, which this hook does not see, so that too is recorded by hand.

## Removed from the predecessor

The Bash and write guard, the other observation hooks (`SubagentStop` and effort recording) and the dispatch guard are gone, by the maintainer's decision; the version-control rules are instruction text, delivered at the right moment by `subagent-start` and `vcs-reminder`, which only add context. `PostToolUse` on Agent returned in a narrower form, above: it records a launch and checks no model. The reasons and the audit figures are in [decisions.md](decisions.md).

## How the hooks start

Every hook is a command hook in exec form: `"command": "bun"` with an `args` list of `--no-env-file`, `--config=${CLAUDE_PLUGIN_ROOT}/scripts/empty-bunfig.toml`, `${CLAUDE_PLUGIN_ROOT}/scripts/holyagent.js`, `hook` and the hook name (`hooks/hooks.json` has the exact list). The bundled CLI `scripts/holyagent.js` is one file made by Bun's bundler.

What the Claude Code hooks reference says about exec form (https://code.claude.com/docs/en/hooks, "Exec form and shell form", read for this page):

- A command hook with `args` is exec form: Claude Code "resolves `command` as an executable on `PATH` and spawns it directly with `args` as the argument vector", with no shell and no shell tokenization on any platform. Without `args` the command goes to a shell: `sh -c` on macOS and Linux, Git Bash on Windows, or PowerShell when Git Bash is not installed. The `shell` field is ignored when `args` is set. So the hooks need no POSIX shell, and a Windows machine without Git Bash can run them.
- `${CLAUDE_PLUGIN_ROOT}` is "substituted into `command` and into each `args` element as plain strings", and exported as an environment variable too (https://code.claude.com/docs/en/plugins/manifest-reference, "Where each variable resolves": hook commands, anywhere in `command` and `args`). Each element is one argument, so a plugin folder with spaces needs no quoting. On Windows the substituted path keeps its native backslashes in exec form.
- On Windows exec form "requires `command` to resolve to a real executable such as a `.exe`"; `.cmd` and `.bat` shims cannot be spawned without a shell. `bun` is `bun.exe` there, and the hooks name the script for it to run, which is the documented "interpreter plus script path" pattern (the docs' example is `node` plus a script).

The flags keep the project out of the CLI. The working directory is the project, and Bun would otherwise load its `.env` and `bunfig.toml`: an `.env` could redirect the state folder, and a bunfig `preload` would run code on every call. So Bun reads no env file and an empty config file (`scripts/empty-bunfig.toml`). The CLI reads neither.

**A missing Bun.** The old wrapper checked for Bun itself and failed loudly: `error: BunMissing` on stderr and exit 127 for every hook. Exec form has no such step. When `bun` is not on the `PATH` of the Claude Code process, the host cannot spawn the hook and reports its own spawn error; the hooks reference says nothing about that case, so what shows is the host's, not this plugin's. The effect follows each hook's `onFailure`: the `workflow` hook blocks the `Workflow` call (safe), and the others let the call through without their context, which is a missing reminder, not a wrong action. The fallback to `$BUN_INSTALL/bin` or `~/.bun/bin` is gone for hooks, so Claude Code must run with Bun's directory on `PATH` (the installers add it; [requirements.md](requirements.md)). `holyagent doctor` is the check for a machine that looks wrong.

**Not verified on Windows.** No Windows machine was available, so the exec-form behavior above is the documented one, not a tested one. One open report says exec form on Windows with Git Bash installed still went through `bash.exe -c` and dropped `args` (https://github.com/anthropics/claude-code/issues/90495). If that is what you see, the hooks would not fail visibly: `bun` with no arguments prints its help and exits 0, so no hook adds its context and nothing says why. A session that shows none of the hook context (no status block at start, no subagent reminder) points to this.

## The sh wrapper

`scripts/holyagent` is a POSIX `sh` wrapper around the same bundle. No hook uses it any more; it stays for a person on macOS, Linux or WSL who wants one command that finds Bun. On Windows start the bundle with Bun directly, as in [the README table](README.md).

- It must be started by its path; started by a bare name from `PATH`, it prints `error: WrapperPath` and exits 127, since the directory it would resolve is the project's.
- It finds `bun` on `PATH`, else in `$BUN_INSTALL/bin` or `~/.bun/bin`. Without one it prints `error: BunMissing: …` with the fix on stderr and exits 127. The same exit and message cover a missing `holyagent.js` bundle.
- It starts Bun with the same `--no-env-file --config=scripts/empty-bunfig.toml` flags.
- On the common path it forks nothing (parameter expansion and builtins only).
