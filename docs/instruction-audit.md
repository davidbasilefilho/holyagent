# Instruction audit for 0.4.0

The baseline was [`3eda3167`](https://github.com/davidbasilefilho/holyagent/tree/3eda31673b0e69ac62d3c938a219f2a7f3e3ff3d). We inventoried 92 shared Markdown sections, 121 behavior requirements and four family mirrors. The published surface was 19 Claude agents, 162 Pi specialist variants, 52 private family guidance files, and a separate native Codex workflow skill and 18 role definitions. Mirror coverage checks that translations exist. It does not prove that a host loaded them or that an agent followed them.

| ------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Pi through T3 Code | HolyAgent prepends the active family's root prompt to Pi's native prompt. Specialists receive the matching role body and private family guidance; other Pi skills stay visible.                                                                    | Tested through the Pi 1.5.0 SDK and RPC. Hosted T3 features and account availability are separate.                                                                                                       |
| Claude Code        | The plugin defines the root and specialist prompts, and start/resume hooks add current workflow state. The exact specialist state rule was also sent at `SubagentStart`. An interactive run and project settings determine the active agent; the plugin's `agent` setting is deprecated and still needs a tested migration.     |

Hosted startup still needs its own test. Existing preferences to disable plugins or automatic skill listing are preserved. |

Three changes matter in practice. A missing attachment in a summary now calls for looking in authorized earlier deliveries, recovering the original and checking the destination. An unavailable specialist stops only that dispatch; native steering can change affected running work without interrupting other paths. A green check is not a merge verdict without the exact head, required reviews and branch protections. Those rules do not create new permissions or make mandatory independent review optional.

The runtime also stopped recommending an inline workflow for one fresh Assignment. The agent CLI returned a one-entry `workflow` on the baseline, even though the instructions said to launch it directly. It now returns `subagent` for a lone ready launch, including when workflows are available. A lone fresh launch plus a warm continuation also needs no inline workflow. Multiple independent launches or a writer followed by its independent reviewer can still use one. Runtime checks hold dependent work and prevent two overlapping writers from dispatching together. This changes the planning action, not model choice, available tools or the approval boundary.

In an isolated two-variant run with the baseline and revised GPT-6.2 guidance, both workers independently recovered the original synthetic report from the earlier delivery and verified identical bytes at the authorized destination. Both rejected an older wrong report in the negative control and left independent progress untouched. Neither asked or regenerated. This checks the behavior on two runs and the presence of the new rule in assembled output. It does not demonstrate a gain over the baseline or measure model consumption.

`hillclimb-iteration` was exercised on two local examples, not a model benchmark. At the same 800 × 600 keyboard-focus state, a contrast trial of 3.08:1 failed the 4.5:1 guardrail and was rejected. The kept visual trial improved 2.54:1 to 7.56:1 with unchanged bounds, focus and keyboard activation. In the nonvisual fixture, six alternating tsrs runs per mode preserved 384 output files byte-for-byte and the expected diagnostic. `--fast` did not improve the measured median, so the default was kept. Neither result is a product performance claim.

An operational trial checked the public `holyagent setup codex --non-interactive` with native Codex 0.172.0 and identical isolated profiles that explicitly disabled plugins. The [published baseline](https://github.com/davidbasilefilho/holyagent/commit/e66866c833bba74a292da3b33d93f0ddb185b07f) exited with a plugin-not-found error after taking the profile from one file to 24. The [new setup](https://github.com/davidbasilefilho/holyagent/commit/5de5c3520b8035e8511a0434d5803719bbaf866d), run from the source-built public entry point, explained that plugins were disabled and left the sole file byte-identical. After enabling plugins in that test profile, setup succeeded. A new native `codex debug prompt-input` saw the workflow, and a repeat preserved the config and setup receipt. This checks recovery and actual instruction loading, not hosted startup or model inference.

## What the examples contribute

The original players would not load in this environment. The evidence below separates what Theo said from what was independently checked. The text sources are a [timestamped transcript of the first video](https://www.usetranscribe.io/yt/NBCM_ZoWZo8/claude-unlimited-usage) and a [mirror of the second video's published automatic captions](https://prepublish.ai/youtube-transcript/D8PikZ1KhUo). Screen-only prompts, visual results and displayed metrics were not verified. Don't infer an exact unpublished prompt or a measured result from either transcript.

- **Skate, reference and metric.** [4:08–7:13](https://www.youtube.com/watch?v=NBCM_ZoWZo8&t=248s) distinguishes the playable prototype from the [trick-recognition benchmark](https://github.com/T3-Content/skatebench). Theo reports that known benchmark items did not generalize, and that a change regressed the inward heel-flip animation. [14:31–17:43](https://www.youtube.com/watch?v=NBCM_ZoWZo8&t=871s) describes a brief that prioritized physics and controller inputs, then let the agent compare shots of similar states with a panel's feedback. Theo reports too much work on the sky and changes that brightened the scene toward the wrong reference, until he changed from Skate 3 to Skate 1. Adopt comparable snapshots, behavior outside the primary metric as a guardrail, and a stop when the evaluator rewards the wrong thing. For an original design, use the brief and qualitative review of comparable rendered states. The controller replay was a proposed check, not one he said he ran. The contrast fixture above tested rejecting a gain that still failed a guardrail.
- **TS Rust, validation and execution.** [12:10–13:16](https://www.youtube.com/watch?v=NBCM_ZoWZo8&t=730s) describes keeping the compiler revision, projects and expected outputs fixed, then aiming for twice the speed once parity was established. The project's [recovery plan](https://github.com/pingdotgg/ts-rust/blob/91f3d021c4f1f102cebee704ac285e85ae0c8ff5/docs/typechecker-reset-plan.md#L11-L66) records 49 lost passing cases and a narrow run reproducing 14 losses. Building the test binary did not exercise its assertions. Adopt [accepted revisions and fresh verdicts](https://github.com/pingdotgg/ts-rust/blob/91f3d021c4f1f102cebee704ac285e85ae0c8ff5/docs/typechecker-accountability.md#L128-L163), not fixed staffing or build limits. The author's [correction about source reuse](https://github.com/pingdotgg/ts-rust/blob/91f3d021c4f1f102cebee704ac285e85ae0c8ff5/README.md#L38-L58) is another reason to record the starting revision. The tsrs fixture above held artifacts and diagnostics constant before accepting any speed claim.
- **Environment and diminishing returns.** [23:00–25:54](https://www.youtube.com/watch?v=NBCM_ZoWZo8&t=1380s) and [31:08–36:57](https://www.youtube.com/watch?v=NBCM_ZoWZo8&t=1868s) describe TS Rust builds queueing, concurrent builds exhausting a machine and a compiler experiment that Theo says barely works for its target. Separate queue latency from work latency, verify prerequisites and stop when another optimization no longer buys the requested result. The timing fixture separates native wait, first progress and end-to-end latency. No new fleet, services or quotas follow from these anecdotes.
- **Complete briefs and scoped work.** In the second video, [around 30:03](https://www.youtube.com/watch?v=D8PikZ1KhUo&t=1803s), Theo describes prescribing fixes that did not solve the original problem. [Around 45:54](https://www.youtube.com/watch?v=D8PikZ1KhUo&t=2754s), he rejects the agent's speculative time estimate and notes that he forgot to ask for PR follow-through in the same brief. He also describes two worktrees trying to check out one branch. Specify the outcome, evidence and authorized handoff, not an untested implementation. Avoid the checkout conflict with a read-only reviewer at the exact revision or a distinct worktree. Keep retries and returns visible and branch protection intact. The dispatch and merge-readiness tests cover those boundaries.
- **Resume, triage and what to reject.** At [55:26–56:51](https://www.youtube.com/watch?v=D8PikZ1KhUo&t=3326s), Theo describes over-broad research undertaken to consume the remaining allowance, then resumes threads whose state he no longer remembers. Reject forced fan-out and maximum consumption as objectives. Adapt the useful part: recover the artifact and current status, then continue the authorized next step or name the blocker. The blind recovery and one-Assignment cases check those behaviors. Account pooling, proxies to evade limits, full-access defaults and automatic merges without authorization were not adopted.

## Efficiency evidence

Product measures answer whether the change works for users: fewer partial writes, a successful recovery, a clearer flow, or lower latency under the same workload. Agent-loop measures answer how much work it took to produce an equivalent verified result. Compare completed tasks with equivalent inputs and quality gates. Preserve each initial and final revision and record the host, model, effort and workload. Use end-to-end elapsed time, latency to useful progress and, when there are enough comparable samples, p50 and p95. Separate task counts, user-visible turns, model calls and other internal operations. Record actual waits and retries only where the corresponding events are visible.

For authorized traces, sum actual attempts across the root and specialists. Report uncached input, cached input and output per session and Assignment when attributable, and aggregate per task without counting an event twice. Subtract cached input from totals only when the host includes it in input. Use deltas for cumulative counters and exclude cache-write from consumption. Cache rate is cached input divided by total input. Judge it alongside absolute use and completed quality, never as a success measure on its own. A missing model-call event or an unobserved specialist is unknown coverage, not zero. CI runtime, API price and fixture token numbers are not evidence of subscription savings.

The external evaluator `bun scripts/agent-loop-evidence.ts <manifest.json>` reads only explicitly listed Codex rollout files. Describe each task with `id`, `scenario`, `variant` (`before` or `after`), `origin` (`native` or `loopback`) and `sessions` (`path`, optional `assignment`). An `accepted` marker identifies the same verified workload and quality bar in both variants. Include separate `elapsedMs`, `firstUsefulProgressMs` or `visibleTurns` only when those events were observed. Include retry session traces in the same task. The evaluator keeps native turns, model responses and visible turns separate and does not compare loopback with real runs. It reports the model and effort from each turn's last context record, links observed response usage to the turn, and counts compaction events. Input tokens count what the observed responses report as input, not unique context or a measured resend. The trace does not establish resend causes or volume, and the evaluator does not export prompt or tool-content text.
