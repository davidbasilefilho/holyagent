# npm publishing

The public package is `holyagent`, packed from `packages/integrations/pi/dist`; the workspace root is private. Its Pi host dependencies are peers supplied by the user's Pi installation. The bundled runtime does not require publishing the internal workspaces.

Before publication, an authorized administrator must create the GitHub environment `npm` and restrict deployment branches to the protected heads `main` and `dev`; verify that the corresponding branch rulesets apply and that bypass permissions are appropriate. The environment name in a workflow does not itself restrict branches. Configure the npm trusted publisher for `holyagent` with owner `davidbasilefilho`, repository `holyagent`, caller workflow `publish.yml`, and environment `npm`. Verify the actual GitHub and npm settings before publishing; this repository does not configure them. Grant no npm token secret. The `publish.yml` caller grants OIDC only to the stable and dev calls, which grant it only to their npm jobs.

Branch pushes run validation first. The stable and dev workflows pack the public Pi distribution with `bun pm pack`, validate its repository metadata against the provenance repository, publish that tarball to npm using trusted publishing, then pass the same published tarball to a dependent GitHub release job. Protected main publishes under `latest`; protected dev publishes under `dev` with the commit UTC timestamp and short SHA in its version. Other branches validate but do not publish. Pull requests have no publication permissions. An npm failure prevents a new GitHub release; a later GitHub release failure may leave an npm version without a GitHub release, so investigate before retrying.

Before npm publication, the helper checks the exact GitHub tag against the intended commit. An absent or matching tag permits publication; a conflict or lookup failure stops it. The release action checks again afterward for races. A race or subsequent release failure can still leave an immutable npm version without its GitHub release; investigate and resolve it through an authorized manual process.

A stable rerun still rejects every existing version. A `dev` rerun can resume a publication whose exact version is already public or whose publish response identifies that exact staged version. It observes npm without changing tags, requires the exact version on `dev`, then verifies the rebuilt bytes and the signed npm provenance for the official workflow and commit. An unrelated conflict, digest mismatch, stale head or failed lookup stops recovery.

After the next protected `dev` push passes validation, the prerelease job also checks its immediate predecessor. To complete a missing release, it rebuilds the packed bytes from that exact Git tree without lifecycle scripts or credentials, verifies the immutable public npm version, and checks the attested attempt's original GitHub validations. An unpublished predecessor with no GitHub tag is left alone. The historical path never changes npm or `dev`, and works even if `dev` has already advanced to the new version. A historical failure is reported without stopping an independently successful current publication from completing. Both paths create only the exact missing tag, prerelease or asset. They do not replace an existing tag or mismatched asset, and cannot create a stable release. Changes to the packaging tool that prevent byte-identical rebuilding fail closed.

## PR preview channels

The preview policy reserves `pr-<number>` for the current, eligible HEAD of that PR and `pr` for the newest open PR HEAD in the repository. It ranks **all** open heads by their Git committer UTC timestamp, then by higher PR number at equal timestamps. PR update time, arrival order, latest commit author time, and last successful build are not ordering inputs. If the winning head targets an unsupported base (anything other than protected `main` or `dev`), is a draft or fork, lacks independent review, changes the trusted controls, has no successful current validation, or has no verified publication, `pr` should be absent. It does not fall back to an older build while the winner remains open. Per-PR channels converge independently.

The live read-only preflight, `bun scripts/npm-preview-live.ts <authorized-reviewer-login> [...]`, gathers this evidence from public APIs and local Git objects. Run it from the protected dev checkout with the reviewed objects available locally. It does not fetch Git data or mutate the repository. An optional `GH_TOKEN` goes only to GitHub read requests. The offline planner, `bun scripts/npm-preview.ts <complete-evidence.json>`, accepts an already collected snapshot. Both only print a plan. It does not build, publish, mutate tags, claim approval, or activate an automation. Its input is **evidence**, not instructions, and manually supplied JSON is not a permission or proof. A trusted collector must obtain the current protected `dev` SHA and its local checkout SHA, the complete paginated set of open PRs, each current HEAD and committer timestamp (including forks and drafts), the PR author and chronologically ordered reviews, and current registry tags. It must confirm exact repository identity for each preview candidate and check active independent reviews by an explicitly authorized reviewer. A reviewer cannot approve their own PR, and dismissals and change requests must be applied before readiness. Never use a prior head's approval or validation after a push.

For a candidate, compare CI, workflow, release controls, package manifests, and tool configuration with the protected trusted source using `comparePreviewControls`. Changes or unavailable evidence make it ineligible until a separately reviewed, trusted-base gate can validate that exact head. A workflow display name or same-named status is not trustworthy on its own. Require the official validation run bound to this PR, source SHA, base SHA, and exact run attempt, with all applicable required jobs complete and successful. Use `packPreview` on approved exact Git objects, not a downloaded or extracted PR archive. It builds from bounded regular tracked blobs in the generated Pi distribution; it neither checks out nor runs candidate code, hooks, dependency scripts or package lifecycle. It rejects symlinks, path aliases and unexpected manifest fields. The immutable version embeds the PR number, UTC time and full SHA. Compare the expected SHA-512 digest with the public registry's exact version metadata. Reuse only identical bytes; an existing different version payload is a blocker, not a reason to overwrite or unpublish it.

Re-evaluate from full evidence before every write and check fresh registry readback after it. Only touch the `pr` and `pr-<number>` namespace. An existing tag outside the managed version/PR convention blocks planning. Closing or marking a PR draft clears its owned tag. Pushing new bytes drops the old tag until the new head is reviewed, validated and verified. Reopening reuses verified identical bytes only if the live evidence still authorizes them. A rerun never restores a stale snapshot, and a failed publish does not move a tag toward pending or mismatched bytes. Failed or partial observation stops all operations, including cleanup. No PR preview operation changes `latest` or `dev`.

An exact, approved, validated candidate first publishes immutable bytes under a temporary `pr-staged-<number>-<sha>` registry tag and verifies integrity without moving a discovery tag. The temporary tag may be visible in registry metadata. Promotion is a separate operation based on fresh evidence. The publisher then removes its verified staging tag. The reconcile job obtains candidate Git objects from public PR refs after the review check, pins the received object to the freshly observed head, and never checks out a candidate. It invokes npm only on its verified archive with lifecycle scripts disabled, not in the checkout or using repository, user, or global npm configuration. It supplies no npm token and passes no GitHub API credential to npm.

After activation, use `bunx holyagent@pr setup` for the newest verified open PR or `bunx holyagent@pr-172 setup` for PR 172's verified current head. An unavailable channel fails to resolve instead of choosing a different PR. `bunx holyagent@dev setup` remains the protected development branch channel, not a way to install a PR. While a new protected HEAD is waiting for validation and publication, the public registry can still show the last published protected version. Compare its Git SHA before testing a new change. Unqualified `bunx holyagent setup` keeps using the stable `latest` tag.

GitHub refs and npm tags cannot be locked in one transaction. A privileged publisher, if activated later, must serialize preview reconciliations, rebuild its plan at execution, verify the exact state immediately before and after each mutation, and stop on drift or conflicting readback. Do not claim that tags are always live during event or registry propagation. If the winner changes between the final GitHub read and an npm write, the next authorized reconciliation can clear or correct the tag; report and investigate partial writes before retrying. Existing `dev` publication also refuses any queued SHA that is no longer the protected `dev` HEAD before writing and checks both npm readback and GitHub HEAD afterward. Its postcheck cannot undo an already successful publication or close that cross-service gap. The stable `latest` path is unchanged.

### Activation boundary

The `.github/workflows/npm-preview.yml` job is disabled unless the repository variable `NPM_PREVIEW_ENABLED` is `true`. Before enabling it, an authorized administrator must create the dedicated `npm-preview` GitHub environment. Restrict its **deployment branches** to protected `dev` and `main` only, allow no tags, and require independent approval. A workflow-level branch check is not a substitute for the environment restriction. Set `NPM_PREVIEW_REVIEWERS` as a protected environment variable with the eligible independent GitHub logins. The authorized npm package admin registers the separate trusted publisher with owner `davidbasilefilho`, repository `holyagent`, filename `npm-preview.yml` and environment `npm-preview`. It needs **Allow npm publish** to publish immutable versions under staging tags, and **Allow npm dist-tag** to reconcile them. Do not add tokens or change the existing `publish.yml` publisher.

The job can run on a protected `dev` push once it is merged and enabled. GitHub makes the manual and scheduled triggers available only after the workflow exists on the default branch. For manual reconciliation select protected `dev`, not a PR or `main`. The schedule runs from protected default `main` and reconciles a trusted checkout of current protected `dev` twice an hour, subject to environment approval. It does not consume PR workflow artifacts, use `pull_request_target`, or receive parameters from PR authors. Until the schedule or a manual run is available and approved, preview tags can be behind PR events. Jobs serialize with one another, and each rereads live refs and tags before and after its writes. Cross-service changes during a write cannot be made atomic.

npm requires CLI 11.21.0 or newer on the 11 line, or 12.2.0 or newer on the 12 line, for OIDC dist-tag operations. The preview job verifies an exact npm CLI 11.21.0 archive from the public registry before use. Check the actual GitHub and npm restrictions out of band before enabling. A green test suite alone does not prove the registry granted writes. Do not use `npm whoami` or a real mutation as a read-only authorization probe. See [npm trusted publishing](https://docs.npmjs.com/trusted-publishers/#managing-dist-tags-with-trusted-publishing).
