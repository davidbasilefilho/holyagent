# Claude parity: which HolyAgent Claude rules become Pi rules

**Status: the carriers below ship in 0.3.0 in the Pi package (the extension, the 18 specialists, the Pi root prompt, the skills, the tool surface and the launcher; [README.md](README.md#what-ships-now-and-what-is-planned) lists the state of each part). A row, or a point under [Still open for the implementation](#still-open-for-the-implementation), that is not built says so on its own line.** Each row names the carrier used on Pi. A carrier marked "Custom" is code HolyAgent writes only where no maintained extension exists; where the maintainer decided on an extension, the row names it. Points the sources leave open are listed at the end.

Pi 1.4.0, commit `4a080252f06caf63a525d7873c5d94d3c23887e0` (the plan pins 1.5.0; see [README.md](README.md#version-risk)). The Claude side was read at commit `a4fa284` of branch `release/0.1.0/feat/claude-integration`: the instruction text in `packages/runtime/src/instructions/` (`claude-5.5/root.md`, `specialist.md`, `writing-bar.md`, `roles/`, `skills/`, `requirements/`), the plugin in `packages/integrations/claude/` (`hooks.json`, `src/agents.ts`, `src/workflows/`) and the CLI it calls (`cli/hook.ts`, `domain/plan.ts`, `domain/route.ts`). In the tables, a link in the Basis column is a Pi source; "Inference" marks a design choice that no Pi document states. Section 1 holds the rules that cut across the rest, so later rows do not repeat them.

## Requirement

Binding, from the Intent (maintainer): "every Claude rule that Pi can carry (instruction, existing or custom extension) must become a Pi rule."

A rule counts as carried when the Pi agent receives the same text or Pi enforces the same behavior. Parity is judged per rule, not per mechanism: a Claude mechanism that exists only because of Claude Code (a permission prompt, a plugin manifest) is carried by what does the same job in Pi, or is listed under section 8 with the reason. Carriers:

- **Instruction**: text in a Pi system prompt, a Pi skill or a role prompt.
- **Existing**: a Pi built-in or a shipped example extension, loaded explicitly (examples are not loaded by default).
- **Custom**: an extension (or Pi package) HolyAgent writes.
- **Cannot**: Pi has no way to carry it; the reason is given.

## 4. Specialists

`specialist.md` and the role file are concatenated into each agent prompt, with `writing-bar.md` added for Worker.implementation and Reviewer.artifact (`agents.ts`). On Pi the same concatenation, from the Kimi family's sources, is the body of each specialist's package agent file (`prompt_mode: replace`), written by `packages/integrations/pi/src/agents.ts` ([extensions.md](extensions.md#the-agent-files)). Frontmatter fields map as in section 3: `tools` from the route's capabilities through `toolArgs` (Search to the web tool, Write to `write`/`edit`/`bash`, Shell to `bash`, Reviewer.code keeps `bash` for `git diff`), `model` and `effort` to the `model` and `thinking` of each `Agent` call, which are not in the file; `cacheTtl` is not carried on Kimi (section 3). The model and effort of each role come from the Kimi routing table ([providers.md](providers.md#routing)). Read-only roles are read-only only through their tool list in Claude, and the same allowlist does it in Pi. The description the root reads is built from the role's first sentence; the `Agent` tool's list reuses it.

## 5. Workflows

The Claude plugin ships no workflow script: the root writes each one inline, with one `agent()` per entry `{id, agent, model, effort, prompt}` (its `agentType` is `holyagent:<agent>`), a pipeline by default and a review stage after its writers. ## Still open for the implementation

The maintainer decided the Pi route table ([providers.md](providers.md#routing)), so the earlier question of which Pi models and levels stand for `haiku`, `sonnet` and `opus` is closed. These points were left open by the sources. Points 1, 2 and 7 are settled in the code; the others are recorded in [t3-code.md](t3-code.md#to-verify) or on the page named in the point when they are settled:

1. The carrier of the root text. Settled: the extension's `before_agent_start` handler puts it in front of Pi's own system prompt, so it reaches Pi as system-prompt text, never as a transcript message.
2. The name and values of the launch flag that selects root, specialist child or other session. Settled: the flag is `--holyagent-role` ([extensions.md](extensions.md#the-extension-entry)).
3. Which launcher requirements `@tintinweb/pi-subagents` meets by itself and which need HolyAgent glue, and whether its tools are callable from codemode scripts ([orchestration.md](orchestration.md#decision-for-030)).
4. T3 Code: the release that contains PR #7211, the exact `preview_*` set, whether T3's bridge re-adds tools after HolyAgent filters them, whether a deferred tool stays discoverable once excluded, and Pi 1.5.0 against T3's `agent_settled` and `clear_queue` assumptions ([t3-code.md](t3-code.md#to-verify)).
5. Whether `@juicesharp/rpiv-ask-user-question` uses `custom()` (`@juicesharp/rpiv-todo` draws a `setWidget` panel that T3 does not render), which decides where a HolyAgent adapter is needed under T3 ([t3-code.md](t3-code.md#dialogs-and-status-only)).
6. Whether a completion notice after `agent_settled` starts a new root turn in T3, how a session learns T3's permission mode, and whether `device_*` reaches Pi ([t3-code.md](t3-code.md#to-verify)).
7. The format of T3's `settings.json`, which decides whether setup writes it or prints the UI steps. Settled: setup writes it ([t3-code.md](t3-code.md#t3-settings-written-by-setup)).
8. Computer use: how the extension's confirmations are turned off ([t3-code.md](t3-code.md#computer-use-through-cua-driver)).
9. What Pi does when HolyAgent is declared at both the global and the project-local scope ([installation.md](installation.md#global-and-project-local-installs)).
