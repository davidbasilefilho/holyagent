# Pi configuration: files, locations, precedence, keys

**Status: the first section describes HolyAgent's own configuration, which the runtime reads in 0.3.0; [How HolyAgent launches Pi](#how-holyagent-launches-pi) says what is built; the sections between are research on Pi's configuration, not HolyAgent behavior.**

Pi 1.4.0, commit `4a080252f06caf63a525d7873c5d94d3c23887e0` (HolyAgent pins 1.5.0; see [README.md](README.md#version-risk)). "Inference:" marks a conclusion drawn here, not a stated fact.

## HolyAgent config.json

HolyAgent reads `.holyagent/config.json` in the project and `~/.holyagent/config.json` for the user ([the user-level config](#the-user-level-config)). The maintainer decided that the Pi integration uses this same file ("alter/extend .holyagent/config.json, pi section and claude section, common stuff should be outside those sections"). The file has three kinds of content:

- a `pi` section, read only by the Pi integration;
- a `claude` section, read only by the Claude plugin (it holds no option yet, and an empty object is valid);
- settings common to both hosts, outside both sections: today the `vcs` section ([commit-authorship.md](../commit-authorship.md)).

The file is the one place that sets the Pi integration's options, which functionality is on, and the model provider. Turning a function or the provider on or off turns on or off the existing Pi extensions and packages that supply it, and a disabled one is neither loaded nor required. The schema is `packages/runtime/src/config/schema.ts` (the `Config` schema, with every default in it); `piPackages(config)` in `packages/runtime/src/config/packages.ts` returns the package sources a config must load, each `npm:<name>@<version>` at the exact release pinned in `packages/runtime/src/config/pi-packages.json`.

Rules for the file:

- It is decoded with Effect Schema and `onExcessProperty: "error"` when it loads, and every option has a documented default.
- An unknown key or an invalid value, at any depth, stops the run with a `ConfigInvalid` error whose message names the field (as a path such as `["pi"]["routes"]["root"]["thinking"]`) and the file, and whose hint points to this page. It never falls back silently, and it never ignores a key it does not know. The one leniency is `"vcs": null`, which older files wrote and which reads as no `vcs` section; `pi` and `claude` stay strict.
- Every command that reads the config decodes the whole file, not only its own section: the `vcs` commands (`vcs commit`, `vcs pr` and the `commit-msg` hook) stop on an invalid key in the `pi` or `claude` section too, with the file and the field named, and so does the Pi integration on an invalid `vcs` section. One file means one schema, so a mistake cannot hide in the section that the current command does not use.
- Every key may be left out; the file `{}` is valid and means all defaults.
- The package lists no dependencies. `holyagent setup` runs `pi install` for each Pi package the config enables, at its pin, and `pi remove` for a feature package the config turns off; re-run it after changing `pi.features` ([installation.md](installation.md#what-setup-and-doctor-do)).

A `false` feature is not loaded and not required: `piPackages` leaves its package out, and with every feature off only `pi-provider-kimi-code` remains (every source carries its pinned version); with `pi.enable` off nothing is loaded, and `holyagent setup` neither installs nor removes a Pi package. The packages come in the order of the capability registry (`@tintinweb/pi-subagents`, `billion-context`, `@juicesharp/rpiv-todo`, `@juicesharp/rpiv-ask-user-question`, `@aliou/pi-processes`, `@amaster.ai/pi-computer-use`) after the provider extension, and only those the form in force offers ([Capabilities](#capabilities)), then `pi-web-kit` when the web choice is `pi-web-kit` (chosen, or a provider without web tools). `pi.features.mcp` is carried by Pi's built-in MCP extension, so it loads no package: `false` adds `--no-mcp` to every process. The same switches shape each role's tool arguments (`toolArgs`: no web tool with `web` `off`, no `computer_use_*` entry with `computerUse` off, no `mcp__` entry with `mcp` off) and the settings data `toolSettings` returns for setup to write ([extensions.md](extensions.md#tool-arguments)). The `pi.codemode` and `pi.t3` settings load no package. T3 Code's context meter is not a setting: setup does not set it.

### Capabilities

Each boolean of `pi.features` is one optional capability, one entry of `CAPABILITIES` in `packages/runtime/src/config/capabilities.ts`; `pi.web` is a three-way choice and stays outside it. The registry is a data module: `pi.features` and its defaults, the package selection (`piPackages`), the tool lists and settings (`toolArgs`, `toolSettings`), the setup flags and screen rows, and the doctor lines all read it, so adding a capability is adding one entry. An entry holds:

| Field                   | Meaning                                                                                                                                                                                                    |
| ----------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `name`, `feature`       | The kebab-case name of the setup flag and the doctor line (`computer-use`), and the `pi.features` key (`computerUse`)                                                                                      |
| `description`, `skills` | What it gives, and the skills it carries (none of today's capabilities carries one)                                                                                                                        |
| `applicability`         | Whose tools it reaches: `root`, `specialists` or `both`                                                                                                                                                    |
| `defaultOn`             | The default of the `pi.features` key, `true` for every capability today                                                                                                                                    |
| `provider`              | The only `pi.provider` it applies to (`luna-reserve` and `context-management`: `openai-codex`); absent for a capability that works with every provider                                                     |
| `nativeHosts`           | The `<platform>-<arch>` hosts its native library covers (`fff`); absent for a capability with none. Elsewhere it is not offered, and the tools it replaces stay Pi's                                       |
| `needs`                 | What it needs of the system, which doctor checks: `display` (a graphical session), `command` (on `PATH`, with the fix to print) or `node` (Node.js at a minimum release); a form can add needs of its own  |
| `forms`                 | The `headless` and the `normal` form: each lists its Pi packages (named, never versioned: `pi-packages.json` pins them), MCP servers, needs and whether doctor checks a pairing, or says it is not offered |
| `tools`, `settings`     | The tool patterns the root excludes, the visual specialists get and a screen Assignment gets ([screen.md](screen.md)), and the package settings setup merges, while it is on and offered                   |
| `health`                | The probes doctor runs: `needs` and `packages`; the pairing of a browser with browse is a flag of the normal form of `browser-use`                                                                         |

The twelve capabilities are `subagents`, `context-compression`, `todo`, `ask`, `processes`, `mcp`, `computer-use`, `browser-use`, `luna-reserve`, `context-management`, `just-bash` and `fff`, each on by default. `computer-use` and `browser-use` differ by form: `computer-use` is not offered `headless`, since it drives a graphical session, and `browser-use` is offered in both, with browse in the normal form and the Playwright MCP server in the headless one. `fff` differs by host, not by form: `nativeHosts` lists the `<platform>-<arch>` hosts its native library covers, and anywhere else it is not offered in either form. `luna-reserve` and `context-management` apply to the Codex provider only: `enabledCapabilities` takes the config's provider and leaves it out under another, so doctor lists it only under Codex.

**The form.** Setup and doctor detect it from the machine: `headless` in a claude.ai cloud session, when `CI` is set to a truthy value (not empty, `0`, `false`, `no` or `off`), and on Linux and the other Unix systems without `DISPLAY` or `WAYLAND_DISPLAY`; `normal` otherwise (macOS and Windows have a display). `--form headless|normal` on `holyagent setup` and `holyagent doctor` overrides the detection. A capability the form does not offer is neither installed nor required: setup leaves its package out and removes a listed one, writes none of its settings and says `~ form: headless (detected: ...)`; doctor prints a `~` line for it and fails nothing. The tool lists of the root and of the ordinary specialists, as `toolArgs` and the generated specialist files carry them, do not depend on the form, because a pattern that matches no registered tool is inert. The screen specialists do: each has one agent file for each form (`<agent>-screen`, and `<agent>-headless-screen` for a headless machine), and the dispatch names the one of the machine's form ([screen.md](screen.md#forms)). The switch itself stays in the config: a `computerUse` of `true` on a headless machine applies once the machine has a display.

**Switching one.** `holyagent setup --<name> on|off` (for example `--computer-use off`) and a row of the setup screen write `pi.features.<key>` to the config of the scope (your `~/.holyagent/config.json` at `--scope user`, the project's `.holyagent/config.json` at `project` and `local`), only for a value that differs from what the config already decides, keeping every other key; the Pi step of the same run then installs or removes the package. A capability flag applies without the screen and is refused with `--undo`, which leaves the config alone.

Three settings grant access, to the computer (`pi.features.computerUse`), to devices (`pi.t3.deviceAccess`) and to the web (`pi.features.web`); a `false` (`"off"` for the web) in the user file is final for them ([the user-level config](#the-user-level-config)).

The route rows, each with the `model` and `thinking` defaults of the Kimi table ([providers.md](providers.md#routing)); a config that selects `openai-codex` gets the Codex table below instead, and a row it overrides keeps the table's value for the key it leaves out. `<row>` is `root` or one of the 18 specialists:

### The user-level config

The maintainer's words: "Add ~/.holyagent config". A user-level `~/.holyagent/config.json` holds per-user defaults:

- It has the same Effect Schema as the project's `.holyagent/config.json`: the common settings, the `pi` section and the `claude` section.
- Its folder is `.holyagent` in `HOLYAGENT_HOME` when that variable is set and not empty (tests and sandboxes use it), else in the home directory (`HOME`, else `USERPROFILE`, else the operating system's answer).
- Both files are decoded with `onExcessProperty: "error"` before they are merged (a `"vcs": null` reads as no section), so an unknown key or an invalid value in either stops the run with a `ConfigInvalid` message that names the field and the file ([rules above](#holyagent-configjson)). A missing file reads as an empty one.
- **The merge is key by key, and the project wins.** The loader decodes the user file and the project file on their own, merges the two, and fills every setting that neither sets with its default. A key the project leaves out keeps the user's value; the project never resets it to the default.
  - Objects merge recursively, down to a single route's `thinking`: a user file that sets `pi.routes.root.model` and a project file that sets `pi.routes.root.thinking` give a root with both.
  - **A user-level off is final** for `pi.features.computerUse`, `pi.t3.deviceAccess` and `pi.features.web`: where the user file sets the first two to `false` or the web to `"off"`, the project config can turn them off but not back on, and a project value that would turn them on is ignored, not an error. A user `true`, or a user web mode other than `off`, binds nothing, and the project can still switch the setting off. These settings give an agent access to the computer, to devices and to the internet, so the person who turns one off for their account stays in control of it. Every other key keeps project-wins, `pi.enable` included.
  - Any other value, a list included, from the project replaces the user's. Lists are not concatenated or merged by element, so the project's `vcs.allowWords` is the whole list and an empty list there clears the user's. The same rule is Pi's own for its settings, except for the resource lists that Pi combines ([Precedence](#precedence)); HolyAgent has no list that combines.
- The project's `.holyagent/config.json` is the config file of the first state folder that has one.
- Tests (`packages/runtime/tests/config/`) cover the merge, the errors and the defaults inside the existing CI jobs.

Inference: Pi itself keeps provider logins, `defaultProjectTrust` and `npmCommand` in `~/.pi/agent`, so the user-level file is for HolyAgent's own defaults and not a second home for those. The file is read by the Claude plugin too; its scopes are in [usage.md](../usage.md#install-scopes).

## Precedence

1. **Settings.** Project `.pi/settings.json` overrides the agent-directory `settings.json`; resource lists (`packages`, `extensions`, `skills`, `prompts`, `themes`) are combined ([settings.md L3](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/docs/settings.md#L3), [settings.md L148-L163](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/docs/settings.md#L148-L163)). In code, the two layers are deep-merged: nested objects merge recursively, any other value (including arrays) from the project replaces the global one, and `defaultTools` has a special rule where a list made only of `+name`/`-name` entries modifies the inherited list ([settings-manager.ts L60-L146](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/src/core/settings-manager.ts#L60-L146)).
2. **Project settings only apply after project trust** (see below). The one exception is `sessionDir`, read before trust ([configuration.md L3](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/docs/configuration.md#L3)).
3. **CLI over settings.** For example, `--tools`, `--no-tools`, `--no-builtin-tools` override `defaultTools`; `--session-dir` beats `PI_CODING_AGENT_SESSION_DIR`, which beats `sessionDir` ([settings.md L58-L60](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/docs/settings.md#L58-L60), [settings.md L66](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/docs/settings.md#L66), [cli.md L96-L97](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/docs/cli.md#L96-L97)).
4. **Credentials.** Order: runtime `--api-key`, then stored `auth.json`, then `apiKey` in `models.json`, then provider environment variables or ambient cloud credentials ([models.md L23](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/docs/models.md#L23)).
5. **System prompt files.** A trusted project `SYSTEM.md`/`APPEND_SYSTEM.md` takes precedence over the agent-directory file of the same name; files are not combined ([configuration.md L39](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/docs/configuration.md#L39)).
6. **Context files** load from the agent directory, the working directory and its parents, and apply below their directory; `AGENTS.override.md` replaces `AGENTS.md`/`CLAUDE.md` only within its own directory; discovery does not need project trust, and `-nc/--no-context-files` disables it ([configuration.md L41-L47](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/docs/configuration.md#L41-L47), [cli.md L214](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/docs/cli.md#L214)).
7. **Reload.** After hand-editing settings, instructions or resources, run `/reload` ([configuration.md L5](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/docs/configuration.md#L5)).

## Project trust

Pi asks for a trust decision before loading `.pi/settings.json`, `.pi/mcp.json`, `.pi/extensions|skills|prompts|themes`, `.pi/SYSTEM.md`/`APPEND_SYSTEM.md` and project `.agents/skills` ([security.md L35-L45](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/docs/security.md#L35-L45)). Decision order: CLI `--approve`/`--no-approve`; then `project_trust` extension handlers (user-level and `-e` extensions only); then saved decisions (closest parent wins); then `defaultProjectTrust` (`ask` by default; agent-directory settings only) ([security.md L59-L73](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/docs/security.md#L59-L73), [settings.md L36](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/docs/settings.md#L36)). Print, JSON and RPC modes cannot show the prompt: with no override, extension or saved decision, `always` loads project resources while `ask` and `never` skip them ([security.md L75-L82](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/docs/security.md#L75-L82)). Trust does not limit what tool calls can do ([security.md L33](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/docs/security.md#L33)).

## How HolyAgent launches Pi

**Status: the first list is built; the second is planned.**

Built:

- `holyagent setup` writes the settings `toolSettings` returns, merging where a key is unset and differs from the package default; at `--scope project` and `local` it writes the project's `.pi` folder, leaves a key your global file sets, and refuses a symlinked `.pi` folder or file ([installation.md](installation.md#what-setup-and-doctor-do)); `holyagent setup --undo` backs it out and `holyagent doctor` reports the files that lack keys.
- Pi starts as plain `pi` after the one-time `pi install` ([installation.md](installation.md#how-holyagent-installs)); that session is the root, because the package's `--holyagent-role` flag defaults to `root` ([extensions.md](extensions.md#the-extension-entry)).
- The root starts specialists through `@tintinweb/pi-subagents`, which runs each as an in-process session of the root's Pi process, so a specialist has no launch line, environment or `--approve` of its own and shares the root's project trust ([extensions.md](extensions.md#specialists-as-package-agents), [orchestration.md](orchestration.md#decision-for-030)). Each specialist's tools are the `tools:` line of its agent file, which `toolArgs` decides from the config ([extensions.md](extensions.md#tool-arguments)).
- Before each run of the root the extension writes `HOLYAGENT_HOST=pi`, `HOLYAGENT_WORKFLOWS`, `PI_CODEMODE_MAX_WORKERS` (from `pi.codemode.maxWorkers`) and `PI_CACHE_RETENTION=long` into its process environment.
- The model and thinking level of each specialist come from the route table in `config.json`; the root passes them with its `Agent` calls ([providers.md](providers.md#routing)).

Planned:

- `holyagent setup` sets Pi's `npmCommand` setting to `bun`, so Pi installs its packages with Bun ([installation.md](installation.md#what-setup-and-doctor-do)).
- `PI_SKIP_VERSION_CHECK=1` and `PI_TELEMETRY=0`, which nothing sets today and which would apply to the whole root process. Specialists run in-process, so a per-specialist session directory, `--model`, `--tools`, `--exclude-tools` or `--approve` does not exist for them (the model and tools come from the agent file and the `Agent` call). All of those are documented flags and variables ([cli.md L55-L110](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/docs/cli.md#L55-L110)). The 1.5.0 docs word `PI_OFFLINE` as disabling automatic network activity, including model catalog refreshes, so the specialists are not run fully offline.

HolyAgent's own state (Intent revisions, Assignment status) has no place in Pi's settings; Pi offers `pi.appendEntry()` for session-attached data ([extensions.md L337-L355](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/docs/extensions.md#L337-L355)), but the Intent store stays in HolyAgent.
