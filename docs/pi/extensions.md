# Pi extensions and packages

**Status: the package and its extension ship in 0.3.0 ([The HolyAgent package](#the-holyagent-package), [The extension entry](#the-extension-entry), [Specialists as package agents](#specialists-as-package-agents)), and the tool surface is built as data and functions ([Tool surface for 0.3.0](#tool-surface-for-030)). Each of those sections says what is not built yet: the prompt templates and the writes of Pi's settings. The sections from [What an extension is](#what-an-extension-is) on are research on Pi's extension API, not HolyAgent behavior.**

The Pi facts below are for Pi 1.4.0 (commit `4a080252f06caf63a525d7873c5d94d3c23887e0`); the plan pins 1.5.0 (see [README.md](README.md#version-risk)). Paths below are relative to `packages/coding-agent/` unless a link says otherwise. Statements marked "Inference:" are conclusions drawn here, not Pi's.

## The HolyAgent package

The Pi integration is one Pi package, built from the same instruction sources as the Claude plugin:

- **Where and how it is generated.** The folder `packages/integrations/pi/` sits beside `packages/integrations/claude/` and reuses the runtime's domain, state, CLI and instructions without copying them. Its generator reads the same instruction sources as the Claude build and writes the Pi package to `packages/integrations/pi/dist/`. That path is in the generated-path list, so a byte-for-byte sync test covers it (`packages/integrations/pi/tests/pi.test.ts`); every generated agent file carries a note naming its source; `mise run build` syncs the version from the root `package.json`.
- **Ship format: built JavaScript.** The maintainer's words: "built js, use bun build". The extension is bundled with `bun build` into the generated package (`extensions/holyagent.js`), not shipped as TypeScript for Pi to transpile.
- **Layout.** A `pi` key in `package.json` names the `extensions/` and `skills/` folders, with the `pi-package` keyword ([Pi packages](#pi-packages)); the package also holds `scripts/` (the wrapper and the bundled CLI). It adds `agents/`, the 18 specialists, named under `pi.subagents.agents` for `@tintinweb/pi-subagents` ([Specialists as package agents](#specialists-as-package-agents)). There is no `prompts/` folder.
- **Host modules are peer dependencies with the range `"*"`.** Pi 1.5.0's package docs require this for `@earendil-works/pi-ai`, `pi-agent-core`, `pi-coding-agent`, `pi-tui` and `typebox`. `scripts/dependency-ranges.test.ts` accepts only caret ranges except for these Pi peer dependencies.
- **Paths stay within 120 characters**, the limit `scripts/repo-paths.test.ts` enforces.
- **The extension itself** is a default-exported factory that starts no process, socket, watcher or timer; it does that in `session_start` and releases it in an idempotent `session_shutdown` ([Events and hooks](#events-and-hooks)). Its handlers do not build Claude-style hook payloads: they run the CLI through the package's wrapper and build the context with the runtime's own context builders ([the extension entry](#the-extension-entry)). It works in TUI, RPC, JSON and print modes and fails closed.
- **It ships the skills of `packages/integrations/pi/dist/skills`** in the Agent Skills format (for example `dev-server` and `user-busy`). The `code-review` and `security-review` prompt templates that [claude-parity.md](claude-parity.md#6-skills-requirements-and-hooks) plans are not built, so the package has no `prompts/` folder.

## The extension entry

**Status: built.** The Pi extension of the package, `extensions/holyagent.js`, gives every Pi session its role and its HolyAgent context. The specialists ship as agents of `@tintinweb/pi-subagents`, and the extension carries the glue the package lacks ([Specialists as package agents](#specialists-as-package-agents)); the Kimi provider, `holyagent setup` and `holyagent doctor` ship too ([providers.md](providers.md), [installation.md](installation.md#what-setup-and-doctor-do)). The root's system prompt, tools and provider checks are built too ([The root on Pi](#the-root-on-pi)).

- **The factory** registers the `--holyagent-role` flag and six handlers (`session_start`, `session_compact`, `before_agent_start`, `message_end`, `tool_call`, `session_shutdown`) and starts nothing. Pi parses flags after the factory runs, so the role is read in the handlers.
- **Roles.** `root` (the default, so plain `pi` starts the HolyAgent root) gets the status and the reminder, and the root prompt in front of Pi's own ([The root on Pi](#the-root-on-pi)). `specialist` gets the status and neither the root rules nor the reminder; a child the package launches runs as `specialist` whatever the flag says ([Child detection](#child-detection)). `session` (any other session) gets the core of the root rules, in the Kimi family's words, with `${HOLYAGENT_PI_ROOT}` filled in with the package folder, then the status. Any other value fails closed: one notice that names the flag and the three roles, no status, and the session is held to the root's prompt and tools, as when the config cannot be read ([The root on Pi](#the-root-on-pi)).
- **What runs.** `session_start` (startup, reload, new, resume, fork) and `session_compact` run `holyagent status`, and a resume and a compaction then run `holyagent reconcile`, one after the other. All of a collection's commands share one deadline of ten seconds, the Claude hook's timeout, and each is also limited to eight; the config and the state folder are asked together, since neither needs the other. A compaction that starts while an older collection is still running stops it, and a shutdown stops the one in flight; the result of a stopped collection is dropped. The status is not a system-prompt change, which would cost the cache: it is a custom message that the next run takes from `before_agent_start`, once. `session_shutdown` stops the commands still running and releases the session, and it waits for every command the session started, older aborted gathers included, up to the 2 s stop grace each; calling it again does nothing.
- **Budget and silence.** The context is built by the runtime's session context builder, so it has the Claude hook's character budget (`CONTEXT_BUDGET`) and the same narrowing of the status. A project with no `.holyagent` state folder gets nothing, except that a `session` role still gets the core, as the Claude hook gives it to a main thread that is not the root. In a git work tree the folder is the one `holyagent state mode` reports, checked after `status`, which makes the state worktree of a project that keeps state. A project that is not a git repository keeps its state in its own `.holyagent` folder, as the Claude hook finds it, so the extension checks that folder and does not ask `state mode`, which fails there.
- **The wrapper.** Pi runs the extension under Node, and the runtime reads files with Bun, so the extension reaches the runtime only through `scripts/holyagent` of the package (run with `sh`), generated from the Claude plugin's wrapper with the same empty Bun config, beside `scripts/holyagent.js`. The bundle is the CLI plus two things of its own: `config <state-folder>...`, which loads the HolyAgent config through the runtime loader and prints it as JSON, and a leading `--project <folder>`, which makes the folder the working directory before the command runs. Under Pi, Bun therefore starts in the package's folder and enters the project in-process through `--project`, after its own startup, so the project's `.env` and `bunfig.toml` are never read; the Claude hook starts the same wrapper in the project itself, which is why the wrapper passes no env file and an empty config. The extension starts every program, `sh` and `git`, in the package's own folder and names the project in the arguments (`--project`, `git -C`), because on Windows a bare program name is looked up in the working directory first, where a project could put its own `sh` or `git`.
- **Config.** `pi.enable: false` makes the extension register no more than its flag and handlers and add no context, prompt, tool change, provider variable or provider check. An invalid config file stops it with the loader's message, which names the file and the field.
- **Failure.** A failing command, a timeout or output it cannot read adds one line to the next run (`holyagent: ...`) and never throws into Pi. A notice is built from text a project or Pi printed, so it loses its C0 and C1 control characters (ESC and CSI start escape sequences), Unicode format characters (bidi overrides, zero-width characters, the Arabic letter mark, the tag block and the like) and variation selectors before it is shown to the user and the model. The handlers use no TUI-only API, only `ctx.cwd`, `pi.exec` and the message result, so TUI, RPC, JSON and print modes behave the same.
- **Not covered yet.** The requirements of the Intent in use are not added after a resume or compaction. `piContext` also leaves out three notices the Claude hook adds: the legacy-state notice (a project with `.holyclaude` or `.holycodex` state and no `.holyagent` folder), the cloud identity text, and the setup notice.

### The root on Pi

What the extension does for the root only, that is a session whose role is `root` and that is not a child, except the provider's environment, which covers every child too. With `pi.enable` off in the merged config none of it runs, except that a project's `pi.enable: false` alone leaves the root its prompt and its tool exclusions (see `pi.enable` off below); only the user's own off takes them away.

- **System prompt.** `before_agent_start` returns the root prompt in front of Pi's own prompt, on every run, because Pi starts each run from its own prompt. The root prompt is the Kimi root sections (`PI_ROOT_SECTIONS` in `packages/runtime/src/pi/root-prompt.ts`: the same files in the same order as the Claude root agent, a test compares them), embedded in the bundle as text, with the maintainers' notes removed and `${HOLYAGENT_PI_ROOT}` filled by `fillPackageRoot`. It is put in front, not in place of Pi's, because Pi's prompt carries what Claude Code keeps outside the agent prompt: the project's `AGENTS.md`, the skills list, the date and the working folder. The root's identity and rules lead, as the Claude plugin's root agent replaces Claude Code's main-thread prompt. A child keeps its own prompt (`prompt_mode: replace`) with the folder filled in. The prompt is returned once the config has been read with `pi.enable` on, even when a later step of the collection failed, and when the config cannot be read at all (the git call, the config command or its decoding, or the role fails): then the defaults decide, the notice is shown and the root keeps its prompt, its tool exclusions and the provider's variables, so a config nobody can read cannot lift them.
- **Tools.** At `session_start` (not at a compaction, which would undo a change the user made) the extension calls `pi.setActiveTools` with Pi's current selection plus the root's `toolArgs` tools (`codemode`) minus its `excludeTools` (`rootActiveTools`; a `*` in an entry matches any run of characters, so `computer_use_*` removes every computer-use tool). This is the command line's `--tools +codemode --exclude-tools ...` done after launch. It covers the tools registered when the session starts; a tool an extension registers later is not excluded. `--no-mcp` cannot be applied from an extension, because it decides which extensions load, so `pi.features.mcp` off takes effect only for a launch that passes the flag. The start's work (the tools and the provider checks) runs once, from the first collection that ends, so a compaction that stopped the start's collection does it and one that follows does not. A `setActiveTools` that throws is reported as a notice of its own, delivered beside the status message and not in its place.
- **Excluded tools.** `setActiveTools` only deactivates, and Pi's `ctx.executeTool` lets a `codemode` script call every registered tool whose exposure is `codemode` or `deferred`, active or not. Of the root's excluded tools two groups are registered that way and stay callable: the computer-use tools beyond the core set (`@amaster.ai/pi-computer-use` 0.1.36 registers them `deferred`, all of them under its `lazy` profile) and `pi-web-kit`'s `web_search` and `web_fetch` (`deferred` while `codemode` is active). `write`, `edit`, the core computer-use tools and the provider's `moonshot_search` and `moonshot_fetch` have direct exposure, so deactivating them is enough. The `tool_call` gate refuses a call to any tool the root excludes (`refuseExcludedTool`, by the same patterns as `--exclude-tools`), whether the model, a script or `tool_search` makes it; the gate runs in the root only, with the defaults' patterns from the session's start (so a run in flight across a reload, resume or fork is gated before the config is read) and when the config cannot be read, and stands down only with the user's own `pi.enable` off. The patterns are the union of the defaults', the user's and the merged config's, so a project can add exclusions but never remove one, and neither a project config that cannot be read nor a failing `git` drops the user's (the user's file is read first, on its own, before and apart from both); within a session the set only grows, so a later collection whose reads fail keeps what an earlier one took from the user (only the user's own `pi.enable` off clears it). A user file that cannot be read, or is still being read when the collection's deadline passes, leaves the defaults' patterns and adds a notice that the home-level config could not be read, delivered once on the next run (joined to the root's tools notice, when there is one): its `computerUse: false` or another `web` mode drops no pattern while the packages stay installed.
- **Provider.** The provider's variables (`providerEnv`: `KIMI_CODE_REGION=global`) are set for the root and for every child as soon as the start's collection has read the config, through the same `applyEnvironment` as the worker cap; a value the user set stays. Pi's `exec` starts the probes with the process environment, so the variables are set before they start. At `session_start` the extension runs `pi auth check --provider <id> --json` and, when the provider is ready, `pi --list-models` (`requireProviderReady` and `validateModelCatalog`), through `pi.exec`, since the extension runs under Node and has no Bun Shell. The checks run beside the session: startup never waits for them, the two have a deadline of their own, as long as the collection's, and a probe that cannot start (a missing `pi` too, which Pi's `exec` reports as exit 1 with the spawn error), is stopped or times out says nothing. A provider that is not ready or invalid, or a route model the catalog does not list, is one notice with the fix (`holyagent: ...`), delivered once on the first run after the checks end, beside the status message. A listing that fails or is not recognised adds nothing. The checks do not run for a child, a compaction or a collection that failed.

## Specialists as package agents

**Status: built.** `@tintinweb/pi-subagents` 0.23.1 runs every child as an in-process `AgentSession` of the root's Pi process (`src/agent-runner.ts`: the session is created with `createAgentSession`, named and prompted in the same function), so a child has no command line. There is no `--tools`, `--session-id`, `-e` or `--append-system-prompt` for it and no environment of its own: the agent file is the one place a role's prompt and tool set can live, and the process environment is shared by the root and every child. The package's own agent files and settings carry the rest, and the extension adds only what the package does not do.

### The agent files

`packages/integrations/pi/src/agents.ts` writes `dist/agents/<name>.md` for each of the 18 specialists, named as the Claude agents are (`worker-implementation`, `reviewer-code`, without the `holyagent:` prefix), and the manifest names the folder under `pi.subagents.agents` (Pi ignores that key, the package reads it from an installed package) and in `files`. Each file is built from the Kimi family's sources, which the Claude plugin's section tables also describe:

- **Frontmatter:** `name`, a `description` that the root reads in the `Agent` tool's list (the role's first sentence, read-only or writing, the independence line), `prompt_mode: replace` and `tools`. There is no `model` and no `thinking`: the package ranks an agent file above the call's parameters on its `Agent` path (`invocation-config.ts`), and the route values are per user, so the root passes them on each call from the route table ([providers.md](providers.md#routing)).
- **Body:** `You are the holyagent <name> specialist`, the role sections, the shared specialist conduct and the conditional sections the role gets (writing bar, merge-ready bar, code quality, interface inspection), passed through `stripCitations`. With `prompt_mode: replace` it is the child's whole prompt: a child loads neither the root's prompt nor `AGENTS.md`.
- **The package folder.** The body keeps `${HOLYAGENT_PI_ROOT}`, because the install folder is not known when the file is built. The extension's `before_agent_start` handler fills it into a child's system prompt with `/` only (`fillPackageRoot`, the same form as the wrapper path, so `sh` takes it for a path on Windows).
- **`tools`.** `agentTools(config, route)` maps what `toolArgs(config, route)` decides, for the default config, into the package's entry forms: Pi's built-ins by name (`read`, `grep`, `find`, `ls`, `write`, `edit`, `bash`); `mcp__t3*code__...` patterns as they are, which the package matches itself; `ext:builtin:codemode` for `codemode`; `ext:pi-computer-use` for the computer-use tools; and `ext:<package>/<tool>` for the web tools, naming the provider's package (`ext:pi-provider-kimi-code/moonshot_search`) or `pi-web-kit`. The package names an extension by its npm name without the scope. Any `ext:` entry turns extension tools into an explicit allowlist, so a specialist has no `todo`, `ask_user_question` or process tool, and the package withholds its own `Agent` and workflow tools from children. A tool without an entry fails the build.

### The settings

**Status: built.** `holyagent setup` writes this file ([Settings that setup writes](#settings-that-setup-writes)); until it has run, the package registers its own default agents and falls back to `general-purpose`.

While `pi.features.subagents` is on, `toolSettings` also yields `~/.pi/agent/subagents.json` (the package reads `getAgentDir()`, which is `PI_CODING_AGENT_DIR` when that is set) with `disableDefaultAgents: true` and `fallbackSubagent: "none"`: the package's `general-purpose`, `Explore` and `Plan` are not registered, and a `subagent_type` that names no enabled agent fails instead of falling back to `general-purpose`, whose tool set is not a specialist's. Only the 18 names launch. An agent file in `.pi/agents`, `.agents/agents` or the global `agents` folder outranks a package's one of the same name, and the package has no setting that ignores such files (`strictAgentFiles` only makes an unreadable file fatal, `packageAgents` only gates the package tier). The gates below stop a type outside the 18 names, not a project that ships its own `worker-implementation.md`: a cloned repository can replace a specialist's prompt and tools, so a project's `.pi/agents` and `.agents/agents` are as trusted as its code, and Pi's project trust is the guard.

### The glue in the extension

Five small exported functions of `extension.ts`, each tested with synthesized event fixtures:

- **Child detection.** `childAgent(sessionName)`: the package names a child's session `<agent>#<first 8 characters of its id>` before it binds the child's extensions (`agent-runner.ts`, `setSessionName` before `bindExtensions`), so the name is readable when the child's events fire. A name of that form with one of the 18 agents is a child. The package loads the extension in each child with the role flag at its default, `root`; the extension runs a child as `specialist` instead: the status and no root reminder, no change to the process environment, and the package folder filled into its prompt.
- **Process environment.** Before each run of a root or any non-child session, `hostEnvironment(pi.getActiveTools())` writes `HOLYAGENT_HOST=pi` and `HOLYAGENT_WORKFLOWS` (`1` when `SubagentWorkflow` and `codemode` are both active tools, else `0`; the package can withdraw `SubagentWorkflow` after load, so it is read again each time) into `process.env`, where the `holyagent` calls of every session read them. Once the config is read and `pi.enable` is on, it also writes `PI_CODEMODE_MAX_WORKERS` from `toolArgs(config, "root").env` (`pi.codemode.maxWorkers`, 4 by default) and `PI_CACHE_RETENTION=long`, unless the variable is already set, so one value holds for the process and the user's own setting wins. The codemode cap and the cache retention are process-wide in Pi (`codemode/execute.js` reads the cap per call), so the root and all concurrent specialists share them. `PI_CACHE_RETENTION=long` helps on the Anthropic and OpenAI adapters and does not extend Kimi's cache ([caching-and-subagents.md](caching-and-subagents.md#cache-target)).
- **The `Agent` gate.** `refuseNonSpecialist` is the `tool_call` handler for the package's `Agent` tool: it blocks a `subagent_type` outside the 18 names (exact match after trimming) and names the allowed ones in the reason. A call with `resume` names an existing agent and is not checked. It reads `model` and `thinking` and changes neither: they stay as the call gave them.
- **The `SubagentWorkflow` gate.** `refuseNonSpecialistWorkflow` is the same `tool_call` check for the package's `SubagentWorkflow` tool, whose script `agent()` calls start the package's `general-purpose` agent, with every tool, unless they name an `agentType`. It runs the runtime's `workflowRefusal` (`workflow-check.ts`, the check behind the Claude plugin's `Workflow` hook) with the 18 bare names, so the script must be plain and every `agent()` call must name one of them by a string-literal `agentType`. The package does not parse the script: it cuts the `meta` fragment by pattern and evaluates it on the host thread, then compiles the script, `export` blanked, as a classic script inside an async arrow function in a worker. The check runs in its Pi mode and parses exactly those two things, with the package's own algorithm (`workflow/meta.ts`, `workflow/worker-source.ts`): the fragment must be an object of literals with plain keys (no identifier, call, `this`, getter, computed key or interpolated template), the meta pattern must match once, and the wrapped script is parsed as a classic script, so an HTML-like comment hides code as it does at run time, and a function declared inside a block (hoisted out of it in a classic script) is refused. A `<!--` or `-->` inside a string is plain text. Only an inline `script` with at most `args` is read: a `scriptPath`, a saved `name` or any other input key is refused. A refusal blocks the call with the reason and never asks for confirmation. The gate runs at `tool_call`, which is too late for one thing: Pi's interactive mode draws a tool call on every streamed update of the model's message and again when a session is reloaded, and the package's own drawing of a `SubagentWorkflow` call (`workflowCallName`) evaluates the same meta fragment on the host thread, so a streamed fragment such as `this.constructor.constructor("return process")()` would reach `process` before the gate refuses the call. Print and RPC mode draw nothing and are not exposed. The extension closes this with `pi.registerToolRenderer`, which Pi runs in every session: for `SubagentWorkflow` it keeps the package's result card and replaces the call line with one that evaluates nothing and shows the workflow's `name` only when the fragment is a vetted object of literals (`literalWorkflowName` in `workflow-check.ts`, which cuts and vets the fragment as the gate does), with control characters removed and the length cut. The package's `execute` still evaluates the fragment, but only for a call the gate let through. A resolver of another extension that loads earlier and returns renderers for `SubagentWorkflow` without calling `next()` would bypass this; Pi runs resolvers in extension load order.
- **`pi.enable` off.** The merged config with `pi.enable` off adds no context and no settings. The root's exclusions, the `tool_call` gate and the root prompt stand down only when the user-level config alone has `pi.enable` off (the extension reads it with a `config` call that names no project folder, beside the merged one on every collection): a project's `.holyagent/config.json` cannot lift them, since a cloned repository would otherwise switch the guard off, and it can add exclusions but not remove one. A config that could not be read leaves them on.
- **Failed reports.** The package counts a child as completed unless its last message stopped with a provider error or hit the length limit with no text, so an empty final message arrives as "No output." and a truncated report as a success. In a child, the `message_end` handler uses `failedFinalMessage` to replace a final assistant message (one without tool calls) that has no text, or whose stop reason is `length`, with the same message at stop reason `error` and an `errorMessage` saying so. The package already turns that into a failed record, and the root reads it as `Agent failed: ...` with the partial output, or in the failure notice of a background child; the reason avoids the words Pi retries a provider error on. Messages that call tools, and every message of the root, are left alone.

Not built here: the reports of an Assignment (`assignment reports` reads the journal and the `subagents:record` entries, [orchestration.md](orchestration.md)). A child's Pi session id is generated by the package and cannot be derived from the Assignment id (it never passes an id to `SessionManager.create`), so the Assignment id travels in the call's `name` and `description`; a continued specialist is `Agent({ resume })` with the agent id the first call returned.

## Tool surface for 0.3.0

**Status: built as data and functions** in `packages/runtime/src/pi/tools.ts` (the tool arguments and settings), `provider.ts` (the web choice) and `config/packages.ts` (the packages). Nothing in them starts a process or writes a file; `holyagent setup` does that with their data. Used today: the agent generator reads `toolArgs` for the specialists' `tools:` lines ([Specialists as package agents](#specialists-as-package-agents)), the extension sets the `env` of the root's `toolArgs` (`PI_CODEMODE_MAX_WORKERS`) and applies its tools with `pi.setActiveTools` ([The root on Pi](#the-root-on-pi)), and `holyagent setup` installs the packages of `config/packages.ts` ([installation.md](installation.md#what-setup-and-doctor-do)). `holyagent setup` also writes the files `toolSettings` returns ([Settings that setup writes](#settings-that-setup-writes)). Not used yet: the root's `--no-mcp`, which an extension cannot apply. The T3 Code integration is planned.

The rule is to reuse existing, maintained Pi extensions for required functionality and write custom code only where none exists. The maintainer decided the packages below. Each is pinned ([installation.md](installation.md#the-pin)) and each is on or off in `config.json`; a disabled one is neither loaded nor required ([configuration.md](configuration.md#holyagent-configjson)). No custom tool exists in this surface: every tool below comes from Pi's built-ins, a built-in extension or a package.

The research found no evidence either way that the `@juicesharp/rpiv-*` packages work on Pi 1.5.0: their listing names Pi 0.80.x or 1.x and tests child sessions on Pi 0.80.6, 1.0.4 and 1.1.0 ([rpiv-mono](https://github.com/juicesharp/rpiv-mono/)). Their behavior on the pinned 1.5.0 is to be verified by the recorded fixtures ([installation.md](installation.md#the-pin)).

Reused from Pi as it is: the built-in `read`, `grep`, `find`, `ls`, `write`, `edit` and `bash` tools replace `Read`, `Grep`, `Glob`, `Write`, `Edit` and `Bash` and are enabled for the root with `--tools` and `--exclude-tools` and for each specialist by its agent file's `tools:` line ([Tool arguments](#tool-arguments)); Pi's native skills replace `Skill`; its prompt templates carry the review first-pass prompts; `builtin:mcp` carries MCP-served tools, T3 Code's among them ([MCP and the T3 Code tools](#mcp-and-the-t3-code-tools)); `builtin:codemode` hosts the workflow scripts and is enabled for the root with `--tools +codemode` ([orchestration.md](orchestration.md#codemode-in-030)).

**Computer use** comes from `@amaster.ai/pi-computer-use` (third-party; 0.1.36 when read, Apache-2.0), which connects Pi to Cua Driver, bundles the driver (there is no separate driver install, and its version moves with the extension pin) and is pinned like the others. Only Worker.visual and Reviewer.visual get its tools (the pattern `computer_use_*`), and the settings data turns its confirmations off ([Settings that setup writes](#settings-that-setup-writes), [t3-code.md](t3-code.md#computer-use-through-cua-driver)).

**The rpiv packages under T3 Code.** T3 renders only the RPC dialogs (`select`, `confirm`, `input`, `editor`), `notify` and `setStatus`; `custom()` returns `undefined` in RPC mode, and `hasUI` is true there, so `@juicesharp/rpiv-ask-user-question` does not remove its tool as it does with no UI. Inference: a tool that depends on `custom()` TUI rendering does nothing under T3. Whether either package uses `custom()` is to be verified; where one does, a HolyAgent adapter maps it to the dialogs and status ([t3-code.md](t3-code.md#dialogs-and-status-only)).

Not loaded: the `protected-paths.ts` and `permission-gate.ts` examples (no gate in 0.3.0, see [auto-mode.md](auto-mode.md)) and the experimental `pi-durable` package. The shipped `todo.ts`, `question.ts` and `questionnaire.ts` examples are no longer the carriers; whether the examples in Pi's tarball can be referenced from a package at all is unknown, since the docs do not say.

### Web tools

- **Default with Kimi:** `moonshot_search` and `moonshot_fetch`, two optional Moonshot-side tools of `pi-provider-kimi-code`. They are off by default and switched on by the `tools` entries of the provider extension's settings file, `~/.pi/providers/kimi-coding/config.json`, which the settings data carries ([Settings that setup writes](#settings-that-setup-writes)). They need the OAuth login, so a user who logs in with `KIMI_API_KEY` cannot use them and `pi-web-kit` stays the fallback for that case. They send queries and URLs to Moonshot's services. The tools are listed in the extension's [README](https://github.com/Leechael/pi-provider-kimi-code). Moonshot itself says its web search is being updated and is not recommended for production workflows for now (reported by the 2026-11-07 research, no page linked), which is why `pi-web-kit` stays as the fallback.
- **`pi-web-kit`** gives `web_search` and `web_fetch`, with Exa among its providers; its `web_search` requires a `purpose` parameter for Exa ([page](https://pi.dev/packages/pi-web-kit), undated, scraped 2026-11-07; its maintenance status is unverified beyond the listing). It is not loaded while the provider extension offers web tools, and it stays selectable in `config.json` as the fallback. The choice is one function, `webChoice`: `pi.features.web` `off` has no web tools; `pi-web-kit` loads the package; `provider` (the default) uses the provider's tools and loads `pi-web-kit` only for a provider that offers none (Kimi offers two, so it never does).
- Other maintained candidates the research found, not chosen: `pi-web-access`, `@zhcsyncer/pi-search-hub`, and any MCP server through Pi's built-in MCP.
- The Claude `WebSearch` and `WebFetch` of the Librarian roles map to these tools ([claude-parity.md](claude-parity.md#3-claude-tools-the-instruction-text-names-and-what-carries-each)).

### Tool arguments

`toolArgs(config, key)` in `packages/runtime/src/pi/tools.ts` is the one place a role's tools are decided; `key` is `root` or one of the 18 specialists, and the result carries `--tools`, `--exclude-tools`, `--no-mcp` and `env` (`PI_CODEMODE_MAX_WORKERS`, from `pi.codemode.maxWorkers`, 4 by default). The root's values are Pi's command line; the extension applies `--tools` and `--exclude-tools` with `pi.setActiveTools` at session start and sets `env` on the process; a specialist runs in that process, so its `tools` become the `tools:` line of its agent file ([The agent files](#the-agent-files)) and the columns below say what each allowlist holds. Every role runs `codemode` in mode `only` ([orchestration.md](orchestration.md#codemode-in-030)). The specialists' allowlists follow the route table's capabilities, as the Claude agents' do:

| Role                                                                | `--tools`                                                                                                   | `--exclude-tools`                                                                      |
| ------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| Root                                                                | `+codemode` (the default selection, so `read`, `bash` and the extension tools of the enabled packages stay) | `write,edit`, the computer-use tools and the web choice's tools, while each is enabled |
| Explorer.map, .lookup, .trace; Reviewer.audit, .security, .artifact | `read,grep,find,ls,codemode`                                                                                | `write,edit,bash`                                                                      |
| Librarian.lookup, .research                                         | the read tools, the web tools of the [web choice](#web-tools) and `codemode`                                | `write,edit,bash`                                                                      |
| Worker.operations, Worker.validation                                | the read tools, `bash` and `codemode`                                                                       | `write,edit`                                                                           |
| Reviewer.code, Reviewer.testing                                     | the read tools, `bash` (`git diff`, the test runs) and `codemode`                                           | `write,edit`                                                                           |
| Worker.mechanical, .implementation, .integration, .debugging        | the read tools, `write`, `edit`, `bash` and `codemode`                                                      | none                                                                                   |
| Reviewer.visual                                                     | the read tools, the T3 Code tools, the computer-use tools and `codemode`                                    | `write,edit,bash`                                                                      |
| Worker.visual                                                       | the Worker tools, the T3 Code tools, the computer-use tools and `codemode`                                  | none                                                                                   |

- A specialist's allowlist is a plain list, so it replaces Pi's default selection, and `codemode` is a plain name in it because plain names and `+name` entries cannot be mixed. It names no `todo`, `ask_user_question`, process or subagent tool: the root alone has them. Under mode `only` the tools registered `model-only`, such as `ask_user_question`, stay directly callable by the model. `--exclude-tools` repeats the write tools the role lacks, so nothing that registers later can hand them back. In the agent file the same list is the package's `tools:` allowlist, where an extension tool is named through `ext:` and the write tools the role lacks are simply absent.
- The T3 Code tools are the patterns of `T3_VISUAL_TOOLS` on the server name `t3-code` (`mcp__t3*code__preview_*`, `t3_preview_*`, `html_render`, `html_preview` and `device_*`; the `*` covers T3's own `mcp__t3-code__` and the `mcp__t3_code__` that Pi makes of a server registered as `t3-code`), present only while `pi.features.mcp` is on; the computer-use tools are `computer_use_*`, present only while `pi.features.computerUse` is on. The root reaches the T3 tools through codemode and needs no entry; a specialist's allowlist names them so they stay active.
- The root excludes the computer-use tools and the web choice's tools (`web_search` and `web_fetch` for pi-web-kit, `moonshot_search` and `moonshot_fetch` for Kimi's provider tools, none when `pi.features.web` is `off`) while each is enabled, besides `write` and `edit`. `+codemode` keeps the default selection, which includes every enabled extension's tools, so without the exclusions the root would hold them. As on the Claude root, which has neither, research goes to the Librarian roles and visual inspection to the visual specialists. `todo`, `ask_user_question`, the process tools and the subagent tools stay on the root.
- `pi.features.mcp` off adds `--no-mcp` to the Pi process, which removes the MCP tools and `/mcp` for the root and every child, and no `mcp__` entry in a specialist's `tools:` line. The extension cannot pass the flag, so it applies only to a launch that does; the agent generator, not the extension, leaves the `mcp__` entries out of the agent files.
- Not tested against a running Pi, which the research did not run: that `pi.setActiveTools` at `session_start` gives the root the same tools as `--tools +codemode --exclude-tools` would, and that an `mcp__` allowlist entry reaches a deferred T3 tool ([t3-code.md](t3-code.md#browser)).

### MCP and the T3 Code tools

`html_render`, `html_preview`, the `preview_*` browser and the `device_*` tools are MCP tools of T3 Code, carried by Pi's built-in `builtin:mcp` extension. HolyAgent writes no bridge for them. They need this from the user:

- **Under T3 Code**, T3's own bridge extension supplies them to Pi ([t3-code.md](t3-code.md#how-t3-runs-pi)).
- **Anywhere else**, the user registers T3 Code's MCP server in Pi's MCP settings (`~/.pi/agent/mcp.json`, or `.pi/mcp.json` in a trusted project) under the name `t3-code`, because the tool names carry the server name (Pi names its tool `mcp__t3_code__html_render`), and keeps `pi.features.mcp` on. HolyAgent does not register the server and does not know its address or credential.
- **Without them**, `html_render` and `html_preview` are unavailable and the visual roles report the inspection as blocked, as the Claude text already says. The same holds with `pi.features.mcp` off.

Any other MCP server the user registers stays reachable from the root's codemode scripts and is not named in a specialist's allowlist.

### Settings that setup writes

**Status: built.** `toolSettings` is the data, and the tool settings step of `holyagent setup` writes it into the files the packages read, and `holyagent setup --undo` backs it out ([installation.md](installation.md#what-setup-and-doctor-do)); `holyagent doctor` reports the files that lack keys.

`toolSettings(config)` returns the settings files the decided tool behaviour needs, as data: each entry is a `file` under the user's home and the `content` to merge into it deeply, never to replace the file with. It is empty with `pi.enable` off, and a disabled feature adds nothing. Setup merges it, never replacing a file, and writes a key only where it is unset in the file and differs from the package's own default. At `--scope project` and `local` it writes the project's `.pi` folder instead of the home directory, skips a key your global file already sets (your global `off` wins), and refuses a symlinked `.pi` folder or file.

## What an extension is

An extension is a TypeScript module that exports a default factory receiving `ExtensionAPI`. The factory may be async, and Pi waits for it before continuing startup ([extensions.md L13-L36](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/docs/extensions.md#L13-L36), [extensions.md L54-L58](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/docs/extensions.md#L54-L58)). Extensions run inside the Pi process with its OS permissions and can inspect prompts, tool calls, files, credentials and session history ([extensions.md L3-L5](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/docs/extensions.md#L3-L5)).

## How extensions load

- **Transpilation:** Pi uses `jiti`, so local `.ts` files need no build step ([extensions.md L38](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/docs/extensions.md#L38), [loader.ts L570-L584](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/src/core/extensions/loader.ts#L570-L584)).
- **Locations:** `<agent-dir>/extensions/` (default agent dir `~/.pi/agent`) and project `.pi/extensions/`. Pi loads direct `.ts`/`.js` files and subdirectories containing `index.ts`/`index.js` ([extensions.md L44-L48](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/docs/extensions.md#L44-L48), [configuration.md L7-L37](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/docs/configuration.md#L7-L37)). Extra paths come from the `extensions` setting ([settings.md L148-L163](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/docs/settings.md#L148-L163)).
- **CLI:** `-e/--extension <path>` loads a file, directory or built-in (repeatable); `-ne/--no-extensions` disables discovered, configured and built-in extensions but explicit `-e` still loads ([cli.md L186-L196](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/docs/cli.md#L186-L196)).
- **Project trust:** project extensions in `.pi/extensions` load only after the folder is trusted. Only personal and explicit command-line extensions can handle the `project_trust` event ([security.md L35-L55](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/docs/security.md#L35-L55), [extensions.md L50](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/docs/extensions.md#L50)).
- **Built-in extensions:** `builtin:mcp`, `builtin:llama.cpp`, `builtin:codemode`, `builtin:tool-search` load by default and can be disabled with `-builtin:<name>` in the `extensions` setting ([settings.md L163](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/docs/settings.md#L163)).
- **Lifecycle rules:** do not start processes, sockets, watchers or timers in the factory, because some invocations load extensions without starting a session. Start them in `session_start` and release them in an idempotent `session_shutdown` ([extensions.md L58-L60](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/docs/extensions.md#L58-L60)). `/reload` replaces the whole extension runtime ([extensions.md L50](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/docs/extensions.md#L50)).
- **SDK embedding:** in the SDK, extensions are passed as inline factories through `DefaultResourceLoader`; SDK sessions do not include the built-in codemode/tool-search/MCP extensions unless the host adds `createCodemodeExtension()` etc. ([sdk.md L110-L118](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/docs/sdk.md#L110-L118)).

## Events and hooks

Per-prompt order: `input`, `before_agent_start`, `agent_start`, then per turn `turn_start`, model-request hooks, tool hooks, `turn_end`, then `agent_end`, `agent_before_settle`, `agent_settled`. A model request runs `context`, `context_with_system`, `before_provider_headers`, `before_provider_request`, `after_provider_response`, `provider_stream_event`. Each tool call runs `tool_execution_start`, `tool_call`, `tool_execution_update`, `tool_result`, `tool_execution_end` ([extensions.md L62-L125](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/docs/extensions.md#L62-L125)). Session events: `project_trust`, `session_start`, `session_before_switch`, `session_before_fork`, `session_shutdown`, `resources_discover` ([extensions.md L127-L145](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/docs/extensions.md#L127-L145)). `agent_end` is not a final-idle signal; `agent_settled` is ([extensions.md L145](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/docs/extensions.md#L145)).

How handler results compose ([extensions.md L203-L215](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/docs/extensions.md#L203-L215)):

| Pattern                       | Events                                                                                             |
| ----------------------------- | -------------------------------------------------------------------------------------------------- |
| Notification (return ignored) | most lifecycle events                                                                              |
| In-place mutation             | `tool_call.input`, `before_provider_headers.headers`, `before_agent_start.systemPromptOptions`     |
| Chained transformation        | `input`, `context`, `context_with_system`, `message_end`, `tool_result`, `before_provider_request` |
| Gate                          | handled `input`, blocked `tool_call`, cancelled session operation, handled `user_bash`             |
| Actionable boundary           | `turn_end`, `agent_before_settle` (can add entries and return `continue: true`)                    |

Gate handlers "should fail closed when their safety decision cannot be made" ([extensions.md L214](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/docs/extensions.md#L214)). Handlers run in extension load order ([extensions.md L197](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/docs/extensions.md#L197)). Tool calls from one assistant message can run in parallel, so handlers must not assume sibling calls exist ([extensions.md L236-L238](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/docs/extensions.md#L236-L238)).

`tool_call` (the interception point used by [approval.md](approval.md)): the event carries `toolName`, `toolCallId`, `input` and optional `parentToolCallId`; the handler may mutate `event.input` or return `{ block, reason, terminate }` ([types.ts L1193-L1265](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/src/core/extensions/types.ts#L1193-L1265), [types.ts L1454-L1463](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/src/core/extensions/types.ts#L1454-L1463)). The runner stops at the first handler that blocks ([runner.ts L1249-L1268](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/src/core/extensions/runner.ts#L1249-L1268)).

Other events useful to an orchestrator: `model_select`, `thinking_level_select`, `message_end`, `tool_result` (redact or replace output), `before_provider_request` (change the serialized payload), `cache_warming_decision` ([types.ts L1597-L1664](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/src/core/extensions/types.ts#L1597-L1664), [extensions.md L234](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/docs/extensions.md#L234)).

## Custom tools

- A tool has a `name`, model-facing `description`, a TypeBox `parameters` schema and `execute()`. The result needs `content` and a `details` field. Throw to signal failure; returning an object does not mark an error ([extensions.md L245-L253](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/docs/extensions.md#L245-L253)).
- `terminate: true` ends the agent loop after the tool batch without an extra model turn, only if every tool in the batch agrees ([extensions.md L253](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/docs/extensions.md#L253), [structured-output.ts L1-L45](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/examples/extensions/structured-output.ts#L1-L45)).
- `outputSchema` plus `structuredContent` return machine-readable results to programmatic callers such as codemode scripts ([extensions.md L259](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/docs/extensions.md#L259)).
- Nested model calls inside a tool should report `usage` so session totals stay right; file-mutating tools should use `withFileMutationQueue()` ([extensions.md L247-L257](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/docs/extensions.md#L247-L257)).
- `ctx.executeTool(name, args)` lets a tool call other tools. Nested calls pass through validation and the `tool_call`/`tool_result` handlers and carry `parentToolCallId` ([extensions.md L261](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/docs/extensions.md#L261)).
- **Exposure** (`direct`, `model-only`, `codemode`, `deferred`, `hidden`) decides whether the model sees a tool, scripts can call it, or both. Tools cannot be unregistered, only re-registered as `hidden` ([extensions.md L265-L277](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/docs/extensions.md#L265-L277)).
- **Annotations** (`readOnlyHint`, `destructiveHint`, `idempotentHint`, `openWorldHint`) follow MCP semantics; MCP tools carry their server's hints; hints are not verified ([extensions.md L279-L291](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/docs/extensions.md#L279-L291)).
- Active tool sets can change at runtime with `pi.setActiveTools()`. Pi records the change in the transcript, and providers that cannot represent the transition get a full checkpoint, which can invalidate the cached prefix ([extensions.md L297-L301](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/docs/extensions.md#L297-L301)).

## Pi packages

- A package is a directory or npm package with conventional `extensions/`, `skills/`, `prompts/`, `themes/` directories or a `pi` key in `package.json`; the `pi-package` keyword makes it discoverable in the gallery ([packages.md L42-L74](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/docs/packages.md#L42-L74)).
- Sources: `npm:`, `git:`, an `https://` git URL, or a local path. Versioned npm specs and git tags/commits are pinned ([packages.md L29-L40](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/docs/packages.md#L29-L40)).
- Commands: `pi install|remove|uninstall|update|list|config`; personal installs are recorded in `~/.pi/agent/settings.json`, `-l/--local` writes `.pi/settings.json` (read only after trust); `-e <source>` tries a package for one run ([packages.md L7-L27](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/docs/packages.md#L7-L27), [cli.md L250-L291](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/docs/cli.md#L250-L291)).
- Host-provided modules (`@earendil-works/pi-ai`, `pi-agent-core`, `pi-coding-agent`, `pi-tui`, `typebox`) must be `peerDependencies` with `"*"` and not bundled ([packages.md L76-L92](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/docs/packages.md#L76-L92)).
- Packages can execute extension code and include skills that instruct the model to run programs; the docs tell users to review third-party source first ([packages.md L21](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/docs/packages.md#L21)). Package resources can be filtered per type with `!pattern`, `+path`, `-path` ([packages.md L94-L121](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/docs/packages.md#L94-L121)).

## Inference for HolyAgent

- Inference: delivering HolyAgent as one Pi package makes the version pin explicit, because Pi pins git tags and commits ([packages.md L29-L40](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/docs/packages.md#L29-L40)). The plan uses a git tag source, not `npm:` ([installation.md](installation.md#how-holyagent-installs)).
- Inference: project-level `.pi/extensions` need trust, and trust prompts cannot show in print, JSON or RPC mode (see [configuration.md](configuration.md#project-trust)). The plan documents the user-level install first, so its loading does not depend on a prompt, and children inherit the parent's project trust: `--approve` only when the parent trusted the project ([installation.md](installation.md#global-and-project-local-installs)). Sourced: only personal and command-line extensions can handle `project_trust` ([security.md L63](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/docs/security.md#L63)).
