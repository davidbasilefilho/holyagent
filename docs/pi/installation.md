# Installing Pi and HolyAgent's Pi package (and what is known about Bun)

**Status: planned for 0.3.0. The first four sections are the plan; the sections after them are research on Pi's own install and are not shipped behaviour.**

Pi 1.4.0, commit `4a080252f06caf63a525d7873c5d94d3c23887e0` (the plan pins 1.5.0; see [README.md](README.md#version-risk)). "Inference:" marks a conclusion drawn here, not a stated fact. Nothing here was installed or executed; the installer script was only read.

## How HolyAgent installs

The plan has the user do two things, once each, after the prerequisites:

1. Install Pi: Node.js 22.19 or newer, then the official installer or `npm install -g --ignore-scripts @earendil-works/pi-coding-agent@1.5.0` (see [Official instructions](#official-instructions)).
2. Install the HolyAgent package from its release tag, where `<version>` is a HolyAgent release:

   ```sh
   pi install git:github.com/davidbasilefilho/holyagent@holyagent-<version>
   ```

After that, plain `pi` starts the HolyAgent root, the way the Claude plugin does. Nothing else is needed to start.

- **The ref follows `@`, not `#`.** Pi splits a git source on the first `@` in the path (`splitRef` in `dist/utils/git.js` of Pi 1.5.0, L2-L33) and documents `pi install git:github.com/example/pi-tools@v1` (`packages.md` L13); a `#` stays in the repository string, so `…holyagent#holyagent-<version>` would not name the tag. Every Pi install command in these docs uses `@holyagent-<version>`.
- **Distribution is the git tag.** The repository already tags each stable release `holyagent-<version>` ([development.md](../development.md)), and Pi pins git tags and commits ([extensions.md](extensions.md#pi-packages)). There is no npm publishing for the Pi package.
- **The package is built JavaScript.** The extension is bundled with `bun build` into the generated package, which the sync check keeps in step with its sources ([extensions.md](extensions.md#the-holyagent-package)). The built package is `packages/integrations/pi/dist/`, and the root `package.json` has a `pi` key that points at its `extensions/` and `skills/` folders. Pi installs a git source by cloning it at the ref, running `npm install --omit=dev` in the clone when it has a `package.json`, and reading that file's `pi` key, whose paths are relative to the package root (Pi's `packages.md`, "Create a package"; `getGitDependencyInstallArgs` and `collectPackageResources` in `dist/core/package-manager.js`), so the key at the root finds the build in the tag. `packages/integrations/pi/tests/pi.test.ts` checks that the root key and the built package's own key name the same folders. That dependency install runs at the repository root, so the root manifest must install with the dev dependencies omitted: no workspace package declares a `workspace:*` range (the integrations import the runtime by relative path, and `npm` stops on `workspace:`), and the root `prepare` script is `bun scripts/prepare-dev.ts`, which installs the git hooks only when the dev toolchain (`mise`) is installed and otherwise prints one line and exits 0. The simulation on a `git archive` of the tree, with the dev dependencies omitted, passes with `npm install --omit=dev --legacy-peer-deps` and with `bun install --production`.
- **Installing the package installs only the dependencies the default `config.json` enables** ([configuration.md](configuration.md#holyagent-configjson)).
- **T3 Code is the primary interface.** After the install, the user enables Pi in T3 Code's Settings, and T3 runs the same install through `pi --mode rpc` ([t3-code.md](t3-code.md)); the plain terminal stays supported.

## Global and project-local installs

**Status: planned for 0.3.0.** The maintainer's words: "for 0.3.0, we will support both local and global installations for holyagent in claude and pi". Both Pi installs work, and the docs present the global one first (the root's default); the Claude Code scopes are in [usage.md](../usage.md#install-scopes). Facts below are from Pi's `latest` docs ([packages](https://pi.dev/docs/latest/packages), [settings](https://pi.dev/docs/latest/settings), [security](https://pi.dev/docs/latest/security)), which the research read in place of 1.5.0's own copy.

| Install                   | Command                                                                       | Declared in                 | Packages land in   |
| ------------------------- | ----------------------------------------------------------------------------- | --------------------------- | ------------------ |
| Global (documented first) | `pi install git:github.com/davidbasilefilho/holyagent@holyagent-<version>`    | `~/.pi/agent/settings.json` | `~/.pi/agent/npm/` |
| Project-local             | `pi install -l git:github.com/davidbasilefilho/holyagent@holyagent-<version>` | `.pi/settings.json`         | `.pi/npm/`         |

- **Precedence.** Project settings override global ones, nested objects merge, and resource lists are combined, so packages declared in both files load ([configuration.md](configuration.md#precedence)).
- **The trust step of a project-local install.** Pi gates project packages, `.pi/settings.json` and `.pi/extensions` on project trust. Interactive Pi asks once and saves the answer in `~/.pi/agent/trust.json`. Print, JSON and RPC modes cannot ask, so they skip the project's `.pi` resources unless `--approve` or `defaultProjectTrust: "always"` is set; `defaultProjectTrust` is settable only in the global settings file. Declining skips the project packages, while context files such as `AGENTS.md` and `CLAUDE.md` load regardless ([configuration.md](configuration.md#project-trust)). So a project-local install loads in a terminal session after the user trusts the folder once. Under T3 Code, which runs Pi in RPC mode, it loads only when a saved decision, `defaultProjectTrust` or an `--approve` launch arg applies. Inference: T3 allows `--approve`, since it rejects only launch args that change the mode or pick a session; this is to be verified ([t3-code.md](t3-code.md#how-t3-runs-pi)).
- **Specialists inherit the parent's trust.** The root's children are started with `--approve` only when the parent session trusted the project (the root's default). A global install needs no trust step for its own loading, because only project resources are trust-gated ([approval.md](approval.md#decision-for-030)).
- **A package declared at both scopes.** The research found no documentation of what Pi does when the same package is declared globally and locally. The behavior is verified during implementation, and this page records the result.
- **Resolution (inference).** Both installs install the same package the same way, so resolving its bundled CLI and extension dependencies should not differ between them; the packages doc says a local-path package is not installed for the user.

## The pin

- **Pi is pinned at 1.5.0** (released 2026-11-02), and every reused extension is pinned with it: `pi-provider-kimi-code`, `@tintinweb/pi-subagents`, `pi-web-kit`, `@aliou/pi-processes`, `@juicesharp/rpiv-todo`, `@juicesharp/rpiv-ask-user-question`, `@amaster.ai/pi-computer-use` (computer use through the Cua Driver it bundles, which moves with this pin, [t3-code.md](t3-code.md#computer-use-through-cua-driver)) and `billion-context`. The versions are chosen when the package is built.
- **A pin moves only through `mise run deps:update`**, the repository's dependency updater ([development.md](../development.md)). For Pi it re-records the CI fixtures, so a Pi change that breaks the integration's contract shows up as a failing replay, not in a user's session ([orchestration.md](orchestration.md#ci-and-windows)). `mise run deps:check` fails when a pin is behind.
- **Why pin hard:** Pi released about weekly, and Billion Context releases about daily ([README.md](README.md#version-risk), [caching-and-subagents.md](caching-and-subagents.md#context-compression-with-billion-context)).

## What setup and doctor do

- **`holyagent setup`** for Pi sets Pi's `npmCommand` setting to `bun`, so Pi installs packages with Bun. The maintainer's words: "in the holyagent setup for pi it should set bun as the npmcommand".
- **`holyagent setup`** also, for T3 Code: walks through the macOS Accessibility and Screen Recording permissions for the Cua Driver that `@amaster.ai/pi-computer-use` bundles (there is no separate driver install), and writes T3's beneficial settings once their format is verified, or prints the T3 Settings steps ([t3-code.md](t3-code.md#computer-use-through-cua-driver), [t3-code.md](t3-code.md#t3-settings-written-by-setup)). Its check states that HolyAgent threads in T3 need Full access ([t3-code.md](t3-code.md#full-access-is-required)).
- **`holyagent doctor`** checks that Pi, Node.js 22.19 or newer and the HolyAgent package are present. It only checks and installs nothing. Inference: the package counts as present when it is installed at either scope ([Global and project-local installs](#global-and-project-local-installs)).
- **The Windows installer's Node minimum rises from 22.13 to 22.19** ([components.md](../components.md#mise-node-bun-gh)), because Pi needs Node 22.19. The installers do not install Pi.

## Bun: only npm (plus installer and Nix) is documented

The official install docs list the installer, npm and Nix. **No page in the 1.4.0 docs gives a Bun install command**: searching `docs/*.md` and the README for "bun" finds only the mentions below, none of which is an install instruction.

What the docs say about Bun:

- The SDK "embeds Pi in a Node.js or Bun process"; RPC docs recommend the SDK for "in-process Node.js or Bun integration" ([sdk.md L3](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/docs/sdk.md#L3), [rpc.md L5-L9](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/docs/rpc.md#L5-L9), [cli-integration.md L7](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/docs/cli-integration.md#L7)).
- For Pi packages, peer dependencies are not auto-installed for packages installed "with npm, pnpm, or Bun" ([packages.md L88](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/docs/packages.md#L88)).
- Codemode has a documented Bun caveat: on Bun, stopping a script or hitting its deadline ends the call promptly, but a built-in that does not poll QuickJS's interrupt handler can keep computing in its worker ([codemode.md L227](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/docs/codemode.md#L227)).

What the source supports:

- **Bun as an install method for self-update.** `detectInstallMethod()` returns `bun-binary` for a Bun-compiled executable and `bun` when `process.versions.bun` is set or the path contains `/install/global/node_modules/`; the self-update command for `bun` is `bun install -g --ignore-scripts --minimum-release-age=0 <package>` ([config.ts L18-L25, L79-L95, L159-L171](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/src/config.ts#L79-L95)). It locates Bun's global `node_modules` via `bun pm bin -g` and `~/.bun/install/global/node_modules` ([config.ts L246-L252](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/src/config.ts#L246-L252)). Older changelog entries show the Bun path being maintained: "Show `bun install` instead of `npm install` in update notification when running under Bun" (0.46.0, [CHANGELOG.md L4382](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/CHANGELOG.md#L4382)), "Fixed Bun-based package manager startup by locating global `node_modules` relative to Bun's install layout" (0.70.6, [CHANGELOG.md L2382](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/CHANGELOG.md#L2382)), and "Fixed Bun package manager `node_modules` discovery when `npmCommand` is configured to use Bun" (0.71.0, [CHANGELOG.md L2342](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/CHANGELOG.md#L2342)). These entries predate the 1.x line and some link to the old `badlogic/pi-mono` repository.
- **Bun-compiled standalone binaries.** `build:binary` runs `bun build --compile` ([package.json L35](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/package.json#L35)), and the changelog mentions "Bun release archives" (0.84.3, [CHANGELOG.md L823](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/CHANGELOG.md#L823)), "Bun standalone binaries" (0.84.1, [CHANGELOG.md L956](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/CHANGELOG.md#L956)) and extension loading in the compiled Bun binary (0.45.4, [CHANGELOG.md L4447](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/CHANGELOG.md#L4447)). GitHub release assets could not be listed (the API was not reachable), so it is unconfirmed which binaries are published for 1.4.0, and the install docs do not point to them.
- **The CLI entry point targets Node.** `bin.pi` is `dist/bundle/cli.js`, whose shebang is `#!/usr/bin/env node` ([bundle/cli.js in the 1.4.0 tarball](https://unpkg.com/@earendil-works/pi-coding-agent@1.4.0/dist/bundle/cli.js), [package.json L9-L11](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/package.json#L9-L11)).

Inference: `bun install -g @earendil-works/pi-coding-agent` is probably installable, because Pi's own updater uses that exact form for Bun-managed installs. A later check (2026-11-07) found that pi.dev lists `bun add -g --ignore-scripts @earendil-works/pi-coding-agent` as an install command ([pi.dev](https://pi.dev)), but the runtime is still Node: the `cli.js` shebang is `#!/usr/bin/env node`, and the maintainer said in [issue #6237](https://github.com/earendil-works/pi/issues/6237) (6 Jul 2026) "we can't have a shebang that works for all runtimes". No official doc calls Bun a supported way to run Pi. Pi's `npmCommand` setting accepts `["bun"]` for package installs ([issue #4160](https://github.com/earendil-works/pi/issues/4160)).

Decision for 0.3.0: Pi runs on Node, and Bun is used by Pi only as its `npmCommand` for package installs ([What setup and doctor do](#what-setup-and-doctor-do)). Bun is documented as a prerequisite of the HolyAgent CLI, not as a way to install Pi. The documented Pi install is Node.js 22.19 or newer plus the official installer or `npm install -g --ignore-scripts @earendil-works/pi-coding-agent@1.5.0`.
