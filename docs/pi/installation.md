# Installing Pi and HolyAgent's Pi package (and what is known about Bun)

**Status: the install path below ships in 0.3.0. The sections from [Official instructions](#official-instructions) on are research on Pi's own install.** What setup and doctor do, the Pi tool settings included, is in [its section](#what-setup-and-doctor-do), with the parts not built yet marked.

Pi 1.4.0, commit `4a080252f06caf63a525d7873c5d94d3c23887e0` (HolyAgent pins 1.5.0; see [README.md](README.md#version-risk)). "Inference:" marks a conclusion drawn here, not a stated fact. The installer script was only read; nothing in the research was installed or executed.

## How HolyAgent installs

You install three things, once each. Pi needs Node.js 22.19 or newer; the HolyAgent CLI that the package runs needs Bun on your `PATH`, so Bun is a prerequisite of HolyAgent and not a way to install Pi ([Bun](#bun-only-npm-plus-installer-and-nix-is-documented)). `git` and an authenticated `gh` are needed as for the Claude plugin ([requirements.md](../requirements.md)).

1. Install Pi 1.5.0, the version HolyAgent pins (the `@earendil-works/pi-coding-agent` version in `bun.lock`), with Node.js 22.19 or newer in place: the official installer ([Official instructions](#official-instructions)) or

   ```sh
   npm install -g --ignore-scripts @earendil-works/pi-coding-agent@1.5.0
   ```

2. Install the HolyAgent package at an explicit version. The release tag `holyagent-<version>` is the pin, where `<version>` is a HolyAgent release (`0.3.0`):

   ```sh
   pi install git:github.com/davidbasilefilho/holyagent@holyagent-<version>
   ```

   Pi also takes a local path, such as `pi install /path/to/holyagent/packages/integrations/pi/dist` for a folder you built yourself, and an `npm:<name>@<version>` source, which pins the same way. HolyAgent publishes no npm package, so the git tag is the documented route. Inference: Pi uses a local folder as it is (the packages doc says a local-path package is not installed), so installing a local build adds no other package either; `holyagent setup` installs the config's packages whichever way you installed the HolyAgent package.

3. Run `holyagent setup`, which installs the Pi packages your `config.json` enables and writes their tool settings (see [What setup and doctor do](#what-setup-and-doctor-do)). Re-run it after you turn a feature on or off in the config, for example when you set `pi.features.web` to `"pi-web-kit"`.

4. Sign in to the model provider and start: plain `pi` starts the HolyAgent root, the way the Claude plugin does. Nothing else is needed to start. The provider login is in [providers.md](providers.md#kimi-for-coding-global).

- **The ref follows `@`, not `#`.** Pi splits a git source on the first `@` in the path (`splitRef` in `dist/utils/git.js` of Pi 1.5.0, L2-L33) and documents `pi install git:github.com/example/pi-tools@v1` (`packages.md` L13); a `#` stays in the repository string, so `...holyagent#holyagent-<version>` would not name the tag. Every Pi install command in these docs uses `@holyagent-<version>`.
- **Distribution is the git tag.** The repository tags each stable release `holyagent-<version>` ([development.md](../development.md)), and Pi pins git tags and commits ([extensions.md](extensions.md#pi-packages)). There is no npm publishing for the Pi package.
- **The package is built JavaScript.** The extension is bundled with `bun build` into the generated package, which the sync check keeps in step with its sources ([extensions.md](extensions.md#the-holyagent-package), [development.md](../development.md#the-generated-pi-package)). The built package is `packages/integrations/pi/dist/`, and the root `package.json` has a `pi` key that points at its `extensions/`, `prompts/`, `skills/` and `agents/` folders. Pi installs a git source by cloning it at the ref, running `npm install --omit=dev` in the clone when it has a `package.json`, and reading that file's `pi` key, whose paths are relative to the package root (Pi's `packages.md`, "Create a package"; `getGitDependencyInstallArgs` and `collectPackageResources` in `dist/core/package-manager.js`), so the key at the root finds the build in the tag. `packages/integrations/pi/tests/pi.test.ts` checks that the root key and the built package's own key name the same folders. That dependency install runs at the repository root, so the root manifest must install with the dev dependencies omitted: no workspace package declares a `workspace:*` range (the integrations import the runtime by relative path, and `npm` stops on `workspace:`), and the root `prepare` script is `bun scripts/prepare-dev.ts`, which installs the git hooks only when the dev toolchain (`mise`) is installed and otherwise prints one line and exits 0. The simulation on a `git archive` of the tree, with the dev dependencies omitted, passes with `npm install --omit=dev --legacy-peer-deps` and with `bun install --production`.
- **The package lists no dependencies; `holyagent setup` installs the feature packages.** Pi loads a package only through its own entry in the `packages` list of Pi's settings, and only `pi install` and `pi remove` write that list (Pi 1.5.0, `package-manager.js`; `packages.md` L102-L143). A `dependencies` entry of the HolyAgent manifest would be installed whatever the config says and loaded by nothing, so the manifest has none. Setup installs each package the config enables ([configuration.md](configuration.md#holyagent-configjson)) at the exact pin of [The pin](#the-pin).
- **T3 Code is the primary interface, and its integration is planned, not shipped.** The plan is that you enable Pi in T3 Code's Settings and T3 runs the same install through `pi --mode rpc` ([t3-code.md](t3-code.md)). The plain terminal works today.

## Global and project-local installs

**Status: both installs are Pi features that the package uses unchanged; the trust-related and same-package behaviors below were read in the docs, not run.** The maintainer's words: "for 0.3.0, we will support both local and global installations for holyagent in claude and pi". The docs present the global install first (the root's default); the Claude Code scopes are in [usage.md](../usage.md#install-scopes). Facts below are from Pi's `latest` docs ([packages](https://pi.dev/docs/latest/packages), [settings](https://pi.dev/docs/latest/settings), [security](https://pi.dev/docs/latest/security)), which the research read in place of 1.5.0's own copy.

| Install                   | Command                                                                       | Declared in                 | Packages land in   |
| ------------------------- | ----------------------------------------------------------------------------- | --------------------------- | ------------------ |
| Global (documented first) | `pi install git:github.com/davidbasilefilho/holyagent@holyagent-<version>`    | `~/.pi/agent/settings.json` | `~/.pi/agent/npm/` |
| Project-local             | `pi install -l git:github.com/davidbasilefilho/holyagent@holyagent-<version>` | `.pi/settings.json`         | `.pi/npm/`         |

- **Precedence.** Project settings override global ones, nested objects merge, and resource lists are combined, so packages declared in both files load ([configuration.md](configuration.md#precedence)).
- **The trust step of a project-local install.** Pi gates project packages, `.pi/settings.json` and `.pi/extensions` on project trust. Interactive Pi asks once and saves the answer in `~/.pi/agent/trust.json`. Print, JSON and RPC modes cannot ask, so they skip the project's `.pi` resources unless `--approve` or `defaultProjectTrust: "always"` is set; `defaultProjectTrust` is settable only in the global settings file. Declining skips the project packages, while context files such as `AGENTS.md` and `CLAUDE.md` load regardless ([configuration.md](configuration.md#project-trust)). So a project-local install loads in a terminal session after the user trusts the folder once. Under T3 Code, which runs Pi in RPC mode, it loads only when a saved decision, `defaultProjectTrust` or an `--approve` launch arg applies. Inference: T3 allows `--approve`, since it rejects only launch args that change the mode or pick a session; this is to be verified ([t3-code.md](t3-code.md#how-t3-runs-pi)).
- **Specialists inherit the parent's trust.** The root's children are started with `--approve` only when the parent session trusted the project (the root's default). A global install needs no trust step for its own loading, because only project resources are trust-gated ([approval.md](approval.md#decision-for-030)).
- **A package declared at both scopes.** The Pi docs do not say what Pi does when the same package is declared globally and locally, and this has not been run, so declare HolyAgent at one scope.
- **Resolution (inference).** Both installs install the same package the same way, so resolving its bundled CLI and extension dependencies should not differ between them; the packages doc says a local-path package is not installed for the user.

## The pin

- **The Pi host used for development and tests** is the `@earendil-works/pi-coding-agent` devDependency of `packages/integrations/pi`; it moves with `bun.lock` through `mise run deps:update`, and a user's own Pi install is theirs (the documented install command names Pi 1.5.0, the version `bun.lock` resolves). Every reused extension is an exact pin, one version with no range: `pi-provider-kimi-code`, `@tintinweb/pi-subagents`, `pi-web-kit`, `@aliou/pi-processes`, `@juicesharp/rpiv-todo`, `@juicesharp/rpiv-ask-user-question`, `@amaster.ai/pi-computer-use` (computer use through the Cua Driver it bundles, which moves with this pin, [t3-code.md](t3-code.md#computer-use-through-cua-driver)) and `billion-context`. The versions are in `packages/runtime/src/config/pi-packages.json`, the one source: `piPackages(config)` returns each enabled package as `npm:<name>@<version>` from it, and `providerSource(config)` reads the provider extension's version from it too.
- **A pin moves only through `mise run deps:update`**, the repository's dependency updater ([development.md](../development.md)). It sets each package in `pi-packages.json` to its newest stable, non-deprecated npm release (a prerelease is never chosen, and a pin is never moved down); the updater does not re-record the recorded CI fixtures, so a Pi change that breaks the integration's contract shows up as a failing replay, not in a user's session, until they are re-recorded by hand ([orchestration.md](orchestration.md#ci-and-windows)). `mise run deps:check` fails when a pin is behind. Do not edit the file by hand.
- **Why pin hard:** Pi released about weekly, and Billion Context releases about daily ([README.md](README.md#version-risk), [caching-and-subagents.md](caching-and-subagents.md#context-compression-with-billion-context)).

## What setup and doctor do

- **Pi counts as in use** when `HOLYAGENT_HOST` is `pi` (the Pi extension sets it) or `pi` is on your `PATH`. Setup and doctor do their Pi work only then, so a machine that uses only Claude Code gets no Pi failure.
- **`holyagent setup`** makes Pi's packages match the config when Pi is in use (never in a claude.ai cloud session, and not with `--undo`). For each package the config enables ([configuration.md](configuration.md#holyagent-configjson)) that the settings of the chosen scope do not list at its pin, it runs `pi install npm:<name>@<pin>`; for each package HolyAgent manages that the settings of the chosen scope list but the config no longer selects, it runs `pi remove npm:<name>`. The managed packages are the feature packages, `pi-web-kit` once the web choice no longer asks for it, and the provider profile packages of a provider the config no longer selects; the HolyAgent package and any package HolyAgent does not ship are never removed. What counts as present depends on the scope, and doctor counts the same way: `--scope user` counts Pi's global settings only, so a repository's `.pi/settings.json` cannot stop a global install; `project` and `local` count the project's `.pi/settings.json` and also the global file, since Pi loads global packages in a project. Removal touches the chosen scope's file only: `--scope user` removes from the global settings, `project` and `local` from the project's. Setup writes the `packages` list through `pi install` and `pi remove` only; the tool settings are a separate step (next bullet). Every command is printed as a report line, and `--dry-run` prints them without running. Packages already listed at their pin are left alone, as is anything setup does not manage. With `pi.enable` off it installs and removes nothing and says so. `--undo` leaves the Pi packages installed. Without `--scope` the Pi step runs at the same scope as the Claude Code step: `user`, or `local` when your own uncommitted `.claude/settings.local.json` enables the plugin; a committed `.claude/settings.json` cannot select `project` or `local`, because a cloned repository must not choose which `.npmrc` a Pi install reads. Scope `user` (the default) works on the global settings, `~/.pi/agent/settings.json` or the folder `PI_CODING_AGENT_DIR` names, runs Pi from your home directory, and decides from your own `~/.holyagent/config.json` only: the `.holyagent/config.json` of the directory you run it in is not read, so a cloned repository cannot turn a feature off and have a package removed from your global settings. `--scope project` and `--scope local` both work on the project's `.pi/settings.json` with `-l`, read the project's config over yours, and run in the current directory, so they install in the project directory and Pi reads its npm settings (`.npmrc`) and `.pi/settings.json` there: run them only in a repository you trust. Setup does not install Pi itself or the HolyAgent package, and when changes are due but `pi` is not on `PATH` it reports a failure that names it.
- **`holyagent setup`** then writes the Pi tool settings, under the same gating as the package step: Pi in use, not a claude.ai cloud session, `pi.enable` on, and the config of the chosen scope read as above. It writes what `toolSettings(config)` returns ([extensions.md](extensions.md#settings-that-setup-writes)) by merging into the files the packages read, one report line per file (`+` added, `=` already set, `~` a value of yours kept, `-` a file with no place at the scope, `!` failed), and never replaces a file. A key is written only where it is **unset** in the file and its value **differs from the package's own default** (for example `codemode.mode` is not written when the config asks for `on`, which is Pi's default); a value you set is never overwritten, so your `off` wins for the risky settings (the computer-use confirmations) as for the rest. At `project` and `local` scope a key your global file already sets, to any value, is not written either (the line says `left out, set in your global file`), so a repository's file cannot override your global choice; a global file that is not a JSON object stops the write with a `!` line, since what it sets is unknown. A `.pi` folder, a folder below it or a settings file that is a symlink is a `!` line at these scopes and nothing is written or undone through it, so a repository cannot redirect the write to a file elsewhere; scope `user` follows its links. Where the files are: scope `user` writes `settings.json` and `subagents.json` in Pi's agent folder (`PI_CODING_AGENT_DIR`, else `~/.pi/agent`), the provider's `~/.pi/providers/kimi-coding/config.json` and Billion Context's file (`BILI_CONFIG_FILE`, else `XDG_CONFIG_HOME`, else `~/.config/billion-context/billion-context.json`); `project` and `local` write `settings.json`, `subagents.json` and `providers/kimi-coding/config.json` in the project's `.pi` folder, and skip Billion Context's setting with a `-` line because that package has no project file. A file that is not a JSON object is a `!` line (the exit code is 1) and stays untouched, and the other files are still written. Each write goes to a temporary file in the same folder that is renamed over the target. `--dry-run` prints the lines ("would add ...") and writes nothing. The keys it adds are recorded in `holyagent/setup-records.json` under your Claude Code folder, as for the Claude settings; if the record cannot be written after a file was, the `!` line names that file and says `--undo` will not remove its keys.
- **`holyagent setup --undo`** also backs the tool settings out, from the files the record names at the chosen scope: a recorded key is removed only while its value still equals what setup wrote, so a value you changed since stays (reported as kept), and a key setup did not add, such as one already in the file before setup, is never removed. An object left empty is dropped, and a file setup created is left as `{}`. It follows the record, not the config or Pi's presence, so it also backs out a feature you turned off since; files without a record print no line, and `--dry-run` shows the removals and keeps the record. At `project` and `local` scope it refuses a symlinked `.pi` path with a `!` line and edits nothing through it. It finds the files of the chosen scope from the current environment, so after changing `PI_CODING_AGENT_DIR`, `BILI_CONFIG_FILE` or `XDG_CONFIG_HOME` since setup, run `--undo` with the old values. The Pi packages stay installed.
- **`holyagent doctor`** prints one `~ pi: not in use` line and nothing fails when Pi is not in use, and runs no Pi check in a claude.ai cloud session. When Pi is in use but `pi.enable` is off in the config of the chosen scope, it prints no Pi line at all, and runs no process. When it is in use and `pi.enable` is on, it checks that `pi` is on your `PATH` at the pinned version or newer, that Node.js is 22.19 or newer, that the HolyAgent package is listed in Pi's settings, and that every package the config enables is listed at its pin (the config of the chosen `--scope`, read as setup reads it: yours alone for `user`, the project's over yours for `project` and `local`), in the global `~/.pi/agent/settings.json` (or the folder `PI_CODING_AGENT_DIR` names) for `user`, which does not read the project's `.pi/settings.json`, and in either that file or the project's `.pi/settings.json` for `project` and `local`. Each package that is missing is a failing `pi feature <name>` line with its `pi install npm:<name>@<pin>` command as the fix (`holyagent setup` runs them all). It also prints a `~ tool settings <file> lacks <keys>; run \`holyagent setup\``line (with`--scope`named for`project`and`local`) for each tool settings file of the scope that lacks keys setup would write, only in these same conditions; a key you set to another value, or that your global file sets at `project`and`local`scope, is not missing, and a file that is not a JSON object or a symlinked`.pi`path is named in a`~`line. These lines are hints and do not fail doctor, and`--fix`does not write them. Doctor only checks: it installs nothing, and`--fix` never installs Pi, Node.js or a Pi package.
- **`holyagent setup`** for Pi does not set Pi's `npmCommand` yet. Planned: it sets Pi's `npmCommand` setting to `bun`, so Pi installs packages with Bun. The maintainer's words: "in the holyagent setup for pi it should set bun as the npmcommand". Until then Pi installs packages with npm, which Node.js brings.
- **`holyagent setup`** also, for T3 Code (planned, not built): walks through the macOS Accessibility and Screen Recording permissions for the Cua Driver that `@amaster.ai/pi-computer-use` bundles (there is no separate driver install), and writes T3's beneficial settings once their format is verified, or prints the T3 Settings steps ([t3-code.md](t3-code.md#computer-use-through-cua-driver), [t3-code.md](t3-code.md#t3-settings-written-by-setup)). Its check states that HolyAgent threads in T3 need Full access ([t3-code.md](t3-code.md#full-access-is-required)).
- **The installers do not install Pi.** The Windows installer's Node.js minimum is 22.19, up from 22.13, because Pi needs it. The WSL installer installs the current Node.js LTS and keeps its own check at 22.13, the floor for ctx7, so `install/wsl-install.sh` still accepts Node.js 22.13 while Pi needs 22.19; if you use an older Node.js, doctor reports it ([components.md](../components.md#mise-node-bun-gh)).

## Bun: only npm (plus installer and Nix) is documented

The official install docs list the installer, npm and Nix. **No page in the 1.4.0 docs gives a Bun install command**: searching `docs/*.md` and the README for "bun" finds only the mentions below, none of which is an install instruction.

What the docs say about Bun:

- The SDK "embeds Pi in a Node.js or Bun process"; RPC docs recommend the SDK for "in-process Node.js or Bun integration" ([sdk.md L3](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/docs/sdk.md#L3), [rpc.md L5-L9](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/docs/rpc.md#L5-L9), [cli-integration.md L7](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/docs/cli-integration.md#L7)).
- For Pi packages, peer dependencies are not auto-installed for packages installed "with npm, pnpm, or Bun" ([packages.md L88](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/docs/packages.md#L88)).
- Codemode has a documented Bun caveat: on Bun, stopping a script or hitting its deadline ends the call promptly, but a built-in that does not poll QuickJS's interrupt handler can keep computing in its worker ([codemode.md L227](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/docs/codemode.md#L227)).

What the source supports:

- **Bun as an install method for self-update.** `detectInstallMethod()` returns `bun-binary` for a Bun-compiled executable and `bun` when `process.versions.bun` is set or the path contains `/install/global/node_modules/`; the self-update command for `bun` is `bun install -g --ignore-scripts --minimum-release-age=0 <package>` ([config.ts L18-L25, L79-L95, L159-L171](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/src/config.ts#L79-L95)). It locates Bun's global `node_modules` via `bun pm bin -g` and `~/.bun/install/global/node_modules` ([config.ts L246-L252](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/src/config.ts#L246-L252)). Older changelog entries show the Bun path being maintained: "Show `bun install` instead of `npm install` in update notification when running under Bun" (0.46.0, [CHANGELOG.md L4382](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/CHANGELOG.md#L4382)), "Fixed Bun-based package manager startup by locating global `node_modules` relative to Bun's install layout" (0.70.6, [CHANGELOG.md L2382](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/CHANGELOG.md#L2382)), and "Fixed Bun package manager `node_modules` discovery when `npmCommand` is configured to use Bun" (0.71.0, [CHANGELOG.md L2342](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/CHANGELOG.md#L2342)). These entries predate the 1.x line and some link to the old `badlogic/pi-mono` repository.

GitHub release assets could not be listed (the API was not reachable), so it is unconfirmed which binaries are published for 1.4.0, and the install docs do not point to them.
- **The CLI entry point targets Node.** `bin.pi` is `dist/bundle/cli.js`, whose shebang is `#!/usr/bin/env node` ([bundle/cli.js in the 1.4.0 tarball](https://unpkg.com/@earendil-works/pi-coding-agent@1.4.0/dist/bundle/cli.js), [package.json L9-L11](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/package.json#L9-L11)).

Inference: `bun install -g @earendil-works/pi-coding-agent` is probably installable, because Pi's own updater uses that exact form for Bun-managed installs. A later check (2026-11-07) found that pi.dev lists `bun add -g --ignore-scripts @earendil-works/pi-coding-agent` as an install command ([pi.dev](https://pi.dev)), but the runtime is still Node: the `cli.js` shebang is `#!/usr/bin/env node`, and the maintainer said in [issue #6237](https://github.com/earendil-works/pi/issues/6237) (6 Jul 2026) "we can't have a shebang that works for all runtimes". No official doc calls Bun a supported way to run Pi. Pi's `npmCommand` setting accepts `["bun"]` for package installs ([issue #4160](https://github.com/earendil-works/pi/issues/4160)).

Decision for 0.3.0: Pi runs on Node, and the only use of Bun by Pi is as its `npmCommand` for package installs, which `holyagent setup` is planned to set ([What setup and doctor do](#what-setup-and-doctor-do)). Bun is documented as a prerequisite of the HolyAgent CLI, not as a way to install Pi. The documented Pi install is Node.js 22.19 or newer plus the official installer or `npm install -g --ignore-scripts @earendil-works/pi-coding-agent@1.5.0`.
