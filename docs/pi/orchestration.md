# Orchestration on Pi: workflows, codemode and the launcher for Intents and Assignments

**Status: planned for 0.3.0. The first three sections are the plan; the sections after them are research on Pi's primitives and are not shipped behaviour.**

Pi 1.4.0, commit `4a080252f06caf63a525d7873c5d94d3c23887e0` (the plan pins 1.5.0; see [README.md](README.md#version-risk)). Sourced facts carry a link. Everything marked "Inference:" is design reasoning, not Pi behaviour. The Claude Code and HolyAgent side of the mapping (dynamic workflows, Intents, Assignments, the 18 Role.task identities) comes from the task brief, not from Pi.

## Decision for 0.3.0

**Status: decided for 0.3.0; the launcher and the workflow tool are not built yet.**

Specialists and workflows run through the **`@tintinweb/pi-subagents`** extension (0.23.1, 4 Nov 2026, [README](https://github.com/tintinweb/pi-subagents/)). Its `SubagentWorkflow` tool (`agent()`, `parallel()`, `pipeline()`) runs Claude-style workflow scripts in the background, so the root stays free and is woken as each specialist finishes. The README claims it runs Claude Code `Workflow` scripts unchanged, and it disables itself if another extension provides a `Workflow` or `SubagentWorkflow` tool. It replaces nicobailon's `pi-subagents` (0.87.0, about 207K downloads a week, needs Pi 1.2.0 or newer, [npm](https://www.npmjs.com/package/pi-subagents)) everywhere; the earlier plan to use that package for the launcher no longer stands.

What follows from it:

- **Reuse before custom code.** The launcher is the package (architecture 2 below describes the custom alternative), and HolyAgent writes a `holy_assign` or any other launcher code only for a requirement the package does not cover. The codemode fan-out of architecture 3 is not planned.
- **The requirements stay.** The Intent for the launcher still asks for: only the eighteen specialist names; model and effort taken from the dispatched entry and the routing table; a launch that does not block the root, with a completion notice that starts a new root turn; a warm specialist continued in the same session only when the CLI's directive says `continue`, and never one whose review must be independent; completion read from `agent_settled`, never `agent_end`; failures mapped to the Assignment status table below; the agent id recorded with `assignment record` under the dispatched-Assignment marker; a workflow script that never asks for confirmation, whatever agents it calls (decided by the maintainer); a direct-subagent fallback when workflows are unavailable; abort and deadlines left to the host. Which of these `@tintinweb/pi-subagents` meets by itself and which need HolyAgent glue is to be verified when the launcher is built.
- **No extra report tool.** A specialist's final message is its report; there is no `assignment_report` tool, and the `evidence:` block the CLI parses stays the report format ([claude-parity.md](claude-parity.md#4-specialists)).
- **Open until built:** whether the package's tools are callable from codemode scripts, which matters under mode `only` (see [Codemode in 0.3.0](#codemode-in-030)), and whether children are driven over RPC or JSON mode when HolyAgent code has to drive one itself. Pi documents both and recommends neither ([rpc.md](https://cdn.jsdelivr.net/npm/@earendil-works/pi-coding-agent@1.5.0/docs/rpc.md), [json.md](https://cdn.jsdelivr.net/npm/@earendil-works/pi-coding-agent@1.5.0/docs/json.md)).
- **The Claude plugin's workflow rules carry over** with the runtime change that makes "workflows available" a host-neutral switch ([claude-parity.md](claude-parity.md#5-workflows)).
- **Under T3 Code, T3's `delegate_task` is not used.** T3 injects its own orchestration tools (`delegate_task`, `task_status`, `task_cancel`, the `t3_thread_*` family and the rest) into every Pi session it runs; HolyAgent deactivates them, along with every other T3 tool outside the `html_*`, `preview_*`, `t3_preview_*` and `device_*` families, and keeps its own specialists, which report through the package's own new-turn trigger ([t3-code.md](t3-code.md#t3s-tools-kept-and-deactivated)).
- **Completion notices under T3.** T3 treats a turn as done on `agent_settled`, so the notice of a background specialist that finishes afterwards has to start a new root turn in T3 (inference: it may not appear otherwise). A recorded fixture of T3's RPC traffic verifies that; what HolyAgent does if it does not is not decided ([t3-code.md](t3-code.md#specialists-and-completion-notices)).

## The runtime under Pi

**Status: built in the runtime for 0.3.0; the Pi extension that sets and uses it is not built yet.** The Claude plugin's output is unchanged.

- **Host.** The extension sets `HOLYAGENT_HOST=pi` on every `holyagent` call (unset or `claude` is Claude). Under `pi`, `plan`, `assignment dispatch`, `reconcile`, the error hints and the help name the tools of `@tintinweb/pi-subagents` (`Agent`, `SubagentWorkflow`, `read`; a warm specialist is reached by the `Agent` tool's `resume`) where Claude's output says Workflow, Read and SendMessage. The help also leaves out the `hook` commands that read a Claude hook payload; `hook commit-msg` stays. Any other value is a usage error.
- **Model and thinking.** Under `pi`, `assignment dispatch` prints each spawned specialist's `model` and `effort` from its row of the `pi.routes` table of the config (the user's `~/.holyagent/config.json` under the project's, as the `config` command loads them), not from Claude's route table. `model` is `<provider>/<id>` (for example `kimi-coding/kimi-for-coding`), which `@tintinweb/pi-subagents` matches exactly in the `model` of `agent()` and of the `Agent` tool, without the `:<thinking>` suffix of `--model`; `effort` is the row's thinking level, which is `agent()`'s `effort` and the `Agent` tool's `thinking` (`off` is a level only the `Agent` tool takes). The root passes both as printed. With `pi.enable` off no row applies, so both are left out and the specialist inherits the session's model and thinking. `plan` names no model; its help says the same. A config that does not load fails the command as `ConfigInvalid`, and Claude's output never reads the config and is unchanged.
- **Workflows available.** `HOLYAGENT_WORKFLOWS=1` or `0` decides on either host. Under `pi` it is `0` until the extension sets it, because only the extension can see whether `SubagentWorkflow` is active; with `0`, `plan` prints the direct subagents (`action: subagent`), and with `1` it prints the workflow with that same work as its `fallback`. Under Claude, unset keeps the detection from `CLAUDE_CODE_DISABLE_WORKFLOWS` and the settings files.
- **Agent ids** for `assignment record --agent`. A direct launch is `pi:<agent-id>`, the ID the `Agent` tool returns; the extension strips `pi:` to resume or steer the agent. A workflow agent is `pi-workflow:<run-id>/<assignment-id>`, with the run ID `SubagentWorkflow` returns and the Assignment id as the `label` the script gave the agent. Under `pi` any other form is refused; under Claude the pi forms are checked and any other id is the host's own. A `pi-workflow:` agent is never continued, like Claude's `workflow:` agent, and a `pi:` agent can be.
- **Session context.** The Pi handlers do not call the runtime's functions in process: Pi runs on Node and the runtime reads files with Bun, so they reach it through the package's `scripts/holyagent` wrapper, which runs `status`, `reconcile`, `state mode` and the bundle's `config` command, and build the context with `piContext`, which uses the same `sessionContext` and `bareContext` builders as `hook session-start`. `hasStateFolder` is the check the Claude hook and the extension share; `statusOf`, `resumeOf` (with `PI_WORDS`), `requirementsOf`, `ROOT_CORE`, `sessionContext`, `bareContext` and `legacyContext` stay exported from `@holyagent/runtime` for a host that can call them directly.
- **Commit text.** Pi adds no commit text of its own (the installed packages hold no co-author or "Generated with" string, and its system prompt does not mention git). Its attribution is the name `pi` and `https://pi.dev` (`PI_ATTRIBUTION` in `@earendil-works/pi-ai`) and the `/share` link `https://pi.dev/session/#<gist>`, so the cleaner removes the forms a model copies from them: a "Generated with [pi](https://pi.dev)" footer, a `Co-authored-by` trailer naming `pi`, `Pi Coding Agent` or an address at `pi.dev`, and `pi.dev/session/` links.
- **Reports.** Under `pi`, `assignment reports <file>` writes each report to its file by Assignment id and prints the same `reports` rows (id, path, words) as under Claude. The file is either of two things, told apart by name:
  - A `<run id>.workflow.jsonl` of `@tintinweb/pi-subagents` (`src/workflow/journal.ts`). Its one entry type, `{index, key, ok, text?, resumed?}`, carries no label, so an entry is tied to its Assignment by its `key`: the first 32 hex characters of the SHA-256 of the JSON of `[prompt, label, model, agentType, effort, isolation, gate, resume]` (`null` for an absent field, the serialized schema appended only when the call had one), which `journalKey` recomputes. The runtime recomputes it for each Assignment from the call the dispatch printed: the dispatch prompt (with `read` as the brief tool), the Assignment id as `label`, the printed `model` and `effort` (absent when pi is off), and the agent name as `agentType` (`worker-implementation`, the name the Pi package ships, which the pi-host dispatch prints in place of `holyagent:worker-implementation`). The script passes no isolation, gate, resume or schema. An Assignment's last entry decides, as a repeated label does under Claude. The journal is decoded strictly, and a line that does not decode refuses the whole file.
  - The root session file, for an Assignment recorded as `pi:<agent-id>`. The package appends a `subagents:record` entry with the full result when a direct agent finishes (`src/agent-record-entry.ts`); the last entry of the agent wins, as it does for the package's own `get_subagent_result`. `piRecordReport` reads one agent's record.
  - An entry that failed, has no text (an `ok` entry with empty text counts as no report) or matches no dispatched call is listed in `notAssignmentIds` as `<run id>#<index> failed|empty|unmatched`, with the Assignment id as `label` when the entry matched one; an agent without a report is listed as `pi:<agent-id> missing|error|aborted|stopped|empty|exit`.
- **Status.** `assignmentStatusOf` maps how a child ended to the Assignment status and the `assignment close --outcome` that records it, and `outcomeOfRecord` reads the outcome from a persisted record:

  | Outcome   | Where the package shows it                                                                        | Status      | Close as  |
  | --------- | ------------------------------------------------------------------------------------------------- | ----------- | --------- |
  | `ok`      | record `completed` or `steered` with a result; journal `ok: true` with text                       | done        | `success` |
  | `error`   | record `error` (a provider failure, `stopReason` `error`); journal `ok: false`                    | failed      | `errored` |
  | `length`  | final turn `stopReason` `length`; the package counts one that wrote text as completed             | failed      | `errored` |
  | `empty`   | settled with no report text: `completed` with an empty result, or journal `ok: true` without text | failed      | `errored` |
  | `exit`    | the process ended before the child settled: a record still `queued` or `running`                  | failed      | `errored` |
  | `aborted` | record `aborted` (hard abort after the turn limit); `agent_settled` with `aborted: true`          | failed      | `errored` |
  | `stopped` | record `stopped`: the root stopped the agent (a failed `aborted` is the turn limit, not a stop)   | interrupted | `stopped` |

- **Not covered.** An entry tied to no call stays unmatched when the script changed anything the key hashes (the prompt, the model or effort it passed, the agent type), so keep the dispatched values; a change to `pi.routes` or `pi.enable` between the dispatch and `assignment reports` changes the key the runtime recomputes and leaves the entry unmatched. The journal records no error text and no stop reason, so a `length` stop that produced text is `ok` there and in a record: only the code that sees the child's stop reason can pass `length`. Reports from a workflow run that was resumed (`resumed: true`) match no call and are listed as unmatched.

## Codemode in 0.3.0

**Status: decided for 0.3.0.** The maintainer: "I wanna specifically use codemode". The setting is:

- **Mode `only` for the root and every specialist.** With `only`, every active tool is hidden from the model and listed in the `codemode` description, so the model reaches everything through scripts ([codemode.md, Pi 1.5.0](https://cdn.jsdelivr.net/npm/@earendil-works/pi-coding-agent@1.5.0/docs/codemode.md), [settings](https://pi.dev/docs/latest/settings)). Tools registered `model-only`, such as `ask_user_question` from `@juicesharp/rpiv-ask-user-question`, stay directly callable by the model and are not callable from scripts; rpiv fixed its issue #310 (the tool not invoked under `only`) that way in 2.14.0 ([CHANGELOG](https://github.com/juicesharp/rpiv-mono/blob/main/packages/rpiv-ask-user-question/CHANGELOG.md)).
- **`PI_CODEMODE_MAX_WORKERS=4`**, set on the root and on every specialist process. The default is 2 workers alive across all sessions in one process; each script gets 256 MB; at capacity, scripts queue in arrival order for up to 60 seconds (or until `timeout_ms`) and then fail without running ([environment variables](https://pi.dev/docs/latest/environment-variables)). The maintainer asked for the limit to be settled after the codemode questions; 4 is the accepted value.

What the research found about scripts, for planning ([codemode.md, Pi 1.5.0](https://cdn.jsdelivr.net/npm/@earendil-works/pi-coding-agent@1.5.0/docs/codemode.md) unless noted):

- A script is raw JavaScript in a QuickJS sandbox with no filesystem, network or timers. It reaches the outside only through `tools.<name>(args)` and `models`.
- A script can call any registered tool, extension tools included, subject to the tool's exposure: `direct` (default) is callable while active; `codemode` whenever registered; `deferred` is callable but not listed; `model-only` and `hidden` are never callable from a script ([Tools in Depth](https://programmer.ie/books/pi/17-chapter/), a third-party book; the [0.99.0 changelog](https://pi.dev/changelog/releases/0.99.0) confirms the five values). Scripts find tools with `searchTools()`, `describeTool()` and `ALL_TOOLS`.
- Chat models are listed but cannot be run from scripts; only classifier and image models run, at most 4 at once per script. A script starts a subagent only through an extension tool.
- `Promise.all` and `Promise.allSettled` over tool calls work. A failed call rejects with an `Error`, calls made before a failure are not undone, calls still running when the script ends are cancelled, and a failed script keeps its partial output.
- `// @options: {"max_output_tokens", "timeout_ms"}` must be the first line. `timeout_ms` is a hard deadline and is unset by default; `max_output_tokens` defaults to 10000, with the full text in a temp file. A script cannot start another `codemode` script. `store` and `load` keep small JSON values across calls.
- Nested calls emit `tool_call`, `tool_result` and `tool_execution_*` events carrying `parentToolCallId`, add no transcript entries, and roll their usage up to the caller ([extensions](https://pi.dev/docs/latest/extensions)).
- Pi 1.5.0 lists no codemode change from 1.4.0.

To be verified when the integration is built:

- **Whether the tools of `@tintinweb/pi-subagents` and `@aliou/pi-processes` are callable from scripts.** The research did not read their registrations.
- **Whether a script blocks the root's turn.** The docs describe a script as one tool call that returns `Script completed` or `Script failed` with the wall time, and document no background mode, so the turn waits; nothing else was found that prevents blocking. The background `SubagentWorkflow` is what keeps the root free.
- **Permissions.** Nested calls pass through `tool_call` handlers, so a permission extension would see them; no per-script permission setting was found. With full access ([auto-mode.md](auto-mode.md)) no such handler is loaded.

## CI and Windows

**Status: decided for 0.3.0.**

- **Recorded fixtures, not a real Pi.** CI replays recorded Pi events for the pinned Pi version. `mise run deps:update` moves the Pi package pins and, through `bun update`, the Pi host used for development and tests within its caret range (a user's own Pi install is theirs); it does not re-record the fixtures, so a move that changes Pi's events shows up as a failing replay until they are re-recorded by hand ([installation.md](installation.md#the-pin)). A real Pi process would need Node 22.19 and network access, which the plan avoids in CI.
- **Inside the existing jobs.** The Pi tests run inside the existing `check` and `windows` jobs, so no job is added or renamed and the rulesets' required check names do not change ([development.md](../development.md)). The `check` job's generated-output freshness check covers the Pi package.
- **A contract test** covers the Pi RPC or JSON events the integration consumes (`agent_settled`, tool events, `extension_ui_request`) against the pinned version. The T3 Code behavior is covered by recorded `pi --mode rpc` fixtures in the same jobs ([t3-code.md](t3-code.md#tests)).
- **Windows.** Extension and launcher code calls the bundled CLI through Bun on `holyagent.js` directly, not through the POSIX `sh` wrapper. Child launches and paths must work on native Windows, where Pi's built-in tool list includes `powershell` beside `bash`. Whether Pi itself behaves on native Windows is not verified: the research read source only and ran nothing there, so the `windows` job is where it is checked.
- **The other gates still pass:** pinned action SHAs with version comments, caret dependency ranges (with the Pi peer-dependency exception, see [extensions.md](extensions.md#the-holyagent-package)) and the path-length test.

## Short answer

Pi has no workflow engine and no `agent()` primitive. It does have all the parts a host needs to build one: an SDK, an RPC mode with a typed client, a JSON event stream, extensions that can register schema-validated tools, and a model-written JavaScript sandbox (`codemode`) that can call tools in parallel. The closest functional match to "workflows parametrized by args" is host or extension code that launches one Pi session per Assignment; the closest match to Claude Code's workflow _scripts_ is `codemode`, but it differs in who writes the script, what it can reach and what is cached. The 0.3.0 plan does not build that engine; it uses `@tintinweb/pi-subagents` (see [Decision for 0.3.0](#decision-for-030)).

## Three architectures

These were the options before the decision. [Decision for 0.3.0](#decision-for-030) picks an existing extension, `@tintinweb/pi-subagents`, as the launcher, so architecture 2 is built only where the package leaves a gap and architecture 3 is not planned; architecture 1 is not used either, because the root stays an interactive Pi process.

1. **Host-driven (Inference; not used).** A HolyAgent runtime process (Bun) owns Intents, Assignments, dependencies, ownership and the status lifecycle. For each Assignment it runs a Pi child over RPC (stdin/stdout JSONL, `RpcClient` pattern) with the HolyAgent extension loaded via `-e`. This mirrors how Claude Code subagents are separate contexts, uses only documented Pi interfaces, and keeps Pi upgrades from touching HolyAgent state. Model-written inline workflow scripts become calls into HolyAgent that create Assignments, which is where `args` and typed results live. Costs: one process per live Assignment, and HolyAgent must implement result caching for resume.
2. **Extension-hosted assignment tool (Inference).** The HolyAgent extension registers a `holy_assign({ agent, prompt, model, effort })` tool whose `execute()` runs one specialist inside the Pi process and reports progress with `onUpdate`; the model fans out by writing the inline script of architecture 3 or by parallel tool calls, and no named workflow tool exists. It could use `createAgentSession` or child processes for the workers. Pros: one model-visible entry point per Assignment, with the 18 agent names as its schema. Cons: it runs in the same process and credentials as the parent, and the parent's context sees only the tool result. Nested tool calls are gated as usual ([extensions.md L261](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/docs/extensions.md#L261)).
3. **Codemode-based (Inference, weakest fit).** Register `holy_assign` with `exposure: "codemode"` and let the model write scripts that fan out `tools.holy_assign(...)`. This keeps orchestration inside the model's turn, but the script is authored by the model, lacks args/schema/resume semantics, is capped at two workers per process, and can reach `bash`/`write` unless HolyAgent hides them or blocks them in a gate by checking `parentToolCallId`. It is useful only for ad-hoc fan-out.

## Gaps and risks

- No resumable workflow runtime: HolyAgent would need its own result cache keyed by run and node (Inference; Pi's documented persistence is the session transcript and `store()`).
- The tool surface changes between releases (1.0.1 to 1.4.0 in three weeks, [npm registry metadata](https://registry.npmjs.org/@earendil-works/pi-coding-agent)). Decided: Pi and every reused extension are pinned, and recorded fixtures replay the RPC/JSON events HolyAgent consumes ([CI and Windows](#ci-and-windows)).
- RPC and JSON modes cannot show the built-in project-trust prompt, so children inherit the parent's project trust and pass `--approve` when the parent session trusted the project (full access, see [auto-mode.md](auto-mode.md) and [installation.md](installation.md#global-and-project-local-installs)).
- Pi has no built-in notion of "blocked on user decision" beyond extension dialogs; the host must answer `extension_ui_request` records or the run stalls until its timeout.
