# Orchestration on Pi: a dynamic-workflow equivalent for Intents and Assignments

Pi 1.4.0, commit `4a080252f06caf63a525d7873c5d94d3c23887e0`. Sourced facts carry a link. Everything marked "Inference:" is my design reasoning, not Pi behaviour. The Claude Code and HolyAgent side of the mapping (dynamic workflows, Intents, Assignments, the 18 Role.task identities) comes from the task brief, not from Pi.

## Short answer

Pi has no workflow engine and no `agent()` primitive. It does have all the parts a host needs to build one: an SDK, an RPC mode with a typed client, a JSON event stream, extensions that can register schema-validated tools, and a model-written JavaScript sandbox (`codemode`) that can call tools in parallel. The closest functional match to "workflows parametrized by args" is host or extension code that launches one Pi session per Assignment; the closest match to Claude Code's workflow _scripts_ is `codemode`, but it differs in who writes the script, what it can reach and what is cached.

## Three architectures

1. **Host-driven (recommended, Inference).** A HolyAgent runtime process (Bun) owns Intents, Assignments, dependencies, ownership and the status lifecycle. For each Assignment it runs a Pi child over RPC (stdin/stdout JSONL, `RpcClient` pattern) with the HolyAgent extension loaded via `-e`. This mirrors how Claude Code subagents are separate contexts, uses only documented Pi interfaces, and keeps Pi upgrades from touching HolyAgent state. Model-written inline workflow scripts become calls into HolyAgent that create Assignments, which is where `args` and typed results live. Costs: one process per live Assignment, and HolyAgent must implement result caching for resume.
2. **Extension-hosted assignment tool (Inference).** The HolyAgent extension registers a `holy_assign({ agent, prompt, model, effort })` tool whose `execute()` runs one specialist inside the Pi process and reports progress with `onUpdate`; the model fans out by writing the inline script of architecture 3 or by parallel tool calls, and no named workflow tool exists. It could use `createAgentSession` or child processes for the workers. Pros: one model-visible entry point per Assignment, with the 18 agent names as its schema. Cons: it runs in the same process and credentials as the parent, and the parent's context sees only the tool result. Nested tool calls are gated as usual ([extensions.md L261](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/docs/extensions.md#L261)).
3. **Codemode-based (Inference, weakest fit).** Register `holy_assign` with `exposure: "codemode"` and let the model write scripts that fan out `tools.holy_assign(...)`. This keeps orchestration inside the model's turn, but the script is authored by the model, lacks args/schema/resume semantics, is capped at two workers per process, and can reach `bash`/`write` unless HolyAgent hides them or blocks them in a gate by checking `parentToolCallId`. It is useful only for ad-hoc fan-out.

## Gaps and risks

- No resumable workflow runtime: HolyAgent would need its own result cache keyed by run and node (Inference; Pi's documented persistence is the session transcript and `store()`).
- The tool surface changes between releases (1.0.1 to 1.4.0 in three weeks, [npm registry metadata](https://registry.npmjs.org/@earendil-works/pi-coding-agent)); pin the version and keep a contract test around the RPC/JSON events HolyAgent consumes.
- RPC and JSON modes cannot show the built-in project-trust prompt, so HolyAgent must pass `--approve`/`--no-approve` or rely on `defaultProjectTrust` ([security.md L75-L82](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/docs/security.md#L75-L82)).
- Pi has no built-in notion of "blocked on user decision" beyond extension dialogs; the host must answer `extension_ui_request` records or the run stalls until its timeout.
