**Status: planned for 0.3.0. The first three sections are the plan for the Kimi provider, the routing and the instructions; the sections after them are research on Pi's provider layer and are not shipped behaviour.**

## Kimi for Coding (global)

Kimi for Coding (global) is the first and, in 0.3.0, the only supported provider. Other providers are later work and are not documented as supported. The maintainer asked whether a maintained Pi extension already gives a full Kimi for Coding global integration; one does, so the plan installs it and builds no provider.

**The provider is Pi's built-in `kimi-coding` with `pi-provider-kimi-code` pinned on top and `KIMI_CODE_REGION=global`.** Requests then go to `https://api.kimi.ai/coding/v1`, Moonshot's overseas host; `api.kimi.com` is mainland China ([Kimi Code models](https://www.kimi.com/code/docs/en/kimi-code/models)).

Points the research leaves open, to be settled when the package is built:

- **The built-in provider's API type.** One read of the source at commit `209bc7b9` gives `api.kimi.com/coding` with the `anthropic-messages` API ([kimi-coding.ts](https://github.com/earendil-works/pi/blob/209bc7b9/packages/ai/src/providers/kimi-coding.ts)); another read of `main` gives `https://api.kimi.com/coding/v1` over `openai-completions`. Which one holds matters only for the caching inference in [caching-and-subagents.md](caching-and-subagents.md#cache-target), which is conditional on the API type; confirm it against the pinned Pi.
- **Pi 1.5.0 compatibility of the extension.** Its v0.6.13 is bumped to Pi 0.99.2. Whether it works unchanged on 1.5.0, and whether Pi's catalog lists `k3.1-pro` for the extension, is checked by the launch-time catalog validation and by the recorded fixtures. The extension's own fallback model list omits `k3.1-pro`; its README says the live catalog `https://api.kimi.com/coding/v1/models` is authoritative.
- **The extension overrides the built-in** `kimi-coding` registration of the same id (its legacy registration), which the pin has to be checked for.
- **Single-maintainer risk** of the extension, and the data the Moonshot-side tools send to Moonshot's services (they are off by default).

How HolyAgent uses the provider:

- It reaches the provider only through Pi's own provider layer, with `--model <provider/id>:<thinking>` (or `set_model` and `set_thinking_level` over RPC). It never calls provider URLs, never reads `auth.json` and never uses `pi auth print-api-key` or `print-bearer-token`.
- Before it launches a root or a specialist it runs `pi auth check --provider <id> --json` (exit 0 ready, 1 not ready, 2 invalid). A provider that is not ready is reported as a blocker with the fix and is never replaced silently.
- It validates model ids at launch against the user's catalog (`pi --list-models` or `get_available_models`) and hard-codes none.
- One mapping turns a route-table model and effort into a `provider/id` and a thinking level, so choosing another provider later changes that mapping only.
- Selecting the provider in `config.json` enables `pi-provider-kimi-code`; deselecting it disables the extension ([configuration.md](configuration.md#holyagent-configjson)).

### Models and efforts

Source for the rows: [Kimi Code models](https://www.kimi.com/code/docs/en/kimi-code/models) (K3.1 Pro rollout; K2.8 Preview rollout 2026-09-11).

| Model id                    | Version             | Context                                                 | Notes                                          |
| --------------------------- | ------------------- | ------------------------------------------------------- | ---------------------------------------------- |
| `k3.1-pro`                  | K3.1 Pro            | 1,048,576 on Pro+/Allegretto+; 262,144 on Plus/Moderato | Thinking only                                  |
| `k3.1-pro-highspeed`        | K3.1 Pro Highspeed  | Up to 1,048,576                                         | About 2-3x speed for about 2x quota; Pro+ only |
| `k3`                        | K3                  | 1M or 256K by tier                                      |                                                |
| `k3-256k`                   | K3                  | 262,144                                                 |                                                |
| `kimi-for-coding`           | K2.8 Preview        | Up to 1,048,576                                         | The same id, upgraded in place                 |
| `kimi-for-coding-highspeed` | K2.7 Code Highspeed | 262,144                                                 |                                                |

- **Efforts** are `low`, `high` and `max`. Kimi Code's default is `high` for K3.1 Pro and K3 and `max` for `kimi-for-coding`; the platform API's own reference defaults K3.1 Pro to `max`, so the two sources conflict. K3.1 Pro rejects thinking-off with a 400. The other models route a thinking-off request, and a mistyped model id, to K2.8 Preview without thinking. Kimi Code maps `xhigh`, `ultra` and `max` to `max`, and `medium` and `high` to `high` ([reasoning effort](https://platform.kimi.ai/docs/guide/use-reasoning-effort), [Kimi Code models](https://www.kimi.com/code/docs/en/kimi-code/models)).
- **What an effort costs is unknown.** Moonshot gives no numbers per level for quality, latency, tokens or quota, no advice on when to use `max`, and every published K3.1 Pro benchmark uses `max` ([quickstart](https://platform.kimi.ai/docs/guide/kimi-k3-1-pro-quickstart), [model card](https://huggingface.co/moonshotai/Kimi-K3.1-Pro)). The root's `max` against `high` is to be measured (see [Routing](#routing)).
- **Quota** is a subscription with a 5-hour rolling window and a monthly quota; legacy plans also keep a weekly window; high-speed variants burn quota faster ([error reference](https://www.kimi.com/code/docs/en/kimi-code/error-reference.html), and a third-party page, [2026-08-23](https://kimi-ai.free/use-cases/developers/)). Per-plan prices are unknown from official sources.
- Image and video input works on all models except `k3-256k`, which takes images only.
- Changing the model or the effort in a session invalidates the context cache ([caching-and-subagents.md](caching-and-subagents.md#cache-target)).

## Routing

**Status: decided for 0.3.0; the table lives in the `config.json` defaults, so it can change without code** ([configuration.md](configuration.md#holyagent-configjson)). It replaces the Claude route table's `haiku`, `sonnet` and `opus` and their efforts for sessions on Kimi. The maintainer's words: "not kimi-for-coding-low, either high or max, kimi k3.1 pro low-high, assess if max is worth it for root".

| Role                                                                                                | Model             | Effort |
| --------------------------------------------------------------------------------------------------- | ----------------- | ------ |
| Root                                                                                                | `k3.1-pro`        | high   |
| Worker.implementation, Worker.debugging, Worker.integration                                         | `kimi-for-coding` | max    |
| Reviewer.code, Reviewer.security, Reviewer.testing, Reviewer.artifact                               | `kimi-for-coding` | max    |
| Worker.mechanical, Worker.validation, Worker.operations                                             | `kimi-for-coding` | high   |
| Explorer.map, Explorer.lookup, Explorer.trace, Librarian.lookup, Librarian.research, Reviewer.audit | `kimi-for-coding` | high   |
| Worker.visual, Reviewer.visual                                                                      | `k3.1-pro`        | low    |

- **Specialists run on `kimi-for-coding`, which is Kimi K2.8 Preview, never at low, except the two visual specialists, which run on `k3.1-pro` at low (below).** The root runs on K3.1 Pro. The sources give no per-role reasons beyond this grouping: the roles that write or judge code run at max, and the mechanical, checking, lookup and research roles run at high.
- **Both visual specialists run at low** because the root makes the final visual pass. The maintainer's words: "both visual specialists must be low, as root does the final review pass".
- **Visual tools.** Under T3 Code the two visual specialists use T3's `preview_*` browser, and only they get the computer-use tools of `@amaster.ai/pi-computer-use` ([t3-code.md](t3-code.md#browser), [t3-code.md](t3-code.md#computer-use-through-cua-driver)).
- **The root's effort is `high`.** `max` is selectable in `config.json`. A later 0.3.x task will measure high against max on real sessions before `max` becomes the default; until then the cost and benefit of `max` for the root are unmeasured.
- **A session keeps one model and effort.** Each Assignment's specialist is launched on its row and is not switched mid-session, because a switch invalidates Kimi's cache.
- **Provider-agnostic structure stays.** The table maps a role to a model and an effort through the one mapping described above; other providers would add rows later and are not part of 0.3.0.

## Instructions for Kimi K3.1

**Status: decided for 0.3.0.** The maintainer's words: "for the pi integration we will need kimi k3.1 specific instructions following its official instruction guide".

- **Moonshot has no K3.1-specific prompting guide.** The instruction set follows three Moonshot guides and cites the section each rule follows, the way the Claude 5.5 set cites Anthropic's guidance: the [prompt best-practice guide](https://platform.kimi.ai/docs/guide/prompt-best-practice) (undated; clear instructions, roles, explicit steps, few-shot examples, length by paragraphs or bullets, reference text, summarizing long histories), the [K3.1 Pro quickstart](https://platform.kimi.ai/docs/guide/kimi-k3-1-pro-quickstart) and the [agent-setup guide](https://platform.kimi.ai/docs/guide/use-kimi-k3-to-setup-agent).
- **It is a separate set.** A per-model folder of the Pi instruction text sits beside `packages/runtime/src/instructions/claude-5.5` (for example `kimi-k3.1/`) and is written to Moonshot's guides, not adapted from the Claude 5.5 wording. Sessions that run on K3.1 through Kimi for Coding (global) load it. The `kimi-for-coding` (K2.8 Preview) specialists load the same set; see [the K2.8 Preview specialists](#the-k28-preview-specialists).
- **It follows the agent guide's structure.** Each role gets a short system prompt that keeps to the role, the workflow and the quality boundaries; argument details go in tool descriptions and the rest in on-demand skills.
- **Request constraints from the quickstart** ([quickstart](https://platform.kimi.ai/docs/guide/kimi-k3-1-pro-quickstart), [reasoning effort](https://platform.kimi.ai/docs/guide/use-reasoning-effort)): thinking is always on and is set with the top-level `reasoning_effort`, so a request does not send `thinking`; `temperature` (1.0), `top_p` (0.95) and `n` (1) are fixed and are omitted; `max_completion_tokens` defaults to 131072 and can go up to 1048576; the whole assistant message, `reasoning_content` and `tool_calls` included, is passed back unchanged; vision does not accept public image URLs. Inference: Pi's provider layer and the extension build the request, so HolyAgent sets only the model and the effort.
- Moonshot's [tool-calling guide](https://platform.kimi.ai/docs/guide/kimi-k3-tool-calling-best-practice) says to pick the effort before the conversation starts, which matches the one-effort-per-session rule.

### The K2.8 Preview specialists

**Status: decided for 0.3.0.** The maintainer's rule: "separate k2.8 or k2.7, or k2.6, k2.5, whichever is more relevant. if k3 or k3.1 is more relevant, we should use it. it depends on how the model behaves". Research of 2026-11-07 resolved it: the specialists on `kimi-for-coding` (K2.8 Preview) load the same Kimi instruction set, written to the K3/K3.1 guides above plus Moonshot's [K3 tool-calling best-practice guide](https://platform.kimi.ai/docs/guide/kimi-k3-tool-calling-best-practice). The K2.6/K2.7 [thinking guide](https://platform.kimi.ai/docs/guide/use-thinking-models) does not apply; it covers only `kimi-k2.7-code` and `kimi-k2.6`.

Why K2.8 Preview counts as K3-like, from how it behaves:

- Moonshot describes K2.8 Preview as "performance close to K3 with more efficient thinking", with efforts `low`, `high` and `max` "consistent with K3" ([Kimi Code models](https://www.kimi.com/code/docs/en/kimi-code/models), [what's new](https://www.kimi.com/code/docs/kimi-code/whats-new.html), Chinese, 2026-09-11 entry).
- It is controlled with the top-level `reasoning_effort` (default `max`), as K3 is; K2.6 and K2.7 use the `thinking` parameter, and K2.7 has no adjustable effort ([Kimi Code models](https://www.kimi.com/code/docs/en/kimi-code/models), [models overview](https://platform.kimi.ai/docs/api/models-overview)).
- Its context is up to 1,048,576 tokens, like the K3 series; K2.6 and K2.7 have 256K ([Kimi Code models](https://www.kimi.com/code/docs/en/kimi-code/models), [models overview](https://platform.kimi.ai/docs/api/models-overview)).

Limits of that finding:

- Moonshot has no K2.8-specific prompting guide, and no model card or changelog says whether K2.8 Preview shares post-training with K2.x or K3. The choice rests on documented behavior, not on lineage.
- The instruction text must not rely on forcing a first-round tool call with `tool_choice` `required`. A secondary source, not Moonshot, says K2.8 Preview accepts only `auto` or `none` ([Tencent Cloud](https://intl.cloud.tencent.com/document/product/1300/80635)); Moonshot's own parameter page confirms `required` only on K3 ([models overview](https://platform.kimi.ai/docs/api/models-overview)).
- The request constraints above are written for K3.1 Pro. For K2.8 Preview the same secondary source gives `max_tokens` (default 32768) in place of `max_completion_tokens` and accepts public image URLs, so the instruction text leaves request settings out; Pi's provider layer and the extension build the request.
- To be verified: the tool-calling and parallel-call specifics on K2.8 Preview, and whether the platform's `kimi-k2.8-preview` behaves as the Kimi Code `kimi-for-coding` endpoint does (the secondary source covers the platform id).

## Provider model in one paragraph

A _provider_ is the service/account, a _model_ is what it serves. Users connect with `/login` (OAuth or API key, stored in `auth.json`) or with environment variables, then pick a model with `/model` ([models.md L5-L35](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/docs/models.md#L5-L35), [providers.md L10-L18](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/docs/providers.md#L10-L18)). Pi ships a bundled model catalog and overlays newer data from pi.dev; `pi update --models` forces a refresh ([models.md L15](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/docs/models.md#L15)). The catalog is also browsable at [pi.dev/models](https://pi.dev/models).

## Selecting models from a host

- CLI: `--provider`, `--model <pattern>` (exact id, fuzzy match, `provider/id`, optional `:<thinking>` suffix), `--thinking off|minimal|low|medium|high|xhigh|max`, `--models` (cycling scope), `--list-models [search]`; thinking is clamped to what the model supports ([cli.md L55-L76](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/docs/cli.md#L55-L76)).
- Readiness probe: `pi auth check --provider <id> --json` prints `ready`, `not_ready` or `invalid` with exit code 0/1/2 and can refresh OAuth tokens ([cli.md L293-L316](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/docs/cli.md#L293-L316)). `pi auth print-api-key` / `print-bearer-token` print secrets to stdout; HolyAgent should not use them.
- RPC: `get_available_models`, `set_model`, `set_thinking_level` ([rpc-commands.md L208-L330](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/docs/rpc-commands.md#L208-L330)).
- Extension / SDK: `ctx.modelRegistry.getAvailable()`, `find(provider, id)`, `hasConfiguredAuth()`, `getProviderAuthStatus()`, `streamSimple()`, `complete()`, `classify()` ([model-registry.ts L64-L180](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/src/core/model-registry.ts#L64-L180)). Extensions may make nested model calls with `ctx.modelRegistry.streamSimple()` ([extensions.md L327](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/docs/extensions.md#L327)).
- Custom endpoints: `models.json` for OpenAI-, Anthropic- or Google-compatible APIs; `pi.registerProvider()` for custom APIs/OAuth; `pi.registerVirtualModel()` for a model that routes each request to a physical model ([models.md L45-L60](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/docs/models.md#L45-L60), [custom-provider.md](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/docs/custom-provider.md), [virtual-models.md L1-L30](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/docs/virtual-models.md#L1-L30)).

Decided for 0.3.0: a role's model and effort map one to one to `--model <provider/id>:<thinking>` (or `set_model` and `set_thinking_level` over RPC), through the single mapping described under [Kimi for Coding (global)](#kimi-for-coding-global); Pi's catalog is the source of truth for which model ids exist, so HolyAgent validates role-to-model choices at launch with `--list-models` or `getAvailable()`. Pi's thinking scale (`off` to `max`) is a superset of Kimi's `low`, `high` and `max`; the plan uses only those three, and never `low` for a specialist on `kimi-for-coding`.
