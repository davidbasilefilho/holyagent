# Pi providers and models

**Status: the Kimi provider and the Codex provider, their readiness and catalog checks and the routing are implemented in `packages/runtime/src/pi/`, and the extension runs the checks and sets the provider's variables at session start; the instructions are in `packages/runtime/src/instructions/kimi-k3.1` and `gpt-6`. The Kimi section and [Routing](#routing) describe Kimi; [Codex](#codex-openai-codex) describes the Codex provider. The sections after them are research on Pi's provider layer and are not shipped behaviour.**

Pi 1.4.0, commit `4a080252f06caf63a525d7873c5d94d3c23887e0` for the Pi source facts (the plan pins 1.5.0; see [README.md](README.md#version-risk)). Kimi facts are from the research of 2026-11-07, and the pages it fetched carried no dates unless a line says so. "Inference:" marks a conclusion drawn here, not a stated fact.

## Kimi for Coding (global)

Kimi for Coding (global) is the default provider, and the only one in 0.3.0; [Codex](#codex-openai-codex) is the second. Other providers are later work and are not documented as supported. The maintainer asked whether a maintained Pi extension already gives a full Kimi for Coding global integration; one does, so the plan installs it and builds no provider.

**The provider is Pi's built-in `kimi-coding` with `pi-provider-kimi-code` pinned on top (an exact release) and `KIMI_CODE_REGION=global`.** Requests then go to `https://api.kimi.ai/coding/v1`, Moonshot's overseas host; `api.kimi.com` is mainland China ([Kimi Code models](https://www.kimi.com/code/docs/en/kimi-code/models)).

Points the research leaves open, to be settled when the package is built:

- **The built-in provider's API type.** One read of the source at commit `209bc7b9` gives `api.kimi.com/coding` with the `anthropic-messages` API ([kimi-coding.ts](https://github.com/earendil-works/pi/blob/209bc7b9/packages/ai/src/providers/kimi-coding.ts)); another read of `main` gives `https://api.kimi.com/coding/v1` over `openai-completions`. Which one holds matters only for the caching inference in [caching-and-subagents.md](caching-and-subagents.md#cache-target), which is conditional on the API type; confirm it against the pinned Pi.
- **Pi 1.5.0 compatibility of the extension.** Its v0.6.13 is bumped to Pi 0.99.2. Whether it works unchanged on 1.5.0, and whether Pi's catalog lists `k3.1-pro` for the extension, is checked by the launch-time catalog validation and by the recorded fixtures. The extension's own fallback model list omits `k3.1-pro`; its README says the live catalog `https://api.kimi.com/coding/v1/models` is authoritative.
- **The extension overrides the built-in** `kimi-coding` registration of the same id (its legacy registration), which the pin has to be checked for.
- **Single-maintainer risk** of the extension, and the data the Moonshot-side tools send to Moonshot's services (they are off by default).

How HolyAgent uses the provider:

- It reaches the provider only through Pi's own provider layer, with `--model <provider/id>:<thinking>` (or `set_model` and `set_thinking_level` over RPC). It never calls provider URLs, never reads `auth.json` and never uses `pi auth print-api-key` or `print-bearer-token`.
- At the start of a root session, the extension runs `pi auth check --provider <id> --json` (exit 0 ready, 1 not ready, 2 invalid) through `requireProviderReady`. A provider that is not ready is reported as a notice with the fix, without blocking startup, and is never replaced silently.
- Once the provider is ready, the extension validates the route table's model ids against the user's catalog (`pi --list-models`) with `validateModelCatalog` and hard-codes none; a model the catalog lacks is a notice with the fix.
- One mapping turns a route-table model and effort into a `provider/id` and a thinking level, so choosing another provider later changes that mapping only.
- Selecting the provider in `config.json` enables `pi-provider-kimi-code`; deselecting it disables the extension ([configuration.md](configuration.md#holyagent-configjson)).

### In the code

`packages/runtime/src/pi/` holds the integration's whole provider layer; `provider.ts` is the only place a provider is named.

- **Mapping.** `routeModel(config, row)` turns a route-table row into the `--model` value `kimi-coding/<model>:<thinking>` (for example `kimi-coding/k3.1-pro:high`). A model id in the config is up to 128 characters of letters, digits and `.`, `_`, `-`, `:`, `/`, `@` and `+`, starting with a letter or digit; anything else is refused when the config is decoded, since the id reaches `--model`, the model's context and the notices. Kimi Code takes the table's `low`, `high` and `max` as they are.
- **Environment.** `providerEnv(config)` is applied by the extension to the process environment when the session's config has been read at start, before the readiness probes start (Pi's `exec` hands them the process environment), for the root and for every child, with a value the user set kept: `KIMI_CODE_REGION=global`, so requests go to `api.kimi.ai` and login to `auth.kimi.ai`.
- **Extension.** `providerSource(config)` is `npm:pi-provider-kimi-code@0.6.13`, an exact pin read from `pi-packages.json` (the table `piPackages` reads too, so the two cannot disagree) and moved only by `mise run deps:update`; `piPackages` returns the extension's pinned source while `pi.enable` is on and nothing when it is off.
- **Login.** `providerReadiness` and `requireProviderReady` run `pi auth check --provider kimi-coding --json`: exit 0 is ready, 1 is not ready (the fix is `/login kimi-coding` in Pi for the OAuth login the Moonshot-side tools need, or `KIMI_API_KEY` as the fallback) and 2, or any other exit, is invalid. The provider is never replaced, and the credential is never read or printed. The extension runs the probes beside the session with `pi.exec` (it runs under Node and has no Bun Shell); they have a deadline of their own, as long as the collection's, and a probe that cannot start (a missing `pi` too, which Pi's `exec` reports as exit 1 with the spawn error), is stopped or times out is not reported, since it says nothing about the provider ([extensions.md](extensions.md#the-root-on-pi)).
- **The root's own model.** The root starts on the route table's `root` row through Pi's settings, not through a launch argument: `holyagent setup` writes `defaultProvider`, `defaultModel` and `defaultThinkingLevel` from `routeModel(config, "root")` into Pi's `settings.json` ([installation.md](installation.md#what-setup-and-doctor-do)): the provider and the model together only when you set neither, and the thinking level where it is unset and differs from Pi's default, so a provider or model you chose wins and T3 Code's picker stays manual; the extension never calls `setModel`.
- **Catalog.** `pi --list-models` prints a table, `provider model context max-out thinking images`, with the models of providers that have credentials only, so readiness comes first. `validateModelCatalog` reads the rows (a line with as many columns as the header whose first two are a provider id and a model id; a footer or note is ignored) and requires every `provider/model` of the route table to be one; each missing id is a blocker that names the rows using it. A successful listing with no row at all is reported as no models listed, most likely because no provider has credentials, not as missing ids. A listing in a format the parser does not recognise is reported as `ListingNotRecognised`. A failing `pi` or readiness check reports what it printed (standard error, then standard output, cut to 400 characters). The extension's notice names the missing models without their rows (`ModelsNotInCatalog.brief`), so the fix is not cut off at the notice's 400 characters; a listing that fails or is not recognised adds no notice.
- **Cache rule.** A session keeps the one model and effort of its row from launch to its end, because changing either invalidates Kimi's context cache.

### Models and efforts

Source for the rows: [Kimi Code models](https://www.kimi.com/code/docs/en/kimi-code/models) (K3.1 Pro rollout; K2.8 Preview rollout 2026-09-11).

| Model id                    | Version             | Context                                                 | Notes                                          |
| --------------------------- | ------------------- | ------------------------------------------------------- | ---------------------------------------------- |
| `k3.1-pro`                  | K3.1 Pro            | 1,048,576 on Pro+/Allegretto+; 262,144 on Plus/Moderato | Thinking only                                  |
| `k3.1-pro-highspeed`        | K3.1 Pro Highspeed  | Up to 1,048,576                                         | About 2-3x speed for about 2x quota; Pro+ only |
| `k3`                        | K3                  | 1M or 256K by tier                                      |                                                |
| `k3-256k`                   | K3                  | 262,144                                                 |                                                |
| `kimi-for-coding`           | K2.8 Preview        | Up to 1,048,576                                         | The same id, upgraded in place                 |
| `kimi-for-coding-highspeed` | K2.7 Code Highspeed | 262,144                                                 |                                                |

- **Efforts** are `low`, `high` and `max`. Kimi Code's default is `high` for K3.1 Pro and K3 and `max` for `kimi-for-coding`; the platform API's own reference defaults K3.1 Pro to `max`, so the two sources conflict. K3.1 Pro rejects thinking-off with a 400. The other models route a thinking-off request, and a mistyped model id, to K2.8 Preview without thinking. Kimi Code maps `xhigh`, `ultra` and `max` to `max`, and `medium` and `high` to `high` ([reasoning effort](https://platform.kimi.ai/docs/guide/use-reasoning-effort), [Kimi Code models](https://www.kimi.com/code/docs/en/kimi-code/models)).
- **What an effort costs is unknown.** Moonshot gives no numbers per level for quality, latency, tokens or quota, no advice on when to use `max`, and every published K3.1 Pro benchmark uses `max` ([quickstart](https://platform.kimi.ai/docs/guide/kimi-k3-1-pro-quickstart), [model card](https://huggingface.co/moonshotai/Kimi-K3.1-Pro)). The root's `max` against `high` is to be measured (see [Routing](#routing)).
- **Quota** is a subscription with a 5-hour rolling window and a monthly quota; legacy plans also keep a weekly window; high-speed variants burn quota faster ([error reference](https://www.kimi.com/code/docs/en/kimi-code/error-reference.html), and a third-party page, [2026-08-23](https://kimi-ai.free/use-cases/developers/)). Per-plan prices are unknown from official sources.
- Image and video input works on all models except `k3-256k`, which takes images only.
- Changing the model or the effort in a session invalidates the context cache ([caching-and-subagents.md](caching-and-subagents.md#cache-target)).

## Routing

**Status: decided for 0.3.0; the table lives in the `config.json` defaults, so it can change without code** ([configuration.md](configuration.md#holyagent-configjson)). It replaces the Claude route table's `haiku`, `sonnet` and `opus` and their efforts for sessions on Kimi. The maintainer's words: "not kimi-for-coding-low, either high or max, kimi k3.1 pro low-high, assess if max is worth it for root".

| Role                  | Model             | Effort | Reason                                                                                      |
| --------------------- | ----------------- | ------ | ------------------------------------------------------------------------------------------- |
| Root                  | `k3.1-pro`        | high   | The strongest model plans, decides and makes the final pass; `max` is selectable, see below |
| Worker.implementation | `kimi-for-coding` | max    | Writes the change that gets merged, so depth is worth the tokens                            |
| Worker.debugging      | `kimi-for-coding` | max    | Finding a root cause is the deepest reasoning a worker does                                 |
| Worker.integration    | `kimi-for-coding` | max    | Spans several systems and contracts, where a missed interaction is the common failure       |
| Reviewer.code         | `kimi-for-coding` | max    | Judges correctness and maintainability; a missed defect costs more than the tokens          |
| Reviewer.security     | `kimi-for-coding` | max    | Judges trust boundaries, where a missed finding costs the most                              |
| Reviewer.testing      | `kimi-for-coding` | max    | Judges whether tests prove the behavior, which needs the same depth as the code             |
| Reviewer.artifact     | `kimi-for-coding` | max    | Judges an instruction or document against its requirements, where wording errors are subtle |
| Worker.mechanical     | `kimi-for-coding` | high   | Bounded edits with a known recipe; extra effort adds cost, not quality                      |
| Worker.validation     | `kimi-for-coding` | high   | Runs the gates and reports their output; the work is execution                              |
| Worker.operations     | `kimi-for-coding` | high   | Runs commands along a documented procedure                                                  |
| Explorer.map          | `kimi-for-coding` | high   | Reads the repository and reports its layout                                                 |
| Explorer.lookup       | `kimi-for-coding` | high   | Answers a narrow question from files                                                        |
| Explorer.trace        | `kimi-for-coding` | high   | Follows one flow through the code; bounded reading                                          |
| Librarian.lookup      | `kimi-for-coding` | high   | Fetches one fact from documentation                                                         |
| Librarian.research    | `kimi-for-coding` | high   | Gathers and compares sources; the root judges the result                                    |
| Reviewer.audit        | `kimi-for-coding` | high   | Checks records against evidence rather than judging a design                                |
| Worker.visual         | `k3.1-pro`        | low    | The root makes the final visual pass, so the specialist stays cheap                         |
| Reviewer.visual       | `k3.1-pro`        | low    | The same: the root makes the final visual pass                                              |

The table is `KIMI_ROUTES` in `packages/runtime/src/config/schema.ts`, the defaults of `pi.routes` in `config.json`; any row can be overridden there.

- **Specialists run on `kimi-for-coding`, which is Kimi K2.8 Preview, never at low, except the two visual specialists, which run on `k3.1-pro` at low (below).** The root runs on K3.1 Pro. The maintainer decided the grouping (roles that write or judge code at max, mechanical, checking, lookup and research roles at high); the reasons in the table are the rationale for it, not separate sources.
- **Both visual specialists run at low** because the root makes the final visual pass. The maintainer's words: "both visual specialists must be low, as root does the final review pass".
- **Visual tools.** Under T3 Code the two visual specialists use T3's `preview_*` browser, and only they get the computer-use tools of `@amaster.ai/pi-computer-use` ([t3-code.md](t3-code.md#browser), [t3-code.md](t3-code.md#computer-use-through-cua-driver)).
- **The root's effort is `high`.** `max` is selectable in `config.json`. A later 0.3.x task will measure high against max on real sessions before `max` becomes the default; until then the cost and benefit of `max` for the root are unmeasured.
- **A session keeps one model and effort.** Each Assignment's specialist is launched on its row and is not switched mid-session, because a switch invalidates Kimi's cache.
- **Provider-agnostic structure stays.** The table maps a role to a model and an effort through the one mapping described above; other providers would add rows later and are not part of 0.3.0.

## Instructions for Kimi K3.1

**Status: decided for 0.3.0.** The maintainer's words: "for the pi integration we will need kimi k3.1 specific instructions following its official instruction guide".

- **Moonshot has no K3.1-specific prompting guide.** The instruction set follows four Moonshot guides and cites the section each rule follows, the way the Claude 5.5 set cites Anthropic's guidance: the [prompt best-practice guide](https://platform.kimi.ai/docs/guide/prompt-best-practice) (undated; clear instructions, roles, explicit steps, few-shot examples, length by paragraphs or bullets, reference text, summarizing long histories), the [K3.1 Pro quickstart](https://platform.kimi.ai/docs/guide/kimi-k3-1-pro-quickstart) the [agent-setup guide](https://platform.kimi.ai/docs/guide/use-kimi-k3-to-setup-agent) and the [tool-calling best-practice guide](https://platform.kimi.ai/docs/guide/kimi-k3-tool-calling-best-practice); `packages/runtime/src/instructions/kimi-k3.1/guide.md` lists the points of all four.
- **It is a separate set.** A per-model folder of the Pi instruction text sits beside `packages/runtime/src/instructions/claude-5.5` (for example `kimi-k3.1/`) and is written to Moonshot's guides, not adapted from the Claude 5.5 wording. The Pi package builds the specialists' agent files and the `session` role's core of the root rules from it; the root's own system prompt is built from the same set (`PI_ROOT_PROMPT`). The `kimi-for-coding` (K2.8 Preview) specialists load the same set; see [the K2.8 Preview specialists](#the-k28-preview-specialists).
- **It follows the agent guide's structure.** Each role gets a short system prompt that keeps to the role, the workflow and the quality boundaries; argument details go in tool descriptions and the rest in on-demand skills.
- **Request constraints from the quickstart** ([quickstart](https://platform.kimi.ai/docs/guide/kimi-k3-1-pro-quickstart), [reasoning effort](https://platform.kimi.ai/docs/guide/use-reasoning-effort)): thinking is always on and is set with the top-level `reasoning_effort`, so a request does not send `thinking`; `temperature` (1.0), `top_p` (0.95) and `n` (1) are fixed and are omitted; `max_completion_tokens` defaults to 131072 and can go up to 1048576; the whole assistant message, `reasoning_content` and `tool_calls` included, is passed back unchanged; vision does not accept public image URLs. Inference: Pi's provider layer and the extension build the request, so HolyAgent sets only the model and the effort.
- Moonshot's [tool-calling guide](https://platform.kimi.ai/docs/guide/kimi-k3-tool-calling-best-practice) says to pick the effort before the conversation starts, which matches the one-effort-per-session rule.

### The K2.8 Preview specialists

**Status: decided for 0.3.0.** The maintainer's rule: "separate k2.8 or k2.7, or k2.6, k2.5, whichever is more relevant. if k3 or k3.1 is more relevant, we should use it. it depends on how the model behaves". Research of 2026-11-07 resolved it: the specialists on `kimi-for-coding` (K2.8 Preview) load the same Kimi instruction set, written to the K3/K3.1 guides above plus Moonshot's [K3 tool-calling best-practice guide](https://platform.kimi.ai/docs/guide/kimi-k3-tool-calling-best-practice). The K2.6/K2.7 [thinking guide](https://platform.kimi.ai/docs/guide/use-thinking-models) does not apply; it covers only `kimi-k2.7-code` and `kimi-k2.6`.

Why K2.8 Preview counts as K3-like, from how it behaves:

- Moonshot describes K2.8 Preview as "performance close to K3 with more efficient thinking", with efforts `low`, `high` and `max` "consistent with K3" ([Kimi Code models](https://www.kimi.com/code/docs/en/kimi-code/models), [what's new](https://www.kimi.com/code/docs/kimi-code/whats-new.html), Chinese, 2026-09-11 entry).
- It is controlled with the top-level `reasoning_effort` (default `max`), as K3 is; K2.6 and K2.7 use the `thinking` parameter, and K2.7 has no adjustable effort ([Kimi Code models](https://www.kimi.com/code/docs/en/kimi-code/models), [models overview](https://platform.kimi.ai/docs/api/models-overview)).
- Its context is up to 1,048,576 tokens, like the K3 series; K2.6 and K2.7 have 256K ([Kimi Code models](https://www.kimi.com/code/docs/en/kimi-code/models), [models overview](https://platform.kimi.ai/docs/api/models-overview)).

Limits of that finding:

- Moonshot has no K2.8-specific prompting guide, and no model card or changelog says whether K2.8 Preview shares post-training with K2.x or K3. The choice rests on documented behavior, not on lineage.
- The instruction text must not rely on forcing a first-round tool call with `tool_choice` `required`. A secondary source, not Moonshot, says K2.8 Preview accepts only `auto` or `none` ([Tencent Cloud](https://intl.cloud.tencent.com/document/product/1300/80635)); Moonshot's own parameter page confirms `required` only on K3 ([models overview](https://platform.kimi.ai/docs/api/models-overview)).
- The request constraints above are written for K3.1 Pro. For K2.8 Preview the same secondary source gives `max_tokens` (default 32768) in place of `max_completion_tokens` and accepts public image URLs, so the instruction text leaves request settings out; Pi's provider layer and the extension build the request.
- To be verified: the tool-calling and parallel-call specifics on K2.8 Preview, and whether the platform's `kimi-k2.8-preview` behaves as the Kimi Code `kimi-for-coding` endpoint does (the secondary source covers the platform id).

## Codex (`openai-codex`)

**Status: implemented in 0.3.1.** `pi.provider` set to `"openai-codex"` runs the root and the specialists on Pi's built-in ChatGPT-subscription provider of that id. HolyAgent adds no package for it, so there is no third-party pin to move: the three models are in Pi's catalog (1.5.0 lists `gpt-6.1-sol`, `gpt-6.1-terra` and `gpt-6-luna`), and what HolyAgent adds is its own module, `packages/runtime/src/pi/codex/` (pure, tested from fixtures) with the extension glue in `packages/integrations/pi/src/codex.ts`. Choosing the Kimi provider again turns all of it off, because every handler of the module returns at once unless the config selects Codex.

```json
{ "pi": { "provider": "openai-codex" } }
```

**Login.** The provider uses a ChatGPT sign-in, not an API key: run `/login openai-codex` in Pi and sign in with the account that has Codex. The readiness check is `pi auth check --provider openai-codex --json` (exit 0 ready, 1 not ready with that fix, 2 or anything else invalid), the same probe as for Kimi, and HolyAgent never reads or prints the credential. The one place the module uses the token is the Luna Reserve status request below, which asks Pi's own credential store for it, sends it in an `authorization` header to the ChatGPT backend and puts it in no message or notice.

**Models and routing.** The root runs on GPT-6.1 Sol at high. Each specialist runs on GPT-6.1 Terra from medium to `xhigh`, or on GPT-6 Luna from low to high (Luna never runs at `xhigh`). Visual work and computer use run on Terra. The table is the default of the `pi.routes` rows of a config that selects Codex (`CODEX_ROUTES`), approved by the maintainer; a row that a file overrides keeps the table's value for the key it leaves out:

| Row                                                                                                   | Model           | Effort |
| ----------------------------------------------------------------------------------------------------- | --------------- | ------ |
| `root`                                                                                                | `gpt-6.1-sol`   | high   |
| `Explorer.map`, `Explorer.lookup`, `Librarian.lookup`, `Worker.validation`                            | `gpt-6-luna`    | low    |
| `Worker.mechanical`, `Worker.operations`                                                              | `gpt-6-luna`    | medium |
| `Reviewer.audit`                                                                                      | `gpt-6-luna`    | high   |
| `Explorer.trace`, `Librarian.research`, `Worker.integration`, `Reviewer.testing`, `Reviewer.artifact` | `gpt-6.1-terra` | medium |
| `Worker.implementation`, `Reviewer.code`, `Worker.visual`, `Reviewer.visual`                          | `gpt-6.1-terra` | high   |
| `Worker.debugging`, `Reviewer.security`                                                               | `gpt-6.1-terra` | xhigh  |

An Assignment that carries the screen capability runs on Terra at medium or above, whatever its role ([screen.md](screen.md#the-route)); no row of this table applies it. The launch-time catalog check validates these ids against `pi --list-models` like the Kimi ones.

**Instructions.** The root's prompt, each specialist's prompt and the skills Pi lists are the GPT-6 family's (`packages/runtime/src/instructions/gpt-6`). The Pi package ships the Kimi family as its own `agents/` and `skills/` and the GPT-6 copies below `families/gpt-6/`; the extension swaps a Codex session onto them: the root gets the family's prompt, a specialist's own prompt is replaced by the family's one for the same agent (whatever Pi adds around it stays), and the `SKILL.md` paths of the skill list are pointed at the family's folder. A skill that a person runs with `/skill:<name>` is still the package's own (Kimi) copy, since Pi reads that file itself.

**Tools.** `apply_patch` is Codex's patch format: `*** Begin Patch`, then `*** Add File:`, `*** Delete File:` and `*** Update File:` operations (with `*** Move to:`, `@@` hunks with context, and `*** End of File`), then `*** End Patch`. It runs in the extension (`packages/runtime/src/pi/codex/apply-patch.ts`), needs no binary, takes relative paths below the working directory only (also once symbolic links are resolved: the real path of each target, or of its nearest existing ancestor, must stay inside the project, so a link cannot carry a write out of it), plans the whole patch in memory first and writes only if every hunk matches, and puts back the files it already wrote if a later write fails, so a failed patch changes nothing (folders it created stay). A `*** Move to:` that names the file's own path is a plain update. The writes go through Bun's file API. Hunks match exactly, then ignoring trailing and surrounding whitespace, then with typographic dashes and quotes read as ASCII. It is added beside Pi's `read`, `write`, `edit` and `bash` for the specialists that have Write (`Worker.mechanical`, `Worker.implementation`, `Worker.integration`, `Worker.debugging`, `Worker.visual`); the root writes no files and never has it. The tool is registered inactive for every provider and a Codex specialist session activates it; if that fails, the specialist is told on its first run and goes on with `write` and `edit`. The specialists' agent files list no entry for it, since the extension activates it.

**`context_management`.** For a Codex request, the module adds `context_management: [{ "type": "compaction", "compact_threshold": N }]` (N is 90% of the model's window) **only while Billion Context is off** (`pi.features.contextCompression` false) and its own switch, `pi.features.contextManagement` (on by default, the `context-management` capability, listed only under Codex), is on; with Billion Context on, the default, no request carries the parameter. The maintainer's rule: the two work differently, and Billion Context is preferred. It compresses the history on the client and keeps it retrievable (its `compress`, `decompress` and `search_context` tools), while the server-side compaction replaces the history with an opaque encrypted item that cannot be searched or expanded, and both rewrite the same request. When the parameter is on, the module keeps the compaction item the server emits and, in the next requests, sends it in place of the input items it stands for (the server compacts before it answers, so the item stands for the request's whole input), until Pi's own history changes (a Pi compaction, a branch), which clears it. Pi's compaction and Billion Context's cancelling of it are untouched.

**Luna Reserve.** The reserve is a separate fallback allowance for Luna that opens once the regular quota is used up (the backend serves it under the model id `gpt-reserve`). The capability `luna-reserve` (`pi.features.lunaReserve`, on by default, listed by `holyagent setup` and `doctor` only under Codex) works like this: when a turn ends on a usage-limit error, the module asks the ChatGPT backend's usage status (`GET https://chatgpt.com/backend-api/wham/usage`) whether the reserve is offered (`rate_limit_upsell.banner_type` is `luna_reserve`); if it is, later requests are sent with the model `gpt-reserve` (their reasoning effort lowered to `high` when above it: Luna never runs at `xhigh`, and the research names no other limit of the reserve, so `high` is a ceiling kept without a measurement) and the user is told to send `continue`. Only a turn that ran on Codex can open it, and a new session starts on the regular model. The status request refuses redirects, so the token goes to that host only. It never redeems reset credits. At each later run it asks again, and when the offer is gone (ordinary usage is back) the requests use the regular model again; a status call that fails keeps whichever state the session is in. The usage endpoint and the banner value come from third-party reports of the backend and a README, not from an OpenAI specification (the research could not read the source), so both are one constant each in `luna-reserve.ts`.

**Auto-review.** The capability `auto-review` (`pi.features.autoReview`, on by default, listed by `holyagent setup` and `doctor` only under Codex) reproduces Codex's own auto-review (its "guardian"): before a risky tool call runs, the `codex-auto-review` model, the reviewer Codex itself uses, judges the exact call and either lets it run or blocks it. It is a `tool_call` gate in the Pi integration (`packages/integrations/pi/src/auto-review.ts`, over `packages/runtime/src/pi/codex/auto-review/`), registered after every other gate so a call they refuse is never sent to review. The maintainer's rule: it works as Codex's does, with no rule list for the user to write.

- **What is reviewed.** Codex reviews only what its sandbox would otherwise stop and ask a human about: escalated commands, edits outside the writable roots, network access that needs approval, and MCP tools whose annotations need approval. Pi has no sandbox, so a classifier (`classify.ts`) stands in for that signal, and everything it does not pick runs without review:

  | Trigger              | Sent to review                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
  | -------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
  | `command`            | A `bash` or `powershell` command outside the read-only safe set. The set is Codex's known-safe list: `cat`, `ls`, `grep`, `head`, `tail`, `wc`, `echo`, `pwd` and the like, `find` without `-exec` or `-delete`, `rg` without `--pre`, a read-only `git` subcommand (`status`, `log`, `diff`, `show`, ...), `sed -n Np`, joined only by `;`, `&&`, `\|\|` or a pipe. Any redirection, substitution, variable or other shell syntax sends the command to review. |
  | `write-outside-root` | `write`, `edit` or `apply_patch` of a path (a patch's move target included) outside the project root, the session's working directory; `~` paths count as outside, and symbolic links are not resolved.                                                                                                                                                                                                                                                         |
  | `network`            | A command that uses the network (`curl`, `git push`, `npm install`, ...) and the web tools (`web_*`, `moonshot_search`, `moonshot_fetch`).                                                                                                                                                                                                                                                                                                                      |
  | `tool-approval`      | A tool of an MCP server whose annotations need approval: Codex's rule, anything that is not `readOnlyHint` and is destructive or open-world, with the MCP defaults (destructive and open-world) for a hint the tool leaves out.                                                                                                                                                                                                                                 |

- **What the reviewer sees.** A request to `chatgpt.com/backend-api/codex/responses` with the session's own Codex token, on the model `codex-auto-review` at low reasoning effort, with a strict `json_schema` answer. The instructions are Codex's policy template (`policy-template.md`) with Codex's default tenant policy (`policy.md`) in its slot and an output contract after it (no tools are offered, since Pi runs no read-only session for the reviewer). The one user message holds a transcript labelled as untrusted evidence between `>>> TRANSCRIPT START` and `END`, then the exact action as JSON (the tool, the working directory, the trigger and its reason, the input with every string cut to 16k tokens) between `>>> APPROVAL REQUEST START` and `END`. The transcript is Pi's session history without the model's reasoning: the user's messages, the assistant's text, and the tool calls with their results, kept to Codex's caps: 10k tokens for messages and 10k for tool entries, 2k per message entry and 1k per tool entry, the last 40 non-user entries, the first and the latest user message always, and a truncation marker in anything cut. The answer must be a `GuardianAssessment` with exactly the four fields `risk_level` (`low`, `medium`, `high`, `critical`), `user_authorization` (`unknown`, `low`, `medium`, `high`), `outcome` (`allow`, `deny`) and `rationale`, decoded strictly with Effect Schema (Codex fills missing fields in; here a missing or unknown field is an invalid assessment).
- **Policy text.** `pi.autoReview.policy` in `config.json` replaces Codex's default tenant policy; `pi.autoReview.extraPolicy` is added after whichever policy stands (Codex's `[auto_review].policy` and `extra_policy`). Both are markdown for the reviewer; a blank value counts as absent, and the template's thresholds apply wherever the text defines no stricter rule: low and medium allow, high allows only with at least medium authorization and a narrow action, critical denies.
- **Decisions.** An allow runs the tool. A deny blocks it with Codex's rejection text, `This action was rejected due to unacceptable risk.`, the reason, and instructions to the model that forbid a workaround and allow only a materially safer path or the user's explicit approval. A review that outlasts 90 seconds is not a denial: the call is blocked with Codex's timeout text (do not assume the action is unsafe, retry once or ask the user), the breaker's count of denials in a row ends, and a retry is reviewed again; a retry that times out too is told to ask the user instead. Any other failure (no Codex login, a failed or refused request, a stream with no message, an invalid assessment, a defect in the client) denies closed as a high-risk, unknown-authorization denial whose reason is `Automatic approval review failed: ...`; Codex does not count it toward the breaker, and neither does this module. The user reads each verdict as a notice.
- **The breaker.** After 3 denials in a row or 10 in one turn (a Pi agent run) the module stops the turn (`ctx.abort()`, and `terminate` on the blocked call) once, with a notice; an allow or a timeout ends the run of denials, and a new agent run starts the counts at zero.
- **The override.** `/approve` approves the latest denied action for one retry; `/approve list` shows the last ten denied actions, newest first, and `/approve <n>` approves the nth. The retry is still reviewed, now with Codex's marker (`The user has manually approved a specific action that was previously 'Rejected'.`) and the action in its transcript, and the policy says such a clear re-approval outranks the other rules. The approval covers exactly that action, once; a timeout keeps it for the next try.
- **Turning it off.** `holyagent setup --auto-review off` or `pi.features.autoReview: false` removes the gate entirely: with no policy held, the handler returns before it classifies anything, so no call is reviewed and the backend is never asked; `/approve` then says auto-review is off. It is its own switch: it has no bearing on `context-management` or Luna Reserve, and under another provider it is not listed and does nothing.
- **Not the same as Codex.** Without a sandbox the classifier replaces Codex's escalation signal, so it is deliberately broad: a command outside the safe set is reviewed even where Codex would have run it in its sandbox. The reviewer runs on the Codex backend with no tools and no reused review session, so it cannot make Codex's read-only checks, and it sees the history of the Pi session as the transcript. Codex's policy template and default policy are Apache-2.0 text of openai/codex ([attributions.md](../attributions.md#other-software)); the formatter adds blank lines after their headings.

**Not in this provider.** The other 0.3.1 modules are separate changes. Web tools come from `pi-web-kit`, since the provider has none: the package reads one agent file per specialist whatever the provider, so a role with Search lists the web tools of every provider's source (`ext:pi-provider-kimi-code/moonshot_*` and `ext:pi-web-kit/web_*`), and the entries of the extension a session did not load match nothing.

## Provider model in one paragraph

A _provider_ is the service/account, a _model_ is what it serves. Users connect with `/login` (OAuth or API key, stored in `auth.json`) or with environment variables, then pick a model with `/model` ([models.md L5-L35](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/docs/models.md#L5-L35), [providers.md L10-L18](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/docs/providers.md#L10-L18)). Pi ships a bundled model catalog and overlays newer data from pi.dev; `pi update --models` forces a refresh ([models.md L15](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/docs/models.md#L15)). The catalog is also browsable at [pi.dev/models](https://pi.dev/models).

## Other providers

Other providers are not supported beyond Kimi for Coding and Codex. The earlier research on the Codex and ChatGPT subscription providers and on `gpt-6-luna` was for the auto-mode reviewer, which was dropped ([auto-mode.md](auto-mode.md)), so it is no longer kept here. ## Selecting models from a host

- CLI: `--provider`, `--model <pattern>` (exact id, fuzzy match, `provider/id`, optional `:<thinking>` suffix), `--thinking off|minimal|low|medium|high|xhigh|max`, `--models` (cycling scope), `--list-models [search]`; thinking is clamped to what the model supports ([cli.md L55-L76](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/docs/cli.md#L55-L76)).
- Readiness probe: `pi auth check --provider <id> --json` prints `ready`, `not_ready` or `invalid` with exit code 0/1/2 and can refresh OAuth tokens ([cli.md L293-L316](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/docs/cli.md#L293-L316)). `pi auth print-api-key` / `print-bearer-token` print secrets to stdout; HolyAgent should not use them.
- RPC: `get_available_models`, `set_model`, `set_thinking_level` ([rpc-commands.md L208-L330](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/docs/rpc-commands.md#L208-L330)).
- Extension / SDK: `ctx.modelRegistry.getAvailable()`, `find(provider, id)`, `hasConfiguredAuth()`, `getProviderAuthStatus()`, `streamSimple()`, `complete()`, `classify()` ([model-registry.ts L64-L180](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/src/core/model-registry.ts#L64-L180)). Extensions may make nested model calls with `ctx.modelRegistry.streamSimple()` ([extensions.md L327](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/docs/extensions.md#L327)).
- Custom endpoints: `models.json` for OpenAI-, Anthropic- or Google-compatible APIs; `pi.registerProvider()` for custom APIs/OAuth; `pi.registerVirtualModel()` for a model that routes each request to a physical model ([models.md L45-L60](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/docs/models.md#L45-L60), [custom-provider.md](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/docs/custom-provider.md), [virtual-models.md L1-L30](https://github.com/earendil-works/pi/blob/4a080252f06caf63a525d7873c5d94d3c23887e0/packages/coding-agent/docs/virtual-models.md#L1-L30)).

Decided for 0.3.0: a role's model and effort map one to one to `--model <provider/id>:<thinking>` (or `set_model` and `set_thinking_level` over RPC), through the single mapping described under [Kimi for Coding (global)](#kimi-for-coding-global); Pi's catalog is the source of truth for which model ids exist, so HolyAgent validates role-to-model choices at launch with `--list-models` or `getAvailable()`. Pi's thinking scale (`off` to `max`) is a superset of Kimi's `low`, `high` and `max`; the plan uses only those three, and never `low` for a specialist on `kimi-for-coding`.
