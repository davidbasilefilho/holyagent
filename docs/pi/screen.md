# The screen capability and browser use

**Status: ships in 0.3.1.** An Assignment can carry the screen capability. Its specialist then has the tools that see and drive a screen, whatever its role, and under the Codex provider it runs on GPT-6.1 Terra. The tools belong to three capabilities of the registry ([configuration.md](configuration.md#capabilities)), split by what they drive, and the browser tools differ by the form of the machine ([Forms](#forms)):

| Tools                                                                                    | Capability     | They drive                                                                                       | Form          |
| ---------------------------------------------------------------------------------------- | -------------- | ------------------------------------------------------------------------------------------------ | ------------- |
| `computer_use_*` (`@amaster.ai/pi-computer-use`)                                         | `computer-use` | Desktop applications and the browser's native chrome (tabs, address bar, dialogs)                | `normal` only |
| `mcp__browse__*` (opencode browse, `@opencode/browse`)                                   | `browser-use`  | The content of a web page in the user's real browser, with its logins and extensions             | `normal`      |
| `mcp__browser_use__browser_exec`, `mcp__browser_use__browser_screenshot` (`browser-use`) | `browser-use`  | A headless Chromium that HolyAgent starts, with a temporary profile; no desktop, no real browser | `headless`    |
| T3's `preview_*`, `t3_preview_*`, `html_render`, `html_preview`                          | `mcp`          | The page shown in T3 Code, and HTML rendered there; only where T3 hosts the session              | both          |

T3's device tools stay with the visual roles and are not part of the screen capability. Every one of the three was already switchable on its own (`pi.features.computerUse`, `pi.features.browserUse`, `pi.features.mcp`); a capability that is off adds nothing to the grant. The MCP servers run in Pi's built-in MCP extension, so with `pi.features.mcp` off no server is registered and no `mcp__` tool is granted, in either form; setup and doctor say so ([Reported states](#reported-states)).

## Asking for it

The draft of an Assignment takes `screen: true` (`assignment create` and `assignment dispatch`; the field is stored only when set and is shown by `assignment show --full`). The root sets it for work that has to see or drive a screen and leaves it off for everything else: `R-SCREEN` in the requirements tree, translated in every model family's `root/assignments.md`.

- **The dispatch names another agent.** For a screen Assignment it prints the role's agent with `-screen` on a machine with a graphical session (`worker-implementation-screen`) and with `-headless-screen` on a headless one (`worker-implementation-headless-screen`), the form detected from the environment of the command ([Forms](#forms)). The package ships three files for each of the 18 specialists: the role's own, and the two screen files with the same prompt and the screen tools of their form added to the role's (`agents/<name>-screen.md`, `agents/<name>-headless-screen.md`, and the same below `families/`). `@tintinweb/pi-subagents` takes a specialist's tools from its agent file alone, so a launch cannot grant them per call; a specialist that is not a screen specialist has none of them, and its tool list stays short. The brief of a screen Assignment says so in one line, and each file's description and that line say which form the machine has (a graphical session, or headless) instead of where the tools come from.
- **A headless specialist is told what it has.** The brief's line says the machine is headless, the specialist has a headless browser (the `mcp__browser_use__browser_exec` and `mcp__browser_use__browser_screenshot` tools, a temporary profile) and no desktop, and the headless prompt ends with the same note. Its file lists those two tools and T3's preview tools and none of the computer-use or browse tools, not even for the visual roles, whose ordinary files have computer use.
- **The launch is checked against the Assignment.** `recordLaunch` refuses a launch whose agent type is not one the Assignment was dispatched to: a screen Assignment started as an agent without the screen tools, and a plain Assignment started as a screen agent (`AgentMismatch`); either form's screen agent is accepted for a screen Assignment, since the form is the machine's. The check runs where the launch carries its agent type (the Claude hook); Pi's `assignment record` carries none, so on Pi the dispatch and the extension's agent gate are what keep a launch to the printed agent.
- **Warm reuse follows it.** A finished specialist is continued only for an Assignment with the same capability: a screen specialist never takes work without it, and the reverse. A registered specialist remembers whether it had the capability.
- **Pi only.** Under the Claude host the dispatch of a screen Assignment is refused (`InvalidDraft`: "the screen capability is available under the pi host only"), not run without the tools.
- **The extension accepts all three names.** `Agent` calls and `SubagentWorkflow` scripts may name `<name>`, `<name>-screen` or `<name>-headless-screen`; the tool gates refuse any other agent type as before.
- **T3's preview tools need T3.** A screen specialist's `tool_call` of a T3 preview or render tool is refused unless T3 hosts the session (`isT3Session`: Pi's RPC mode with T3's environment), also where the names are registered, for example by a T3 MCP server added by hand. Under T3 they are granted as above.

## The route

Under Codex a screen Assignment runs on `gpt-6.1-terra` at the higher of its row's effort and `medium`, whatever its role: a role on Luna moves to Terra (`Explorer.lookup`: Luna `low`, so Terra `medium`), and a row above `medium` keeps its effort (`Worker.debugging` stays at `xhigh`). Under Kimi the row stands, model and effort. The rule is `screenRoute` of the Codex provider profile, applied by `routeModel(config, key, { screen: true })` and printed by the dispatch like any other launch. The form does not change it.

## The MCP servers and their pins

Both servers are registered by the extension with `pi.registerMcpServer` at the start of a screen specialist's session only (`registerScreenServers` in `screen.ts`), and nowhere else: Pi starts the servers of every session, a child's included, so a server in `~/.pi/agent/mcp.json` would start in the root and in each of the 18 specialists. Setup writes no file for either. The root excludes `mcp__browse__*`, `mcp__browser_use__*` (every tool of that server) and the computer-use tools. A registration that fails, or none because browser use or the MCP extension is off, is told to the specialist on its first run, so it reports the missing tools instead of working around them.

Neither is a Pi package: Pi installs nothing for them. Browse runs as `npx` at an exact pin of `pi-packages.json`, and browser-use as `uvx` at an exact pin of `pypi-packages.json`, a table of PyPI names next to the npm one. `mise run deps:update` moves both like a Pi package and `mise run deps:check` checks them; the PyPI pin moves to the newest stable, non-yanked release of the project's JSON API (`https://pypi.org/pypi/<name>/json`), never to a prerelease (`rc`, `a`, `b`, `dev`) or a post release, and never down.

**The public registry is passed explicitly.** Every launch is `npx --registry=https://registry.npmjs.org/ --@<scope>:registry=https://registry.npmjs.org/ -y <package>@<pin> ...` (`npxServerArgs` in `capabilities.ts`). npm reads the `.npmrc` of the project it runs in, and a scope's own `@scope:registry` line outranks the plain `registry`, so both are set: a repository's `.npmrc` cannot redirect where the code of a server with browser or desktop control comes from. A test holds every `npx` server of the registry to it. The servers also start from the user's home folder, not the project: `npx` runs a package it finds in a `node_modules` of its working directory or above without fetching it, so a repository's own `node_modules` could stand in for the pinned package of a server with browser control (the extension registers each `npx` server, and the browser launcher below, with that `cwd`).

**PyPI is passed explicitly too.** The browser-use launch is `uvx --no-config --default-index https://pypi.org/simple --from browser-use==<pin> browser-use --cli-mcp` (`uvxServerArgs` in `capabilities.ts`). `--no-config` makes uv skip every `uv.toml` and `pyproject.toml` setting, and `--default-index` names the public index, so a repository's uv configuration cannot redirect where the code of a server with browser control comes from; `==<pin>` is the exact release.

### Normal: opencode browse

[opencode browse](https://github.com/anomalyco/browse) (`@opencode/browse`, MIT, pinned at `0.0.15`) is a stdio MCP server and a paired browser extension: the server drives the user's own Chromium-family browser through the extension, with Playwright code run in the visible tab. It runs as `npx ... @opencode/browse@0.0.15 mcp` and needs Node.js 22.19 or newer (the package's `engines`).

- **The tools** (read from the 0.0.15 package): `execute` (Playwright code in the user's tab), `status`, `settings`, `network`, `recording`, `flight_recorder`, `session_new`, `session_use`, `session_list`, `session_reset`, `session_delete`, `session_adopt`, `session_allowlist`, `tabs_cleanup` and `secrets_list`, `secrets_status`, `secrets_refresh`, `secrets_run`. Pi names them `mcp__browse__<tool>`.
- **The pairing.** The server cannot act until a browser has the extension and has been paired: `npx -y @opencode/browse@<pin> install` opens the extension's Chrome Web Store page when no browser has it and pairs the browser, and `pair` prints a one-time code to enter in the extension's options instead. Browse keeps each pairing in `browser-tokens.json` below its data folder (`OPENCODE_BROWSER_HOME`, else `$XDG_DATA_HOME/browse`, else `~/.local/share/browse`).
- **It starts no browser.** `executablePath` is among the options its `execute` refuses, so on a machine with no graphical session and no browser it has nothing to drive: that is why the headless form is not browse.

### Headless: the browser-use MCP server

[browser-use](https://github.com/browser-use/browser-use) (`browser-use` on PyPI, MIT, pinned at `1.0.0`, the newest stable release when it was chosen; Python 3.11 or newer) ships a stdio MCP server, `browser-use --cli-mcp`, with direct browser tools and no agent of its own: no LLM key is needed. HolyAgent launches it as

```
uvx --no-config --default-index https://pypi.org/simple --from browser-use==1.0.0 browser-use --cli-mcp
```

- **What it needs.** [uv](https://docs.astral.sh/uv/) (`uvx`), which fetches the pinned release and provides the Python 3.11 or newer it requires, and a Chromium on the machine. Node.js, `npx` and a display are not needed.
- **It attaches to a browser; it does not start one.** `--cli-mcp` drives a Chrome that is already running and reachable on a DevTools URL (`BU_CDP_URL`). So the extension registers `holyagent browser-server` and not `uvx` itself: Pi's MCP configuration takes a fixed command, and the browser has to exist, with its own port and profile, before the server starts and be gone after it ends. The command (`cli/browser-server.ts`, `pi/browser-launch.ts`) does, in order:
  1. installs handlers for `SIGINT`, `SIGTERM` and `SIGHUP`, which stay until cleanup is done;
  2. creates a temporary directory for the run;
  3. starts the Chromium (below) headless: `--headless=new --remote-debugging-port=0 --remote-debugging-address=127.0.0.1 --user-data-dir=<temporary>/profile`, so DevTools listens on 127.0.0.1 only, and `--no-sandbox` only when the process runs as root (Chromium refuses to start as root otherwise). The port is 0, so Chromium binds one itself and the launcher reads it from `DevToolsActivePort` in the profile (its first line): a port probed beforehand could be taken by another local process, which would then answer for the browser;
  4. waits, up to 20 seconds, until that port answers `http://127.0.0.1:<port>/json/version`, and fails at once if Chromium exits first;
  5. runs the `uvx` command above on this process's stdin and stdout, which are the MCP connection, with `BU_CDP_URL=http://127.0.0.1:<port>`, `BU_NAME=holyagent-<port>`, `ANONYMIZED_TELEMETRY=0`, and `BROWSER_USE_CONFIG_DIR`, `BH_HOME` and `BROWSER_HARNESS_HOME` inside the temporary directory, and an allowlisted environment ([Security](#security-of-the-headless-form)).
- **Cleanup.** When the server exits, when Chromium exits under it, or when a `SIGINT`, `SIGTERM` or `SIGHUP` arrives at any point, including while Chromium is still starting, the server is stopped, then Chromium (each as a process group: asked to end, killed after three seconds), then the temporary directory is removed. The group is signalled even when its leader has already exited, so helpers it left behind end too; on Windows `taskkill /T /F` ends the tree at once, since there is no signal to ask first. The handlers stay installed during cleanup, so a repeated signal does not cut it short. A start that fails at any step undoes the steps before it the same way, so a missing `uvx`, a Chromium that does not start and a DevTools endpoint that never answers leave nothing running and nothing on disk. A process killed with `SIGKILL` cannot run any of this and leaves its Chromium and directory behind.
- **Telemetry is off and nothing is kept.** `ANONYMIZED_TELEMETRY=0` is set whatever the person's environment says, and browser-use's config, its state (login data, sockets, logs, screenshots) and the Chromium profile all live in the temporary directory. uv's own package cache is the one thing that persists, so the pinned release is downloaded once.
- **The Chromium the machine provides** (`findChromium`, `setup/chromium.ts`): the path in `HOLYAGENT_CHROMIUM_PATH` when the person set one, else in `PLAYWRIGHT_MCP_EXECUTABLE_PATH`, its old name from the Playwright server; a configured path that does not exist counts as no Chromium, and the launcher and doctor name it and the variable it is in; else the `chromium` entry or the newest `chromium-<revision>` build in `PLAYWRIGHT_BROWSERS_PATH` when it names a folder (Playwright looks nowhere else then), else in `/opt/pw-browsers`, where cloud images put it (`/opt/pw-browsers/chromium`). With none, the launcher fails with that list and doctor reports it. Neither browser-use nor HolyAgent downloads a browser: `PLAYWRIGHT_BROWSERS_PATH=<folder> uvx playwright install chromium` puts one where the folder rule finds it.
- **The tools** (read from the server's documentation at 1.0.0): `browser_exec` (Python on the browser's DevTools connection with the Browser Harness helpers; its namespace persists between calls), `browser_screenshot` and `browser_login` (which opens a browser for the person to approve a login). Pi names them `mcp__browser_use__<tool>`, from the server key `browser_use`. The agent files grant `mcp__browser_use__browser_exec` and `mcp__browser_use__browser_screenshot` by name and not `browser_login`, so a specialist cannot start a login prompt that nobody can answer; the root is kept from every tool of the server.
- **To turn it off.** `pi.features.browserUse: false` (`holyagent setup --browser-use off`) removes the capability in both forms: no server is registered and no tool is granted. The headless form alone cannot be switched off apart from the normal one; `pi.features.mcp: false` removes every MCP server.

**In T3 browser-use is not started.** In a session T3 hosts (`isT3Session`), `withoutBrowserUseInT3` in `screen.ts` drops the browser-use server from what the extension registers, whatever the form, so no Chromium is launched and a screen specialist there drives T3's browser through the `preview_*` tools; the headless note and the brief's line say so. T3 exposes no endpoint browser-use could attach to, so it would only add a second, invisible browser. Browse in the normal form stays, since it drives the person's real browser, which T3's pane does not replace. `holyagent doctor` and `setup` run outside the session, where Pi's RPC mode cannot be known, so they still list the headless server. See [T3 Code](t3-code.md#browser).

### Security of the headless form

- **`browser_exec` is host code execution.** It runs arbitrary Python on the host, not only on the DevTools connection, so a screen specialist has code execution on the host, as it had with the Playwright server's run-code tool. The Python runs with the server's environment, which is an allowlist of the launcher's (`SERVER_ENVIRONMENT_ALLOWLIST` in `pi/browser-launch.ts`): `PATH`, `HOME`, the user, locale, time zone, temporary-folder and terminal variables, the proxy and CA-bundle variables, uv's cache and TLS settings, and on Windows the system variables a process needs, plus the variables HolyAgent sets above. Provider API keys, other secrets and the package-source overrides (`UV_INDEX`, `UV_EXTRA_INDEX_URL`, `UV_FIND_LINKS`, `PIP_*`, `PYTHONPATH`) are not passed, so none of them can redirect the pinned package or reach that Python. The Chromium itself inherits the whole environment.
- **The DevTools port has no authentication.** It listens on 127.0.0.1 only, but on a host shared with other local accounts another user can connect to it while the run lasts and drive the browser.
- **`--no-sandbox` as root.** Chromium runs without its sandbox when HolyAgent runs as root, as on cloud images, so a page that exploits the browser is not contained.

## Forms

Setup and doctor detect the form from the machine ([configuration.md](configuration.md#capabilities): `headless` in a cloud session, in CI and without `DISPLAY` or `WAYLAND_DISPLAY`; `normal` otherwise), and `--form` overrides it; the dispatch detects it the same way from its own environment, so the agent it names is the form's. A need that is missing is reported in the form in force, never dropped:

| Capability     | `normal`                                                                                                  | `headless`                                                                                   |
| -------------- | --------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| `computer-use` | `@amaster.ai/pi-computer-use`, which needs a graphical session                                            | Not offered: it drives a graphical session and the machine has none                          |
| `browser-use`  | The `browse` MCP server; needs a graphical session, `npx` and Node.js 22.19 or newer; reports the pairing | The `browser_use` MCP server; needs `uvx` and a Chromium; no display, no Node.js, no pairing |
| `mcp`          | T3's preview tools, where T3 hosts the session                                                            | The same                                                                                     |

A screen specialist takes its form from the agent file it was launched as, so its servers and its tools agree.

### Reported states

- **Doctor** prints the form, judges each need on the platform it detected the form for, then `pi capability browser-use` (`ok`, or `FAIL ...` naming each unmet need and its fix, or a `~` note when the form does not offer a capability), then, in the normal form, `pi capability browser-use pairing`:
  - `ok` with the paired browsers (the extension is installed and paired);
  - `~` **installed, not paired**: the extension is in a browser's profile but nothing is paired, with `pair` as the next step;
  - `~` **not installed**: no scanned browser has the extension and nothing is paired, with `install` (the Web Store page) as the next step;
  - `FAIL` when the pairing file cannot be read.

  Neither `~` fails doctor: a machine is in that state until the person adds the extension. Installed and not installed are told apart the way browse's own setup does, by reading the `Secure Preferences` and `Preferences` of each profile of the Chromium-family browsers it knows (Chrome and its channels, Chromium, Edge, Brave, Opera, Vivaldi, and Arc on macOS) for the extension's id; a browser outside that list is not scanned, and the line names the ones that were. Nothing is started and nothing is written.

- **The Node.js need** (normal form only) runs `node --version` and compares it with browse's minimum, 22.19.0 (its `engines`). An older or silent `node` is a `FAIL` line with the fix.
- **The headless needs** are `uvx` on `PATH` (the fix names uv, which provides Python 3.11 or newer) and a Chromium as `findChromium` finds it; each missing one is a `FAIL` line in doctor and a `~` line in setup, with its fix.
- **With `pi.features.mcp` off** doctor prints `~ pi capability browser-use: pi.features.mcp is off, so the MCP server is not registered and screen specialists get none of its tools`, and setup's line says the same instead of listing a server; the specialist is told on its first run, once for the process. It is a note, not a failure.
- **Setup** changes nothing for browser use and prints the same facts in its `browser-use:` lines: the form, the server the extension registers, each need that is unmet, in the headless form the Chromium that will be used, and in the normal form the pairing state above. A pairing file that cannot be read is one `~` line there (`cannot tell whether a browser is paired: ...`), so it never fails the step; doctor fails on it.
- **A screen Assignment on a machine that lacks a tool** still gets the tools that exist; the brief tells the specialist to report one that is missing instead of working around it.

## What is not confirmed

Nothing here started Pi, a browser, either server, `uvx` or T3 Code; the launcher is tested with fake processes. Not confirmed: that a server registered from `session_start` of a child connects before the child's first call (the Pi documentation says a server registered after load connects right away); that `npx` or `uvx` finds or downloads the package inside a child on a machine with a cold cache within the server's timeout; that the Chromium flags above start the preinstalled Chromium of a cloud image and that browser-use 1.0.0 attaches to it through `BU_CDP_URL` (read from the project's documentation, not run); that the per-session daemon browser-use starts for a `BU_NAME` exits with its browser; the names of the variables that move browser-use's config and state (`BROWSER_USE_CONFIG_DIR`, `BH_HOME`, `BROWSER_HARNESS_HOME`, read from its documentation, one of which may be ignored); the behavior of a browse auto-update (`OPENCODE_BROWSER_AUTO_UPDATE`) under an `npx` run; and, for a project whose `node_modules` already holds a package of that name, that `npx` takes the registry's copy over the local one (the registry flags settle where a download comes from, not which copy `npx` prefers).
