# The bash tool on just-bash

**Status: ships in 0.3.1 as the `just-bash` capability (`pi.features.justBash`, on by default).** Pi's `bash` tool, for the root and every specialist, runs on [just-bash](https://github.com/vercel-labs/just-bash), a simulated shell written in TypeScript, instead of a real `bash`. Commands it implements run inside it; every other command runs the real program on the machine. The same shell works on Linux, macOS and Windows, so a machine without Git Bash needs nothing extra.

## The decisions

- **Backend (maintainer, 2026-11-09).** The bash tool runs on just-bash, through Pi's `BashOperations`. just-bash 3.6.0 cannot run host executables itself, so commands it lacks resolve to the real programs on `PATH` and the other places a developer's tools live, and `git`, `bun`, `bunx`, `mise`, `gh`, `node` and the `holyagent` CLI keep working.
- **Built-ins win (maintainer, 2026-11-09: "prefer them instead of the ones in PATH").** Where just-bash implements a command (`rg`, `grep`, `sed`, `awk`, `jq`, `find`, `ls`, `xargs`, `tar`, `diff`, and the rest), its own runs, and the machine's program of that name is not registered. `host-<name>` reaches the machine's program (`host-cat`). Two just-bash commands give way to the machine's program, since they cannot do their job here: `node`, which only prints "use js-exec" (without a machine `node` the refusal stays, since it names the way forward), and `sqlite3`, which needs a worker file that the one-file bundle does not have.
- **TypeScript first, JavaScript as the fallback (maintainer, 2026-11-09).** `js-exec` is just-bash's QuickJS runtime. Inline code (`js-exec -c '...'`) and code on standard input are read as TypeScript and run with the types removed (Bun's transpiler, which also compiles enums); code that TypeScript's grammar refuses, such as repeated parameter names, runs as written. A file is left to `js-exec`, which reads `.ts` and `.mts` as TypeScript by its extension.
- **Billion Context's bash guardrails are off (maintainer, 2026-11-09).** See [the guardrails](#billion-contexts-guardrails).
- **A module of its own (maintainer, 2026-11-09).** The shell is its own capability behind a narrow seam, can be turned off alone, and its one third-party package sits at an exact pin that only `mise run deps:update` moves.

## How a call runs

Pi runs on Node, so the shell cannot live in the extension: just-bash and the host-program passthrough use Bun's APIs. For each call the extension starts Bun on the package's `scripts/just-bash.js` (found the way the CLI's Bun is found, and started with no env file and the empty Bun config), writes one JSON line to its standard input (the command, the folder, the whole environment) and reads one JSON line per frame from its standard output: output chunks as they arrive (base64, so binary output passes unchanged), then the exit code and the state the command left. A process per call is about 100 ms of startup, and it makes cancel simple: an abort or Pi's `timeout` kills the process and everything it started (the process group on POSIX, `taskkill /T` on Windows), which stops even a shell loop that never gives the event loop a turn. Pi's contract holds: an abort rejects with `aborted`, a timeout with `timeout:<seconds>`, a missing folder with Pi's own message.

- **State.** The working folder and the variables a call leaves are kept for the next call, as in a terminal, for as long as Pi passes the same folder (variables a call sets stay set, exported or not, since just-bash reports the shell's variables). A call that runs `exit` keeps them too. just-bash drops the state of a run that `exit` ends and has neither `trap ... EXIT` nor a way to override `exit`, so before the command line runs, each `exit` in it (in a function, a condition or a list too) gets a call to a command of the shell that records the state, and a final call marks a script that ran to its end, whose state just-bash reports itself. Both pass `$?` on, so a bare `exit` still exits with the last status. An `exit` in a subshell or a command substitution ends that subshell only, as in bash, and records nothing (the recording command compares `$$` with `$BASHPID`), so it cannot replace the state of the shell around it; a command line with no `exit` is not changed. Variables a function made `local` (or `declare`d without `-g` in a function) are not state: after an `exit` in a function the call reports the value the run started with for each name that `local` or `declare` declares in a function anywhere in the command line (the function may be called from another one), and none for a name the run did not start with. A `declare` outside a function declares session state, `exit` or not. Calls that overlap (Pi may run two at once) each add only what they changed to the state at the moment they end, and a call that stayed in its folder does not undo another call's `cd`.
- **Files.** The shell sees the real disk at real paths (just-bash's `ReadWriteFs`). Its own `/usr/bin` and `/bin` are in-memory folders with one stub per command, because just-bash resolves a command only from a file at exactly `/usr/bin/<name>` or `/bin/<name>`; the shell's `PATH` is those two folders followed by the call's own `PATH`, so `$PATH` reads as the real one. A program given by path (`./target/debug/app`, `node_modules/.bin/tsc`, an absolute path) or found in a folder the command added to `PATH` (`export PATH=$PWD/bin:$PATH`) runs on the machine. just-bash runs a file it is told to run as a shell script: it asks its file system whether the path exists, then for its `stat`, then reads it, and nothing else asks in that order (`cat` and `grep` read without the `exists`, and a file test such as `[ -x ./bin ] && cat ./bin` is followed by the reading command's own lookup before it reads, which breaks the sequence). The file system the shell is given answers that read with a one-line script that calls a command of the shell, `holyagent-run`, which starts the file on the machine; any other read of the file is the file, so `cat ./bin` and `[ -x ./bin ] && cat ./bin` print a binary's real bytes. A file counts as the machine's when it is a binary (a NUL byte in its first 4 KB) or starts with a `#!` line for an interpreter other than `sh`, `bash`, `dash` or `ash` (`#!/usr/bin/env node`); a shell script, with or without a `#!` line, still runs in the shell. On Windows a file with a `PATHEXT` extension is the machine's whatever it holds, and `stat` reports the execute bit for it, which just-bash requires and the disk does not have. The `PATH` a host program gets is the shell's `PATH` at that moment, so a folder the command added is in it, in the machine's spelling and without the shell's two folders, followed by the places a launcher's `PATH` may leave out. A change of `PATH` is kept for the next call like any other variable.
- **Host programs.** Looked up in the call's `PATH`, then in Bun's install folder (`BUN_INSTALL`, `~/.bun/bin`), `~/.local/bin`, mise's shims, cargo's `bin`, Homebrew, Git for Windows' `cmd` folder and the system folders, so a Pi started from a desktop app with a short `PATH` still finds them. A program starts with that `PATH`, never the shell's. On Windows a program is a file with a `PATHEXT` extension, named without it, and each existing drive is a folder of the shell (`C:\proj` is `/c/proj`); the folder and the arguments that name a file below a drive are mapped back for the program, and the folder a call ends in goes back to Pi and into the next call as the Windows path, while `pwd` and `$PATH` inside the shell print the shell's spelling (`/c/proj`). A host program that is the whole command (found by name, or a program given by path) streams its output as it arrives; in a pipe or a list the output is sent when the command ends, and when the output is nothing but host programs' (no builtin wrote any, no redirect to a file), standard output and standard error are sent in the order they arrived, also with `2>&1`; otherwise just-bash's own result stands, all of standard output and then all of standard error. The folders besides the call's `PATH` come from variables (`HOME`, `BUN_INSTALL`, `MISE_DATA_DIR`, `LOCALAPPDATA`, `APPDATA`, and on Windows `ProgramFiles` and `ProgramW6432` for Git's `Git\cmd`, `LOCALAPPDATA` for a per-user `Programs\Git\cmd`), and a relative value names no folder, as a relative `PATH` entry names none. On Windows a `.cmd` or `.bat` file starts through `cmd.exe /d /s /c call <file> <args>`, with the arguments refused or quoted by the rules the extension uses for its own `.cmd` shims (the shared `cmdExeArguments` in `cmd.ts`: no `"`, `%`, `^`, `!` or control character, and no `cmd.exe` operator in an argument without a space).
- **`/dev/null`.** A redirect to it (`>/dev/null`, `2>/dev/null`, `&>/dev/null`, also on a host program) discards the output, and reading it gives empty input. just-bash writes such a redirect as a file, which the disk refuses as a special file, so the shell answers every file system call of its own on that device itself, and none reaches the host's device. A path is the device by where the file system resolves it (the real parent folder plus the name, so a missing leaf counts), not by its spelling: `/dev//null`, `/dev/../dev/null`, `/proc/self/root/dev/null` and `/tmp/d/null` with `ln -s /dev /tmp/d` all are. Writes, `cp` to it, `chmod` and `utimes` are dropped (a `cp` from a missing file or a folder fails as to any file), reads are empty, and `cp /dev/null file` makes an empty file. A call that would remove, replace or link the device (`rm`, `mv` to or from it, `mkdir`, `ln` and `ln -s` of it, `readlink`, a listing) fails with the error the disk would give, so `rm -f /dev/null` fails silently and the device stays; `rm` or `mv` of `/dev` or of a folder that holds it (`/`) fails the same way, and `/dev/null/` gives `ENOTDIR`. A link to the device that something else made is removed or moved as a link, and is not followed by this check. The guard covers the shell's own file system calls only: a host program run by name or by path (`unlink`, `dd`, `/usr/bin/rm`) is a process on the machine and bypasses it, so it can remove or overwrite the device when the machine's user may.
- **Limits.** just-bash's command, loop, work-unit and JavaScript time limits are raised so that only Pi's `timeout` and abort end a call.

## Billion Context's guardrails

Billion Context adds three guardrails to the `bash` tool: a default 60 s timeout for a call that names none, a 50 KB cap on a result, and a repeated-call breaker (which watches every tool, not only bash). While the capability is on, HolyAgent turns all three off through Billion Context's own settings:

- the environment, `BILI_GUARDRAIL_BASH_TIMEOUT=0`, `BILI_GUARDRAIL_MAX_OUTPUT_BYTES=0` and `BILI_GUARDRAIL_REPETITION=0`, which the extension sets for the Pi process (a value you set stays) and `toolArgs` lists in `env`;
- its file, `guardrails.bashTimeout`, `guardrails.maxOutputBytes` and `guardrails.repetition`, which `holyagent setup` writes (a value you set stays) while Billion Context itself is on.

Billion Context reads its environment when its extension loads, which can be before the HolyAgent extension has read the config and set the variables; the file is read at that same moment and needs no load order, so both are set. The environment wins when both are present. With the capability off, the environment is not set, and `holyagent setup` takes the file's keys back out, by its record: only a key setup recorded writing, and only while it still holds what setup wrote. A guardrail you had set before setup, or changed since, stays (a changed one is named in the setup output), and the other keys of the file are never touched. The same applies while Billion Context itself is off, when the keys are no longer written, and with `pi.enable` off, when setup writes nothing else but still takes these keys back out by its record.

## The capability

| Entry    | Value                                                                                                                                                                                                   |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Name     | `just-bash`, switched by `pi.features.justBash` (`holyagent setup --just-bash on\|off`), on by default                                                                                                  |
| Needs    | Bun on `PATH`; `holyagent doctor` fails the line and says where to get it. No display, so the headless and the normal form are the same                                                                 |
| Installs | Nothing: no Pi package, no MCP server                                                                                                                                                                   |
| Applies  | The root and the specialists, under every provider                                                                                                                                                      |
| Off      | The extension never registers its `bash` tool, so Pi's own tool, with its shell settings (`shellPath`, `shellCommandPrefix`), is untouched, and `holyagent setup` restores Billion Context's guardrails |

The extension registers the tool when a session's config says the capability is on, not at load: Pi's own `bash` tool definition (schema, truncation, rendering) with the shell's operations and a few guideline lines for the model. While it is on, `shellPath` and `shellCommandPrefix` do not apply. Pi's `!` command, which runs through `user_bash`, is not changed.

## The pin and the bundle

just-bash is an exact `3.6.0` in `packages/runtime/package.json`, not a range: it decides how a shipped feature behaves, so its upgrade is one deliberate step. `mise run deps:update` moves it (and `--check` fails when it is behind) through `EXACT_PACKAGES` in `scripts/dependency-pins.ts`; `scripts/dependency-ranges.test.ts` refuses a range for it. The shell is bundled for Bun into `scripts/just-bash.js` (`packages/runtime/src/pi/bash/entry.ts`), a file of its own, so a move of the pin changes that file and no other. The bundle leaves out `sql.js` (replaced by a stub, since `sqlite3` is not offered) and the optional native add-ons `node-liblzma` and `@mongodb-js/zstd` (`xz` and `zstd` archives report them missing), so that it is the same on every machine and needs nothing beside it.

## Not verified

The Windows paths (drive mounts, `PATHEXT`, `.cmd` shims and their quoting, the execute bit `stat` reports for a program given by path, `taskkill`) are covered by unit tests on their pure parts and by the tests that start real programs; no Windows machine ran the whole path. Whether Bun quotes the arguments of the `cmd.exe` launch the way Node does is assumed from the extension's own `.cmd` handling, not tested. The registration of the tool after session start rests on Pi's documented behavior (`registerTool` works after startup and a tool under a built-in's name replaces it); no Pi session was started.
