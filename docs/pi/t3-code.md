# T3 Code: the primary interface for HolyAgent on Pi

**Status: built for 0.3.0, except the macOS permission walkthrough for computer use and the adapter for rpiv tools that need `custom()`; the specifics still to verify are in [To verify](#to-verify).** What the code does under T3 Code: the extension detects a T3 session, keeps only the T3 tools HolyAgent uses active, blocks a call to any other T3 tool, and warns when the thread is below Full access ([T3's tools](#t3s-tools-kept-and-deactivated), [Full access](#full-access-is-required)); `holyagent setup` writes T3's settings through an interactive screen with flags ([T3 settings](#t3-settings-written-by-setup), [the setup screen](#the-setup-screen-and-its-flags)); and a replay of synthesized T3 traffic tests it ([Tests](#tests)). HolyAgent 0.2.x supports Claude Code only. This page records what the maintainer decided for T3 Code as the primary interface of the Pi integration, with the research it rests on. Where a section says "decided" or "will" without a "built" note, check [the Pi status table](README.md#what-ships-now-and-what-is-planned).

The maintainer's words: "also I want holyagent pi to be compatible with t3 code", in scope "In 0.3.0"; then "t3code shall be the primary interface for the pi integration, so we will deeply integrate with it. that means we can rely on its integrated browser, computer use, as well as enable anything beneficial we can from it globally or locally".

The research read T3 Code's documentation and pull requests on 2026-11-07. Several T3 source files were read through mirrors rather than upstream `main`; those links are labelled "third-party", and so are the third-party packages. T3's Pi provider is Early Access, so details change: the T3 release must be checked before a detail is relied on ([To verify](#to-verify)). "Inference:" marks a conclusion drawn here, not a stated fact. The Claude plugin under T3 Code is a separate case, described in [usage.md](../usage.md#t3-code).

## The primary interface

T3 Code is the primary interface for HolyAgent on Pi. The Pi documentation leads with it, and HolyAgent relies on T3's browser, dialogs, pickers, worktrees and the rest instead of rebuilding them.

**Start here.**

1. Install Pi and the HolyAgent package as in [installation.md](installation.md#how-holyagent-installs). Use the user (global) install: the T3 step of setup runs at `--scope user` only, and a project-local install loads under T3 only once a saved trust decision, `defaultProjectTrust` or an `--approve` launch arg applies ([installation.md](installation.md#global-and-project-local-installs)).
2. Run `holyagent setup` in a terminal. It turns on T3's Pi provider and, on [the setup screen](#the-setup-screen-and-its-flags), lets you choose device access and worktrees for new threads; it skips the T3 step when T3 Code is not installed.
3. In T3 Code, start a thread on the Pi provider and set its access mode to Full access ([why](#full-access-is-required)). The same install serves plain `pi`, so nothing else is needed.

The plain `pi` terminal stays supported: everything in the other [Pi pages](README.md) works there, and no terminal path is removed. The pieces below that exist only under T3 (the MCP bridge tools, the dialogs) are absent in a terminal, and the visual roles report an inspection as blocked when their tools are missing, as the Claude text already does ([claude-parity.md](claude-parity.md#8-what-pi-cannot-carry)).

## How T3 runs Pi

Sourced from T3's [Pi provider page](https://github.com/pingdotgg/t3code/blob/main/docs/user/providers-pi.md) and [PR #7211](https://github.com/pingdotgg/t3code/pull/7211) (merged 2026-09-10; the PR marks the provider "Early Access"):

- T3 Code (`pingdotgg/t3code`, MIT) lists Pi as a built-in provider next to Codex, Claude, Cursor, Grok, OpenCode, Antigravity and fx ([FAQ](https://github.com/pingdotgg/t3code/blob/main/docs/user/faq.md)). Pi is off by default and is enabled in T3 Settings.
- T3 runs the user's own `pi` install, so Pi's models, authentication, extensions, skills and context files carry over. It needs Pi 0.80.5 or newer; HolyAgent develops against Pi 1.x ([installation.md](installation.md#the-pin)), which satisfies the floor.
- The protocol is `pi --mode rpc` over stdio JSONL. T3 rejects launch args that change the mode or pick a session. Pi's own [RPC](https://pi.dev/docs/latest/rpc) and [extension UI](https://pi.dev/docs/latest/rpc-extension-ui) docs describe the same protocol.
- T3 injects its own MCP bridge extension into Pi, started as `pi --mode rpc --extension <t3 mcp extension>` with `T3_MCP_URL` and `T3_MCP_BEARER_TOKEN`; it routes calls to `http://127.0.0.1:<port>/mcp` with a per-session credential ([orchestrator-mcp-server.md](https://github.com/pingdotgg/t3code/blob/main/docs/orchestration-v2/orchestrator-mcp-server.md), "Pi V2"). Pi does not need `builtin:mcp` to reach these tools. Pi's own project MCP servers are separate, and untrusted folders skip them; T3's `mcp.json` entries override Pi's native MCP registrations (research of 2026-11-07, from T3's docs).
- Pi keeps its own discovery: user extensions and skills load from `~/.pi` (or `PI_CODING_AGENT_DIR`), and project `.pi/` extensions, skills and MCP load only after the folder is trusted ([configuration.md](configuration.md#project-trust)). A Pi instance in T3 can set the binary path, environment variables and launch args.

**What HolyAgent does under RPC mode.** Its extension sees `ctx.mode` as `"rpc"` and `ctx.hasUI` as true, and sets no launch args for mode or session. It already has to work in RPC mode for its own children ([extensions.md](extensions.md#the-holyagent-package)).

## Dialogs and status only

The maintainer's words: "I want tthem to run with t3code's dialogs/ui, no weird tui stuff". Decided: under T3, every HolyAgent interaction uses only the RPC extension UI that T3 renders, which is:

| Pi call                                | Where T3 shows it | Source                                                                      |
| -------------------------------------- | ----------------- | --------------------------------------------------------------------------- |
| `select`, `confirm`, `input`, `editor` | T3's composer     | [rpc-extension-ui](https://pi.dev/docs/latest/rpc-extension-ui), T3 Pi page |
| `notify`                               | The work log      | same                                                                        |
| `setStatus`                            | Near the composer | same                                                                        |

HolyAgent never calls `custom()`, widgets, footer, titles or theme methods. `setWidget` and titles have no T3 equivalent, and `custom()` returns `undefined` in RPC mode.

- **The todo panel does not show under T3.** `@juicesharp/rpiv-todo` (2.15.0, the pin) draws its list as a live panel through `setWidget`, which T3 does not render, so the panel is absent. The `todo` tool itself still works: the model creates and updates tasks and reads them back, and the list lives in the session as before. Under T3 the root's task list is therefore visible to the model and not to you; ask the root for its list, or use the plain `pi` terminal to see the panel. HolyAgent has no adapter for it yet, an improvement that would render the list through `notify` or `setStatus`.
- **Ask-user follows the rule.** Inference: `@juicesharp/rpiv-ask-user-question` (2.15.0) may depend on `custom()` TUI rendering, which is dead under T3 unless the tool falls back to the dialog methods; this has not been verified ([extensions.md](extensions.md#tool-surface-for-030)). HolyAgent has no adapter for it either.
- **Consequence for progress and notices.** Since widgets are not used, anything HolyAgent shows the user under T3 goes through `notify` or `setStatus`.

## Full access is required

The maintainer's words: "Require Full access". HolyAgent threads in T3 run in T3's Full access mode, consistent with full access as the default ([auto-mode.md](auto-mode.md)).

- **How T3 applies modes (sourced):** Supervised, Auto-accept edits and Full access are applied through Pi's blocking tool hook; extension tools prompt in Supervised and Auto-accept edits; changing the mode restarts the Pi session and resumes it; there is no "Auto" mode for Pi.
- **Why not the other modes (inference):** HolyAgent's extension tools and codemode would prompt on every call, and background specialists' tool calls could stall waiting on a human.
- **What HolyAgent does (built, `packages/integrations/pi/src/t3.ts`):** a session counts as a T3 session when Pi runs in RPC mode and T3's bridge set `T3_PI_RUNTIME_MODE` or `T3_MCP_URL`. The mode is the value of `T3_PI_RUNTIME_MODE` (`approval-required`, `auto-accept-edits` or `full-access`); an unset mode counts as Full access, as in T3's bridge. Below Full access the extension sets the `holyagent` status near the composer and delivers one notice with the next run (T3 drops a notification outside a turn), both telling you to switch the thread to Full access, after which T3 restarts the session. The warning is the only enforcement: the thread keeps running, and `holyagent setup` writes no access mode. Pi's own launch of `pi` outside T3 has no such mode and no warning.

## Specialists and completion notices

The maintainer's words: "pi's stuff". Specialists and workflows run through `@tintinweb/pi-subagents` ([orchestration.md](orchestration.md#decision-for-030)), and its own new-turn trigger reports each completion to the root. T3's `delegate_task` is not used, and the tool is deactivated ([next section](#t3s-tools-kept-and-deactivated)).

- **Why it needs a check (inference):** T3 treats a turn as done on Pi's `agent_settled`, so a completion notice from detached work that arrives afterwards may not appear as a turn. T3 does handle detached compaction at settlement. This needs a real test.
- **The test:** a synthesized fixture of T3's RPC traffic documents that a completion notice arriving after `agent_settled` starts a new root turn. It is not a regression test, because it needs `@tintinweb/pi-subagents` and T3 Code, which the tests do not run ([Tests](#tests), [development.md](../development.md#re-recording-the-pi-fixtures)). What HolyAgent does if T3 behaves otherwise is not decided.
- **What T3 would give instead (sourced):** `delegate_task` creates T3 child threads, which are durable, while Pi's example `subagent` extension shows as progress cards only and its children cannot be resumed. Inference: HolyAgent's specialists would appear like those cards if they work like that extension. Choosing `delegate_task` would couple HolyAgent to T3, which the maintainer did not choose.

## T3's tools: kept and deactivated

T3's bridge registers its tools under the prefix `mcp__t3-code__`; on current Pi it also registers hidden `mcp__t3_code__` aliases that the model cannot call. The names come from T3's orchestrator doc, PR #7211 and the bridge source ([mcpExtensionSource.ts](https://git.cafe/pingdotgg/t3code/blob/c273a8f6fa921f02e7f2fc2d055aa6891cfe04f9/packages/provider-pi/src/server/mcpExtensionSource.ts), third-party mirror); a third-party adapter, `pi-pstack-adapter` 0.7.0, uses the same `mcp__t3-code__delegate_task`.

| Tool                                                                                                                                                                                                                                                 | Decision   | Why                                                                                                                                                                      |
| ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `html_render`, `html_preview`                                                                                                                                                                                                                        | Keep       | HolyAgent's visual route for the root ([html-renders](https://github.com/pingdotgg/t3code/blob/main/docs/user/html-renders.md))                                          |
| `preview_*`, the integrated browser, and `t3_preview_*` (`t3_preview_list`, `t3_preview_close`)                                                                                                                                                      | Keep       | The visual specialists' browser ([Browser](#browser))                                                                                                                    |
| `device_*` (`device_list`, `device_open`, `device_screenshot`, `device_close`)                                                                                                                                                                       | Keep       | HolyAgent's device access for simulators and emulators ([Devices](#devices))                                                                                             |
| `orchestrator_capabilities`, `delegate_task`, `task_status`, `task_cancel`                                                                                                                                                                           | Deactivate | They duplicate `@tintinweb/pi-subagents`                                                                                                                                 |
| `create_threads`, `t3_thread_launch`, `t3_thread_list`, `t3_thread_read`, `t3_thread_update`, `t3_thread_send`, `t3_thread_wait`, `t3_thread_interrupt` (the `t3_thread_*` family), `schedule_task`, `list_scheduled_tasks`, `delete_scheduled_task` | Deactivate | They are outside HolyAgent's flow; T3's scheduled tasks stay usable from T3's UI, which needs no agent tool                                                              |
| `t3_pending_request`                                                                                                                                                                                                                                 | Deactivate | It reads and answers a child thread's questions, so with delegation off it is unneeded (inference); the research marked this one to verify                               |
| Any other `mcp__t3-code__` tool outside the kept families (the research also saw `t3_thread_search` and PR watch and worktree tools in [PR #15219](https://github.com/pingdotgg/t3code/pull/15219), third-party mirror)                              | Deactivate | Same rule: HolyAgent keeps the families above and removes the rest. The doc names `OrchestratorToolkit` as the authoritative list, and the research read it only in part |

**Mechanism.** Pi's `pi.getAllTools()`, `pi.getActiveTools()` and `pi.setActiveTools(names)` work on any tool, including ones another extension registered; `setActiveTools` ignores unknown and `hidden` tools, and Pi has no `unregisterTool` ([extensions](https://pi.dev/docs/latest/extensions)). Built (`isDeactivatedT3Tool` in `packages/runtime/src/pi/tools.ts`, the glue in `packages/integrations/pi/src/extension.ts`): the extension calls `pi.setActiveTools` with the registered T3 tools outside the kept families removed, under either spelling of the server name (`mcp__t3-code__` and `mcp__t3_code__`), so only the kept T3 families (`html_render`, `html_preview`, `preview_*`, `t3_preview_*` and `device_*`) stay. It applies to the root's tools only; a specialist's tools are the `tools:` line of its agent file.

- It applies once at the start of a T3 session, before the first request, and on `before_agent_start` and `session_tree` takes out again only the deactivated tools that T3's bridge has added back, so a call that changes nothing leaves the tool list, and the prompt cache, as it was. Pi's own example [tools.ts](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/examples/extensions/tools.ts) reapplies on `session_tree` too. Inference: T3's bridge calls `getActiveTools` and probably `setActiveTools` itself when its exposure changes and after tree restores, so it may re-add tools after HolyAgent's call; filtering by prefix each time is the mitigation.
- A `tool_call` handler blocks a call to any deactivated `mcp__t3-code__` tool as a backstop, because hiding a tool is not an execution policy (third-party source).
- **There is no T3 setting for this.** The research found none for Pi: issue [#4150](https://github.com/pingdotgg/t3code/issues/4150) asks for a browser-MCP toggle and says none exists, and its workarounds are for Codex and Claude only. A Pi launch-arg route (`--tools` as a strict allowlist, per a third-party source) would drop Pi's own tools too and was not verified.
- **Resume and restart.** A restart reloads extensions and fires `session_start` with a reason (startup, resume or fork), so the filter runs again. The research found no persistence of the active tools across restarts.
- **Residue (to verify):** disabled tools may still leave a small orchestration-instructions residue in T3's first-turn prompt.

**Prompt caching.** The active tool set is fixed at `session_start` and not toggled mid-session, so the cached prefix holds. Pi's docs say a change of the active tools updates the prompt contributions and the provider tools; models without mid-conversation system messages take a cache miss per change ([caching-and-subagents.md](caching-and-subagents.md#cache-target)). Inference: a reapplication that finds the set already right changes nothing.

## Browser

The visual roles use T3's integrated browser. The toolkit has these twelve tools (source: a mirror of [`toolkits/preview/tools.ts`](https://git.kaki87.net/VibedByKaKi/t3-code-android-nightly/src/branch/main/apps/server/src/mcp/toolkits/preview/tools.ts), third-party; DeepWiki, third-party; [discussion #24799](https://github.com/pingdotgg/t3code/discussions/24799)); upstream `main` was not read directly:

- `preview_status`, `preview_open`, `preview_dialog`, `preview_navigate`, `preview_resize`, `preview_set_appearance`;
- `preview_snapshot` (accessibility tree, console, network and a screenshot);
- `preview_act` (click, type, hover, select, drag, upload, press, scroll);
- `preview_evaluate`, `preview_wait_for`, `preview_recording_start`, `preview_recording_stop`.

Console and network output arrive through snapshot diagnostics; dedicated `preview_console` and `preview_network` tools are only a proposal in the discussion. The same discussion names `t3_preview_list` and `t3_preview_close`, which are kept with the rest of the `t3_preview_*` family. The bridge is always on for Pi and T3 has no toggle for it ([issue #4150](https://github.com/pingdotgg/t3code/issues/4150)).

Decided: the fixed tool set pins these names (with `html_render`, `html_preview`, `t3_preview_list` and `t3_preview_close`), because on Pi 0.99 and newer only `orchestrator_capabilities`, `delegate_task` and `task_status` are exposed directly and every other T3 tool, `preview_*` included, is `deferred` behind Pi's `tool_search`. The alternative the research offered, keeping `tool_search` active, is not taken. Inference: pinning by name activates the deferred tools at session start; whether a deferred tool stays discoverable once it is excluded is to be verified.

**Screen specialists in T3 use T3's browser, and browser-use is not started.** In a session T3 hosts (`isT3Session`), HolyAgent registers no browser-use server, whatever the form of the machine, so no Chromium is launched and no `mcp__browser_use__*` tool reaches a specialist: it drives the pane through the `preview_*` tools. T3 exposes no endpoint, such as a Chrome DevTools Protocol URL, that browser-use could attach to, so inside T3 it would only add a second, invisible browser. Opencode browse and computer use stay in the normal form: they drive the person's real browser and desktop, which T3's pane does not replace. Outside T3 nothing changes ([screen.md](screen.md#headless-the-browser-use-mcp-server)).

## Computer use through Cua Driver

T3 serves no OS-level desktop control of its own. Codex threads get Codex's computer use, Claude threads get none, and the Pi adapter is not mentioned ([issue #31437](https://github.com/pingdotgg/t3code/issues/31437)); a proposal for a T3-mediated desktop toolkit on Linux ([#32088](https://github.com/pingdotgg/t3code/issues/32088), quoted in #31437 by a third-party comment) is unshipped as far as the research found. So HolyAgent adds computer use itself.

The maintainer's words: "cua driver". Decided, from the research ([trycua/cua](https://github.com/trycua/cua)):

- **What it is.** Cua Driver (`trycua/cua`, `libs/cua-driver`) is a background computer-use driver. It reads the accessibility tree and sends input to windows without moving the user's pointer or taking focus. It is MIT-licensed (the optional `cua-perception` extension is AGPL-3.0-only and is not needed). It runs on macOS 14 or newer, Windows 10 and 11, and x86_64 Linux on X11 or XWayland with AT-SPI 2 (Linux is described as preview builds, [quickstart](https://cua.ai/docs/cua-driver/quickstart)). It controls the host desktop, not a VM. The research identified it from the two words "cua driver"; the decision confirms it.
- **How HolyAgent connects it.** Through the existing Pi extension [`@amaster.ai/pi-computer-use`](https://pi.dev/packages/@amaster.ai/pi-computer-use) (third-party; 0.1.36, Apache-2.0, published 2026-11-05 when read), pinned and moved only through `mise run deps:update` ([installation.md](installation.md#the-pin)). The driver is the copy the extension bundles: there is no separate driver install, and the bundled version moves with the extension pin. The research read it as exposing about 62 `computer_use_*` tools with a core profile by default. Cua's docs list Pi as a client that uses one-shot `cua-driver call` commands, without MCP ([connect your agent](https://cua.ai/docs/cua-driver/guides/connect-your-agent)); whether Pi accepts an MCP entry natively is unverified, and HolyAgent does not rely on it.
- **Permission mode and prompts.** The driver runs in `standard` mode, its default, which allows input to every app; the mode is fixed at launch ([operate](https://cua.ai/docs/cua-driver/guides/operate)). The extension's confirmations (it asks on app launch and dangerous actions, per the research) are off, in the maintainer's words "Full access, no prompts".
- **Who gets it.** Only Worker.visual and Reviewer.visual receive the computer-use tools, pinned by name in their fixed tool set like the browser tools. Everyone else gets none.
- **Setup.** There is no driver to install, because the extension carries it. `holyagent setup` for Pi walks through the macOS permissions only: Accessibility and Screen Recording, which the bundled driver needs to read the screen and send input ([quickstart](https://cua.ai/docs/cua-driver/quickstart)).
- **The browser stays on T3's `preview_*` tools.** Computer use is for what the browser cannot reach, such as native and desktop apps.

**Security.** Inference: under T3's Full access, a Pi agent with these tools can operate any app of the user's, including a signed-in mail client, and the screenshots enter the model's context. Only the two visual roles have the tools, and the research found no dedicated Cua security page. A user who does not want this leaves the extension off in `config.json` ([configuration.md](configuration.md#holyagent-configjson)).

The research read the extension as bundling Cua Driver 0.37.0 through npm while the latest standalone driver release was 0.41.3 (2026-11-07); the decision is to run the bundled copy, so the driver version follows the extension pin and lags Cua's releases until the pin moves.

To verify: how the extension's confirmations are turned off; the Linux preview quality; and whether the prompts of the extension, if left on, would route through T3's dialogs.

## Devices

T3's device tools (`device_list`, `device_open`, `device_screenshot`, `device_close`; taps and typing go through the `agent-device` CLI) cover iOS simulators and Android emulators. They need macOS with Xcode for iOS or the Android SDK. They are enabled in T3 under Settings, Integrations, Devices, "Agent device access", and the session is restarted afterwards ([devices.md](https://git.cafe/pingdotgg/t3code/blob/d06f0ff1048d42a156824765316c5a2dc54f5bca/docs/user/devices.md), third-party mirror).

Decided (the root's default from the maintainer's "enable anything beneficial"): device access is enabled where the host supports it. The research found no documented way for a Pi session to reach `device_*`; the orchestrator doc lists only the `preview` and `orchestration` credential capabilities. Whether Pi reaches it, and so whether the visual roles can use it, is verified during implementation. The `device_*` tools are kept by the deactivation rule above. If Pi reaches them, the fixed set pins them for the visual roles, which the implementation settles.

## T3 settings written by setup

Built. `holyagent setup` for Pi merges the settings below into T3's server settings file, `userdata/settings.json` under `T3CODE_HOME` (default `~/.t3`), and `holyagent setup --undo` backs them out. `holyagent doctor` reports the state. The step is part of the Pi steps: Pi in use, not a claude.ai cloud session, `pi.enable` on. It reads the user's own `~/.holyagent/config.json` only, since the file is the user's and a repository's config must not steer it, and runs at `--scope user` only (a `project` or `local` run leaves T3 alone). The step is skipped when T3 is not installed, meaning the T3 home folder does not exist.

**How it writes.** T3 writes the file sparsely (a key at its default is absent) and watches it for edits from outside; the maintainer confirmed that on [issue #18571](https://github.com/pingdotgg/t3code/issues/18571), the same issue that records the two risks the step guards against. A key is written only when the file does not have it and the value differs from T3's default; a value the user set stays, whatever it is. A group of keys that mean something together (`backgroundActivity`, `sourceControlWritingStyle`) is written only while the file has no such key at all. The write goes through a temporary file renamed over the target only while the file still has the text setup read, so a save by T3 Code made after setup read the file is detected right before the rename: the step fails naming the file and writes nothing, and a rerun picks up T3's change. Two narrow windows remain: a file T3 creates when none existed before setup's first write, and a save between that last check and the rename. The file is read again afterwards. A `settings.json` that is not a JSON object stops the step with an error naming the file and is left as it is. When the read-back does not decode or differs from what was written (a T3 client saving its cached settings right after ours is the known cause, issue #18571), the previous content is put back, or the file removed when there was none, and the step fails naming the file; close T3 Code and run setup again. That is done only while the file still holds what the read-back saw: after a newer save it is left as it is, and the failure says so. A rerun reports the groups setup wrote earlier (`backgroundActivity`, `sourceControlWritingStyle`, known from the setup record) as already written, not as left out. Existing keys, including ones HolyAgent does not know, are never touched.

**What it writes.** Key names, values and defaults are from the settings schema (`packages/contracts/src/settings.ts` and `packages/shared/src/backgroundActivitySettings.ts` on T3's `main`, read 2026-11-08); T3's Pi provider is Early Access, so re-check them against the T3 release in use.

| Keys                                                                                                                                                                    | Value                                                                                                                             | T3 default                     | Only when                                                                                                                  |
| ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- | ------------------------------ | -------------------------------------------------------------------------------------------------------------------------- |
| `providerInstances.pi` (`driver`, `enabled`)                                                                                                                            | `"pi"`, `true`                                                                                                                    | the Pi driver is off           | `pi.enable` is true; not when `providerInstances.pi` is another driver's or its `config.enabled` is false                  |
| `enableDeviceSupport`, `enableAgentDeviceAccess`                                                                                                                        | `true`                                                                                                                            | `false`                        | Xcode's iOS simulator platform (macOS) or an Android SDK is found, `pi.t3.deviceAccess` is true and the setup option is on |
| `defaultThreadEnvMode`                                                                                                                                                  | `"worktree"`                                                                                                                      | `null` (local)                 | `pi.t3.worktrees` is true and the setup option is on                                                                       |
| `backgroundActivity`: `profile` `"custom"` on `baseProfile` `"balanced"`, with `overrides` `pauseWhenHostLocked`, `pauseWhenHostLowPower` and `pauseWhenClientLowPower` | `false`                                                                                                                           | `true` in the balanced profile | no `backgroundActivity` in the file                                                                                        |
| `sourceControlWritingStyle` (`mode`, `customInstructions`)                                                                                                              | `"conventional_commits"`, instructions that keep AI agents, sessions and attribution trailers out of commit and pull request text | `"repo_conventions"`, empty    | no `sourceControlWritingStyle` in the file                                                                                 |
| `branchNamingMode`, `branchNameInstructions`                                                                                                                            | `"custom"`, the rule below                                                                                                        | `"static"`, empty              | each key on its own is absent                                                                                              |
| `removeAgentCreditsOnMerge`, `autoResumeLimitedThreads`, `snoozeLimitedThreads`, `defaultAutoPull`                                                                      | `true`                                                                                                                            | `false`                        | the key is absent                                                                                                          |
| `storageCleanup.worktreeOnMerge`                                                                                                                                        | `true`                                                                                                                            | `false`                        | the key is absent                                                                                                          |
| `storageCleanup.logsAfterDays`, `browserArtifactsAfterDays`, `worktreeSettledAfterDays`                                                                                 | 30, 14, 14                                                                                                                        | `null` (never)                 | the key is absent                                                                                                          |

T3 applies `backgroundActivity.overrides` only under the `custom` profile, and the balanced profile pauses background work while the host is locked or in low power mode, which would stall unattended specialists; hence the three overrides. `pauseWhenOnBattery` is already off in the balanced profile and is not written. Device access needs the host check because T3's device tools need macOS with Xcode or an Android SDK ([Devices](#devices)); setup finds Xcode through `DEVELOPER_DIR`, else `/Applications/Xcode.app`, and the Android SDK through `ANDROID_HOME`, `ANDROID_SDK_ROOT` or Android Studio's default folder, and runs no process. `pi.t3.scope` `project` writes nothing yet: per-project overrides (the branch naming rule is global, see below) come in a later change. The two setup choices, devices and worktrees (both default to on), are made on [the setup screen](#the-setup-screen-and-its-flags) or with flags.

**Branch naming.** T3 names the branch of a new thread itself: `static` mode (its default) uses the `t3` prefix. Setup switches the environment-wide setting to `custom` and gives the generator this rule: "Name each branch by the repository's own branch naming convention, as its AGENTS.md, CONTRIBUTING guide or existing branch names show it. When the repository states none, use a short, lowercase, hyphenated name under the `t3/` prefix." Each key is written only while it is absent, so a mode or instructions set in T3 stay (and a `static` or `semantic` mode kept by the user makes the instructions inert). The rule is global, with no per-project override, because T3's `projectSettingsOverrides` is keyed by project id, a random UUID that T3 mints when a project is added (the web app and `t3 project add`) and stores in its own database: setup cannot derive it from a repository, and reading T3's database or running `t3 project add` to learn it is outside what setup does. `pullRequestMergeMethod` is not written: T3's default (`null`) keeps the method last chosen on the device, and the maintainer chose to leave it. The research did not find a length limit on the instructions field; the rule is kept short. Change it in T3's settings.

**What the generator reads.** Read on 2026-11-09: `apps/server/src/textGeneration/TextGenerationPrompts.ts` in `pingdotgg/t3code` at commit `78f462c4`; the Pi provider's `packages/provider-pi/src/server/textGeneration.ts` and `mcpInjection.ts` from a mirror of T3 Code (`git.kaki87.net/VibedByKaKi/t3-code-android-nightly`, branch `main`); and T3's `docs/user/providers-pi.md`. `ThreadLaunchService.ts` was not read. Re-check against the release in use. T3 appends the custom instructions to its naming prompt, which holds the thread's first message; attached images reach it only as metadata (name, MIME type, size), because the Pi runner sends the prompt as text and the generator sees no image content. It gives the generator no repository search. The generator runs in the thread's worktree on the text-generation model you chose in T3 (setup never picks one). When that model is on the Pi provider, T3 starts Pi with `--no-tools` and `--no-extensions` and does not pass `--no-context-files`, so Pi's own context files, `AGENTS.md` and `CLAUDE.md` from Pi's agent directory, the worktree and its parents, are the only repository text it can see. A `--no-context-files` entry in the user's own Pi launch arguments in T3 is passed through, and it would hide `AGENTS.md` and `CLAUDE.md` from the generator too. Other providers act as they do for any text generation, which this page did not check. So a branch convention reaches the generator through the first message and through `AGENTS.md` or `CLAUDE.md`; a CONTRIBUTING guide or the existing branch names help only where one of those files repeats them, because the generator cannot open them, whatever the rule says. State the branch convention in `AGENTS.md`.

**Storage cleanup values.** They are HolyAgent's choice; T3 turns every one off. Logs are kept 30 days, enough to look into a failure. Browser artifacts (the screenshots and recordings of the visual specialists) are kept 14 days, the evidence of a piece of work that is over within that time. The worktree of a thread that has settled (merged or closed) is removed after 14 days, and a worktree is removed at once when its pull request merges. T3 removes a worktree only while it has no uncommitted changes (its `worktreeKeepWhen` default), so unfinished work stays whatever these say. Change a value in T3's Settings, Worktrees, Cleanup; setup does not overwrite it.

**Never written.** The context meter (`contextWindowMeterEnabled`, a per-device client setting), model choices (`defaultModelSelection`, `textGenerationModelSelection` and the like), Pi launch settings (`config.binaryPath`, `launchArgs`, `environment`) and provider update checks, and every client setting. Keys whose wanted value is T3's default are also left out: `defaultRuntimeMode` (`"full-access"`), `enableAgentBrowserAccess`, `continueThreadsAfterServerUpdate`, `newWorktreesStartFromOrigin`, `sidebarAutoSettleOnMerge`, `followUpBehavior` (`"steer"`) and `planModeEnabled`. A managed policy that caps the permission mode below Full access is not checked.

**Undo.** The keys the step adds are recorded in `holyagent/setup-records.json` under the Claude Code folder, as for the other settings. `holyagent setup --undo` removes a recorded key only while its value still equals what setup wrote, so a value changed since stays and is named; a key setup did not add is never removed, and an object the removal empties is dropped. The removal is written, guarded and read back like the install, and a failed undo keeps the record so it can be run again. `--dry-run` shows the lines and writes nothing.

**Doctor.** With Pi in use, `pi.enable` on and T3 installed, `holyagent doctor` prints one line at `--scope user`: `ok t3 settings` when the file holds every key setup would write, a `~` hint naming the missing keys, or a `~` hint naming a file that does not decode. A key the user set to another value counts as held. The lines never fail doctor, `--fix` does not write them, and nothing is said about per-device client settings.

What is known from T3 ([project-settings](https://github.com/pingdotgg/t3code/blob/main/docs/user/project-settings.md); the `useSettings.ts` source, read through a third-party mirror): server-side settings apply to all environments or to one, with per-project overrides, and a provider can be switched on or off per project; appearance, confirmations and browser profiles are per device. `~/.t3/service.env` takes `T3CODE_*` variables for the background service.

The settings that stay with the user, as UI steps: turn on the context meter and the notification settings in T3's Settings (per device), and choose a Pi model for new threads and for commit and pull request text generation.

## The setup screen and its flags

The T3 part of `holyagent setup` is an interactive screen with a flag for each choice. It shows when the T3 step has work (Pi in use, scope `user`, T3 Code installed, not `--undo`, not a cloud session) and the terminal can draw it; the flags and the line-based setup cover every other case.

**Rows.** The screen is built with OpenTUI's Solid renderer in the style of holycodex v0.16.12 (its Tokyo Night tokens, `❯` focus marker, `[x]`/`[ ]` boxes, uppercase headings and a hint line for the focused row), and offers:

| Row                      | Starts        | What it sets                                     | Shown                                                                                        |
| ------------------------ | ------------- | ------------------------------------------------ | -------------------------------------------------------------------------------------------- |
| Pi provider              | `[x] fixed`   | `providerInstances.pi`                           | Always: it stays on while `pi.enable` is true, so there is nothing to choose                 |
| Agent device access      | `[x] enabled` | `enableDeviceSupport`, `enableAgentDeviceAccess` | Only where Xcode's iOS simulator or an Android SDK is found and `pi.t3.deviceAccess` is true |
| New threads in worktrees | `[x] enabled` | `defaultThreadEnvMode`                           | While `pi.t3.worktrees` is true                                                              |

Space switches a choice between `[x] enabled` and `[ ] disabled`; the screen never says "selected". The review names a switched-off choice as `off; nothing written`.

**Capability rows.** When Pi is in use and the config loads with `pi.enable` on, the screen also shows a row for each capability of the registry ([configuration](configuration.md)), and opens for them alone where the T3 step has no work. Each row starts from what the merged config decides and writes `pi.features.<key>` only when you change it, so an untouched row never freezes a default into the file; a capability the detected form does not offer is listed as not offered. At scope `project` or `local` the choice is written to the project's `.holyagent/config.json`, which setup refuses to write through a symlink, and turning on a capability that the user config switches off for good (`computerUse`) is refused with a message naming the user setting. When the choices cannot be saved, setup does not run the package and settings steps.

Pi as the default model is not offered. The other keys setup writes (background activity, the writing style, the branch rule, thread resume and snooze, auto pull and storage cleanup) get no row; the review lists them, each with the keys and values it adds, what is already set, or why a group is left out.

**Keys.** Up and down (or `j` and `k`) move, Space toggles, Enter opens the review, Esc, `q` or Ctrl-C cancels and writes nothing. On the review, Enter on Apply runs setup with the choices and shows its report lines; Back returns to the rows with the choices kept; Esc, `q` or Ctrl-C cancels (Esc stays a cancel there, as on the rows, so one key means one thing on every screen). On the result, Enter, Space, Esc or `q` closes the screen. Text wraps at the width, a path or key after its last `/`, `.`, `_` or `-` that fits; a review or result taller than the window scrolls with Page Up and Page Down, shows `Lines a-b of n` above the actions, and names the keys in the hint line only then. On a dry run the review and the result say what would change and that nothing was written; a failed review or run names the next step. Ctrl-C during the apply stops the screen and the run. `NO_COLOR` (or `TERM=dumb`) removes the colour and keeps bold; `FORCE_COLOR` forces it; a locale that is not UTF-8 gets ASCII glyphs.

**Flags.** Each choice has a flag, and giving one skips the screen and applies directly, with the other choice left on:

| Flag                      | Effect                                                                                 |
| ------------------------- | -------------------------------------------------------------------------------------- |
| `--worktrees on\|off`     | New threads start in worktrees (`defaultThreadEnvMode "worktree"`) or stay as they are |
| `--device-access on\|off` | Device access is written where a host is found, or left out                            |
| `--no-tui`                | No screen; both choices on                                                             |

The line-based setup also runs, with one `~ t3 tui:` line saying why, when stdin or stdout is not a terminal, `CI` is set to a truthy value (not empty, `0`, `false`, `no` or `off`), `TERM` is `dumb`, `--no-tui` or a choice flag was given, or the screen cannot be installed or started (offline). With no T3 work (the capability rows alone), a run that cannot use the screen prints no `~ t3 tui:` line.

**Packaging.** OpenTUI's native renderer cannot be bundled into the platform-neutral `holyagent.js`, and neither the Claude plugin nor the Pi package ships `node_modules`. So the screen is its own bundle, `scripts/setup-tui.js` beside `holyagent.js` in both, built at HolyAgent build time with the `@opentui/solid` Bun plugin and with `@opentui/core`, `@opentui/solid` and `solid-js` left as imports. The first time setup shows the screen it runs `bun install --frozen-lockfile --ignore-scripts` of those three packages, with no `.env` and the empty Bun config the plugin ships. The build embeds the three exact versions and a lockfile subset cut from `bun.lock` (exactly the entries the three packages reach, with the repository lock's resolutions and integrity hashes, so Solid's `s-js` and the native `@opentui/core-<platform>` resolve as they do in the repository; `mise run deps:update` keeps them current with no second pin table). The install goes into HolyAgent's own cache folder (`XDG_CACHE_HOME`, else `~/.cache`, on Linux and macOS; `LOCALAPPDATA` on Windows) under `holyagent/setup-tui/<versions>_<lock hash>`. It runs in a fresh temporary folder beside the final one, which is renamed into place with a completion marker (`.holyagent-installed`) written last, so a folder without the marker counts as absent and an interrupted install or half-written file is never used; two first runs at once each install and the first rename wins. The cache folders are created with mode 0700, and a folder that is a link, belongs to another user or can be written by group or others (POSIX) is refused: setup says why in its one `~ t3 tui:` line and uses the line-based setup. A later run finds the packages in place and installs nothing. The bundle is written next to the installed packages as a new file renamed over the old one, so a link planted at its path is replaced and never followed, and imported from there. A line of the install's error output shown on failure has its escape sequences and control characters removed. Needs the network on the first run and a Bun that OpenTUI supports: `@opentui/core` declares `engines.bun` as `>=1.3.14`. HolyAgent checks no Bun version itself; if the install or the start fails, setup uses the line-based setup.

## Tests

CI covers T3 with fixtures of `pi --mode rpc` traffic that are synthesized from T3's launch code and Pi's RPC types, not recorded from T3, inside the existing `check` and `windows` jobs, as the other Pi tests do ([orchestration.md](orchestration.md#ci-and-windows)); no job is added or renamed. `mise run deps:update` moves the Pi host used for development and tests with the lockfile, and the Pi package pins, but does not rewrite the fixtures; a move that changes Pi's traffic shows up as a failing replay until they are written again ([development.md](../development.md#re-recording-the-pi-fixtures)). The replay runs the real extension and covers:

- the `ctx.ui` calls HolyAgent makes: only `select`, `confirm`, `input`, `editor`, `notify` and `setStatus`, and no `setWidget`, `custom()` or `setTitle` call, with the one `setStatus` warning below Full access.

Unit tests (`packages/integrations/pi/tests/t3.test.ts` and `extension.test.ts`) cover the rest: T3 session detection, the access-mode check, the active tool set after the start and its correction, and the `tool_call` block on a deactivated T3 tool.

The late-completion fixture, a completion notice after `agent_settled` opening a new root turn, documents an assumed T3 behavior and is not a regression test.
