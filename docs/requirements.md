## Why Bun canary

The repository's toolchain is Bun's own `bun check`, `bun lint` and `bun fmt`, which exist only in canary builds. mise cannot install `bun@canary`, so it installs the stable base and `bun upgrade --canary` replaces the binary in place (mise's `postinstall` hook, the installer and `holyagent doctor --fix` do this). A later `mise upgrade bun` that installs a new stable version brings stable back, so every repository gate first runs the `toolchain` task and fails with the fix when Bun is not canary. A `--smol` in `BUN_OPTIONS` makes `bun upgrade` fail, so the `postinstall` hook in `mise.toml` (from the CI pull request, #10) and `holyagent doctor --fix` (from the public CLI pull request, #6) run the upgrade with `BUN_OPTIONS` unset; when you upgrade by hand, run `env -u BUN_OPTIONS bun upgrade --canary`.

The plugin's runtime only calls `bun` and does not check the build. Running the plugin needs Bun; developing HolyAgent needs the canary.

## Claude Code version

- Documented minimums: `subagentPromptCacheTtl` (written by `holyagent setup claude`) 2.1.242 or later, agent `experimental.cacheTtl` (set in every specialist file) 2.1.248 or later, hook `onFailure: "block"` 2.1.295 or later (stated on the Claude Code [hooks](https://code.claude.com/docs/en/hooks.md), [sub-agents](https://code.claude.com/docs/en/sub-agents.md) and settings reference pages). The 55-minute reuse window assumes the 1-hour cache that `subagentPromptCacheTtl` selects. The plugin was tested with 2.1.310.
- Only the `workflow` hook uses `onFailure: "block"`, the `vcs-reminder` entries use `if` filters and the `subagent-start` hook is a `SubagentStart` hook (both only add context), the launch recorder is a `PostToolUse` hook on Agent, and the inline workflow scripts the root writes use the `Workflow` tool. Workflows are also subject to your plan and settings: `enableWorkflows: false`, `disableWorkflows: true` or `CLAUDE_CODE_DISABLE_WORKFLOWS=1` turns them off, and `plan` then recommends direct subagents (see [cache-and-workflows.md](cache-and-workflows.md)).
- Plugin `settings.json` supports `agent` (and `subagentStatusLine`) only, which is why `holyagent setup claude` exists.

| --------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

| Claude Code on native Windows                 | Written for, not tested on a Windows machine. The hooks are exec form (`bun` with arguments, no shell), the documented CLI invocation runs in PowerShell, cmd and bash, and `install/windows-install.ps1` sets up the environment (see below) |

## Native Windows

Claude Code on native Windows runs the plugin without WSL and without a POSIX shell. `install/windows-install.ps1` mirrors the WSL installer in eight steps (prerequisites with `winget`, mise, Node LTS, Bun canary, Claude Code, Billion Context, ctx7, verification); it needs Windows PowerShell 5.1 or PowerShell 7 and `winget` for `git` and `mise`, and runs in a normal, not elevated, window.

- **Hooks.** Exec form needs a real executable on `PATH`, `bun.exe` here, so install Bun the usual way (the installer does) and start Claude Code from a window that sees it. Git Bash is not needed for the hooks; Claude Code's own Bash tool still uses Git Bash when it is installed, and falls back to PowerShell otherwise.
- **Invoking the CLI by hand.** `bun "<plugin>/scripts/holyagent.js" <command>` runs unchanged in PowerShell, cmd and bash (add `--no-env-file "--config=<plugin>/scripts/empty-bunfig.toml"` before the script in a repository you do not trust, as the hooks do). The `sh` wrapper `scripts/holyagent` is for POSIX shells only.
- **Developing here.** `mise run` tasks are Bun scripts (`scripts/toolchain.ts`, `scripts/prepare.ts`) and the git hooks call Bun directly, so they need no `grep`, `env` or `/dev/null`.
- **Not tested.** There was no Windows machine. The path handling (separators, `PATH` casing and delimiter, home directory, glob patterns, commit scope) is unit tested with the platform's separator passed in, and the hook form follows Claude Code's documentation; the installer, the exec-form hooks, `git` worktree paths (`C:/…` from git) and the bundled `rg.exe` and `fd.exe` were not run on Windows. ctx7 and Billion Context file locations on Windows follow the Linux defaults (`~/.config`), which those projects may not use there.

The public `holyagent` CLI is a Bun program (`packages/cli/src/index.ts`, with a `bun` shebang). Run it from a checkout, after `bun install` there, with `bun packages/cli/src/index.ts <command>`, or put that file on your `PATH`.
