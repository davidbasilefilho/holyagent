## Why Bun canary

The repository's toolchain is Bun's own `bun check`, `bun lint` and `bun fmt`, which exist only in canary builds. mise cannot install `bun@canary`, so it installs the stable base and `bun upgrade --canary` replaces the binary in place (mise's `postinstall` hook does this). A later `mise upgrade bun` that installs a new stable version brings stable back, so every repository gate first runs the `toolchain` task and fails with the fix when Bun is not canary. A `--smol` in `BUN_OPTIONS` makes `bun upgrade` fail, so the `postinstall` hook in `mise.toml` (from the CI pull request, #10) runs the upgrade with `BUN_OPTIONS` unset; when you upgrade by hand, run `env -u BUN_OPTIONS bun upgrade --canary`.

Running the plugin needs Bun, whatever its build; developing HolyAgent needs the canary, and the plugin's runtime, `holyagent setup` and `holyagent doctor` do not check for it.

## Claude Code version

- Documented minimums: `subagentPromptCacheTtl` (written by `holyagent setup`) 2.1.242 or later, agent `experimental.cacheTtl` (set in every specialist file) 2.1.248 or later, the root's `modelSettings` entry 2.1.251 or later for `effortLevel` and 2.1.288 or later for `autoCompactWindow` (100000 to 1000000 tokens), hook `onFailure: "block"` 2.1.295 or later (stated on the Claude Code [hooks](https://code.claude.com/docs/en/hooks.md), [sub-agents](https://code.claude.com/docs/en/sub-agents.md) and settings reference pages). The shorter `attribution: false` form needs 2.1.281 or later; `holyagent setup` writes the object form, which earlier versions also read. The highest minimum the plugin depends on is 2.1.295, so it needs 2.1.295 or later. The 55-minute reuse window assumes the 1-hour cache that `subagentPromptCacheTtl` selects.
- Tested version: the `@anthropic-ai/claude-code` version in `bun.lock`. The CI validation step and the plugin tests run `claude plugin validate --strict` with it. The hook `if` globs and the exec form were also probed by hand on 2.1.310; the hooks reference documents no minimum version for exec-form `args` or the `if` field.
- Only the `workflow` hook uses `onFailure: "block"`, the `vcs-reminder` entries use `if` filters and the `subagent-start` hook is a `SubagentStart` hook (both only add context), the launch recorder is a `PostToolUse` hook on Agent, and the inline workflow scripts the root writes use the `Workflow` tool. Workflows are also subject to your plan and settings: `enableWorkflows: false`, `disableWorkflows: true` or `CLAUDE_CODE_DISABLE_WORKFLOWS=1` turns them off, and `plan` then recommends direct subagents (see [cache-and-workflows.md](cache-and-workflows.md)).
- Plugin `settings.json` supports `agent` (and `subagentStatusLine`) only, which is why `holyagent setup` (`/holyagent:setup`) exists.

## Native Windows

Claude Code on native Windows runs the plugin without WSL and without a POSIX shell, and the maintainer has tested it on a Windows machine. `install/windows-install.ps1` mirrors the WSL installer in five steps (prerequisites with `winget`, Node LTS, Bun, `gh`, verification), or six with `-Dev`, which adds mise; it needs Windows PowerShell 5.1 or PowerShell 7 and `winget` for `git`, Node LTS, `gh` and, with `-Dev`, `mise`, and runs in a normal, not elevated, window.

- **Hooks.** Exec form needs a real executable on `PATH`, `bun.exe` here, so install Bun the usual way (the installer does) and start Claude Code from a window that sees it. Git Bash is not needed for the hooks; Claude Code's own Bash tool still uses Git Bash when it is installed, and falls back to PowerShell otherwise.
- **Invoking the CLI by hand.** The form in [How the hooks start](hooks.md#how-the-hooks-start) runs unchanged in PowerShell, cmd and bash. The `sh` wrapper `scripts/holyagent` is for POSIX shells only.
- **Pi on Windows: the Kimi wrapper runs through bash.** Under Pi, the Kimi instructions tell the root and the specialists to run `holyagent <command>` as `${HOLYAGENT_PI_ROOT}/scripts/holyagent`, the `sh` wrapper, through Pi's `bash` tool, which needs Git Bash (Git for Windows) on Windows. The installer's `git` step installs it; make sure Pi's `bash` tool finds it. The roles also get Pi's `powershell` tool wherever they get `bash`, and the root has it on Windows even where Pi's default selection has only `bash`, but the wrapper is a POSIX script and does not run in PowerShell. The extension's own calls need no shell: it starts Bun directly ([pi/orchestration.md](pi/orchestration.md#ci-and-windows)).
- **Developing here.** `mise run` tasks are Bun scripts (`scripts/toolchain.ts`, `scripts/prepare.ts`) and the git hooks call Bun directly, so they need no `grep`, `env` or `/dev/null`.
- **Notes.** The path handling (separators, `PATH` casing and delimiter, home directory, glob patterns, commit scope) is also unit tested with the platform's separator passed in, and the hook form follows Claude Code's documentation. ctx7 file locations on Windows follow the Linux defaults (`~/.config`), which that project may not use there.
