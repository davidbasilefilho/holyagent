# Subscription routing

`normal` and `fast` name per-provider subscription targets of $100 and $20 a month. They are not aggregate budgets, speed guarantees, or statements of account entitlement. Activate specialist selection explicitly with `HOLYAGENT_ROUTING_PROFILE=normal` or `fast` for either host. Pi also accepts `pi.profile` in HolyAgent configuration; the session environment variable takes precedence. Without activation the existing launch behavior is retained.

Pi and T3 Code setup seed their untouched native startup preferences from `pi.routes.root`, including the effective provider, model and effort. The startup choice applies to new sessions only and does not select a primary provider for specialists. Later user choices are preserved. You can still override the model in the host or explicitly at launch. For example, launch Pi with `pi --model openai-codex/gpt-6.2-sol:high`. For Claude, setup leaves the root model unchanged. Launch with `claude --agent holyagent:holyagent --model sonnet` for fast or `--model opus` for normal. The account and host must support the chosen model.

To rank specialists, provide a versioned `routing` object in the user or project HolyAgent config. It contains `version: 1`, `maxAgeDays` (1–365), `candidates`, `benchmarks`, and `evidence`. A candidate declares `role`, runtime `harness` (`pi` or `claude`), `provider`, `model`, `effort`, `plan`, `tier`, `availability`, `capabilities`, `requiredCapabilities`, and `identityStable`. Availability and each capability are `yes`, `no`, or `unknown`. A benchmark declares `role`, runtime `harness`, `benchmark`, `benchmarkVersion`, `benchmarkHarness`, `qualityUnit`, and `requiredCapabilities`. The benchmark harness identifies the shared proxy used to compare the rows; it does not need to be the production host.

The evidence object contains `version: 1`, a `revision`, `retrievedAt`, `generatedAt`, and `rows`. Each row identifies the same role, runtime harness, provider, model, effort, plan, tier, benchmark, benchmark version, benchmark harness and quality unit. It also supplies `region`, `monthlyUsd`, `allowance`, `utilization`, `cacheAssumptions`, `direction` (higher), `quality`, positive `taskCostUsd`, `costKind` (subscription), `measuredAt`, `sourceUrl`, `planSourceUrl`, `planSourceDate`, and `confidence`. Dates must fall within the configured freshness window and sources must be HTTP(S). The schema rejects unknown fields. The deterministic examples in `packages/runtime/tests/routing-dispatch.test.ts` illustrate this shape; they are test fixtures, not actual market data.

Candidates must declare the role's required capabilities, including `tools` and `vision` for screen assignments. The declarations express configured eligibility, not live account entitlement. Ranking excludes missing, stale, ambiguous or API-price fallback rows and unsupported capability declarations. Eligible comparable values are quality divided by positive subscription task cost, normalized to the maximum. Dispatch reports the selected score, source revision, plan, cost and coverage, or explicitly reports the existing unscored policy and reason. Published data currently lacks comparable subscription task-cost rows for several exact model, effort and plan combinations; no synthetic rows are shipped as real evidence.

Without an explicit `pi.providers` list, Pi may select only providers already named by `pi.provider` or an explicit role route; the candidate list constrains ranked evidence and does not add providers, credentials or tool permissions. When comparable evidence is missing, the separately configured unscored policy supplies the fallback model, which need not appear in the candidate list. Explicit per-role provider, model and thinking overrides take precedence. For a managed Pi direct Agent call, the gate reads the current Assignment and config, checks the role and screen capability, requires the saved dispatch to match the current selection, and checks the exact authenticated provider/model and thinking level. A stale or missing dispatch requires redispatch. Agent definitions and host/user overrides remain under the host’s control; the effective model is not attested and account entitlement remains unverified. The pinned workflow resolver can switch providers through fuzzy matching, so profiled plans use direct Agent calls and profiled workflow calls are refused. Unknown selected models fail closed with an actionable message. Claude's Agent tool accepts model aliases `sonnet`, `opus`, `haiku`, and `fable`; other configured Claude IDs are ineligible. Host authentication, tool access and screen permissions remain independently enforced.

Profiled dispatch records the intended launch, not an observed model. Because the host does not provide a trusted observed worker model, profiled workers are not reused. Existing unprofiled continuation remains unchanged. Native Codex harness support is planned for 0.4.

## Mixed Pi routing

When `pi.providers` contains two or more providers, HolyAgent does not consult the legacy `pi.provider` as a primary route. A per-role `pi.routes` override still takes precedence, provided that provider remains enabled and the exact model is available. Provider enablement does not change the root's chosen model, credentials or tool permissions.

Mixed routing compares Pi measurements from the [Artificial Analysis Coding Agent Index v2.1](https://artificialanalysis.ai/agents/coding-agents) when a configured evidence snapshot contains exact model and effort matches. Comparisons use the published Pi index score (from 0 to 1) only, not API cost figures or subscription-price estimates. Use `costKind: "quality-only"`, `benchmark: "Artificial Analysis Coding Agent Index"`, `benchmarkVersion: "2.1"`, `benchmarkHarness: "Pi"`, and `qualityUnit: "index"`. Identify the role, runtime harness, provider, concrete model, effort, configured plan and tier, and record the source, observation date and confidence. Omit the subscription-cost fields. A provider ranking, a differently hosted result, or a model or effort that differs from the route is not a match. The index does not expose a public API. HolyAgent does not fetch or ship a ranking or supply unverified values. In the source checked on November 25, 2026, the Pi comparisons use GPT-6 Luna at max (HolyAgent's Luna routes use low, medium or high) and GLM-5.3-Flash at max (not one of the supported Pi routes). The Kimi K3.1 Pro result uses Kimi Code CLI, not Pi. None applies to the shipped Pi routes.

Without comparable data, HolyAgent can choose among exact enabled models Pi reports as available. A deterministic per-role fallback spreads roles across those routes without using checkbox order, and dispatch reports it as unscored. The Pi adapter reads the current authenticated model catalog. The standalone CLI can read the same catalog through a trusted installed `pi --list-models` in offline mode; if it cannot establish a choice across providers, use the Pi-native tools or specify a provider for the role. No benchmark can replace a missing current catalog. An explicit per-role provider can identify a dispatch when the catalog is unavailable, but the launch gate still requires the exact model to be available. An unavailable or stale selection is not silently substituted.

In Pi `provider` web mode, a search specialist can use the Kimi provider's `moonshot_search` and `moonshot_fetch` only if that installed extension exposes them. They are opt-in and use Kimi OAuth; an API key alone does not establish eligibility. Pi's Codex Responses API documentation does not establish an exposed native Pi search tool. The pinned Kimi extension executes its search independently of the selected model, and returns its own authentication and network failures. No failure silently switches to another service. `pi-web-kit` is an explicit user choice and remains available when selected even if native exposure is unknown or a native tool is active. Pi does not reveal sufficient information to distinguish an absent extension from a disabled unregistered tool, so the unknown case needs further host inventory support. HolyAgent does not change credentials, authorization or tool settings to obtain search.

Previously setup proposed `enabled: true` for Kimi's optional tools when their settings were unset. It now leaves that provider file alone, because an unset value does not establish the user's opt-in. Existing settings are left intact; enabled tools remain discoverable.

To opt in with the pinned Kimi 0.6.14 extension, set `tools.moonshot_search.enabled` and `tools.moonshot_fetch.enabled` to `true` in `~/.pi/providers/kimi-coding/config.json`, then restart Pi. Both default to `false`. Registration exposes a tool to Pi; it does not establish OAuth access or service entitlement. Doctor's setup-settings checks do not verify that native search is available.
