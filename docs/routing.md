# Subscription routing

`normal` and `fast` name per-provider subscription targets of $100 and $20 a month. They are not aggregate budgets, speed guarantees, or statements of account entitlement. Activate specialist selection explicitly with `HOLYAGENT_ROUTING_PROFILE=normal` or `fast` for either host. Pi also accepts `pi.profile` in HolyAgent configuration; the session environment variable takes precedence. Without activation the existing launch behavior is retained.

Root model choice remains an explicit host launch setting. For example, launch Pi with `pi --model openai-codex/gpt-6.1-terra:high` for fast or `pi --model openai-codex/gpt-6.1-sol:high` for normal. For Claude use `claude --agent holyagent:holyagent --model sonnet` for fast or `claude --agent holyagent:holyagent --model opus` for normal. These are session choices; a profile alone does not replace the host's root model. The account and host must support the chosen model.

To rank specialists, provide a versioned `routing` object in the user or project HolyAgent config. It contains `version: 1`, `maxAgeDays` (1–365), `candidates`, `benchmarks`, and `evidence`. A candidate declares `role`, runtime `harness` (`pi` or `claude`), `provider`, `model`, `effort`, `plan`, `tier`, `availability`, `capabilities`, `requiredCapabilities`, and `identityStable`. Availability and each capability are `yes`, `no`, or `unknown`. A benchmark declares `role`, runtime `harness`, `benchmark`, `benchmarkVersion`, `benchmarkHarness`, `qualityUnit`, and `requiredCapabilities`. The benchmark harness identifies the shared proxy used to compare the rows; it does not need to be the production host.

The evidence object contains `version: 1`, a `revision`, `retrievedAt`, `generatedAt`, and `rows`. Each row identifies the same role, runtime harness, provider, model, effort, plan, tier, benchmark, benchmark version, benchmark harness and quality unit. It also supplies `region`, `monthlyUsd`, `allowance`, `utilization`, `cacheAssumptions`, `direction` (higher), `quality`, positive `taskCostUsd`, `costKind` (subscription), `measuredAt`, `sourceUrl`, `planSourceUrl`, `planSourceDate`, and `confidence`. Dates must fall within the configured freshness window and sources must be HTTP(S). The schema rejects unknown fields. The deterministic examples in `packages/runtime/tests/routing-dispatch.test.ts` illustrate this shape; they are test fixtures, not actual market data.

Candidates must declare the role's required capabilities, including `tools` and `vision` for screen assignments. The declarations express configured eligibility, not live account entitlement. Ranking excludes missing, stale, ambiguous or API-price fallback rows and unsupported capability declarations. Eligible comparable values are quality divided by positive subscription task cost, normalized to the maximum. Dispatch reports the selected score, source revision, plan, cost and coverage, or explicitly reports the existing unscored policy and reason. Published data currently lacks comparable subscription task-cost rows for several exact model, effort and plan combinations; no synthetic rows are shipped as real evidence.

Pi may select only providers already named by `pi.provider` or an explicit role route; the candidate list is an allowlist of models and does not add providers, credentials or tool permissions. Explicit per-role provider, model and thinking overrides take precedence. The pinned Pi host checks an exact authenticated provider/model registry entry before a profiled direct Agent call; account entitlement remains unverified and backend failures remain visible. The pinned workflow resolver can switch providers through fuzzy matching, so profiled plans use direct Agent calls and profiled workflow calls are refused. Unknown selected models fail closed with an actionable message. Claude's Agent tool accepts model aliases `sonnet`, `opus`, `haiku`, and `fable`; other configured Claude IDs are ineligible. Host authentication, tool access and screen permissions remain independently enforced.

Profiled dispatch records the intended launch, not an observed model. Because the host does not provide a trusted observed worker model, profiled workers are not reused. Existing unprofiled continuation remains unchanged. Native Codex harness support is planned for 0.4.

In Pi `provider` web mode, a search specialist can use the Kimi provider's `moonshot_search` and `moonshot_fetch` only if that installed extension exposes them. They are opt-in and use Kimi OAuth; an API key alone does not establish eligibility. Pi's Codex Responses API documentation does not establish an exposed native Pi search tool. The pinned Kimi extension executes its search independently of the selected model, and returns its own authentication and network failures. No failure silently switches to another service. `pi-web-kit` is an explicit user choice and remains available when selected even if native exposure is unknown or a native tool is active. Pi does not reveal sufficient information to distinguish an absent extension from a disabled unregistered tool, so the unknown case needs further host inventory support. HolyAgent does not change credentials, authorization or tool settings to obtain search.

Previously setup proposed `enabled: true` for Kimi's optional tools when their settings were unset. It now leaves that provider file alone, because an unset value does not establish the user's opt-in. Existing settings are left intact; enabled tools remain discoverable.

To opt in with the pinned Kimi 0.6.13 extension, set `tools.moonshot_search.enabled` and `tools.moonshot_fetch.enabled` to `true` in `~/.pi/providers/kimi-coding/config.json`, then restart Pi. Both default to `false`. Registration exposes a tool to Pi; it does not establish OAuth access or service entitlement. Doctor's setup-settings checks do not verify that native search is available.
