# Usage

## What it fits

HolyAgent is not only for multi-PR projects. The root sizes the plan to the request: one Assignment for a small change, several for a larger one, a read-only specialist for a question. It picks the cheapest specialist whose description fits.

- **A one-file fix or a small feature.** One Assignment, run as a one-entry workflow, with an independent review of its commit. It lands as one branch and one PR, or as the repository's conventions ask, which come first.
- **A bug with an unknown cause.** Worker.debugging diagnoses it in phases and repairs it; a bug with a known reproduction goes to Worker.implementation as a fix with a regression test.
- **Questions about a codebase or a library.** The explorers answer from the repository and the librarians from documentation and the web (through the Exa connector). They are read-only, so nothing is edited or committed.
- **Reviewing an existing PR or branch.** Reviewer.code, Reviewer.security, Reviewer.testing and the other reviewers judge a committed range and report findings. The root replies on a thread only when you ask for it or the repository's workflow does.
- **Refactors and mechanical changes.** Worker.mechanical applies a specified transformation consistently, and an independent reviewer judges the change like any other.
- **Front-end and UI work.** Worker.visual changes the interface and inspects it at the relevant viewports and states, and Reviewer.visual inspects the result independently. For each visual Assignment the root picks the platform design skill (`web-design`, `mobile-design`, `desktop-design` or `tui-design`) and names its file in both specialists' criteria; they read it and judge against its checklist. The root then makes its own final pass on the reviewer's final captures at the listed sizes and variants and decides acceptance.
- **Docs and configuration.** Worker.implementation changes them like code, and Reviewer.artifact (Sonnet, unlike the Haiku mechanical roles) reviews documents, configuration and instruction text.
- **Personal, coursework and solo repositories.** Tell the root it is yours and works on one branch, and which state mode you want: `local` keeps state out of every commit and branch, `work` commits it with the work (see [User settings](#user-settings)). Without a stated mode, the root follows the order under [User settings](#user-settings): an owned repository with no tracked state and no independent-PR convention gets `branch` mode, with its `holyagent/state` branch. Pushing to the base branch still waits for your approval. In a repository you do not control, keep the clone out of `work`.
- **Larger deliveries.** Several Assignments run in parallel on disjoint paths and land as stacked PRs, one reviewed change each (see [Stacks](#how-a-session-works)).

## Install

Check [requirements.md](requirements.md) first: Bun on `PATH`, Node.js LTS, `git`, an authenticated `gh`, and ripgrep and fd on `PATH` (`brew install ripgrep fd`, `sudo apt install ripgrep fd-find`, `sudo dnf install ripgrep fd-find`, `sudo pacman -S ripgrep fd`, or `winget install BurntSushi.ripgrep.MSVC` and `winget install sharkdp.fd` in a new terminal; HolyAgent does not bundle them). HolyAgent installs as a plugin, with these two commands and nothing else (no clone, no `bun install`).

**Marketplace.** The plugin is published from this repository's `main` branch. From a shell:

```sh
claude plugin marketplace add davidbasilefilho/holyagent
claude plugin install holyagent@holyagent
```

Inside Claude Code the same steps are `/plugin marketplace add davidbasilefilho/holyagent` and `/plugin install holyagent@holyagent`. The plugin has no dependencies. The Search specialists get their web tools from the Exa connector (see **Web search** below). The plugin's own `settings.json` makes the main thread the root agent (`agent: holyagent`) while the plugin is enabled, except in a claude.ai cloud session, where that setting did not take effect and the hooks give the main thread the rules instead ([hooks.md](hooks.md#root-rules)).

**A specific release.** Every push to `main` publishes the tag `holyagent-<version>` (for example `holyagent-0.2.1`) and a GitHub Release, and every other branch push publishes a pre-release tagged `holyagent-<version>-dev-<short-hash>`. Claude Code takes a Git ref after `#` on a marketplace source, so adding the marketplace at a tag installs the plugin as built at that tag, because the built plugin is committed:

```sh
claude plugin marketplace add davidbasilefilho/holyagent#holyagent-0.2.1
claude plugin install holyagent@holyagent
```

Inside Claude Code: `/plugin marketplace add davidbasilefilho/holyagent#holyagent-0.2.1`, then `/plugin install holyagent@holyagent`. The CLI reference also accepts `owner/repo@ref`. There is no `name@tag` form on `plugin install`: the tag pins the marketplace, not the plugin name. This follows the Claude Code [install](https://code.claude.com/docs/en/plugins/install) and [CLI](https://code.claude.com/docs/en/plugins/cli-reference) pages; this repository's tag names have not been run through it yet.

**First launch: `/holyagent:setup`.** The plugin can only set `agent` and `subagentStatusLine`, so on the first launch run `/holyagent:setup` in a session. It runs `holyagent setup`, which installs the ctx7 CLI, then merges the recommended keys into your user settings (`~/.claude/settings.json`, or `CLAUDE_CONFIG_DIR`; see [User settings](#user-settings)), or into one project's settings with `--scope project|local` (without `--scope`, only your own untracked `.claude/settings.local.json` that enables the plugin picks `local`; see [Setup and doctor follow the scope](#install-scopes)), and `--undo` backs them out ([Scope and undo](#scope-and-undo)). The choices behind the keys are explained under [Opinionated by design](#opinionated-by-design). Until it has run, the session-start hook adds one line suggesting `/holyagent:setup` whenever `ctx7` is missing or a key is missing from the user settings and from the project and local settings of the session folder alike, so the line also stops once a `--scope project|local` setup ran there; it never appears in a claude.ai cloud session, where setup skips `ctx7` ([hooks.md](hooks.md)). The command takes these flags, which `/holyagent:setup` passes through:

```sh
holyagent setup [--scope user|project|local] [--undo] [--dry-run] [--subagent-cache-ttl 1h|5m] [--skip-ctx7] [--<capability> on|off] [--form headless|normal] [--worktrees on|off] [--device-access on|off] [--no-tui]
```

`--<capability> on|off` turns one Pi capability on or off (`--subagents`, `--context-compression`, `--todo`, `--ask`, `--processes`, `--mcp`, `--computer-use`, `--browser-use`, `--just-bash`, `--fff`) by writing `pi.features.<key>` to the config of the scope, and `--form headless|normal` overrides the headless or normal form that setup otherwise detects from the machine ([Capabilities](pi/configuration.md#capabilities)); a capability flag is refused with `--undo`. The last three flags belong to the T3 Code step for Pi and are explained under [The T3 Code setup screen](#the-t3-code-setup-screen); they change nothing else. Every step checks its own result first, so a re-run changes nothing that is already set, and a failed step does not stop the others; the command exits 1 at the end if any step failed. `--dry-run` shows what would change and installs and writes nothing. The steps run in this order: ctx7, the capability choices, the Pi packages, the Pi tool settings, the T3 Code settings (Pi in use, `--scope user` only), a report that `rg` and `fd` are installed ([components.md](components.md#ripgrep-and-fd)), settings. The Pi step runs only when Pi is in use (`HOLYAGENT_HOST=pi` or `pi` on `PATH`) and not in a cloud session: it runs `pi install` for each package your `config.json` enables that neither Pi's global nor its project settings list at its pin and `pi remove` for each HolyAgent-managed package the config no longer selects (with `pi.enable` off it removes nothing and says so), at Pi's global settings for `--scope user`, which reads your own `~/.holyagent/config.json` only, and at the project's `.pi/settings.json` (`-l`, run in the project directory, which reads its npm and Pi settings, so only in a repository you trust) for `project` and `local`, so after you turn a feature on or off, such as `pi-web-kit`, re-run setup. The tool settings step follows it under the same conditions and merges the settings the config implies (codemode mode, the computer-use confirmations, the subagent and Moonshot tool settings, Billion Context's) into the files the Pi packages read, one line per file, without overwriting a value you set; at `project` and `local` it writes the project's `.pi` folder, leaves a key your global file already sets, and refuses a symlinked `.pi` folder or file, and `--undo` removes the keys it added ([pi/installation.md](pi/installation.md#what-setup-and-doctor-do)). The output has one line per step: `+` done now, `=` already done, `-` skipped, `~` kept or needs you, `!` failed (with `--undo`, `-` means removed and `=` nothing to remove). Context7 authentication is managed separately; setup no longer installs external Context7 skills or rules and leaves existing files and credentials alone. Restart Claude Code when the report shows a `+` line. What setup and `holyagent doctor` do, piece by piece, is in [components.md](components.md#what-holyagent-setup-and-holyagent-doctor-do).

**`holyagent doctor [--scope user|project|local] [--form headless|normal] [--fix]`** checks what setup configures, one line each (`ok` or `FAIL`), and exits 1 when a check fails; when Pi is in use it also checks Pi, the form (detected, or named by `--form`) and the health of each capability the config turns on (its system needs and its packages at their pins), and otherwise prints one informational `~ pi: not in use` line; `--fix` runs the setup steps behind a failing check ([components.md](components.md#what-holyagent-setup-and-holyagent-doctor-do)). `holyagent` here is the CLI form under [How the hooks start](hooks.md#how-the-hooks-start); inside a session `/holyagent:setup` is the shortcut.

**The prerequisites on a clean machine.** The installers set up only what the plugin needs around it, and a re-run skips what is already right. They do not install Claude Code, the plugin, ripgrep or fd (install the last two with the command for your platform in [components.md](components.md#ripgrep-and-fd)): each ends by printing the two commands above.

- **WSL Ubuntu.** Run `bash install/wsl-install.sh [--dev]` as your own user, not through sudo; it calls sudo itself only for apt. It installs the prerequisites listed in [components.md](components.md#mise-node-bun-gh) in five steps with a final verification, or six with `--dev`, which adds a mise step. It warns, and continues, on a system that is not WSL or not Ubuntu. Open a new shell when it finishes so `PATH` picks up Bun. The script's header lists what you opt into: the two apt repositories and one line added to `~/.bashrc`.
- **Native Windows.** Run `powershell -ExecutionPolicy Bypass -File install\windows-install.ps1 [-Dev]` in a normal (not elevated) window; it runs the same steps with `winget`, and your user `PATH` in place of `~/.bashrc`. Native Windows is supported and was tested by the maintainer on a Windows machine ([requirements.md](requirements.md#native-windows)). CI also runs the test suite on `windows-latest` (the `windows` job); its run shows any failing tests. For Pi on Windows, the Kimi wrapper (`scripts/holyagent`) runs through Pi's `bash` tool, so Git Bash (Git for Windows, which the installer installs) must be present ([requirements.md](requirements.md#native-windows)).
- **Developing HolyAgent.** Pass `--dev` (`-Dev` on Windows) to also install mise, which a checkout needs; without it the installers neither install nor use mise ([components.md](components.md#mise-node-bun-gh), [requirements.md](requirements.md#why-bun-canary)).

**This repository.** `.claude/settings.json` already declares the checkout as the `holyagent` marketplace (a `directory` source with the relative path `.`, whose `.claude-plugin/marketplace.json` points at `packages/integrations/claude/dist`) and enables `holyagent@holyagent`, so a session started here runs the root from the local build. Trusting the folder in an interactive session registers the declared marketplace. From a shell on a new machine, register it in your user settings instead (`marketplace add ./` run without `--scope user` would write an absolute path into the project settings), then install the plugin for the project: `claude plugin marketplace add ./ --scope user`, and `claude plugin install holyagent@holyagent --scope project`. In WSL, after the checkout was opened and trusted, Claude Code recorded a project-scope install for the plugin in `installed_plugins.json`.

**Updates here.** A directory marketplace is read from its source folder at the start of every session: `claude plugin list` prints `Read from <source>` for it, and the session loads the plugin from that folder. After `mise run build` changes the plugin, start a new session or run `/reload-plugins`; no `plugin update` or `marketplace update` command is needed. The cache copy and the record in `installed_plugins.json` go stale and do not matter, because `claude plugin update` rewrites the cache only when the version changes, or refreshes it in place when the plugin declares no version.

**The Claude desktop app lists a second copy.** The desktop app reads plugins from its own account store (`AppData/Roaming/Claude/rpm` on Windows), which never shows the WSL project install (the desktop Plugins screen showed "This project: 0" as seen in the desktop app). There `holyagent` appears as a user-added marketplace plugin, a full copy with its own version label, kept as a separate record, so the desktop list says nothing about what a Code-tab session on this checkout loads. To remove the duplicate, uninstall the plugin or remove the user-added `holyagent` marketplace in the desktop app under Settings > Plugins; the project install keeps working.

**Web search: the Exa connector.** The Search specialists (Librarian.lookup and Librarian.research) search and read pages with Exa, and Claude Code's own `WebSearch` and `WebFetch` are denied, so the connector is the only web path. Connect Exa once at [claude.ai/customize/connectors](https://claude.ai/customize/connectors); the tool names, the account-login limit and the reasons are under [Exa](components.md#exa), and how to drop the deny is under [Opinionated by design](#opinionated-by-design).

The two install commands above install at user scope; [Install scopes](#install-scopes) shows project and local scope and how a team shares one. Restart Claude Code after installing so the plugin loads. `holyagent doctor [--fix]` checks the result (see [components.md](components.md#what-holyagent-setup-and-holyagent-doctor-do)).

## User settings

`holyagent setup` does this as its last step. A plugin can only set `agent` and `subagentStatusLine`, so the rest of the recommended settings are this command's job. It adds the missing keys to the settings file of `--scope` (your user settings, `~/.claude/settings.json` or the file in `CLAUDE_CONFIG_DIR`, unless you pick another or your own untracked local file selects `local`) and never changes a value that is already set (`+` added, `=` already that value, `~` kept, with the recommendation shown). The settings step's only other write is its record of the keys it added, `holyagent/setup-records.json` under `CLAUDE_CONFIG_DIR` (else `~/.claude`), with mode 600 (see [Scope and undo](#scope-and-undo)).

| Key                                     | Value                                                        |
| --------------------------------------- | ------------------------------------------------------------ |
| `permissions.deny`                      | `["WebSearch", "WebFetch"]`; an existing list is kept        |
| `modelSettings["claude-opus-5-5"]`      | `effortLevel: "high"`, `autoCompactWindow: 450000`           |
| `includeGitInstructions`                | `false`                                                      |
| `attribution.commit`, `attribution.pr`  | `""`                                                         |
| `attribution.sessionUrl`                | `false`                                                      |
| `subagentPromptCacheTtl`                | `1h`; `--subagent-cache-ttl 5m` only when the key is missing |
| `extraKnownMarketplaces.holyagent`      | GitHub `davidbasilefilho/holyagent`                          |
| `enabledPlugins["holyagent@holyagent"]` | `true`                                                       |

`attribution` is written as an object (`commit`, `pr`, `sessionUrl`), the form earlier Claude Code versions also read (the shorter `attribution: false` has its own minimum under [Claude Code version](requirements.md#claude-code-version)). The reasons for each key are under [Opinionated by design](#opinionated-by-design).

**The root's effort and window.** The root agent file declares `effort: high`, but Claude Code ignores an agent's `effort` when the agent is the main thread (anthropics/claude-code#81677, #97829); the field applies when the root runs as a subagent. The main thread's level comes from your settings, and a plugin cannot ship them: a plugin's `settings.json` honors only `agent` and `subagentStatusLine`, and a top-level `effortLevel` in user settings does not apply to Opus 5.5, so the level and the window are per-model `modelSettings` entries (minimum versions under [Claude Code version](requirements.md#claude-code-version)). `holyagent setup` and `holyagent doctor` check for them, this repository's `.claude/settings.json` carries the same block, and an existing value of yours is kept. `/effort` and `/autocompact` write these keys too.

- **A claude.ai cloud session** has its own container, so the settings on your machine do not reach it. Run `/holyagent:setup` in the session (setup still merges the user settings there), or commit the same `modelSettings` block to the repository's `.claude/settings.json`, which every session of that repository reads. `CLAUDE_CODE_AUTO_COMPACT_WINDOW=450000` in the cloud environment's variables sets the window alone.
- **A Sonnet root** ([below](#run-the-root-on-sonnet)) is keyed by its own model name: add `"claude-sonnet-5-5": { "effortLevel": "high", "autoCompactWindow": 450000 }` under `modelSettings` in your user settings or the project file; setup writes only the Opus entry.
- **The key follows the model the `opus` alias resolves to.** `holyagent setup` and `holyagent doctor` write and check `claude-opus-5-5` only, so when the alias moves to another model, add the same entry under that model's name.
- **Never set `CLAUDE_CODE_EFFORT_LEVEL`.** It overrides the `effort` of every specialist, which the routes set.

The project state is a `.holyagent/` folder created by the first `intent create`. Where it lives is the clone's state mode, read and set with `holyagent state mode [branch|work|local]` and kept in the clone's git config (`holyagent.stateMode`, never a repository file): `branch`, the default, puts it on its own branch, `holyagent/state`, in one worktree shared by every worktree of the clone, so work branches never carry it and the root pushes that branch with the work; `work` keeps it in the work tree, where `vcs commit` stages the changed state files with the work; `local` keeps it in the work tree too, excluded through `.git/info/exclude` (not `.gitignore`), so no commit or PR carries it (see [decisions.md](decisions.md)). The root sets the mode before the first Intent of a project, by the signal order in [decisions.md](decisions.md): your words, a repository you do not control, tracked state (not `config.json`), independent-PR conventions, else `branch`. The command moves no records: it refuses to leave `branch` once the state branch exists, to enter it while the work tree's `.holyagent/` holds records, and to set `local` while git tracks state in `.holyagent/` (`config.json` aside). Everything under `.holyagent/local/` is per clone and ignored by git: the specialist registry, the Intent in use of each work tree and `work-trees.json`, the work tree each Running Assignment was dispatched from, so writers in different work trees can own the same paths. `.holyagent/config.json` holds optional project settings (`vcs.allowWords`; an old `vcs.api` is still read and ignored). A user-level `~/.holyagent/config.json` is planned for 0.3.0 ([Install scopes](#install-scopes)).

**Choosing a mode in a repository that tracks state.** When git tracks files under `.holyagent/` other than `config.json`, `local` is refused, because an exclude entry cannot hide tracked files, and `vcs commit` in `local` refuses a commit that stages any of them. `work` then stages the changed state files with the work, so they enter the repository's history: choose it only when the repository's owner (you, or someone who agreed) wants Intent state there. In a repository you do not control, keep the clone out of `work` and leave the tracked files alone; `branch` keeps the records on the state branch, but it is refused while a work tree's `.holyagent/` already holds records. `vcs commit` refuses a short Windows name (8.3, such as `HOLYAG~1` or a hashed `HOA3F2~1`) as the first part of a path unless it is a real entry of the work tree or a name still in HEAD's tree (for example a folder whose removal is staged), since Windows would resolve it to the state folder; name the folder by its full name.

**A clone that ran the unreleased build of `local`.** An earlier unreleased build could leave an unmarked `/.holyagent/` line in `.git/info/exclude` when it entered `local`. The current build removes only the two lines it adds itself (a comment `# added by holyagent (state mode local)` and the `/.holyagent/` line under it), because it cannot tell an unmarked line from one you wrote. After leaving `local` for `work`, `.holyagent/` stays git-ignored in such a clone and `git status` does not show it. Open `.git/info/exclude` (in a linked work tree, the one in the main clone's `.git/info/`), delete the `/.holyagent/` line that has no marker comment above it, and run `git status` to see the state files.

## Scope and undo

`holyagent setup` and `holyagent doctor` take the flags listed under [First launch](#install). `--scope` picks the settings file, named like Claude Code's own [scopes](https://code.claude.com/docs/en/settings):

| Scope            | File                                                                                        |
| ---------------- | ------------------------------------------------------------------------------------------- |
| `user` (default) | `CLAUDE_CONFIG_DIR/settings.json`, else `~/.claude/settings.json`; applies to every project |
| `project`        | `.claude/settings.json`, shared with everyone who clones the repository                     |
| `local`          | `.claude/settings.local.json`, your untracked personal file for this repository             |

`project` and `local` resolve `.claude` in the git top-level of the current directory, else in the current directory itself. A git top-level that is not the current directory or one of its ancestors is ignored (a crafted `core.worktree` can make git name any folder), the current directory is used and a hint says so. A `.claude` folder or settings file that is a symlink is refused with a `!` line and nothing is written, so a repository cannot redirect the write; `user` follows its links. ctx7 is installed for you whatever the scope. To try HolyAgent in one repository, run `holyagent setup --scope local` there (or `/holyagent:setup --scope local`), and pass the same `--scope` to `holyagent doctor`, which then checks that file and, with `--fix`, merges into it. Setup writes `enabledPlugins` into the file of the scope too, but the plugin install is separate, and the two Install commands install at user scope, where the plugin's `agent: holyagent` setting makes the root take every session. To confine HolyAgent to one repository, install the plugin at that scope instead. `claude plugin install` takes `--scope` ([plugin discovery docs](https://code.claude.com/docs/en/discover-plugins), "Manage plugins from your shell"; it acts on user scope when the flag is absent). In the repository:

```sh
claude plugin marketplace add davidbasilefilho/holyagent
claude plugin install holyagent@holyagent --scope local     # or --scope project
holyagent setup --scope local                               # same scope; /holyagent:setup --scope local in a session
```

If you already installed it for your user, remove that copy first with `claude plugin uninstall holyagent@holyagent` (user scope by default), or turn it off there with `claude plugin disable holyagent@holyagent --scope user` (both take `--scope`; see `claude plugin --help`). `holyagent setup --undo` removes `enabledPlugins["holyagent@holyagent"]` from the `--scope` file only when setup recorded adding it; when the plugin install wrote that key first, undo keeps it and reports `~`, so disable or uninstall the plugin at that scope to turn it off. `--scope local` keeps the install to you and `--scope project` shares it with everyone who clones the repository, who then each run `claude plugin install holyagent@holyagent --scope project` once.

`--undo` backs setup out of the `--scope` file and installs nothing. Setup records the keys it added, and the record is kept in `holyagent/setup-records.json` under the user's Claude Code folder (`CLAUDE_CONFIG_DIR`, else `~/.claude`), outside the project, so a repository cannot forge it to steer an undo. `--undo` removes only recorded keys, and only when the value is still the one setup wrote. A key whose value you changed is kept and reported with `~`, and so is a key setup has no record of adding (one that was there before setup, or that an earlier version added); the line tells you to remove it by hand. From `permissions.deny` it removes only the `WebSearch` and `WebFetch` entries setup added, so the rest of your list stays, and it drops objects it leaves empty. A record that cannot be read stops setup before it writes and stops `--undo` with an error naming the file. A real undo clears the file's record. Without `--scope`, `--undo` infers the scope as setup does, and a first undo can remove the `enabledPlugins` entry that made `local` inferable, so pass `--scope` on a repeated `setup --undo`. It does not uninstall ctx7 or the Pi packages, and it does not disable the plugin outside that file. With `--undo` the report reads `- ... removed` for a removed key and `= ... nothing to remove` for an absent one, and `--dry-run` shows the same lines without writing. Restart Claude Code after a real run that removed something.

## Install scopes

Claude Code installs a plugin at one of three scopes, and each records `enabledPlugins` in a settings file ([plugin discovery docs](https://code.claude.com/docs/en/discover-plugins)). The terminal, the desktop Code tab and VS Code read the same files. Each scope also has a `holyagent setup` and `holyagent doctor` scope of the same name ([Scope and undo](#scope-and-undo)).

| Scope     | Install                                                     | `enabledPlugins` lives in                | Who gets it                        |
| --------- | ----------------------------------------------------------- | ---------------------------------------- | ---------------------------------- |
| `user`    | `claude plugin install holyagent@holyagent`                 | `~/.claude/settings.json`                | You, in every project              |
| `project` | `claude plugin install holyagent@holyagent --scope project` | `.claude/settings.json`, committed       | Everyone who clones the repository |
| `local`   | `claude plugin install holyagent@holyagent --scope local`   | `.claude/settings.local.json`, untracked | You, in this repository            |

**Precedence.** A local entry overrides a project entry, and a project entry overrides a user entry. Managed settings (`managed-settings.json` or MDM, which can carry `extraKnownMarketplaces` and `enabledPlugins`, per [Anthropic's organization rollout page](https://claude.com/docs/plugins/org-rollout)) also exist; the page that states where a plugin is enabled was read truncated, so their precedence is unverified.

**Sharing a project-scope install with a team.** A committed project entry enables the plugin but does not download it. One person installs at project scope and runs `holyagent setup --scope project`, which writes `extraKnownMarketplaces`, `enabledPlugins` and the other recommended keys of [User settings](#user-settings) into `.claude/settings.json`; commit that file only when the team wants those keys. Each collaborator then runs `claude plugin install holyagent@holyagent --scope project` once ([plugin discovery docs](https://code.claude.com/docs/en/discover-plugins)).

**Setup and doctor follow the scope.** Install, `holyagent setup`, `holyagent doctor` and the session-start setup check work the same at user, project and local scope. Without `--scope`, setup and doctor run at `user`, for the Claude Code settings and the Pi packages alike, with one exception: when `.claude/settings.local.json` sets `enabledPlugins["holyagent@holyagent"]` to `true`, the folder is a git work tree whose top-level the scope trusts (the current directory or an ancestor holding a `.git` entry), and that file is untracked, both run at `local`. Untracked means the index has no entry for the file or for `.claude` itself (a repository can commit `.claude` as a submodule, whose checkout holds the file), whatever the letter case of the names, and `.claude` is not another git repository's work tree; when git cannot answer, the file does not count as untracked. Only your own uncommitted local file moves the default, because a cloned repository must not choose where setup writes or which registry a Pi install uses (`pi install -l` reads the repository's `.npmrc`). A local file that enables the plugin but is not untracked in that sense, or sits in a folder that is not a trusted git work tree (a source archive, say), leaves the run at `user` and prints `~ scope: /repo/.claude/settings.local.json enables HolyAgent but git tracks it, so it is not taken for your own uncommitted file; using user; --scope local targets it` (or `but git tracks .claude itself`, `but .claude is inside another git repository`, `but git could not say whether it tracks it`, `but the folder is not a trusted git work tree`) after the scope line, and `--scope local` is how you target that file. Known limit: an archive that ships its own `.git` with an index that omits the file still counts as untracked, so unpack an archive you do not trust with no `.git` in it, or pass `--scope`. A committed `.claude/settings.json` that enables the plugin never changes the scope: the run stays at `user` and prints `~ scope: the repository enables HolyAgent in /repo/.claude/settings.json; --scope project targets it` after the scope line, and `--scope project` is how you target that file. An explicit `false` in the local file means the plugin is disabled for this project: the run uses `user` and a line says so. An explicit `--scope` always wins. The first line of the output names the scope used and where it came from, for example `~ scope: local (inferred: holyagent@holyagent is enabled in /repo/.claude/settings.local.json)` or `~ scope: user (default)` for setup and `ok   scope: project (from --scope)` for doctor. A local file that is not a JSON object is an error naming the file, and nothing else runs; a symlinked local or project file is not read (a line says so for the local file), so a bare run in such a repository still installs for the user, and writing through a symlink stays refused for the scope that writes; `--scope` skips the search. For a local-scope install:

```sh
claude plugin install holyagent@holyagent --scope local
holyagent setup                     # writes .claude/settings.local.json: the plugin is enabled there
holyagent doctor                    # checks the same file
```

For a project-scope install, name the scope: `holyagent setup --scope project` and `holyagent doctor --scope project`.

The session-start hint already checks the user, project and local settings ([First launch](#install)). The Pi integration has its own two scopes, global and project-local ([Pi](#pi)), and claude.ai chat and Cowork install per account ([claude.ai](#claudeai)). The one `--scope` of `holyagent setup` and `holyagent doctor` covers both hosts: `user` is Claude's user settings and Pi's global settings, and `project` and `local` are Claude's project or local file and Pi's project `.pi/settings.json`; the table is in [pi/installation.md](pi/installation.md#global-and-project-local-installs).

**A user-level HolyAgent config.** A `~/.holyagent/config.json` with the same schema as the project's `.holyagent/config.json` holds your per-user defaults, and the project file overrides it key by key. Both files are decoded with `onExcessProperty: "error"` before they are merged. The schema, with its common settings and its `pi` and `claude` sections, is described in [pi/configuration.md](pi/configuration.md#holyagent-configjson).

## Pi

HolyAgent also runs on the Pi coding agent, as a Pi package with the same root, the 18 specialists and the skills ([components.md](components.md), [pi/README.md](pi/README.md)). Pi runs on Node.js; the package's CLI runs on Bun, so both must be installed. **T3 Code is the primary interface for HolyAgent on Pi**: it runs your own Pi through `pi --mode rpc`, and HolyAgent uses its browser, dialogs, pickers and worktrees ([pi/t3-code.md](pi/t3-code.md)). The plain `pi` terminal works with the same install.

**Install.** Global first, once each:

```sh
npm install -g --ignore-scripts @earendil-works/pi-coding-agent@1.5.0   # or Pi's official installer; Node.js 22.19 or newer
pi install git:github.com/davidbasilefilho/holyagent@holyagent-<version>
```

`1.5.0` is the Pi version HolyAgent pins, and the tag `holyagent-<version>` pins the package (for example `holyagent-0.3.0`). Pi records the global install in `~/.pi/agent/settings.json`. The package pulls in nothing else: run `holyagent setup` afterwards, which installs the packages your `config.json` enables and, where T3 Code is installed, turns on its Pi provider ([the setup screen](#the-t3-code-setup-screen)), and re-run it when you change `pi.features` ([pi/installation.md](pi/installation.md#what-setup-and-doctor-do), [pi/configuration.md](pi/configuration.md#holyagent-configjson)). For one project instead, add `-l` (`pi install -l git:...`): Pi records it in `.pi/settings.json` and loads it after you trust the folder ([pi/installation.md](pi/installation.md#global-and-project-local-installs)).

**Both scopes.** Pi installs at user scope (global, the default) or project scope (`-l`), and Claude Code at user, project or local scope; the two hosts keep separate files, and the narrower scope wins within each. Pass the same `--scope` to `holyagent setup` and `holyagent doctor` for both: `user` covers Claude's user settings and Pi's global settings, `project` and `local` cover Claude's project or local file and Pi's project `.pi/settings.json`. The T3 Code step runs at `user` only, and a project-local Pi install loads under T3 Code only after a saved trust decision, `defaultProjectTrust` or an `--approve` launch arg ([pi/installation.md](pi/installation.md#global-and-project-local-installs)). For T3 Code use the global install. On Windows the wrapper that runs `holyagent` commands goes through bash, so Git Bash must be installed ([requirements.md](requirements.md#native-windows)). Bun is needed by the HolyAgent CLI and is not a way to install Pi. `holyagent doctor` reports a missing or older Pi, a Node.js older than 22.19, a missing HolyAgent package and each missing feature package, with the command that fixes it, and installs none of them.

**Start the root.** In T3 Code, enable the Pi provider (setup does it), start a thread on it and set the thread's access mode to Full access: HolyAgent warns in Supervised and Auto-accept edits, because every tool call, background specialists' included, would ask for approval ([pi/t3-code.md](pi/t3-code.md#full-access-is-required)). In a terminal, plain `pi` starts the root, the way the Claude plugin does: the package's extension reads its `--holyagent-role` flag, which defaults to `root`, puts the root prompt in front of Pi's own, limits the root's tools (no `write` or `edit`, and no web or computer-use tools) and adds the status of the project's Intents and Assignments (`.holyagent/`) to the session. If the provider is not logged in or does not list a model of your routes, the first prompt after the check shows a one-line notice with the fix, and startup does not wait for the check. Sign in to the model provider the first time ([pi/providers.md](pi/providers.md#kimi-for-coding-global)). `--holyagent-role session` starts a session that gets the core of the root rules but is not the root, and the specialists the root launches run as `specialist` whatever the flag says ([pi/extensions.md](pi/extensions.md#the-extension-entry)).

**Configure.** `.holyagent/config.json` in the project and `~/.holyagent/config.json` for you set the model route of each role and which features load, each with a default ([pi/configuration.md](pi/configuration.md#keys-and-defaults)). `"pi": { "enable": false }` turns the integration off. Update the package with `pi update --extensions` and remove it with `pi remove`; both are Pi commands ([pi/installation.md](pi/installation.md#official-instructions)).

**The task list.** The root keeps its task list with the `todo` tool of `@juicesharp/rpiv-todo`. The tool works everywhere, but its live panel is a Pi widget that T3 Code does not render, so under T3 Code the list is not shown to you (the plain `pi` terminal shows it); ask the root for its list ([pi/t3-code.md](pi/t3-code.md#dialogs-and-status-only)).

**Specialists and approvals.** The root runs its specialists in-process, in the same Pi session process, so they share its project trust and take no approval of their own; the thread's access mode covers them ([pi/approval.md](pi/approval.md#decision-for-030)).

Not built yet: setting Pi's `npmCommand` from `holyagent setup`, the macOS permission walkthrough for computer use, and an adapter that would show the todo list under T3 Code ([pi/README.md](pi/README.md#what-ships-now-and-what-is-planned)).

### The Codex provider

`"pi": { "provider": "openai-codex" }` in a HolyAgent config runs the root on GPT-6.1 Sol and the specialists on GPT-6.1 Terra and GPT-6 Luna, on the GPT-6 instruction family, with `apply_patch` beside `read`, `write`, `edit` and `bash` for the specialists that write. Log in once with `/login openai-codex` in Pi (a ChatGPT sign-in, no key); `holyagent doctor` reports a missing login. It sends the server-side `context_management` only when Billion Context is off (`pi.features.contextCompression` false) and `pi.features.contextManagement` is on (the default; `holyagent setup --context-management off` turns it off), falls back to Luna Reserve when the usage limit is reached (`holyagent setup --luna-reserve off` turns that off), and has the `codex-auto-review` model judge risky tool calls before they run, as Codex's own auto-review does whenever the active model is Codex's (only your own user-level config turns that off, with `holyagent setup --auto-review off`; a project's config cannot; `/approve` lets one denied action retry). The route table, the details and the limits are in [pi/providers.md](pi/providers.md#codex-openai-codex).

On Pi the `bash` tool runs on [just-bash](https://github.com/vercel-labs/just-bash) while the `just-bash` capability is on (`pi.features.justBash`, on by default; `holyagent setup --just-bash off` turns it off and Pi's own `bash` tool is back). Commands just-bash implements (`rg`, `grep`, `sed`, `jq`, `find`, and the rest) run inside it, and every other command (`git`, `bun`, `mise`, `gh`, `node`, `holyagent`) runs the real program; `js-exec` runs TypeScript first and JavaScript as the fallback. Bun must be on `PATH` (`holyagent doctor` checks). Billion Context's bash guardrails (the 60 s default timeout, the 50 KB output cap and the repeated-call breaker) are off while it is on. The details are in [pi/shell.md](pi/shell.md).

On Pi the specialists' `find` and `grep` tools are [fff](https://github.com/dmtrKovalenko/fff)'s (`@ff-labs/pi-fff` in override mode) while the `fff` capability is on (`pi.features.fff`, on by default; `holyagent setup --fff off` gives Pi's own tools back). Where fff's native library has no build for the machine, the capability is not offered and Pi keeps its own tools ([pi/search.md](pi/search.md)).

### The T3 Code setup screen

When Pi is in use (the `pi.enable` of your config on) and the run is not `--undo` or a claude.ai cloud session, `holyagent setup` shows an interactive screen in your terminal with one row for each Pi capability, headed by the form in force (headless or normal, [Capabilities](pi/configuration.md#capabilities)), each starting at what your config decides; Space switches one, and the review lists what each switch does (turned on, turned off, unchanged, or not offered in the form) before the run writes the changed ones to the config and installs or removes their packages. A capability flag (`--todo off`) applies directly and keeps the screen out. When also the scope is `user` and T3 Code is installed (its home folder, `T3CODE_HOME` or `~/.t3`, exists), the screen also covers the choices setup makes in T3's settings, then a review of every key it will change, and applies on confirm. It has two rows to switch beside the fixed Pi provider row: agent device access (offered only where Xcode's iOS simulator or an Android SDK is found and `pi.t3.deviceAccess` is true) and new threads in worktrees (while `pi.t3.worktrees` is true); both start enabled. Up and down (or `j` and `k`) move, Space toggles, Enter opens the review and applies it from there, and Esc, `q` or Ctrl-C cancels and writes nothing. The first time, the screen installs its renderer (OpenTUI and Solid, at the versions of the release) into HolyAgent's cache folder with `bun install`, which needs the network and a Bun that OpenTUI supports (`@opentui/core` declares Bun 1.3.14 or later in its `engines`; HolyAgent checks no Bun version itself). The rows, keys and packaging are in [pi/t3-code.md](pi/t3-code.md#the-setup-screen-and-its-flags).

Three flags make the choices without the screen:

| Flag                      | Effect                                                                                                         |
| ------------------------- | -------------------------------------------------------------------------------------------------------------- |
| `--worktrees on\|off`     | New T3 Code threads start in worktrees (`defaultThreadEnvMode "worktree"`), or setup leaves that setting alone |
| `--device-access on\|off` | Device access is written where a host is found, or left out                                                    |
| `--no-tui`                | No screen; both choices on                                                                                     |

Giving `--worktrees` or `--device-access` applies directly and leaves the other choice on. `--no-tui` is the line-based fallback, and setup also falls back to it, with one `~ t3 tui:` line saying why, when stdin or stdout is not a terminal, `CI` is set to a truthy value (not empty, `0`, `false`, `no` or `off`, in any case), `TERM` is `dumb`, a flag above was given, or the screen cannot be installed or started (for example offline). The fallback applies both choices on; nothing about the screen changes the other setup steps, `--dry-run` shows what would change on the review and the result, and `holyagent setup --undo` backs the T3 keys out like the rest.

## Opinionated by design

HolyAgent makes choices that Claude Code's defaults do not, and it makes them on purpose, so that every session follows the same rules on every machine. Each decision below says what it sets, why, and how to change it. Where the reason is a judgment call and not a measured result, it says so. You can judge the trade-offs yourself, then keep, drop or confine any of them: `holyagent setup` never overwrites a value you set, and `holyagent setup --undo` backs the rest out (see [Scope and undo](#scope-and-undo)).

**The root takes every session, and the settings are user-wide.** Enabling the plugin sets `agent: holyagent`, so the main thread is the root in every project where the plugin is enabled (a claude.ai cloud session excepted, see [Install](#install)), and `holyagent setup` writes to your user settings by default, or to your own `.claude/settings.local.json` when that file already enables the plugin. The reasons are practical and a design choice. A plugin can set only `agent` and `subagentStatusLine` ([plugin docs](https://code.claude.com/docs/en/plugins/components): "Two keys take effect, `agent` and `subagentStatusLine`, and every other key is dropped"), so everything else has to live in settings; installing once and using everywhere is the least to remember; and consistency is the point, since every session then follows the same Intent, review and commit rules. If that is more than you want, confine HolyAgent to one repository or back the settings out; the commands, and what `--undo` leaves, are under [Scope and undo](#scope-and-undo).

**Web work goes through Exa: `permissions.deny` for `WebSearch` and `WebFetch`.** Claude Code's own web tools are denied, and the Search specialists use the Exa connector (see **Web search** above). The reasons:

- _Quality._ A [benchmark by context.dev](https://www.context.dev/blog/introducing-context-highlights) (2026-09-25) on Exa's WebCode set scored Exa highlights at 75.6% groundedness (286 tokens on average) against 50.4% for Claude Code 2.1.280's WebFetch (231 tokens). Its author sells a competing product, and the sizes are close, so this supports better answers and not fewer tokens.
- _WebFetch is lossy by design._ Per Claude Code's [tools reference](https://code.claude.com/docs/en/tools-reference) (WebFetch tool behavior, read 2026-11-03), WebFetch runs your prompt against the page in a separate model call for most fetches, and Claude receives that call's result, not the raw page; the page calls this "lossy by design".
- _Less noise._ Exa's [MCP tools](https://exa.ai/docs/reference/exa-mcp) return search highlights, and its fetch returns the full page as clean markdown.
- _One route._ With one web path, behavior is predictable across sessions and machines. This is a design argument; no source tests it.

This needs the Exa connector (connect it once at [claude.ai/customize/connectors](https://claude.ai/customize/connectors)); without it the Search specialists have no web access, and the deny blocks the built-in tools. To drop it, remove `WebSearch` and `WebFetch` from `permissions.deny` in the settings file and keep the key itself, even as `[]`: setup and `holyagent doctor` add the whole list back only when `permissions.deny` is missing, and setup never edits a list that exists. `holyagent setup --undo` removes just those two entries for you.

**The root runs Opus at high effort: `modelSettings["claude-opus-5-5"].effortLevel: "high"`.** The root adapts to the request, plans, judges and accepts, so its mistakes cost the most; cheap Haiku and Sonnet specialists do the volume. That split is a design choice, not a measured result. Only settings can set the root's effort, because Claude Code ignores an agent's `effort` frontmatter on the main thread (see [the root's effort and window](#user-settings)). Cost: a high-effort Opus root uses a Pro plan's limits faster than a smaller model would. To lower it, [run the root on Sonnet](#run-the-root-on-sonnet), or change the level with `/effort`.

**The root compacts at 450000 tokens: `modelSettings["claude-opus-5-5"].autoCompactWindow: 450000`.** Every call re-reads the whole context, so a call's cost grows with context size, even though Anthropic [bills the same per-token rate up to 1M](https://platform.claude.com/docs/en/about-claude/pricing) with no long-context tier for these models. Claude Code compacts a native 1M window such as Opus 5.5's at [about 967K by default](https://code.claude.com/docs/en/model-config); [claude-code#101067](https://github.com/anthropics/claude-code/issues/101067) reports Opus 5.5 compacting at 281K to 845K on 2.1.296 instead, and was not checked for a fix, so the real default may be lower. The root grew to hundreds of thousands of tokens per call in the audited sessions, with cache reads the largest part of its cost ([decisions.md](decisions.md)). The number is a project choice, not a documented default; the paragraph below shows what it costs against the cost-only optimum. Change it with `/autocompact`, by editing the key (100000 to 1000000 tokens), or with the `CLAUDE_CODE_AUTO_COMPACT_WINDOW` environment variable, which overrides every setting. `CLAUDE_CODE_DISABLE_1M_CONTEXT=1` forces compaction at 200K, and a gateway that rejects requests above 200K needs `CLAUDE_CODE_AUTO_COMPACT_WINDOW=200000`.

**Why 450000.** The cost model, with prices from the pricing page for Opus 5.5 (checked 2026-11-03):

- Each call re-reads the context at the cache-read price, $0.20 per million tokens (0.05x input), and there is no long-context price tier.
- Compaction costs a summary call plus a cold cache rewrite of the new prefix (5-minute cache write, $5 per million tokens).
- With `W` the window, `B` the context right after a compaction (system prompt, tools, summary), `g` the tokens added per call, `S` the summary size, `r` the cache-read price, `w` the cache-write price and `o` the output price, the cost per call is smallest at `W* = B + sqrt(2g((r + w)B + oS) / r)`.

The table assumes `S` = 10k tokens, 1.5k output tokens per call, a cache hit on every call, and no subagent context; none of that is measured. The optimum for four scenarios, and what 450000 costs over it in total cost per call:

| `B` / `g` (tokens) | Optimum `W*` | 450000 over the optimum |
| ------------------ | ------------ | ----------------------- |
| 30k / 2k           | 114k         | +42%                    |
| 50k / 5k           | 202k         | +16%                    |
| 50k / 10k          | 265k         | +7%                     |
| 80k / 15k          | 384k         | +1%                     |

Claude Code's default of about 967K costs 20% to 120% more than the optimum. The curve rises slowly above the optimum and steeply below it, and 300k is the cost-only minimax: within 4% of the optimum in three scenarios and 20% over in the light-growth one.

450000 stays for two reasons. The model leaves out two costs: the re-orientation after each compaction, and the quality lost to every extra lossy compaction, which a lower window makes more frequent (Anthropic's [context-engineering post](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents) says compaction is lossy and that overly aggressive compaction drops subtle context). And the root probably grows fast, which is an inference, not a measured growth rate: the recorded 365k to 747k tokens are context sizes, and they only suggest the high-`g` scenarios, where 450k is within 1% to 7% of the optimum. For light sessions (small `g`) 300000 is a reasonable choice, and measuring your own `B`, `g` and `S` would settle it.

Codex compacts at [90% of the window](https://github.com/openai/codex/issues/10365) when `model_auto_compact_token_limit` is unset. The window of GPT 6.1 Sol in Codex conflicts between sources (500k in one, 272k in another, which would compact at about 245k), so no figure is asserted for it; check `codex debug models`.

**Branches and merges: conventional branches, atomic commits, squash merge.** The root never works on a branch the platform assigns (a claude.ai cloud session starts on `claude/<name>`), because that name carries no meaning; it creates a branch named as the stack plan sets and leaves the assigned one alone. Each commit on a branch is atomic (one logical change that builds and passes the gates on its own, generated files included) and a Conventional Commit, so review and bisect on the branch stay readable. PRs merge by squash by default, with the PR title as the Conventional summary, so the base keeps one commit per PR. The repository's own conventions, branch protection and merge settings come first, because the PR has to be mergeable. To change any of these defaults, state the rule where the root reads conventions: the repository's `AGENTS.md` or `CLAUDE.md`, or `CONTRIBUTING` (for example "merge with a merge commit" or "name branches `feature/<ticket>`"), or tell the root in the session, which then records it in the Intent. No setting holds them. What happens when the push of the conventional branch is refused, and what claude.ai allows, is under [claude.ai](#claudeai).

**Claude Code's git instructions are off: `includeGitInstructions: false`.** Claude Code's built-in commit and PR instructions tell the model to add a `Co-Authored-By` trailer and a "Generated with Claude Code" line and give it their own commit workflow. That conflicts with commits authored by you through `holyagent vcs commit`, and cloud sessions commit as Claude by default, which `holyagent vcs identity` fixes by setting you as author ([commit-authorship.md](commit-authorship.md)). The instructions also cost context on every call. The setting is documented as removing "the built-in commit and PR instructions" from the context ([settings reference](https://code.claude.com/docs/en/settings-reference)); the `CLAUDE_CODE_DISABLE_GIT_INSTRUCTIONS` environment variable takes precedence over it. The root carries its own git rules instead: never bypass hooks or signing, no amend or rewrite of published history, a secrets check and `git status` and `git diff` before each commit, non-interactive git, and no git config edits. To get Claude Code's instructions back, set it to `true` or delete the key.

**No attribution: `attribution.commit` and `attribution.pr` as `""`, `attribution.sessionUrl` as `false`.** Same reason: the history should read as your work, with the owner accountable for it, so no trailer, PR line or claude.ai session link. The keys are in the [settings reference](https://code.claude.com/docs/en/settings-reference): `commit` and `pr` change or hide the trailer and the PR line, and `sessionUrl` omits the claude.ai session link from cloud and Remote Control commits. `vcs commit` and the `commit-msg` hook clean the text either way ([commit-authorship.md](commit-authorship.md)). To restore them, delete the keys or set your own text.

**Specialists stay warm: `subagentPromptCacheTtl: "1h"`.** Specialists stay warm for the reuse window, so a repair or follow-up continues a cached agent instead of paying a fresh start ([cache-and-workflows.md](cache-and-workflows.md)). The trade-off is price: on the [pricing page](https://platform.claude.com/docs/en/about-claude/pricing) a 1h cache write for Opus 5.5 costs $8 per million tokens against $5 for the 5m write, so `1h` pays more at each write and saves a cold rewrite when a specialist is reused after more than five minutes. To change it, edit `subagentPromptCacheTtl` in the settings file to `5m`. `--subagent-cache-ttl 5m` sets the value only when setup finds the key missing (a first run); an existing value is kept and reported with `~`.

**The marketplace and plugin keys.** `extraKnownMarketplaces.holyagent` and `enabledPlugins["holyagent@holyagent"]` declare the marketplace and turn the plugin on in the settings file, so a reinstall, or another machine that reads the same file, finds both in place. Remove them to stop that; what `--undo` does with them is under [Scope and undo](#scope-and-undo).

## Migrate legacy state

`holyagent migrate [--dry-run]` converts a project's `.holyclaude/` and `.holycodex/` state into `.holyagent/` records. Run the dry run first: it prints the counts per source and every record that cannot convert, with the reason, and writes nothing. The real run writes nothing unless every record converts, no target file exists and no Assignment is Running (holyclaude) or executing (holycodex) or has a pending holycodex transaction; it then reloads `.holyagent/` and fails if a record does not decode. It lists the project files that still name a legacy folder, such as lint and format ignore lists, without editing them. Deleting the legacy folders and committing `.holyagent/` stay with you. `holyagent migrate --help` lists every field that does not carry over.

## How a session works

The root agent (Opus by default, the main thread; see [Run the root on Sonnet](#run-the-root-on-sonnet)) owns the conversation, decisions, acceptance and version control. Everything else goes to specialists: explorers, librarians, workers and reviewers, each pinned by the CLI to a model and effort. The root calls the runtime CLI as `bun` on the plugin's `scripts/holyagent.js` (the plugin folder is not on your `PATH`). The read-only commands are safe to run by hand: `status`, `plan`, `reconcile`, `intent show|list`, `assignment show|list`. Its rules for asking, assignments, stacks and resuming are in its prompt (the situational rules are skills it loads when the situation arises), and the details of each command are in `holyagent help [command]`; the plugin has skills of its own, all for the root: `dev-server` (Worker.operations starts one render target per platform, such as a web app, a terminal UI or an emulator, that the visual specialists share, or reports why it cannot run here), `user-busy`, `visual-judging` (loaded before the first visual dispatch, it also says how the root picks the platform design skill), the platform design skills `web-design`, `mobile-design`, `desktop-design` and `tui-design`, `evidence-judging` (how the root accepts or rejects a verdict from compact evidence), `ci-watch`, `instruction-writing` and `state-mode`. The commands that take a JSON draft (`intent create`, `intent update`, `assignment create`, `assignment dispatch`) read it from `--input '<json>'` or, without the flag, from stdin; when both are given, `--input` wins and stdin is not read, so the root never writes a draft file. A specialist's report always goes on stdin. The mergeability rubric and the interface inspection rules are fixed text in the specialists that need them; the visual specialists get their design guidance from the platform design skill that the root names in their criteria.

1. **Intent.** The root records one objective and its requirements (`intent create`). Your constraints go in verbatim as binding requirements, and every Assignment carries them as criteria.
2. **Assignments.** Each unit of work is an Assignment: objective, scope, constraints, ownership paths for writers, criteria marked blocking or non-blocking across six dimensions (behavior, regressions, tests, scope, style, repo-standards) and evidence labels. Under the pi host an Assignment can also carry the screen capability (`screen: true`): its specialist then gets the computer-use, browser-use and T3 preview tools, and under Codex runs on GPT-6.1 Terra at medium or higher effort ([pi/screen.md](pi/screen.md)).
3. **Three calls per Assignment.**
   1. `assignment dispatch` takes the draft (`--input '<json>'` or stdin), writes the brief to a file under the git common directory (the state folder's `local/briefs` outside a git repository), where it stays with the reports until its Intent closes, and prints which agent, model and effort to spawn (or which warm agent to continue) and then a two-line prompt that points to the brief, so the root never reads or re-emits it.
   2. The root runs it as an `agent()` of an inline workflow script it writes, a single Assignment as a one-entry workflow. After the run's notice it records each entry with `assignment record <id> --agent workflow:<run-id>/<id>` and reads the reports from files that `holyagent assignment reports <journal.jsonl>` writes, one per `agent()` label ([cache-and-workflows.md](cache-and-workflows.md)). Only when the `Workflow` tool is disabled or unavailable does it launch the specialist in the background as printed; a hook then records an agent started through the `Agent` tool ([hooks.md](hooks.md)). A continued agent (`SendMessage`) is recorded by hand with `assignment record <id> --agent <agentId>`, and `--failed` marks a launch that failed.
   3. When the specialist's report arrives (from its report file for a workflow agent), `assignment close <id> --outcome <o>` with the report on stdin, verbatim; `--accept "<rationale>"` accepts it when the report's `evidence:` block supports every blocking criterion and required label.
4. **Several Assignments.** The root creates them with `assignment create`, runs `plan` and runs what it names as an inline workflow script it writes on the spot. Work that continues a warm specialist goes by `SendMessage` beside it. Workflows run all new work, and choosing the holyagent agent is your opt-in to the `Workflow` tool; `plan` prints direct subagents as a fallback for a session where the tool is disabled or unavailable. See [cache-and-workflows.md](cache-and-workflows.md).
5. **Commit, review, push.** The order is a local commit of the writer's work, an independent review of that commit, repairs as new local commits, a re-review, one validation of the final head, and the push once the reviews accept. Reviewer.code starts with Claude Code's built-in `/code-review` and Reviewer.security with `/security-review`, both on the committed range (the other reviewers have no built-in); Reviewer.security runs before the push when the change touches a trust boundary. Only blocking findings start a repair. `holyagent vcs commit` commits the accepted paths with the Intent state and the configured git identity (in a claude.ai cloud session the user as author and Claude as committer, set once per clone by `holyagent vcs identity`), after the message check; branches, pushes, merges and CI are plain Git and `gh` (the root never force-pushes or pushes to a protected branch without your approval), and `holyagent vcs pr` opens the PR; see [commit-authorship.md](commit-authorship.md).

The root keeps its context small: it runs no gates, probes or data checks, never opens or re-emits a brief, reads an image only to show you, settle a concrete doubt or make its final pass on the reviewer's final captures, decides rendered work by that pass with Reviewer.visual's recorded observations as input, and closes each Assignment from a report file. It keeps everything in a task list for the whole request (TaskCreate, TaskUpdate, TaskList, TaskGet): every PR, task, step, dispatch, wait, verdict and repair, none of which it mentions in a message. It writes to you only for a decision, a blocker only you can clear and the final report, apart from a brief acknowledgment of each message of yours. A decision always goes through `AskUserQuestion` with options and a recommended default, and only when it materially changes the result and neither the repository nor your words settle it. Hook feedback is handled silently. The root runs no gates itself (a specialist does), judges delegated work from the diff summary and the check output, and accepts nothing without a check run on the current head. It never polls, schedules check-ins or runs wait loops: the completion notices of the specialists are its only wake-ups (a wake that changes nothing gets one short line), `Monitor` on `gh pr checks --watch` is its only CI wait, and a new message from you leaves running specialists alone. A specialist interrupted by accident is resumed with `SendMessage`, never launched again.

**Stacks.** One branch and one PR per reviewable change. Every PR of one delivery stacks in work order by default, each reviewed and merged on top of the one before it; the repository's own conventions come first. Every new PR, a new delivery's first included, stacks on the open stack's top once the PRs under it pass holyagent's independent review, not human review; the root's Stack plan sets the base cases, the owner's-branches-only boundary and the base merge into a lagging stack. A change that adds CI goes first, from the base, and parallel writers get disjoint paths. A PR is opened or updated in the same step as every push, so nothing stays only local.

**Long mechanical work.** Hundreds of calls, such as paging or exporting, are split into batches across fresh specialists, each saving its results to a named file outside the scratchpad and `.holyagent/`, which the root reads.

**Resume.** After a resume or compaction the root runs `status` (open Intents, Running Assignments, Succeeded ones not yet accepted) and `reconcile` (Running Assignments with their agent ids), then closes as `interrupted` a Running Assignment only once its agent is confirmed gone (by `SendMessage` or the transcript; an exited parent session proves nothing), and otherwise leaves it Running. The session-start hook adds a capped open-work status as context, and after a resume or compaction the `reconcile` result of the Running Assignments too ([hooks.md](hooks.md)).

## Run the root on Sonnet

The root runs on Opus by default: its agent file has `model: opus`. Claude Code's [model configuration](https://code.claude.com/docs/en/model-config) page documents `ANTHROPIC_DEFAULT_OPUS_MODEL` as the setting for what the `opus` alias resolves to, so the root resolves to the model you set. Add this to `~/.claude/settings.json` (all projects) or to `.claude/settings.local.json` (one project, not committed), then restart Claude Code:

```json
{ "env": { "ANTHROPIC_DEFAULT_OPUS_MODEL": "claude-sonnet-5-5" } }
```

- The variable changes what the `opus` alias resolves to, so it also applies to anything else that selects the `opus` alias.
- The specialists are pinned to `haiku` and `sonnet`, so they do not change.
- After restarting, run `/status` to confirm the model that is active.
- Add the matching `modelSettings` entry for the Sonnet model so the root keeps its effort and window (see [the root's effort and window](#user-settings)).

You can also switch the model in the running session with `/model sonnet` instead. The environment variable is the more reliable route, because it applies from the start of every session.

Sonnet 5.5 costs less than Opus 5.5 per token: $2 / $10 against $4 / $20 per million input / output tokens on Anthropic's [pricing page](https://platform.claude.com/docs/en/about-claude/pricing) (read 2026-10-30). Opus stays the default because the root judges reports and plans the work.

## claude.ai

Chat and Cowork became one Claude on 2026-09-16 on claude.ai on the web, desktop and mobile ([announcement](https://claude.com/resources/articles/cowork-is-now-claude), [help article](https://support.claude.com/en/articles/16761823-claude-cowork-and-chat-are-one-claude)). A conversation starts as a chat and continues in a Cowork cloud session when a task needs to run code or work with files, and your plugins carry over. Anthropic's [plugin platform support](https://claude.com/docs/plugins/platform-support) page says plugin agents and hooks load in Cowork sessions and in Claude Code, and are skipped where a conversation stays plain chat; it also says commands load as skills and local MCP servers and settings are ignored in plain chat, and that a top-level `bin/` makes claude.ai refuse the whole plugin, which is why this plugin has no `bin/` folder (its executable is `scripts/holyagent`). The [skills documentation](https://code.claude.com/docs/en/skills.md) lists the frontmatter keys claude.ai skill uploads accept: `name`, `description`, `license`, `compatibility`, `metadata` and `allowed-tools`; HolyAgent's skills use `name` and `description`. So in plain chat, a conversation that has not moved into a Cowork session, only the plugin's skills load: there is no root agent, no runtime CLI calls and no hooks. In a Cowork session the agents and hooks load too. Inference: Anthropic's [platform support](https://claude.com/docs/plugins/platform-support) page says a plugin `settings` key is ignored in Cowork, and the plugin's `agent: holyagent` is such a key, so in Cowork the `agent` setting does not apply and the root there rests on the session-start hook, as in cloud sessions.

**HolyAgent works correctly in claude.ai chat and Cowork.** The maintainer tested it in unified chat and Cowork sessions, and it works correctly there. What that means for the install:

- **Plugins install per account, not per machine or per repository.** Install HolyAgent from Customize > Plugins in claude.ai; the install belongs to your account and syncs to Claude Code at its next session start ([platform support](https://claude.com/docs/plugins/platform-support), [support article](https://support.claude.com/en/articles/13837440-use-plugins-in-claude)). There is no local or global choice there and no project-level install; the user, project and local scopes of [Install scopes](#install-scopes) belong to Claude Code.
- **In an organization, an Owner controls it.** An Owner can set a plugin to Not available, Available, Installed by default or Required, so the nearest thing to a team-wide install there is Installed by default or Required ([organization rollout](https://claude.com/docs/plugins/org-rollout), [support article](https://support.claude.com/en/articles/13837440-use-plugins-in-claude)).
- **Plain chat still loads skills only.** A conversation that stays plain chat does not run the root or the CLI, as above.

Cloud sessions (claude.ai/code) are a different case: plugins installed on your account are synced into them, and commits follow the cloud rules in [commit-authorship.md](commit-authorship.md).

**The session panel in cloud sessions.** The panel shows the branch the platform assigned (`claude/<name>`) and the diff of the primary checkout, with a Create PR button for that branch. HolyAgent leaves the primary checkout on the assigned branch at its start commit and works in git worktrees, so the diff stays empty and the button stays unused. The PRs the root opens do not belong to that branch; they appear in the panel's list of PRs (observed on 2026-11-09, when the changes list of this repository's own cloud session showed its merged and open HolyAgent PRs). The platform sets the branch label when the session starts, and nothing in a session renames it. If the primary checkout ends up on a detached HEAD or on another named branch than it started on, the session start and `holyagent status` add a notice with the `git switch` that returns it, because the panel would then show that checkout's commits as a stray diff and offer a PR for them.

**Branch pushes in cloud sessions.** A cloud session starts on a platform-assigned `claude/<name>` branch, and the root creates a conventionally named branch instead ([Opinionated by design](#opinionated-by-design)). Whether that push works is a platform matter, and the sources disagree by date:

- Pushes were limited to `claude/*` branches: a [report from 2026-02-09](https://github.com/anthropics/claude-code/issues/24535) has the git proxy answering 403 to any other branch.
- A [report from 2026-08-31](https://github.com/anthropics/claude-code/issues/91018) shows the branch selected in the web UI being pushed to directly. That is a user report, not documentation.
- The [cloud sessions page](https://code.claude.com/docs/en/claude-code-on-the-web) says only that GitHub operations go through a proxy that attaches the credential on the server side. A check on 2026-11-03 found no sentence there that limits pushes to a branch, and no current official statement of the rule for interactive sessions.
- Interactive cloud sessions have no documented setting for branch pushes. Routines (scheduled cloud runs) do: at claude.ai/code/routines, edit the routine, and under Permissions turn on "Allow unrestricted branch pushes" for the repository. That setting is described by a mirror of the routines page and a third-party how-to, and a [report](https://github.com/anthropics/claude-code/issues/44949) says a routine pushed to `main` with it off, so it may not always be enforced.
- GitHub branch protection applies whatever the platform allows.

If a push is refused, the root stops, does not work around the refusal, and asks whether to push to the assigned branch instead.

## T3 Code

T3 Code drives Claude Code through the Claude Agent SDK. From its source (read 2026-10-24; it is early software and changes):

- It loads the user, project and local settings like the CLI, so the plugin and the user settings from `holyagent setup` apply, unless a provider instance sets a custom `CLAUDE_CONFIG_DIR`.
- It appends to Claude Code's system prompt rather than replacing it.
- It exposes tools under `mcp__t3-code__`: `html_render` and `html_preview` for visual replies, `preview_*` and `t3_preview_*` for the integrated browser and `device_*` for simulators. Every agent inherits them; the root uses `html_render` and `html_preview`, and the visual specialists use the browser and device tools named in their interface inspection rules. Tool names differ across T3 versions.
- Its "Auto-compact after" setting maps to Claude Code's top-level `autoCompactWindow`, which HolyAgent never sets; the Opus 5.5 entry of `modelSettings` takes precedence over it for the root in the same file.

This section is about the Claude plugin under T3 Code. T3 Code is also the primary interface of the Pi integration, where it runs Pi through `pi --mode rpc`; what that does, including which T3 tools are kept and which are deactivated, is in [pi/t3-code.md](pi/t3-code.md), and the setup screen is in [Pi](#the-t3-code-setup-screen).
